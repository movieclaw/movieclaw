# MovieClaw 转码器

MovieClaw 转码器是 MovieClaw 远程转码协议的当前 macOS Apple Silicon Worker
实现。它以菜单栏 App 运行，接收服务端下发的 ffmpeg 任务，从服务端签名地址读取源
视频，并把 HLS fMP4 产物上传回服务端。

远程转码协议本身不绑定 macOS，未来可以实现 Linux、Windows 或其他硬件平台的 Worker。
当前 App 最低支持 macOS 12，目标运行环境是 Apple Silicon Mac。

界面在 macOS 26 起是液态玻璃（Liquid Glass）风格：点菜单栏图标弹出的状态面板是一块
液态玻璃，按钮、窗口由系统绘制成新外观，页眉徽标用玻璃材质。macOS 12–15 上功能完全一致，只是没有玻璃质感。从源码构建时要用
Xcode 26 或更新版本才会带上液态玻璃；旧版 Xcode 也能编译，但产物是旧样式。

Worker 不挂载 NAS 文件系统，也不把源视频和 HLS 产物保存到 Mac 硬盘。ffmpeg 通过
HTTP(S) 读取源文件；上传代理只在本机回环地址监听，并将单个产物暂存在内存后上传。
App Support 仍会保存 ffmpeg 包、版本信息和普通配置，日志也会写入用户日志目录，
这些不属于媒体临时文件。

## 1. 安装

推荐直接下载：每个 MovieClaw Release 都附带
`MovieClawTranscoder-macos-arm64.zip`，解压后把「MovieClaw 转码器.app」拖到
「应用程序」即可，不需要装 Xcode，也不需要 clone 仓库。

旧版本的 App 叫「MovieClaw Transcoder.app」。升级时先退出并删掉旧的那个再拖新的进去，
否则「应用程序」里会同时有两个；设置、配对授权和日志都沿用，不需要重新配置。如果在
「系统设置 → 通用 → 登录项」里加过旧 App，也换成新的。

**首次打开会被系统拦住**，提示「无法打开，因为无法验证开发者」。这是因为当前发布
的构建使用 ad-hoc 签名、没有 Apple 公证。放行方式：

1. 在「应用程序」里 **右键点击** App 图标，选「打开」；
2. 在弹出的对话框里再点一次「打开」。

只需要做一次，之后正常双击即可。如果右键菜单里没有「打开」，可以去
「系统设置 → 隐私与安全性」，在页面下方点「仍要打开」。

### 从源码构建（可选）

想改代码或验证构建时：

```bash
cd macos/MovieClawTranscoder
chmod +x scripts/package-app.sh
scripts/package-app.sh
open "dist/MovieClaw 转码器.app"
```

脚本会执行 Swift Release 构建、生成 App Bundle，并默认使用 ad-hoc 签名（构建完会
提示这一点）。正式分发时通过 `MOVIECLAW_SIGNING_IDENTITY` 指定 Developer ID 签名
身份，之后还需要完成公证。这个变量只用于 App 打包签名，不是远程转码运行配置。

ad-hoc 签名有个实际影响：每次重新构建后第一次读令牌会弹窗要钥匙串密码，
原因见下面「系统弹窗要『登录』钥匙串密码」。

## 2. 服务端配置

先在 MovieClaw 网页打开「系统 → 应用 → 远程转码」，**把开关打开就行**。

这里没有令牌要配：Worker 的凭证是逐台设备配对签发的，在「设置 → 设备」里
审批与吊销（见 `docs/design/device-auth.md`）。

地址也不用配：服务端下发任务时用的取源地址和产物回传地址，直接取自这台 Worker
连上来时用的那个地址——你在 App 里填的就是它。只有当反向代理把 `Host` 改写成了
上游地址时才需要在页面「高级」里指定一个覆盖地址（见
`docs/design/remote-transcode.md` §2.1）。

不要从 Docker、Compose 或旧配置文件中设置远程转码环境变量，服务端只读取网页配置。

## 3. App 首次配置

第一次打开时设置窗是三步引导（连接 → 批准 → 完成），**唯一需要填的是 movieclaw
地址，也只需要点一次按钮**：

1. 选服务器 → 点「连接并配对」。窗口打开时会自动在局域网里找一次，找到的
   movieclaw 列成卡片，点一下就选中（只找到一台时会替你预选）；找不到或想用别的
   地址，就在下面手动填写。建议用局域网地址和端口：转码要来回传输大量视频分片，
   走公网或反向代理会明显变慢，也更容易中断（找到的可能是你为播放器配的对外
   地址，不一定是最快的那个）。

   查找依赖服务端的「Jellyfin 兼容层」开关，跨网段、VPN 或桥接网络下可能
   找不到，手工填写即可。首次使用时 macOS 会询问「允许访问本地网络」。
2. App 会先验证地址真的通（填错了当场就说，而不是保存之后表现成「连不上」），
   然后自动发起接入请求、显示一段配对码并打开网页。到网页「设置 → 设备」核对
   配对码后批准即可。令牌会自动回到这台 Mac 并存进 Keychain，**全程不需要你
   看到或抄写任何密钥**。
3. 批准后进入「一切就绪」，这一页同时显示 Jellyfin-ffmpeg 的下载与校验进度。

配好之后再打开设置，是「连接 / 转码 / 关于」三页，**改动即时生效，没有保存按钮**：

- **连接**：服务器地址（只读）与实时状态、已连接多久；这台 Mac 的名称（网页设备
  列表里显示的名字，默认取机器名）；启动后自动连接（默认打开）。要换地址、换机器，
  或者授权被吊销了，点「断开并重新配置…」回到引导第一步——地址不能就地改；
- **转码**：ffmpeg 来源（App 管理的 Jellyfin-ffmpeg，或自选已有的
  `jellyfin-ffmpeg`，选好后先检测硬件编码能力、不合格不保存）、检测到的
  VideoToolbox 编码器、同时转码的路数（1 到 4）；
- **关于**：版本、打开日志、复制脱敏诊断信息、到网页管理这台设备。

改名、换 ffmpeg、调并发要重启一次与 NAS 的连接；手上有任务在转时会先问一句。

令牌只保存到 macOS 钥匙串，界面上不再有它的展示位；其他非敏感配置保存到
UserDefaults。要停用这台机器，到网页「设置 → 设备」里吊销它——本机的「断开并
重新配置」只删本地副本，不会吊销服务端的授权。

### 系统弹窗要「登录」钥匙串密码

钥匙串里的每条记录都带着**创建它的那个程序**的访问控制表，系统靠代码签名认人。

- **正式签名的版本**（Developer ID）身份稳定，读令牌不会弹窗。
- **ad-hoc 签名的版本**（自己 `scripts/package-app.sh` 构建的默认结果）没有证书，
  系统只能拿二进制的 cdhash 当身份，而它**每重新构建一次就变一次**。新构建在旧
  记录眼里是另一个程序，于是要一次授权。

弹出来时选「**始终允许**」而不是「允许」：后者只放行这一次。选了「始终允许」之后，
同一份二进制不会再问；换了新构建还会再问一次，这是系统机制，不是 App 的 bug。

**什么时候会问、什么时候不会：**

| 场景 | 会不会弹 |
|---|---|
| 全新安装、还没配过服务器地址 | **不会**——没配过地址就不可能配过令牌，答案是确定的，不去问 |
| 配对过程本身（填地址 → 连接并配对 → 网页批准） | **不会**——令牌是这一刻新写进去的，写入不需要授权 |
| 关掉了「开机自动连接」，冷启动 | **不会**——没让 App 连，就不去读令牌 |
| 开着「开机自动连接」，冷启动 | 可能问一次，紧接着就是自动连接 |
| 在状态面板里点「连接」 | 可能问一次 |

会问的两处都紧跟着一个用户自己发起的动作，不会再出现「什么都没做就冒出来一个
系统授权框」。同一次运行里令牌只真读一次（读到就在内存里缓存），所以最多问一次，
不会像早期版本那样开一次 App 被问五六遍。

**弹之前 App 会先说明。** App 读令牌前会先静默试一次；要授权的话，先弹一个简短的
说明「需要存储连接密钥」（连接密钥就是这个令牌，配对时生成，不是你的密码）。点「继续」
才出现系统弹窗；选「暂不连接」就先不连，之后在状态面板里点「连接」再问。系统弹窗里
提到的条目名是「MovieClaw 转码器连接密钥」（旧版本存的条目没有名字，弹窗里显示
`com.movieclaw.transcoder`，授权一次后会自动改名）。

## 4. Jellyfin-ffmpeg

App 启动时会检查当前 ffmpeg 是否包含 `h264_videotoolbox`。缺少可用版本时，会询问
是否从 [Jellyfin 官方 Releases](https://github.com/jellyfin/jellyfin-ffmpeg/releases)
下载 macOS arm64 portable 版本：

- 确认后在设置的「转码」页显示下载进度，并校验 Release API 提供的 SHA-256 digest、
  压缩包路径和编码器能力；
- 取消后状态面板「更多」菜单与「转码」页都保留下载入口，安装成功后变为更新入口；
- 下载包临时保存在 App Support，完成后删除，不进入媒体目录；
- 更新托管版本前会先停止接收新任务，并等待当前任务完成；
- 更新失败不会替换现有可用版本；
- 已配置的自定义 ffmpeg 路径不会被自动覆盖。

如果官方 Release 没有唯一的 macOS arm64 资产或缺少可验证的 digest，App 会拒绝安装，
不会回退到第三方镜像或任意下载地址。

## 5. HTTPS 和可信内网 HTTP

公网或不可信网络必须使用 HTTPS。若服务端和 Mac 位于可信内网，可以在网页和 App 中
填写实际的内网 HTTP 地址，例如：

```text
http://10.1.1.254:实际映射端口
```

端口只是示例，必须替换成 NAS 当前 Nginx 的实际映射端口。HTTP 模式下控制面使用
`ws://`，源视频、HLS 产物、控制消息和临时 Token 都是明文；只允许防火墙放行给 Mac
Worker，绝不能把该端口发布到公网。App 会在保存 HTTP 地址时再次要求确认，不会因为
HTTPS 连接失败而自动降级到 HTTP。

## 6. 开机自启动与自动恢复

「设置 → 连接」里的「开机时自动启动」默认打开：App 在
`~/Library/LaunchAgents/com.movieclaw.transcoder.plist` 放一份 launchd 配置，登录后由系统
拉起它。「系统设置 → 通用 → 登录项」里能看到，也能在那边关掉。这份配置顺带兜住 App 本身
的崩溃：意外退出（包括被强制退出）后系统约 10 秒内会重新打开它；点「退出」则不会。

- 更新 App、或者把它挪了位置（比如从下载目录拖进「应用程序」）后，打开一次就行：配置会
  自动指向新位置。手动打开的那个会把自己交给系统管（菜单栏图标可能闪一下），之后崩溃
  照样会被拉起。
- 以前照旧版说明手动装过同名配置的，不用管：App 会直接用自己的配置替换它。

App 分成两个进程：菜单栏 App 和「转码内核」（活动监视器里是两个同名的
`movieclaw-transcoder`，内核带 `--core` 参数）。连 NAS、管 ffmpeg 的都是内核，出了问题
只重启内核，菜单栏 App 一直在，面板上能看到恢复进度。各种意外的兜底：

| 情况 | App 怎么处理 | 要不要你管 |
|---|---|---|
| 转码内核崩溃 | 1、2、4、8…秒后自动重启（最长 60 秒） | 不用；10 分钟内崩溃 5 次才停下，面板上点「重试」 |
| 转码内核卡死 | 35 秒没有任何响应就强制结束、重启 | 不用 |
| 内核内存超过 1 GB | 等手上没有任务时重启一次 | 不用 |
| ffmpeg 卡住不动 | 起转 90 秒没进度、或 60 秒没有新进度就结束它，NAS 会重试 | 不用 |
| 连续 3 个任务刚开始就失败 | 暂停接单 10 分钟并自检 ffmpeg，自检通过到点自动恢复 | 自检不过时在设置里重新下载 ffmpeg |
| 内核崩溃后留下的 ffmpeg | 新内核启动时清掉（只认本 App 起的转码进程，你自己跑的 ffmpeg 不受影响） | 不用 |
| 睡眠唤醒、换网络 | 立刻确认连接，断了就重连 | 不用 |
| NAS 连不上、握手没响应 | 自动重连，间隔逐步拉长到 30 秒；握手 20 秒没完成就断开重来 | 不用 |
| 服务端没打开远程转码 | 每分钟重试一次 | 在网页「应用 → 远程转码」打开开关 |
| 这台 Mac 的授权失效 | 每 5 分钟重试一次 | 在网页「设置 → 设备」重新配对 |
| App 本身崩溃 | 系统约 10 秒后重新打开它（要开着「开机时自动启动」） | 不用 |

面板底部会显示「24 小时内自动恢复过 N 次」和最近一次的时间、原因。设计细节见
[`docs/design/remote-transcode.md`](../../docs/design/remote-transcode.md)「Worker 容错」。

## 7. Headless 排障模式

菜单栏 App 是默认部署方式。需要在没有图形界面的环境中排障时，可以使用同一个 Release
可执行文件的 Headless 模式。Headless 只接受显式命令行参数，不读取环境变量：

```bash
.build/release/movieclaw-transcoder \
  --headless \
  --nas-url https://nas.example.com \
  --token '<在网页「设置 → 设备」里为这台机器签发的令牌>' \
  --ffmpeg /opt/homebrew/bin/jellyfin-ffmpeg \
  --worker-id macmini-m1 \
  --max-jobs 1
```

Headless 没有界面，走不了配对流程，因此需要显式传令牌。启动时会检查
`h264_videotoolbox`；能力不满足时不会向服务端登记。Headless 适合临时验证连接和
ffmpeg，不建议把令牌长期写入 shell 历史或启动脚本。

## 8. 运行状态和日志

点菜单栏图标弹出状态面板：

- 转码时每个任务一张卡片，回答「看片的人播得顺不顺」：
  - 「播放流畅」：转码比播放快（实时速度 ≥ 1.3 倍，暂停的时间不算）；
  - 「已提前准备好」：转码已领先播放一两分钟，NAS 让它先歇着，播放追上来再接着转——
    这是最健康的状态；
  - 「刚好跟得上」（1～1.3 倍）/「转码跟不上」（不到 1 倍，观众会缓冲，卡片上给出处理建议）；
  - 「观众暂停了」：画面已经准备好，继续播放不用等；
  - 右边的「看到 25:10 / 1:52:10」是观众真实的播放位置（NAS 按播放器的进度上报推过来），
    下面的进度条像播放器一样：实心段是看到的位置，浅色段是已经转好的部分；服务端版本
    较旧、推不来观众位置时退回「已准备到 25:40」（转码准备到的片中位置）。倍速等数字在
    悬停提示里。
- 空闲时显示今天转了几次、转出的片子一共多长（是片子的时长，不是花了多久）、有没有
  失败，以及最近几条任务的结果（「整部转完」「看到 25:10」「失败」，失败原因悬停可见）。这份记录只存在本机
  （片名与统计数字，最多 7 天、50 条），同一任务拖动进度条导致的多次重启合并成一条；
- 连上之后下面有两张 iStat Menus 式的小图表：「转码 CPU」「转码内存」，是正在转码的
  ffmpeg 最近 2 分钟的占用（每 2 秒一格），没在转时就是 0；本 App 自身的开销（界面、心跳、
  上传代理里暂存的分片，约几十 MB）不算在内，悬停提示里单独写。CPU 按整台 Mac 算百分比（所有核合计
  100%），灰色底是整机 CPU；内存与「活动监视器」的「内存」一栏同口径，下面对照整机已用 /
  总内存。VideoToolbox 硬件编码在 Apple 芯片的媒体引擎上跑，不计入 CPU；
- 断线、出错时是一张提示卡片，「立即重连」「复制诊断」等按钮直接放在卡片里；
- 底栏「更多」里是断开连接、立即重连、ffmpeg 下载/更新、日志和脱敏诊断信息。

App 开着就接单，没有「暂停接单」开关。更新 ffmpeg 时会自动先停止接新任务、等手上的
转完再换，不会打断正在看的人。

菜单栏图标本身也会提示状态：转码中右下角是一个实心圆点，断线重连或出错时是感叹号。
日志文件位于：

```text
~/Library/Logs/MovieClawTranscoder.log
```

日志会在超过约 5 MiB 后轮转，并脱敏 Worker Token 和签名 URL 的 `token=` 查询参数。
两个进程写同一个日志文件，转码内核写的行带「[内核]」前缀。
遇到播放卡住或 Worker 闪退时，优先查看：

1. 状态面板里的状态是否为「空闲」或「转码中」；
2. 服务端「远程转码」页面是否显示配置就绪；
3. 服务端地址的 WebSocket Upgrade、Range 读取和 PUT 上传是否都能从 Mac 访问；
4. App 日志中的 ffmpeg 退出原因、产物上传中断和 NAS 断线信息。

服务端会在 Worker 断线或任务失败后释放远程会话，并走播放器已有的重试或降档路径。
