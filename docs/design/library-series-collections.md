# 系列合集：让 TMDB / NFO 里的「系列」自动成集

> 目标（用户 2026-09-10 提出）：
> 1. 刮削时 TMDB 有系列 → 按 NFO 规范写出，同时我们这边自动建合集；
> 2. Jellyfin 播放器接口正确输出；
> 3. NFO 里读得出系列 → 入库时我们的合集也要有记录可见。
>
> 前置：合集本身的模型与接口见 [library-collections.md](library-collections.md)，
> 筛选见 [library-filtering.md](library-filtering.md)。本文只讲「系列」这一层。

## 0. 现状（2026-09 核实过的，不是印象）

| 事 | 现状 |
|---|---|
| 刮削存系列吗 | **不存**。`MediaMetadata` 没有任何系列字段 |
| TMDB 给了吗 | **给了，而且免费**：`belongs_to_collection` 在 `/movie/{id}` 的基础响应里，`fetch_media_profile` 已经拿到了 `data`，只是没读它 |
| NFO 写系列吗 | **不写**。`write_full_nfo` 的标签是 title/originaltitle/year/tmdbid/uniqueid/plot/tagline/runtime/mpaa/premiered/ratings/genre/studio/country/director/actor，**没有 `<set>`**——而 Emby/Jellyfin/Kodi 认合集正是靠它 |
| NFO 读系列吗 | **不读**。`read_entry_metadata` / `read_local_sidecar` 都没有解析 `<set>` |
| 唯一碰系列的地方 | 发现页详情的实时链路（`movieclaw_media/service.py::_movie_collection`），拉 `collection/{id}` 渲染「系列电影」一行，**用完即弃** |

结论：这三件事**全部是新增**，没有既有实现可以复用，也没有既有数据可以迁移。

## 1. 第一性判断：系列合集不是新实体

最容易走错的一步，是给「系列」单开一张表（`media_series` + `series_item`），
然后写一套同步逻辑把它和 `collection` 对起来。**不要。**

系列合集就是**规则驱动的合集**，规则是「属于系列 X」：

```
rules = [{"field": "series_key", "op": "any_of", "values": ["tmdb:1241"]}]
```

这一句话决定了后面所有事都不用写：

| 想要的行为 | 谁做的 |
|---|---|
| 新入库一部《哈利·波特》续集，自动进合集 | 不用做。规则驱动的合集本来就是查询时求值（collections.md 1.3 不物化） |
| 网页与 Jellyfin 成员一致 | 不用做。两边都走 `resolve_members()` → `_wall_page_ids()` |
| Jellyfin 里出现一个 BoxSet | 不用做。`visible_collections()` 已经把所有合集下发成 BoxSet |
| 合集详情页、chip、封面 | 不用做。F3.2 那套 UI 不区分合集从哪来 |

**这正是 collections.md 1.2「这个抽象要吃掉既有特例」的第二次兑现**——第一次是
「我的收藏」。真要新开一张表，就说明抽象没立住。

## 2. 数据模型：一列 + 一个规则字段

### 2.0 为什么叫 `series_` 而不是 `collection_`

`collection` 在本仓库已经指四样东西（collections.md 1.2.1 那张表）。再加一列
`collection_key` 只会让第五个人读错。**代码里一律用 `series` 指「作品系列」，
`collection` 只留给「合集」这个容器**——系列是内容的属性，合集是装东西的盒子。

### 2.1 `media_metadata` 加两列

```python
series_key: str | None   # 成员判定的唯一依据："tmdb:1241" / "name:哈利波特系列"
series_name: str | None      # 系列展示名，建合集时用；不参与判定
```

**为什么是标量列而不是多对多**：TMDB 的 `belongs_to_collection` 是**单值**——
一部电影至多属于一个系列。既然上游就没有多对多，就不要为它建关联表。

**为什么是一个 `series_key` 而不是 `tmdb_id` + `set_name` 两列**：
两列意味着两个规则字段，而一部片可能两者都有（TMDB 给了 id，NFO 还写着名字），
于是它同时落进两个合集，用户看到两个几乎一样的系列。一个规范化的 key 从构造上
杜绝这件事——写入时定优先级：**有 TMDB id 就是 `tmdb:{id}`，否则才是 `name:{规范化名}`**。

`name:` 那一支只会出现在**没有 TMDB 身份的条目**上（本地库、认不出的片），
与 `tmdb:` 天然不相交。

### 2.2 筛选加一维

`items.py` 的 `LibraryFilter` 加 `series_keys: tuple[str, ...]`，
`_filter_subquery()` 加一条 `MediaMetadata.series_key.in_(...)`。
`collections.py` 的 `rules_to_filter()` 认 `series_key` 字段。

一维、一条 WHERE、一个字段名——**筛选的唯一收窄点不变**。

### 2.3 迁移

纯新增两列，向前兼容（CLAUDE.md 硬约束 3）。旧版本回退后不认识这两列，读写都不碰。

## 3. 刮削侧：写 NFO + 建合集

### 3.1 取值（零额外请求）

`fetch_media_profile` 已经有 `data`，加两行：

```python
summary = data.get("belongs_to_collection") or {}
profile.series_tmdb_id = summary.get("id")
profile.series_name = summary.get("name")
```

`MediaProfile` 加这两个字段，`apply_display_profile()` 落到 `media_metadata`
（顺手把 `series_key` 拼出来）。

> 系列自己的海报/背景要另拉 `collection/{id}`——**一期不做**，封面用现成的
> 「首位成员海报叠放」（F3.2 已实现，实机看下来够用）。见第 9 节开放问题。

### 3.2 写 NFO

`write_full_nfo()` 加 `<set>`，按 Kodi v18+ 的嵌套写法：

```xml
<set>
  <name>哈利·波特系列</name>
</set>
```

三条硬约束：

- **必须走现有闸门**：`effective_mirror_flags(library)` 的 `write_nfo` 与
  `trusted_entries`。加了 `<set>` 不等于可以绕过"要不要动用户媒体目录"这一问。
- **不发明非标标签**。不往 `<set>` 里塞 `tmdbid`——那不是通行写法；重装后
  重新刮削一次就能把 id 拿回来，不值得为它污染别人的库。
- **内容不变则不改 mtime**：现有 `write_full_nfo` 已经这么做，加字段后仍成立。

### 3.3 建合集（幂等）

刮削落库后，若 `series_key` 非空，就 ensure 一个合集：

```
builtin = f"series:{series_key}:{library_id}"     # builtin 上有唯一约束
name    = series_name
rules   = [{"field": "series_key", "op": "any_of", "values": [series_key]}]
sort    = "release_date_asc"                     # 上映**正序**（见 6 节那张表）
```

与 `ensure_builtin_collections()` 同一手法（先查后插，幂等），放在
`services/library/collections.py`，不要写在刮削里——刮削只管落列。

## 4. 读 NFO 侧：第三方整理过的库

这一支服务的是「用 TMM/Kodi 整理过、直接挂进来」的用户。

- `read_entry_metadata()` 与 `read_local_sidecar()` 加 `<set>` 解析，**两种写法都认**：
  `<set>名字</set>`（Kodi v17-）与 `<set><name>名字</name></set>`（v18+）。
- 扫描入库时，若该条目**没有 TMDB 身份**（本地库 / 认不出），把 `name:{规范化名}`
  写进 `series_key`，并 ensure 同样一个合集。
- 若有 TMDB 身份，NFO 里的 set **只作参考不落 key**——以 TMDB 为准（2.1 的优先级）。

> **注意现状**：`read_entry_metadata` 今天只在**详情页降级展示**时被调用
>（`items.py:1891`），不在入库路径上。所以第 4 节要在扫描侧**新接一处**读取，
> 不是改个现成的调用点。这是本次改造里最容易低估的一块。

## 4.5 汇总：什么时候往 `collection` 表写行

两条读取路径最后汇到**同一个 ensure**，都发生在入库那一刻：

| 触发时机 | 谁给的系列 | 写 `media_metadata` | 写 `collection` 行 | 写 `collection_item` |
|---|---|---|---|---|
| 扫描 → 识别 → TMDB 刮削 | `belongs_to_collection` | `series_key = "tmdb:{id}"` + `series_name` | ensure 一行（幂等） | **不写** |
| 扫描 → 本地/认不出条目 → 读 NFO `<set>` | NFO | `series_key = "name:{规范化名}"` | ensure 一行（幂等） | **不写** |
| 重新刮削 / 刷新元数据 | 同上，可能变 | 覆盖 | ensure 新的那个 | **不写** |
| 本地条目「重新读取 NFO 与封面」 | NFO，可能变 | 以 NFO 为准覆盖；`<set>` 删了清成空串 | ensure 新的那个 | **不写** |
| 存量回填作业 | 轻量详情 | 补列 | ensure | **不写** |

三件要点：

1. **只写合集行，不写成员行。** 成员是规则求值出来的（`series_key = X`），
   所以：不需要"把这部片加入合集"的动作；一部片改了识别、`series_key` 变了，
   它自动从旧合集消失、进新合集，**没有任何清理逻辑要写**。
   `collection_item` 那张表只服务用户手挑的固定名单。
2. **ensure 是每条目一次 SELECT**（`builtin` 上有唯一约束，走索引）。
   一次一千部的扫描多一千条点查，可以忽略；真嫌多可以在扫描收尾按
   distinct `series_key` 批量做一次——但先别提前优化。
3. **受 6.6 那个展示开关管**。关着的时候前两列照写，第三列不写。

### 4.5.1 为什么一定要有这一行（不能纯靠推导）

理论上"有哪些系列"可以从 `GROUP BY series_key` 现算，一行不建。但合集行承载了
推导不出来的东西：

- **稳定 id**——网页路由 `/library/{id}/c/{cid}` 与 Jellyfin 的 BoxSet GUID 都要它；
- **改名**（TMDB 的系列名不一定是用户想要的）；
- **隐藏**（6.1 那个墓碑）；
- **封面指定**（`cover_item_id`）；
- **排序位置**（`position`）。

所以建行，但**行里不存成员**——存的是"这个容器叫什么、怎么显示"，
成员永远现算。

### 4.5.2 库维度：同一个系列在两个库里是两行

规则驱动的合集必须指定所属库（`create_collection` 里就是这么校验的）。
所以《哈利·波特》如果同时躺在「电影库」和「4K 电影库」，会是两行、两个
BoxSet。这是"合集挂在库下面"那条 IA 决策的自然结果，不是 bug——
跨库合集统一等 F4。

## 4.6 生命周期：条目删了、合集空了怎么办

自动生成之后合集数量会从"几个"变成"几十个"，"内容没了怎么办"就从一个
边角问题变成天天发生的事。这一节把**现在已经是什么行为**（读代码核实过）
和**应该保持什么行为**写清楚。

### 4.6.1 删掉一条作品

`library.items.delete` 是全站唯一真删磁盘的接口，它删完文件之后会走
`cleanup_orphan_items`：条目**不在任何库、也没有订阅**时连 `media_item`
行一起删。合集这边分三条路，**全部是既有外键与既有查询在兜底，没有一处
需要为合集写删除钩子**：

| 合集形态 | 条目被删时发生什么 | 靠什么 |
|---|---|---|
| 规则驱动 | 成员实时求值，`library_file` 行没了它就不在墙上，也就不在合集里 | `resolve_members` = `_wall_page_ids` 的薄适配 |
| 名单驱动（手动 / 固定当前命中） | `collection_item` 行随条目行级联删除 | `collection_item.media_item_id` `ON DELETE CASCADE` |
| 任意形态的封面 | 封面指针置空，回落到"取首个成员" | `collection.cover_item_id` `ON DELETE SET NULL` |

条目还在别的库或还有订阅时 `media_item` 行保留，名单行也跟着保留；但
`resolve_members` 是**按 `library_id` 跑**的，本库已经没有文件，它照样不出现。

### 4.6.2 进回收站期间：合集和海报墙口径一致，这是特性不是遗漏

核实的结果和直觉不一样，值得写下来：**海报墙的成员查询没有文件状态条件**
（`_titles_sorted` / `_wall_page_ids` 只限定 `library_id` +
`unidentified_code IS NULL`）。所以文件被移进回收站、7 天保留期还没到的时候，
条目**仍然在墙上，也仍然在合集里**，直到 `purge_due_files` 到期删行才走 4.6.1。

不要为合集单独加一条 `in_place()`。"墙上有什么、合集里就有什么"是这套设计
最值钱的一条性质，给合集加一条自己的 WHERE 等于把它换成纪律。要改就改墙的
口径，两边一起改。

> **2026-09-10 更新：这一节的结论被推翻了一半，口径已经统一。**
>
> 初稿在这里记了一笔"既有的不一致，本次不动它"：`refresh_stats` 统计作品数
> 只算 `in_place()`，海报墙不看状态，于是"最后一个文件进了回收站"的条目，
> 库卡片的作品数已经减一、墙上还摆着。既然要动，就按当时那句"要改就改墙的
> 口径，两边一起改"改了：
>
> - `LibraryFile.on_shelf()`（`state != TRASHED`）成为**在架**口径的唯一判别；
> - 海报墙、筛选 facet、合集、Jellyfin 全部经过 `items._wall_scope()`；
> - 库卡片的作品数 / 分集数 / 待识别数跟着改用在架口径（文件数与容量仍按
>   在位算——失联的文件不占盘）。
>
> **失联的片仍然在架**，这是与 `in_place()` 的关键差别：用户要看得见它才知道
> 该去插硬盘，而「有文件失联」那一档筛选找的正是这些片。把它们一起摘掉会让
> 那档筛选永远为空——这是实现时才发现的，`in_place()` 用在这里太强。
>
> 回收站里的片恢复之后自己回到墙上，没有补偿逻辑要写（成员永远现算）。

### 4.6.3 合集空了：行留着，只是不出现

三处闸门都是**读时过滤**，没有一处删行：

- `list_collections` 丢掉 `item_count == 0`（`include_empty=true` 才给）；
- Jellyfin `_boxset_dtos` 丢掉空合集；
- `/UserViews` 用 `has_any_member()` 探测第一个真有成员的合集，才下发合集视图。

**不要给空合集加 GC。** 四条理由：

1. **id 是对外契约**：`/library/{id}/c/{cid}` 是可分享的深链，Jellyfin 的
   BoxSet GUID 也由 id 派生。删了重建就是另一个 id、另一个 GUID——客户端侧
   的收藏、播放队列、"继续观看"全指向空气。
2. **行上挂着用户状态**：名字、封面、`position`、`visibility`、`sort`、
   "设为本库的收藏范围"。删行等于把用户配过的东西一起扔掉。
3. **空对规则合集是常态，而且可逆**：「2160p HDR」在你删掉最后一部 4K 的
   那一刻是空的，下回下载回来它自己就满了——成员是实时求值的，不需要任何
   人去"恢复"它。为一个暂态删掉持久状态是净损失。
4. **删行并不省下什么**：空不空本来就是读时算出来的。

代价是明确的：死行仍然要在列表路径上跑一次 `resolve_members` 才知道它是空的
（5.5 量到的 `11 × N` 里，死行和活行一样贵）。这是 **S0 缓存计数**的又一条
理由——内容定义型合集的计数退化成一条 `WHERE` 之后，死行的判定成本接近零，
"不删行"这个决定的代价才是有界的。

### 4.6.4 用户主动删合集，以及删库

| 动作 | 归宿 |
|---|---|
| 删用户自建的合集 | 真删行，`collection_item` 级联清掉 |
| 删自动生成的合集（内置 / 系列） | 落 `hidden` 墓碑——真删了下次 ensure 又长回来（见 6.1，**这个机制目前还不存在**，那句报错在承诺一个没实现的操作） |
| 删整个媒体库 | 合集随库级联删除，这是唯一真删行的路径——"这个库里的一批片"这个定义本身消失了，留着就是幽灵数据 |

隐藏必须**可逆**：库设置里要有一个"显示已隐藏的合集"把它放回来（接口侧
`include_hidden` 与既有的 `include_empty` 同形）。否则「隐藏」就是一个单向
黑洞，和现在那句"可以隐藏"一样，是一句用户兑现不了的话。

## 5. Jellyfin：现在怎么处理，以及为什么"零改动"只对了一半

### 5.1 现在已经实现的（F3.3）

| 客户端问法 | 我们怎么答 |
|---|---|
| `GET /UserViews` | 有可见且**非空**的合集时，追加一个 `CollectionFolder`（`CollectionType="boxsets"`）。判定用 `has_any_member`（LIMIT 1，命中即停） |
| `GET /Items?ParentId=<合集视图>` | 全部可见合集 → `BoxSet` DTO，成员为空的丢掉，带 `ChildCount` |
| `GET /Items?IncludeItemTypes=BoxSet&Recursive=true` | 同上（不少客户端的首页拼装方式） |
| `GET /Items?ParentId=<BoxSet>` | 成员作品。**走 `resolve_members()`——协议层不写查询** |
| `GET /Items/{BoxSet GUID}` | 单条 BoxSet；不可见按 404（GUID 可枚举，空对象等于确认存在） |
| `GET /Items/{BoxSet}/Images/Primary` | 回落到首位成员的海报 |
| `Users/Me` 的 `Configuration` | `DisplayCollectionsView: true` |

系列合集就是 `Collection` 行，**以上七条自动适用**——这一半的"零改动"是成立的，
有 9 条用例压着（`tests/jellyfin/test_boxsets.py`）。

### 5.2 但读完代码发现三处，自动生成之后会暴露

**我上一版说"Jellyfin 不需要新代码"下早了。** 手建的一两个合集掩盖了这三处：

| # | 问题 | 今天为什么没事 | 自动生成之后 |
|---|---|---|---|
| 1 | `_boxset_dtos()` **每个合集一次完整 `resolve_members`**，而且**先全解析再切片**（`Limit` 帮不上忙） | 合集就一两个 | 40 个系列 = 每次打开合集视图 40 次墙查询。电视端会反复拉这个视图，比网页端更疼 |
| 2 | `_wants_boxsets()` 里 `IncludeItemTypes=BoxSet` **直接短路，完全不看 `ParentId`** | 合集都在同一个库 | `?ParentId=<电影库>&IncludeItemTypes=BoxSet` 会把**剧集库的合集**一起返回 |
| 3 | BoxSet 列表这条路径 **绕过 `_sort_entries`**，直接 `query_result(page)` | 一两个合集，顺序无所谓 | 客户端给的 `SortBy` 对合集列表无效，恒按 `position`——几十个合集时用户会觉得"排序坏了" |

第 1 条与网页端是同一个悬崖（5.5），但**必须分别修**：那边批量化的是封面聚合，
这边要批量化的是成员计数。第 2、3 条是协议正确性，与合集从哪来无关——
**现在就该修，不必等系列功能**。

### 5.3 仍然没核实的一件事：影片页怎么显示「所属系列」

我们的 `movie_dto` 里**没有任何回指合集的字段**（读过了：`ParentId` 指向库视图，
没有 BoxSet 的踪影）。Jellyfin 的 `BaseItemDto` 上有没有这么一个标准字段、
各家客户端（Infuse / Jellyfin 官方端 / Emby）在影片页读什么来显示系列，
**我没有核实过，不能假设"我们输出了 BoxSet 就自动有"**。

三种可能，验完才知道该走哪条：

1. 客户端根本不显示 → 那就只有我们自己的网页端做「所属系列」入口，电视端靠 BoxSet 进；
2. 客户端读某个我们没输出的字段 → 补上即可（协议原生字段，不发明扩展）；
3. 客户端靠 NFO 自己扫 → 那是 S3 写 `<set>` 的收益，与协议层无关。

**列为验收项，不是已知能力。** 按 collections.md 4.10 那张清单在真机上各验一遍。

## 5.5 先修性能悬崖：自动生成之前必须做的一件事

**这是复盘时量出来的、v1 方案漏掉的最要紧一条。**

`GET /collections` 现在每个合集调一次 `_view()`，而 `_view()` 里：

- `resolve_members()` —— 至少 1 条查询；
- `_aggregate_wall_views()` 取封面 —— **10 条查询**（数过的，不是估的）。

于是列表接口的代价是 **≈ 11 × 合集数**。今天合集是手建的，一两个，33 条查询无所谓。
自动生成之后一个 300 部的电影库可能有 40 个系列，就是**一次页面加载 440 条查询**——
在 NAS 的 SQLite 上是肉眼可见的卡。

**这是我自己会造出来的悬崖**：`_view` 当初就是按"手建的几个合集"写的。

### 5.5.1 封面聚合批量化（S0，必须先做）

列表接口先把所有合集的封面 id 收齐，**一次** `_aggregate_wall_views()` 覆盖全部，
再按合集分回去。40 × 10 条 → 10 条。这不违反"合集没有自己的查询"——
成员判定仍然一个合集一次 `resolve_members()`，批量化的只是取图。

### 5.5.2 计数：内容型可以缓存，成员型不行

collections.md 2.4 定过"成员数不缓存"，理由是「我的收藏」点一下心就变、而点心
不碰任何库级时间戳。**那条理由对系列不成立**——系列的成员只在
「文件增删 / 重新刮削」时变，而那些**正是已经在调 `refresh_stats` 的写路径**。

所以规则可以说得更准，而不是一刀切：

| 合集类型 | 成员取决于 | 能不能缓存计数 |
|---|---|---|
| 收藏、观看态 | **看的人** | 不能——每人一份，且点一下就变 |
| 系列、类型、年代、画质 | **库里有什么** | 能——跟着 `refresh_stats` 一起刷 |

一期先不缓存（S0 的批量化已经把大头削掉了），但**列表接口要写成"计数可替换"的
形状**，别把 `resolve_members` 散落到各处，否则以后想缓存得先做一遍考古。

真要缓存时，配一条回归测试压住「缓存计数 == `count_members()`」——把纪律风险
变成 CI 能抓的风险，这一招在墙 vs 合集那条用例上已经用过了。

## 6. 产品面：怎么不把用户淹没

这是本次最容易做砸的地方。一个 300 部的电影库可能有 40+ 个系列，
如果它们和用户自己存的三五个筛选混在一起平铺，**用户存的那几个就没了**。

| 问题 | 对策 |
|---|---|
| 一部片也算"系列" | **照样列出**（2026-09-11 改）。最初是成员 < 2 不下发，但只入库一部的系列恰恰最需要补缺片，而且影片页「所属系列」点得进、合集页却列不出，看起来像被隐藏了。淹没问题交给分组 + 可隐藏 + 展示开关；网页与 Jellyfin 同一口径：只有空合集不列 |
| 系列淹没自建合集 | 合集视图**分组**：「我的合集」在前，「系列」在后；chip 行只放自建的 |
| 用户不想要某个系列 | **需要一个隐藏态**——见下方缺口 |
| 完全不想要这功能 | **一个**开关，且是**展示**开关不是刮削开关——见 6.6 |
| 看《哈利·波特》要按顺序 | 系列合集 `sort = release_date`（3.3 已定） |
| 从影片页找到系列 | 影片详情页加一行「所属系列」chip，点进合集详情页（filtering.md 4.3 提过的「所属合集」） |
| 分不清合集从哪来 | 卡片副行：自建写「自动收录」，系列写「系列 · 8 部」 |

### 6.1 已发现的缺口：内置合集删不掉也藏不住（**已补齐**）

`delete_collection` 现在对 builtin 报「内置合集不能删除（**可以隐藏**）」，
但**代码里没有任何隐藏机制**——`visibility` 只有 household/private，没有 hidden。

只有「我的收藏」一个内置合集时这句话不疼不痒（没人想删它，空了还会自动不列）。
一旦自动生成几十个系列合集，"删不掉也藏不住"立刻变成真问题。

**必须一起做**，而且要**只有一个机制**：`collection` 加 `hidden: bool`，
`visible_collections()` 过滤掉。自动生成的合集（内置 / 系列）对用户仍然显示
「删除」，但那个动作**落成 `hidden = true`**——因为真删了，下次刮削 ensure 一遍
它又长回来，用户会觉得"删不掉"。留着行当墓碑，语义上也更诚实：
你删掉的是"我不想看见它"，不是"这个系列不存在"。

用户自建的合集照旧真删。同一颗按钮、两种归宿，由 `builtin is None` 推导——
与"形态是推导的、不存 mode 列"同一条思路。

**已实现**（2026-09-10）：`collection.hidden` 列 + `visible_collections(include_hidden=)`
+ 接口的 `include_hidden` 参数 + 合集页 ⋯ 菜单里的「显示已隐藏的合集」。
`delete_collection` 对自动合集落墓碑并返回 200（不再是那句 400 的空话），
合集详情页的 ⋯ 里给「恢复显示」。ensure 遇到墓碑**不复活**——否则下一次
刮削就把用户的选择顶掉了，那正是"留行当墓碑"要解决的事。

## 6.6 开关到底应该有几个：一个

初稿把「要不要开这个功能」写成了一个放在 `MetadataScrapeSetting` 里的刮削开关。
**那是想岔了**——这里其实藏着四件互相独立的事，混成一个开关，用户既不知道自己
关掉了什么，我们也说不清关掉之后系统是什么状态。

拆开之后，需要开关的只有一个：

| 事 | 给不给开关 | 为什么 |
|---|---|---|
| 刮削取 `belongs_to_collection` 落 `series_key` | **不给** | 零额外请求、零副作用，还是其他三件的前提。给开关等于给用户一个"把功能关一半"的机会，关了之后 NFO 也写不出、缺片也算不了 |
| NFO 写 `<set>` | **不给**（跟随已有的 `mirror_nfo`） | 「要不要动我的媒体目录」这个意图，用户在 `mirror_nfo` 里已经表达过一次了。再给一个 set 级开关是让他把同一个问题回答两遍 |
| **自动在合集页生成系列合集** | **给** | 这是唯一直接改变用户看到什么的一件事：升级之后合集页凭空多出几十个东西 |
| 缺片补齐 | **不给** | 它只是合集详情页里的一块，不想看就不点。而且改成懒加载之后（6.5.1）它连请求都不发 |

### 6.6.1 那个开关放哪、控制什么

**不放在刮削配置里**——它不是刮削的事。它是**媒体库的展示偏好**，
和「首页显示哪些库」「相册墙密度」同类。

关键分寸：**开关控制的是展示，不是数据。**

关掉之后：

- `series_key` 照常落库——**接口与规则层面**仍然可以按系列取（手写一条规则、
  或分享一个带参数的链接）。但**界面上不给"系列"这一维下拉**：一个库几百个
  系列，下拉根本没法用，合集才是它正确的呈现形态；
- NFO 的 `<set>` 照常写（下游 Kodi/Emby 不受影响——**他们的合集不该因为我们
  界面上的一个偏好而消失**）；
- 只是不自动创建 `collection` 行，合集页只有用户自己存的那些。

**打开时怎么补上**：跑一次 ensure（每个库一条 `GROUP BY series_key` 拿到全部
取值，缺哪个建哪个），**不重新联网、不重新刮削**——数据早就在列里了。
这条"数据照落、展示可关"与产品既有的判断同源：**可逆的展示偏好可以关，
不可逆的数据缺失不能**。

## 6.5 让这个功能真正有用：缺片补齐

到这里为止，方案只做到了「把已有的片归归类」。**对一款 PT 自动化产品，这远远
不够——真正的价值在于告诉用户「你缺哪几部」，并且一键去补。**

TMDB 的 `GET /collection/{id}` 会回整个系列的 `parts[]`（每部带 tmdb id、
标题、上映日、海报）。拿到它之后：

```
《哈利·波特》系列          已有 6 / 共 8
[有][有][有][有][有][有]  [缺 混血王子]  [缺 死亡圣器(上)]
                            └── 一键订阅 ──┘
```

**订阅是现成能力**：`subscriptions.create` 吃 `title_ref = "tmdb:movie:{id}"`
（核实过），而 `parts[]` 正好给这个 id。所以「缺片一键订阅」不需要新的下游链路，
只是把两个已有的东西接起来。

这条把系列合集从「整理」变成「补齐」，与产品既有的**剧集缺集补齐**是同一个心智，
用户不需要学新东西。

### 6.5.1 代价与取舍

- **懒加载，不在刮削期拉**：用户第一次打开某个系列合集的详情页时才发
  `GET /collection/{id}`，之后走缓存（parts 极少变）。这样刮削一点不变重，
  用户从没点开的系列一个请求都不花。初稿写的是"刮削时每个系列一次"，
  那是白白给扫描加负担。
- 比 v1 里我为了海报而犹豫的那次请求划算得多——**这次换回来的是功能，不是一张图**。
- 存哪：`collection` 行上一列 `series_parts JSON`（tmdb id + 标题 + 上映日 + 海报路径）。
  它是外部档案的快照，不是我们的事实源，脏了重拉即可。
- 顺带白拿系列官方海报/背景（同一次响应里就有），v1 里单列的「开放问题 1」自动解决。

### 6.5.2 分寸

- **只在合集详情页展示缺片**，不要在合集卡片上显示「缺 2 部」——那会把浏览
  变成催办，一屏几十个红色角标是压迫感不是帮助。
- 已经在追的（有订阅工单）显示「追踪中」而不是「订阅」按钮，走既有的
  `effectiveLibraryId` / 订阅状态那套。
- 用户明确不想要的那几部，要能标「不看」，否则「缺 2 部」永远消不掉。
  这一条可以后置，但要先想清楚它存在，别把状态设计成只有"有/没有"。

## 7. 存量库怎么办

新列默认 NULL，**已经刮削过的库一部都不会自动成系列**。不能要求用户整库重刮
（大库要跑很久，还会重下图）。

方案：一个轻量回填作业，只对 `tmdb_id 非空 且 series_key 为空` 的电影
发一次 `GET /movie/{id}`（**不带 append_to_response**，比完整刮削便宜一个量级），
只取 `belongs_to_collection` 落列 + ensure 合集。可中断可重入，
按现有作业中心的惯例给进度。

> NFO 那一支的回填同理：扫描时顺带补，不单开作业。

| 期 | 内容 | 验收 |

| **S2** | 刮削取值落库 + ensure 合集 + `sort=release_date` | 刮一部《哈利·波特》，合集自动出现且按上映排序；再刮一部续集，数量自己 +1 |

| **S4** | 产品面：分组、`< 2` 不下发、影片页「所属系列」、**展示开关**（6.6） | 40 个系列的库里，用户自建的合集仍在第一屏 |
| **S5** | **缺片补齐**（6.5）：拉 parts、详情页显示已有/缺、一键订阅 | 手动移走系列里一部，详情页出现「缺 1 部」且能订上；顺带拿到官方系列海报 |
| **S6** | 读 NFO 的 `<set>`（含扫描侧新接的读取点） | 拿 TMM 整理过的目录挂进来，不联网也能成集 |
| **S7** | 存量回填作业 | 老库跑完之后系列齐了，且没有重复刮削整份档案 |

**实现完成后的实际情况（2026-09-10，S0–S7 全部落地）：**

| 期 | 结果 | 与计划的出入 |
|---|---|---|
| S0 | ✅ | 封面批量化之外还多做了一件：**计数改走 `_wall_count`**（一条 `COUNT(DISTINCT)`）。原计划只批量化取图，但按标题排序的合集每数一次都要把全库标题取出来在 Python 里做拼音排序，那才是更陡的那一段。收窄条件仍只有一处（共用 `_narrow` + `_wall_scope`），换的只是投影，回归用例压着 `_wall_count == len(_wall_page_ids)` |
| S1 | ✅ | `series_key` 多了一个**空串**取值：「查过了，没有系列」。不区分的话存量回填每轮都会把本来就没系列的片重新问一遍 TMDB，永远跑不完（三态铁律的直接应用） |
| S2 | ✅ | 实现时撞出一个**真 bug**：`effective_rules()` 原本是"builtin 非空就去规则表查"，于是任何自动生成的合集规则都被整条丢掉、成员恒为空。改成"行上存了规则就用行上的，只有规则长在代码里的（「我的收藏」）才查表" |
| S3 | ✅ | 按计划 |
| S4 | ✅ | 展示开关落在 `library.auto_series_collections`（与「首页展示」「生成章节」同一处），不在刮削配置里。**后补（2026-09-11）**：整库补齐（扫描收尾每轮都跑）起初没查开关，关了开关扫一次库合集就全回来；现在条目级与整库两支同一口径。其他库（家庭录像）也显示这个开关，系列来自 NFO 的 `<set>`；照片库不显示 |
| S5 | ✅ | 按计划：懒加载 parts + 快照 + 缺片一键订阅（复用 `title_ref="tmdb:movie:{id}"`），系列官方海报同一次响应里白拿 |
| S6 | ✅ **做了**（原建议先砍） | 落点比预想的窄也更省：`read_local_sidecar` 已经在扫描路径上（本地条目的 sidecar 读取），加一个 `_parse_set_name` 就够，不必"在扫描侧新接一处读取"。两种写法都认（v17- 裸文本 / v18+ 嵌套） |
| S7 | ✅ | **简化**：没做成带进度条的作业中心任务，做成了 5 分钟一轮、每轮 50 部的定时任务。同样的用户价值（升级完自己就补齐），少一大截样板，而且"中断了下次接着跑"是**构造上**成立的（判据就是"这一列还是 NULL"），不靠状态机记录跑到哪 |

**顺序上的两条硬话**：

- **S0 必须在 S2 之前**。自动生成会把合集数从个位数拉到几十个，而列表接口
  今天的代价是 `11 × 合集数` 条查询。先自动生成、再回头优化，等于先给用户
  一个卡顿版本——这类回归比晚一周上线贵得多。
- **S6（读 NFO）可以最后**，甚至可以砍。它只服务"用第三方软件整理过、且不联网"
  这一小撮场景，却要在扫描侧新接一处读取、外加系列名规范化（繁简/空格/大小写）
  的一堆麻烦。**我的建议：S1–S5 先上，S6 看有没有人真的要。**

**S1 与 S2 之间不要跳**：S1 的验收（同一批 id）是整条链路的地基，
它一旦不成立，后面每一层都会各写一套查询。

## 9. 我的建议与仍需你拍板的

### 9.1 建议（我会这么做）

1. **先做 S0**。自动生成之前把列表接口的代价从 `11 × N` 削下来，否则第一个
   大库用户拿到的是"合集页变卡"这个回归。
2. **S5 的缺片补齐是这个功能的真正价值**，别当成锦上添花。只做归类的话，
   用户装个 Emby 也有；能告诉他"缺哪两部、点一下就去补"的，只有这个产品。
3. **系列海报跟着 S5 白拿**（同一次 `collection/{id}` 响应里就有），v1 里
   单列的那个开放问题自动消失——为一张图专门发请求不划算，为 parts 发就很划算。
4. **S6（读 NFO 的 `<set>`）建议先不做**，理由见分期表下的第二条硬话。
   等真有人提再说，那时也更清楚他要的是哪一种写法。
5. **剧集明确不做**，并且在文档和 UI 上说清楚，免得用户以为漏了。

### 9.2 拍板结果（2026-09-10）

用户的答复是「开工，规划内容全部做完，bug 也要修」——三个口味问题没有单独
点名，按 9.1 的建议做了，落点如下：

| 问题 | 落地 |
|---|---|
| 卡片上要不要显示「缺 N 部」 | **不显示**。卡片副行只写「N 部 · 系列」，缺片信息留在详情页 |
| NFO 里要不要带 id | **不带**。`<set>` 里只有 `<name>`，不发明非标写法 |
| 自动生成默认开还是默认关 | **默认开**（`library.auto_series_collections` 默认 true）。关掉只是不建合集行，`series_key` 与 NFO 照写 |
| S6（读 NFO）做不做 | **做了**——落点比预想的省（见 8 节的对照表） |

### 9.3 原始的三个待拍板项（存档）

1. **卡片上要不要显示「缺 2 部」**。我倾向**不显示**（6.5.2）：一屏几十个红角标
   是压迫感不是帮助，缺片信息留在详情页。但你可能认为"看见才会补"更重要——
   这是产品口味，不是技术问题。
2. **NFO 里要不要带 id**。现在定的是不带（不发明非标写法），代价是换个软件
   认不出这是同一个系列。
3. **自动生成系列合集，默认开还是默认关**（就是 6.6 里那唯一一个开关；
   刮削落库与写 NFO 都不受它管，也不给开关）。我倾向**默认开**——默认关的话
   多数人不会发现有这个功能，等于白做。代价是升级之后合集页会突然多出几十个
   东西，所以需要配一次"这是新功能"的说明，否则像是出了 bug。

## 10. 风险

| 风险 | 应对 |
|---|---|
| 写 `<set>` 动了用户的媒体目录 | 沿用 `write_nfo` 闸门与 `trusted_entries`，不新开旁路；内容不变不改 mtime |
| 自动合集淹没自建合集 | 第 6 节整节都是为这件事；分组 + 可隐藏 + 可关（`< 2` 不下发已于 2026-09-11 撤掉，见 6 节表格） |
| 系列名多语言漂移（重刮换语言 → 合集改名） | 成员判定只认 `series_key`（语言无关的 id），名字变了只是合集改名，成员一个不动 |
| 回填打爆 TMDB 限流 | 只发轻量详情、走现有作业中心的并发与退避 |
| 「内置合集可以隐藏」是空头支票 | 6.1 一起补上 hidden，否则这个功能一上线就有一堆删不掉的合集 |
| **合集列表查询数随合集数线性涨**（今天 `11 × N`） | S0 先批量化封面聚合；计数按"内容型 / 成员型"分类，为以后缓存留形状（5.5） |
| 缺片列表把浏览变成催办 | 缺片只进详情页，不上卡片角标；已订阅的显示「追踪中」；留一个"不看"的位置（6.5.2） |
| 升级后合集页凭空多出几十个 | 需要一次新功能说明；展示开关可整体关，且关掉不影响落库与 NFO（6.6） |

## 11. 初稿改了什么（留痕）

| 初稿 | 现在 | 为什么 |
|---|---|---|
| 列名 `collection_key` | `series_key` / `series_name` | 「collection」在本仓库已经四义（collections.md 1.2.1），再加一个只会让下一个人读错。系列是内容属性，合集是容器 |
| 没提列表接口的代价 | **S0：先批量化封面聚合** | 数过了：`_view()` 每合集 1 + **10** 条查询，自动生成后 40 个系列 = 一次列表 440 条。这是我自己会造出来的悬崖 |
| 「成员数一律不缓存」 | 分成**内容型 / 成员型** | 2.4 那条理由（点心就变、不碰时间戳）对系列不成立——系列只在已经调 `refresh_stats` 的写路径上变 |
| 只做归类 | **加缺片补齐（S5）** | 只归类的话装个 Emby 也有。能说出"缺哪两部、点一下去补"的只有这个产品，而订阅入口 (`tmdb:movie:{id}`) 是现成的 |
| 系列海报单列为开放问题 | 跟着 S5 白拿 | 为一张图专门发请求不划算；为 parts 发很划算，图在同一次响应里 |
| hidden 与 delete 两套语义 | **一套**：自动合集的「删除」= 置 hidden | 真删了下次刮削又长回来，用户会觉得"删不掉"。留行当墓碑也更诚实 |
| 读 NFO 与其他期并列 | **建议先砍**（S6 或不做） | 只服务"第三方整理过 + 不联网"这一小撮，却要新接扫描侧读取 + 系列名规范化一堆麻烦 |
| 一个含糊的"刮削开关" | 拆成四件事，**只有"自动生成合集"给开关**，且是展示开关 | 混成一个的话，用户不知道自己关掉了什么，我们也说不清关掉后系统是什么状态。落库与写 NFO 不该被界面偏好左右 |
| parts 在刮削期拉（每系列一次） | **懒加载**：打开合集详情页才拉 | 白白给扫描加负担；用户从没点开的系列不该花请求 |
| 「Jellyfin 不需要新代码」 | **只对了一半**：七条问法自动适用，但另有三处（性能、库范围、排序）自动生成后会暴露 | 手建的一两个合集把它们全掩盖了。第 2、3 条是协议正确性，与系列无关，现在就该修 |
| —（实现期新发现） | **`effective_rules()` 会把自动合集的规则整条丢掉** | 原本是"builtin 非空 → 去规则表查"，而系列合集的规则活在行里。不修的话每个系列合集成员恒为空、一个都不下发。改成"行上存了规则就用行上的" |
| S7 = 作业中心任务 | **定时任务，5 分钟 50 部** | 同样的用户价值，少一大截样板；"中断了下次接着跑"变成构造上成立（判据是"这列还是 NULL"），不靠状态机 |
| 4.6.2 "本次不动回收站口径" | **动了，统一到 `on_shelf()`** | 既然这一期就在改墙的查询，把"库卡片说 119 部、墙上摆着 120 部"一起收掉。实现时发现 `in_place()` 太强——失联的片必须留在架上，否则「有文件失联」那档筛选永远为空 |
| `sort = release_date` | **新增 `release_date_asc` 一档** | 实现完在浏览器里一看：《天气之子》(2019) 排在《你的名字》(2016) 前面——墙上的 `release_date` 是倒序（浏览语义），而规则条上写着"按上映顺序排列"。一句假话 + 一个用户会当成 bug 的顺序，靠截图才看出来 |
| （6 节写了「chip 行只放自建的」，实现时漏了） | **补上** | 不滤的话一个库几十个系列会把 chip 行挤满，用户自己存的那三五个就没了——而 chip 行的全部价值就是"把我常用的那几组条件放在手边"。移动端 e2e 的版式守卫（条件行不能钻到顶部导航键底下）先一步把它逼出来 |
| 没写「内容没了怎么办」 | **补 4.6 生命周期**：删条目 / 进回收站 / 合集空了 / 删合集删库，四条路各自的归宿 | 自动生成之后合集从"几个"变成"几十个"，这从边角问题变成天天发生的事。核实下来结论是"几乎什么都不用做"——既有外键与既有查询已经兜住；唯一要拍板的是**不给空合集加 GC**（id 是对外契约），代价挂在 S0 上 |
