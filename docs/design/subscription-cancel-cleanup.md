# 取消订阅的联动清理：种子与媒体库资源可选一并删除

> 状态：已实施。取消订阅的默认语义**不变**（只是不再追了，什么都不删）；
> 本文只描述新增的两个显式开关，以及为什么它们必须是后台任务、
> 为什么清理计划必须在删订阅之前快照。

## 1. 问题

取消订阅=删除订阅记录与追踪工单，已下载的种子任务和已入库的文件原样保留。
这个默认是对的（资源是全家的，取消订阅不该悄悄毁掉内容），但它只覆盖了一半
真实意图：用户说"这部片我不要了"时，往往连带着"下载器里的任务和媒体库里的
文件也别留了"。此前要满足这半个意图，得自己去下载器找到那几个种子、再去媒体库
找到那部作品逐个删——两处都不好找，而且找的时候订阅已经没了，**"这条订阅
投递过哪些种子"这件事再也查不回来**（`subscription_download_attempt` 随订阅
级联删除）。

## 2. 决策

取消订阅时提供两个**默认关闭**的开关，勾选与否由用户在确认弹窗里显式选择：

| 开关 | 范围 | 通道 | 可逆性 |
|---|---|---|---|
| 删除相关的种子 | 该订阅历次投递（含换源试用、洗版）留下的、仍可定位的下载任务 | `download_tasks.delete_download_task(delete_files=True)` | 不可逆（连下载目录里的数据一起删） |
| 删除媒体库资源 | 该订阅对应条目在**所有**媒体库里的台账文件 | `library.recycle.recycle_file` | 可逆（进回收站，保留期内可恢复） |

三条设计立场：

1. **动作走各自领域已有的唯一通道**，本机制不新增第二种删除实现——种子删除
   与「下载任务」页的删除是同一个函数，文件回收与洗版旧版本清理是同一个
   状态机（见 `library-file-recycle.md`）。
2. **媒体库侧用回收站而不是真删**。这是一次从订阅页发起的批量破坏性操作，
   给 7 天后悔窗口的成本为零；回收站本就是媒体库层的公共安全网。
3. **H&R 风险如实告知，不替用户决定**。预览会报出"其中 N 个种子仍在考核或
   考核状态未知"，勾选与否是用户的判断——自动清理（换源）可以保守跳过，
   用户点名要删的不该被静默拦下。

## 3. 机制：先快照，再删订阅，最后后台执行

```
DELETE /subscriptions/{id}?delete_torrents=&delete_library_files=
  ├─ build_cleanup_plan()      读投递记录 + 台账文件 → 计划快照
  ├─ enqueue_cleanup_job()     计划写进 job.input_data（commit=False）
  └─ repo.delete(subscription) 同一事务提交：订阅没了，任务已入队
                               ↓（后台）
      subscription.cleanup     逐个删种子 → 逐个回收文件 → 刷新库统计 + 通知媒体服务器
```

三个要点：

- **计划必须在删订阅之前建**：投递记录随订阅级联删除，之后无从重建。任务此后
  只认这份快照，不再依赖订阅存在——也因此进程崩溃重启后仍能继续。
- **入队与删除共用一个事务**：要么订阅删掉且清理已入队，要么两件事都没发生，
  绝不会出现"订阅还在但文件已被回收"。
- **必须异步**：删种子要逐个连下载器（慢、可能超时），回收文件要逐个搬磁盘。
  用户点的是"取消订阅"，接口必须立刻返回、订阅立刻消失，清理进度去任务中心看。

任务的失败策略：`max_attempts=1`，单项失败只计数并在结果里逐条说明，不中断
其余清理——下载器不可达不该让媒体库那一半白等。重跑是安全的：种子删除本身
幂等，已在回收站的台账行直接跳过，不会被搬第二次。

## 4. 权限与入口

清理开关只属于管理员的「永久删除订阅」（`subscriptions.delete`）。成员的
「取消关注」（`subscriptions.unsubscribe`）语义是退出、不是删除资源，维持
原样——删媒体库文件本来也要管理员权限。

Web 端的确认弹窗（`subscription-cancel-dialog.tsx`）在打开时拉
`subscriptions.preview-removal`，把两条清单的数量、媒体库体积、回收站保留
天数和 H&R 警示都摆在勾选框旁边；数字没回来之前开关保持禁用——没数字的
勾选框等于让用户盲签。
