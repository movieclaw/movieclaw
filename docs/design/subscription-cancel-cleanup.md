# 取消订阅的联动清理：种子与媒体库资源可选一并删除

> 状态：已实施。取消订阅的默认语义**不变**（只是不再追了，什么都不删）；
> 本文只描述新增的两个显式开关，以及为什么它们必须是后台任务、
> 为什么清理计划必须在删订阅之前快照。

## 1. 问题

取消订阅=删除订阅记录与追踪工单，已下载的种子任务和已入库的文件原样保留。
这个默认是对的（资源是全家的，取消订阅不该悄悄毁掉内容），但它只覆盖了一半
真实意图：用户说"这部片我不要了"时，往往连带着"下载器里的任务和媒体库里的
文件也别留了"。此前要满足这半个意图，得自己去下载器找到那几个种子、再去媒体库
找到那部作品逐个删——两处都不好找，而且找的时候订阅已经没了，**"这条订阅
投递过哪些种子"这件事再也查不回来**（`subscription_download_attempt` 随订阅
级联删除）。

## 2. 决策

取消订阅时提供两个**默认关闭**的开关，勾选与否由用户在确认弹窗里显式选择：

| 开关 | 范围 | 通道 | 可逆性 |
|---|---|---|---|
| 删除相关的种子 | 该订阅历次投递（含换源试用、洗版）留下的、仍可定位的下载任务 | `download_tasks.delete_download_task(delete_files=True)` | 不可逆（连下载目录里的数据一起删） |
| 删除媒体库资源 | 该订阅**覆盖过的季**在所有媒体库里的台账文件 | `library.recycle.recycle_file` | 可逆（进回收站，保留期内可恢复） |

四条设计立场：

1. **动作走各自领域已有的唯一通道**，本机制不新增第二种删除实现——种子删除
   与「下载任务」页的删除是同一个函数，文件回收与洗版旧版本清理是同一个
   状态机（见 `library-file-recycle.md`）。
2. **媒体库侧用回收站而不是真删**。这是一次从订阅页发起的批量破坏性操作，
   给 7 天后悔窗口的成本为零；回收站本就是媒体库层的公共安全网。
3. **H&R 风险如实告知，不替用户决定**。预览会报出"其中 N 个种子仍在考核或
   考核状态未知"，勾选与否是用户的判断——自动清理（换源）可以保守跳过，
   用户点名要删的不该被静默拦下。
4. **范围按季收口，不按条目**（2026-09 修正）。此前媒体库侧按 `media_item_id`
   一刀切，只订了第 3 季的用户取消订阅会连带回收自己刮削进来的第 1、2 季，
   而弹窗只显示一个总数、看不出来。现在取 `_covered_seasons`：`selected_seasons`
   ∪ 工单季号（两者都不能省——整季在库的勾选季不建工单，追新进来的新季不在
   `selected_seasons` 里）。电影不按季设限，整部作品就是它的范围。
   种子侧天然不受影响：投递记录本来就只属于这条订阅。

## 3. 机制：先快照，再删订阅，最后后台执行

```
DELETE /subscriptions/{id}?delete_torrents=&delete_library_files=
  ├─ build_cleanup_plan()      读投递记录 + 台账文件 → 计划快照
  ├─ enqueue_cleanup_job()     计划写进 job.input_data（commit=False）
  └─ repo.delete(subscription) 同一事务提交：订阅没了，任务已入队
                               ↓（后台）
      subscription.cleanup     逐个删种子 → 逐个回收文件 → 刷新库统计 + 通知媒体服务器
```

三个要点：

- **计划必须在删订阅之前建**：投递记录随订阅级联删除，之后无从重建。任务此后
  只认这份快照，不再依赖订阅存在——也因此进程崩溃重启后仍能继续。
- **入队与删除共用一个事务**：要么订阅删掉且清理已入队，要么两件事都没发生，
  绝不会出现"订阅还在但文件已被回收"。
- **必须异步**：删种子要逐个连下载器（慢、可能超时），回收文件要逐个搬磁盘。
  用户点的是"取消订阅"，接口必须立刻返回、订阅立刻消失，清理进度去任务中心看。

任务的失败策略：`max_attempts=1`，单项失败只计数并在结果里逐条说明，不中断
其余清理——下载器不可达不该让媒体库那一半白等。重跑是安全的：种子删除本身
幂等，已在回收站的台账行直接跳过，不会被搬第二次。

## 4. 权限与入口

清理开关只属于管理员的「永久删除订阅」（`subscriptions.delete`）。成员的
「取消关注」（`subscriptions.unsubscribe`）语义是退出、不是删除资源，维持
原样——删媒体库文件本来也要管理员权限。

Web 端的确认弹窗（`subscription-cancel-dialog.tsx`）在打开时拉
`subscriptions.preview-removal`，把两条清单的数量、媒体库体积、回收站保留
天数和 H&R 警示都摆在勾选框旁边；数字没回来之前开关保持禁用——没数字的
勾选框等于让用户盲签。

## 5. 同一机制的第二个入口：减季后的按季清理

减季（「调整订阅」里取消勾选某一季）此前只把工单置为出域，什么都不删，用户要让
那一季从机器上消失仍得自己去两个地方找。现在复用同一套机制按季清理：
`build_cleanup_plan(seasons={2})` → `enqueue_cleanup_job` → 同一个任务处理器
（它吃的是 file_id 与 infohash 的快照清单，本来就不关心季）。

与整条退订的四点不同：

1. **两步，而不是一步**。减季的「保存」维持原样、不带任何破坏性；保存成功后
   才追问一次（`season-cleanup-dialog.tsx`）。两个理由：保存按钮不该变成破坏性
   操作（同一个弹窗还能改入库库），而清理数量必须是实测的——想在保存前给出
   数量就得把后端的出域判定复制一份到前端，那是第二份真相源。
2. **跨季包不删**。覆盖单元跨到范围外的整季包/全剧包（`attempt.units` 超出本次
   清理的季）一律保留——删了会把仍在追的季一起毁掉；它们进 `CleanupPlan.retained`
   由弹窗如实告知"另有 N 个跨季种子仍被保留的季使用，不会删除"。`units` 为空
   的存量数据同样按"无从按季定位"保留。整条退订时不设此限：每个尝试都属于
   这条订阅。
3. **必须退回工单**（`reset_cleaned_wanted`）。内容清掉后出域工单仍停在
   imported/grabbed 就成了谎：用户日后重新勾选这一季，引擎会认为它早已满足，
   既不下载也不报缺，那一季就此静静地永远缺着。只退回"内容确实被清掉了"的那些
   （删了文件才退 imported，删了种子才退 grabbed/downloaded），字段清理口径与
   `reopen_unfulfilled_wanted` 一致。
   安全性来自一条既有不变量：缺口搜索、被动匹配、投递三处都只看
   `in_scope=True` 的工单，出域行退回后不会触发任何搜索或下载；只有重新勾选
   那一季时它才重新变成缺口——那正是此刻该有的结果。因此这里**不排期**，
   重新纳入时由 `SubscriptionService.update` 统一重挂。
4. **只认已出域的季**。`cleanup_seasons` 拒绝仍在订阅范围内的季（勾选的季 ∪
   还有在域工单的季）——这个接口是"减季之后顺手清理"，不是"绕过减季直接删
   内容"的后门。

入队与退回工单共用一个事务。清理任务若在后台失败，退回的工单因为出域不会触发
任何搜索，下一次该条目的库存对账（`close_fulfilled_wanted`）也会把仍在库的单元
重新标回 imported——不留需要人工收拾的中间态。

接口：`GET /subscriptions/{id}/removal-preview?seasons=2`（不传 seasons = 整条
退订的范围）、`POST /subscriptions/{id}/season-cleanup`。两者都要管理员权限，
与 `subscriptions.delete` 同级。
