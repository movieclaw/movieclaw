# 账号切换：一个浏览器里同时登录多个账号——设计

> 状态：已实施（2026-09）。
> 关联文档：[member-management.md](member-management.md)（超管 + 成员的双身份
> 体系与会话失效语义，本文完全建立在其之上）。

## 0. 定位与第一性

**问题**：管理员经常需要用多个账号访问同一套 movieclaw——自己的超管号做管理，
若干成员号各自隔离一份观影数据；家庭共用的 iPad / 电视盒子浏览器上也是几个人
轮流用。今天的做法是"退出 → 重新输密码 → 登录"，每切一次都要打一遍密码。

**目标形态**：与 Google / GitHub 网页端一致——浏览器同时保存多个账号的登录态，
用户菜单里点「切换账号」弹出全部账号，点一下就切过去；**只要那个账号的登录状态还没过期，
切换不需要再输密码**（含切到超管，这是明确的产品决策）。

**产品原则**：

1. **不新增任何凭证形态**。浏览器里多存几份的就是现有的会话令牌本身，签发、
   验签、失效全部复用 `services/auth.py` 已有的那一套；
2. **安全属性不退让**。全部凭证仍在 HttpOnly + SameSite=Lax 的 Cookie 里，
   JS 读不到，切换是 POST。凡是"把令牌放 localStorage 让前端换请求头"的做法
   一律不采用；
3. **鉴权层零改动**。`require_login` / `deps.py` 只认 `movieclaw_session` 这一个
   Cookie，本功能不动它——多账号只是"旁边多放一个装令牌的袋子"。

## 1. 业界做法与取舍

| 做法 | 代表 | 凭证放哪 | 与 movieclaw 的适配 |
|---|---|---|---|
| 服务端多会话 | Google（`authuser=N`）、GitHub（Cookie 内会话列表，上限 10） | HttpOnly Cookie | **采用**。与现有 Cookie 模型同构 |
| 客户端令牌仓库 | X、Slack、Discord | localStorage，切换换请求头 | 放弃：要放弃 HttpOnly，XSS 直接偷走全部账号 |
| 只记账号不记凭据 | 登录页头像列表预填用户名 | 无 | 放弃：仍要输密码，只是"快捷登录" |

## 2. 数据模型

### 2.1 两个 Cookie

| Cookie | 内容 | 角色 |
|---|---|---|
| `movieclaw_session`（已有） | 一枚会话令牌 | **当前激活账号**。鉴权只看它 |
| `movieclaw_accounts`（新增） | itsdangerous 签名的 `{"t": [令牌, …]}` | **已登录账号袋**。只在账号相关接口里读写 |

两个 Cookie 的安全属性完全一致（HttpOnly / SameSite=Lax / Secure 随配置 /
path=/）；账号袋的 `max_age` 取"记住我"的 30 天上限，里面每枚令牌自带过期时间，
袋子活得久一点没有意义也没有危害。

签名 salt 为 `movieclaw.accounts.v1`，与会话令牌、Agent 令牌、取流 token 做域隔离。
袋子本身签名不是安全必需（里面每枚令牌都会独立验签），只是让篡改后的垃圾在
第一步就被整袋丢弃、并把大小控制在服务端手里。

### 2.2 解析规则（`resolve_saved_accounts`）

每次读袋子都走同一条路径，产出"当前浏览器持有的有效账号列表"：

1. 把当前激活令牌放在最前，再接上袋子里的令牌；
2. 逐枚 `verify_session_token`：签名不对、过期、成员被停用、`token_version`
   不匹配的**静默丢弃**——因此超管改密轮换密钥、成员改密/停用这些既有的失效
   语义对袋子自动生效，本功能没有自己的失效逻辑；
3. 按身份去重（超管一个位置，成员按 id），先出现者胜——激活令牌排在最前，
   所以改密后重签的新令牌总能覆盖袋子里同身份的旧令牌；
4. 截到上限 5 个。

**为什么把激活令牌也并进去**：改密接口会重签激活 Cookie；超管改密还会轮换密钥
让整个袋子验签失败。把激活令牌当成列表的第一元素后，这些场景下列表至少还有
当前账号，不会出现"我明明登着，账号列表却是空的"。

### 2.3 上限与淘汰

上限 5 个（单枚令牌约 150 字节，Cookie 总量 4KB，留足余量）。登录第 6 个账号时
淘汰袋尾（最久未用）的那个，而不是拒绝登录——登录永远要能成功，前端在满员时
隐藏"添加账号"入口即可。

## 3. 接口

全部挂在 `/auth` 下；除登录/登出外都要求登录态（Cookie 主体；成员亦可用，
已登记进成员白名单守护测试）。

| 方法 | 路径 | 语义 |
|---|---|---|
| `POST` | `/auth/login` | 不变。**登录成功后总是并入袋子**（同身份替换、超限淘汰）。会话过期后重新登录，其余账号不丢 |
| `GET` | `/auth/accounts` | 当前浏览器持有的全部账号：用户名、昵称、头像、角色、是否激活。激活账号排第一 |
| `POST` | `/auth/accounts/switch` | 按用户名切换：把对应令牌写回 `movieclaw_session`。找不到（已过期/被停用）→ 404，提示重新登录 |
| `DELETE` | `/auth/accounts/{username}` | 从袋子里移除一个账号。移除的是激活账号时自动切到下一个；返回体带切换后的会话，空则表示已全部退出 |
| `POST` | `/auth/logout` | 退出**当前**账号并切到下一个（等价 DELETE 激活账号）；`{"all": true}` 时清空两个 Cookie。仍是公开接口，无登录态调用也能顺利清 Cookie |
| `GET` | `/auth/avatar?account=<用户名>` | 读取袋子里某个账号的头像（只有袋子里有它才能读，天然按持有者隔离） |

修改密码（`PUT /auth/password`）同步重写袋子：新令牌置顶，其余按 §2.2 解析
后保留——成员改密不影响袋子里的超管，超管改密后袋子只剩自己（其余账号的
令牌随密钥轮换一起失效，这是"密钥可能泄露时全端下线"语义的自然延伸）。

## 4. 前端

- **用户菜单**（`components/user-menu.tsx`）保持简单，只有三项：设置 / 切换账号 /
  退出登录。"退出登录"只退当前账号，浏览器里还有别的账号时自动切过去。
- **切换账号弹窗**（`components/account-switcher-dialog.tsx`）：常规产品的形态——
  一个弹窗列出本浏览器登录过的全部账号，当前账号打勾，点其他账号即切换（不用
  再输密码），每行尾部可从本浏览器移除；底部是"添加账号"（满员时改为提示）与
  "退出全部账号"。
- **切换后整页跳转**（`window.location.href`），落点用 `accessiblePathFor` 按身份
  算（成员进 `/library`）。复用登出/登录既有的"整页刷新重置全部前端状态"策略——
  工作台各 Store、`auth-gate.tsx` 的模块级会话缓存、背景图缓存、界面偏好缓存
  都随页面一起清零，绝不会串到上一个账号的数据。
- **登录页**带 `?add=1` 时进入"添加账号"形态：不再因为"已登录"自动跳走，
  标题改为"添加账号"，登录成功后进该身份能进的页面。后端并入袋子的行为与
  普通登录完全一致，前端不需要传任何额外参数。

## 5. 安全边界

- **切到超管不验密码**：与 Google / GitHub 一致——会话本来就已经授予，袋子
  里的令牌与直接持有 `movieclaw_session` 的能力等价，多一道密码不改变威胁模型
  （拿到 Cookie 的人两边都能进）。共用设备的正确做法是"退出全部账号"或不勾
  "记住我"。
- **不新增匿名可达面**：`/auth/logout` 本就公开；新接口全部要求登录态。
- **CSRF**：切换/移除都是 POST/DELETE，SameSite=Lax 下跨站发起不带 Cookie。
- **Jellyfin 兼容客户端与 CLI 令牌不受影响**：它们各自持有独立凭证，不走这两个
  Cookie。
