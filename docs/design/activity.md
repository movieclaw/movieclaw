# 活动

## 定位

`/activity` 是全局的**活动页**，按领域分两个一级视角，它们维度不同、互不从属：

- **观看**：媒体库的实时活动（谁在看什么、设备、观看历史）。纯观察，没有
  需处理/成功/失败的处置语义；
- **任务**：下载、入库与后台作业，按"是否需要我处理"分四个状态。

这两件事回答的问题不同——观看回答"现在正在发生什么"，任务回答"有什么需要我
处理"。把观看做成任务的第五个状态 tab 是维度混用：它看起来像过滤器（同一批
数据的切片），点下去却整页换内容，既误导又稀释了"需要处理"的优先级。因此一级
按领域切换（形态沿用发现页 TMDB/豆瓣 的分段控件，不新造交互词汇），二级才是
任务自己的状态。

视角切换器的窄屏位置也照搬发现页：活动页同为侧栏一级入口、没有 PageNav，
切换器若在窄屏自己占一行就会与全局顶栏摞成两排 header，因此移动端挂进全局
顶栏那一行（字标与搜索之间本来就空着），桌面端留在页头右上角。

页面默认落在**观看**——媒体库的实时动静是日常最常瞥一眼的东西；但只要侧栏入口
亮着角标，落点就跟着角标走：有需要处理的任务时亮警示色并深链到任务视角的
「需要处理」，只有进行中任务时深链到「进行中」。角标数的是任务，落点就必须是
任务视角里对应的那一片——把人送进「观看」再让他自己找"为什么有提醒"，等于让
提醒自证失败。角标为空时才回到默认的观看。

一级切换器上的「任务」同样带角标，与侧栏同色同数：用户是被侧栏那个数字带进来的，
从观看视角看过去必须仍然看得见任务那边有几件事。两枚提示的语义刻意不同——观看
是"此刻有人在播"，没有处置含义，用一颗呼吸的绿点；任务要回答"有几件事等着我"，
所以给数字。

三处提醒（侧栏角标、一级切换器、任务视角的状态选项卡）共用 `lib/task-activity`
这一份计数口径：一个下载任务和它触发的入库 Job 是同一件事，只能算一件。各算各的
会让同一屏出现"侧栏 3 / 进行中 2"的自相矛盾，数字对不上，提醒就失去可信度。

URL 只用一个 `view` 参数承载视角：带合法状态值即任务视角，缺省即观看。旧路径
`/tasks` 永久重定向到 `/activity` 并透传查询，历史深链（`?view=active`）迁移后
原样落地。

## 任务视角

任务视角是**观察与处置页面**，不是第三套任务执行框架。它把用户关心的
异步活动放在同一处，但不篡改各领域的事实源：

- 后台 Job：`job` 表是事实源，承担排队、执行、恢复、取消、重试和事件时间线；
- 下载任务：qBittorrent / Transmission 是事实源，MovieClaw 只读取实时快照；
- 订阅任务：`wanted_item` 表表达业务工单，通过 infohash 与下载器任务关联；
- 手动下载：`manual_download_intent` 在入库前提供媒体身份，入库后随意图消费而消失。

这种“统一观察、分域执行”的边界避免把下载进度周期性复制到 SQLite，消除了外部
下载器状态与本地台账漂移的问题。

用户手动扫描、建库后的首次扫描和修改根路径后的补扫都归为 `library.scan` 后台作业，
因此可在任务中心持续观察并安全取消；文件监听与定时对账只作为自动触发器，不把每次
轻量盘点写成一条用户历史。

## 页面信息架构

任务视角按用户需要采取的行动提供四个状态切片：

1. **全部**：需要处理、正在进行与最近历史的统一 Feed；
2. **需处理**：失败、阻塞、任务缺失和可立即换种等需要用户判断的事项；
3. **进行中**：下载器实时任务与排队、执行、等待中的后台作业；
4. **历史**：最近成功、取消，以及被用户忽略的后台作业。


### 「需要处理」必须有出口：忽略

失败（`failed`）是终态，取消对它无效，因此在补上忽略之前，一条失败任务
**没有任何办法**从「需要处理」里下架——只有重试、看日志、交给 Agent 三条
"接着处理"的路。用户决定不处理时，任务就永远挂着，侧栏红角标永不熄灭
（issue #221）。一个数不下去的角标很快会被整体无视，连带真正紧急的事一起被忽略。

忽略因此是**计数口径的一部分**，不是一个隐藏按钮：

- **不做成新的 JobStatus**。状态是执行语义（终态集合、重试链、日志溯源都建立
  在它上面），忽略是用户态度，两者正交；多一个终态会让每一处状态判定跟着改。
  忽略记在 `job.dismissed_at` 上，任务仍然是 `failed`。
- **只对失败任务开放**。活跃任务（含 `blocked`）仍占着去重键与资源锁，要真正
  终结得走取消——光藏掉提醒会留下一个谁也看不见、却挡着同名任务再次创建的幽灵。
- **必须可逆**。忽略是用户在信息不全时按下的，「已结束」里给「撤销忽略」。
- **必须能批量**。一次扫描收尾可能建出几十个字幕任务，配置错了就几十条一起失败；
  「需要处理」分区头部给「全部忽略」，服务端一次事务收口，不在前端循环发请求。

判定写在 `lib/job-attention.ts` 一处（`jobNeedsAttention` / `jobIsHistorical`），
侧栏角标与页面分区共用，避免侧栏 3、进行中 2 的自相矛盾。

#### 第二层：静音自动来源

只把卡片藏起来还不够。入库后自动生成字幕的"同一文件本进程只自动尝试一次"是
**内存**集合，容器一重启就清零——用户忽略掉的失败任务会在下次扫描时原地复活，
忽略于是成了西西弗斯。所以忽略对话框对有自动来源的任务类型（当前是
`subtitle.generate`）默认勾上「不再自动为这个文件生成字幕」，写进
`subtitle_auto_mute` 台账，扫描前置查表短路；撤销忽略时连带解除。

手动触发始终不受静音限制——静音防的是系统自动反复重试烧钱，不是禁止用户
自己再试一次。这与「监听导入清单」的人工忽略同构：用户拍板的忽略是持久的，
恢复走显式动作，不靠系统自愈。

任务来源不再作为同级导航，下载任务、Web / CLI / Agent / Scheduler 后台作业都沿同一
阅读路径展示。需要处理的任务脱离普通时间顺序置顶；其余进行中任务进入“现在”时间线，
历史按本地日期分组，最近一组默认展开、较早日期折叠。下载器的历史做种仍不展示，避免一次
读取上千条与 MovieClaw 无关的存量种子。

历史是页面唯一内容时直接承接选项卡，不额外绘制分区顶线；只有前面确实出现“需要处理”或
“现在”时才用顶线分隔。文件明细折叠后必须从时间线网格中完全移除高度，不能留下空白轨道。

标题下方只保留一条轻量状态栏：进行中、需要处理和下载器可用性。数字使用正文尺寸，
仅异常或阻塞采用强调色；需处理、进行中与历史数量作为选项卡的弱提示，首屏空间优先交给
任务列表。底部来源区继续展示每台下载器是否可用以及本次快照里的任务数。

后台作业按行动级别使用两种密度：失败与阻塞保留带边界的操作卡，容纳错误说明与处理动作；
正常运行和历史则使用无外框 Feed 行。运行行的主标题只回答“处理谁”，正文回答“正在做什么、
做到哪里”，并展示进度条、处理数量、来源和取消动作。历史行固定为“时间 + 完成/取消图标 +
业务标题 + 一行结果”，不再复用完整 Job 卡片；长 release 名优先由已确认的作品名替代。
颜色只表达运行状态和异常，不按任务类型着色。

入库成功历史必须回答“本次处理了什么”，不能用“内容已全部在库”暗示整部剧已经更新完成。
当 Job 保存了 `imported_files` 时，主摘要展示本次新增的季集范围与文件数，并可展开核对完整
文件名；无需搬运时用 `ready_files` 展示本次检查的季集范围并明确“均已在库，未复制”。旧任务
若只保存了候选文件和复制数量，界面必须标注未保存具体复制文件，不得从候选列表反推结果。

下载任务按稳定媒体条目合并；当 `download:<infohash>` 关联到 `library.ingest` Job 时，进行中
Feed 行把“已投递 → 下载 → 入库”投影为一条纵向业务过程，并从普通 Job Feed 隐去重复的入库
记录。只有异常下载保留操作卡片。这只是展示层串联，不新增统一状态表，也不改变下载器与 Job
的事实源。

状态与审计信息不混成同一个控件：状态独立固定在右上角，移动端压缩为单个彩色圆点；触发
来源与发起时间固定在卡片底部，作为低对比度审计签名。时间使用 `created_at` 表达实际发起
时刻，不使用会随进度更新的 `updated_at`；悬停可查看完整来源与本地绝对时间。

字幕生成成功后的主摘要展示目标语言（双语任务同时展示两种语言），不重复长输出文件名。
存在模型调用记录时提供按需展开的消耗区，展示请求数、输入/输出/缓存 Token、供应商模型
以及累计/最慢响应耗时；旧任务没有保存用量时不伪造数据。

侧栏入口直接进入 `/activity`（带上角标对应的视角），减少一次无意义的中转操作。侧栏计数
与页面计数同出一源（`useTaskActivity`），只读全站共享的 Job / 下载快照 Provider，
不额外请求下载器。

## 下载聚合契约

`GET /downloaders/tasks` 并行读取所有下载器的一次列表快照，并批量建立两类关系：

- `wanted_item.in_scope=true + info_hash` → 订阅、媒体条目、季集单元；
- `manual_download_intent.info_hash` → 手动下载确认的媒体条目。

接口只返回：

- 下载器中的未完成任务；
- 虽已下载完成、但订阅工单或手动意图仍在等待入库收尾的任务；
- 本地仍有业务工单/意图、但可用下载器中已经找不到的缺失任务。

无业务关联的完成/做种历史被过滤。单台下载器读取失败只将该来源标为 `error`，其余
下载器继续返回；前端展示修复入口，不因局部故障让整个任务中心白屏。

取消季订阅后，该季的工单仅保留历史身份，不再构成业务关联；仍留在下载器里的种子
按外部任务展示。用户删除该下载器任务后，`cancelled` 尝试不得单独合成缺失任务，
因此记录会立即从任务中心消失。

已识别的订阅和手动下载同时返回 `media_item_id`、标题、类型与海报地址。前端只按稳定的
`media_item_id` 把同一电影或剧集的多个资源合成作品卡片，作品层展示海报，资源层继续
保留每个种子的下载状态、进度、季集范围和入库状态。未识别资源没有可靠身份锚，必须
保持独立卡片，不能仅凭相似标题猜测合并。

前端页面可见时每 10 秒读取一次下载快照，窗口恢复可见时立即校准。后台 Job 仍走
SSE + 15 秒低频轮询，两者分别遵守自己的更新节奏。页面不提供重复的手动刷新按钮，
最近更新时间作为自动更新是否正常的轻量反馈；瞬时断线保留最近快照并由下一轮自动恢复。

监听规则确认下载完成后创建 `library.ingest` Job，并以 `download:<infohash>` 来源资源
关联原下载。下载卡片据此继续投影“正在入库 / 入库待处理”和 Job 的真实阶段、进度或
错误；关联 Job 合入下载卡的业务过程，不在同一 Feed 重复展示。没有 infohash 的浏览器、
网盘等来源仍作为独立后台作业观察，不伪造下载器关系。

## 观看视角

观看视角两段数据、两个事实源，全部只读投影，不新增状态表、不做迁移：

- **正在播放 / 正在下载**：`movieclaw_playback.activity` 的进程内实时注册表。
  播放器上报（/Sessions/Playing*）提供"谁在看什么、看到哪、是否暂停"，取流响应
  （DisconnectAwareFileResponse 的 byte_sink）提供"传了多少字节、多快"，两条通路
  以设备 device_id 关联。会话超过 5 分钟无上报且无活跃流即过期；进程重启清空，
  与下载器"实时快照不落库"同哲学。
- **最近观看**：`playback_state` 领域表的全成员视角（每个成员×作品只保留最后
  活动的一集），与首页按成员隔离的 `/playback/recent` 是同一事实源的不同口径。

### 设备的处置而非罗列

页面不单列设备清单。一个只读的设备列表比没有更糟——它把"这台设备我不认识"
这种安全信号摆出来，却不给任何处置手段。设备身份已经写在每张播放/下载卡的
元信息行里（成员 · 客户端 · 设备名 · 版本），处置能力挂在卡片右上角的菜单上
（形态复用任务中心的 `TaskActionsMenu`，不新造交互）。

菜单只提供「注销此设备」，因为这是本页能对一台设备安全表达的唯一动作。注销
要同时做三件事，缺一不可：删 `jellyfin_device` 行（设备级长期 AccessToken 即刻
失效）、`activity.report_stop`（否则实时视图还会按保鲜期显示一台已不存在的设备
在播放）、`stop_device_streams`（播放器不会因 token 失效就主动断开已建立的 Range
连接，不停就会继续为已注销的设备转磁盘）。观看进度按成员保存，不受注销影响。

已知缺口：这条路径只能处置**当前正在播放或下载**的设备。真正需要注销的往往是
卖掉的旧设备、长期未用却仍持有有效凭据的设备——它们不在活动页出现。补齐要靠
独立的设备管理入口（设置分区），本期不做。

`playback_state` 没有设备维度（键是 成员×条目×季×集，且是"状态"不是"日志"，
同一集重看会覆盖），因此"最近观看"无法标注是哪台设备播的，也无法按设备聚合
播放历史。要做需要新增一张播放日志表，是独立一件事，不在本期。

速率语义如实呈现：本地文件直连展示滑动窗口平均速率、累计字节与连接数；strm
网盘条目播放走 302 直链、流量不经过服务器，标注"网盘直链"而不是伪造 0 速率。
播放方式认台账里的文件形态（是否 strm），不靠"是否已经看到字节"倒推——上报先于
取流到达是常态，用字节证据会把刚开播的本地文件误标成网盘直链；只有条目没有在位
台账行时才退回字节证据。速率在还没有字节流时输出 null（展示为"本地直连"），
与真实的 0 速率区分。同一设备同一文件的多条 Range 连接（断点续传、并发分段）
在展示层聚合为一条，字节与速率求和。

整文件下载的进度按「Range 起点 + 本次已传」还原真实下载位置——断点续传从文件
中段开始，只看本次已传字节会把进度算回 0。多连接取推进得最远的那条：顺序下载
（播放器离线缓存的常态）下即真实位置，并发分段下载会偏乐观，不为该类客户端把
读数复杂化。文件大小未知时不画进度条，而不是画一条假的。

进度条贴卡片底边、横跨全宽、3px 细条（Jellyfin 控制台、Plex 活动、Netflix 缩略图
的通行形态）：多张卡片的进度共享同一基线可以互相比较，进度条只当视觉指示器，
具体时刻与百分比留在文字区，不被拉到卡片另一端。状态徽标在窄屏收敛为单个彩色
圆点（与本页既有约定一致），文字降为 sr-only 而非从 DOM 摘除，读屏仍可听到状态。
整文件下载（/Items/{id}/Download 的离线缓存）**独立成「正在下载」分区**——它不是
播放，把它塞进「正在播放」会让标题名不副实、计数也把非播放算进去。下载相对少见，
因此该分区只在真有下载时渲染，常态下页面仍只有一个实时分区；分区标题已表明性质，
卡片不再重复一个同义徽标。它不参与会话判定，但同样计量速率。

聚合接口是 `GET /playback/activity`（管理员专属，跨成员可见，沿用本页的
`require_admin` 边界）；前端按 8 秒节奏轮询，页面隐藏时暂停。

轮询按**权限**门控，不按视角——「观看」旁的实时圆点（有播放或下载在进行时亮起）
要在任务视角也能亮，那正是它存在的意义：处理任务时一眼看到家里有人在播。只在
观看视角轮询的话，圆点只有在你已经盯着播放卡片时才亮，等于没用。门控口径与
download-tasks / jobs 两个 Provider 一致，成员直接访问本页不会拉出 403 报错。

同理，页面组件不能按视角加 `key`：切视角要经 `router.replace` 改写查询串，带 key
会让整个视图重新挂载、把已拉到的活动快照连同轮询状态一起丢掉（表现就是切到
任务后圆点熄灭）。视角状态由页面组件自己持有，浏览器前进/后退经一个同步 effect
回灌。播放失败上报（Failed=true）目前仍静默丢弃，未来若进"需要处理"区需要
单独设计事件留存。

## 权限与动作

任务中心属于管理员运维视角：Job 可能暴露执行输入、错误与模型使用信息，下载器视图
涉及全局下载资源，均沿用管理区的 `require_admin`。成员的“我的订阅”继续使用已有的
订阅详情页，不获得全局下载器可见性。

任务中心只提供其能安全表达的动作：

- Job：取消、重试、打开设置/日志、交给 Agent；
- 下载任务：回到订阅详情或下载器设置排障。

暂停、删除种子等破坏性下载器操作不在这一期增加；若未来引入，必须先扩展下载器抽象
的跨客户端控制契约，并对删除数据提供单独确认。
