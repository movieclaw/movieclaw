# 活动

## 定位

`/activity` 是全局的**活动页**，按领域分两个一级视角，它们维度不同、互不从属：

- **观看**：媒体库的实时活动（谁在看什么、设备、观看历史）。纯观察，没有
  需处理/成功/失败的处置语义；
- **任务**：下载、入库与后台作业，按"是否需要我处理"分四个状态。

这两件事回答的问题不同——观看回答"现在正在发生什么"，任务回答"有什么需要我
处理"。把观看做成任务的第五个状态 tab 是维度混用：它看起来像过滤器（同一批
数据的切片），点下去却整页换内容，既误导又稀释了"需要处理"的优先级。因此一级
按领域切换（形态沿用发现页 TMDB/豆瓣 的分段控件，不新造交互词汇），二级才是
任务自己的状态。

视角切换器的窄屏位置也照搬发现页：活动页同为侧栏一级入口、没有 PageNav，
切换器若在窄屏自己占一行就会与全局顶栏摞成两排 header，因此移动端挂进全局
顶栏那一行（字标与搜索之间本来就空着），桌面端留在页头右上角。

页面默认落在**观看**——媒体库的实时动静是日常最常瞥一眼的东西；但只要侧栏入口
亮着角标，落点就跟着角标走：有需要处理的任务时亮警示色并深链到任务视角的
「需要处理」，只有进行中任务时深链到「进行中」。角标数的是任务，落点就必须是
任务视角里对应的那一片——把人送进「观看」再让他自己找"为什么有提醒"，等于让
提醒自证失败。角标为空时才回到默认的观看。

一级切换器上的「任务」同样带角标，与侧栏同色同数：用户是被侧栏那个数字带进来的，
从观看视角看过去必须仍然看得见任务那边有几件事。两枚提示的语义刻意不同——观看
是"此刻有人在播"，没有处置含义，用一颗呼吸的绿点；任务要回答"有几件事等着我"，
所以给数字。

三处提醒（侧栏角标、一级切换器、任务视角的状态选项卡）共用 `lib/task-activity`
这一份计数口径：一个下载任务和它触发的入库 Job 是同一件事，只能算一件。各算各的
会让同一屏出现"侧栏 3 / 进行中 2"的自相矛盾，数字对不上，提醒就失去可信度。

URL 只用一个 `view` 参数承载视角：带合法状态值即任务视角，缺省即观看。旧路径
`/tasks` 永久重定向到 `/activity` 并透传查询，历史深链（`?view=active`）迁移后
原样落地。

## 任务视角

任务视角是**观察与处置页面**，不是第三套任务执行框架。它把用户关心的
异步活动放在同一处，但不篡改各领域的事实源：

- 后台 Job：`job` 表是事实源，承担排队、执行、恢复、取消、重试和事件时间线；
- 下载任务：qBittorrent / Transmission 是事实源，MovieClaw 只读取实时快照；
- 订阅任务：`wanted_item` 表表达业务工单，通过 infohash 与下载器任务关联；
- 手动下载：`manual_download_intent` 在入库前提供媒体身份，入库后随意图消费而消失。

这种“统一观察、分域执行”的边界避免把下载进度周期性复制到 SQLite，消除了外部
下载器状态与本地台账漂移的问题。

用户手动扫描、建库后的首次扫描和修改根路径后的补扫都归为 `library.scan` 后台作业，
因此可在任务中心持续观察并安全取消；文件监听与定时对账只作为自动触发器，不把每次
轻量盘点写成一条用户历史。

## 页面信息架构

任务视角按用户需要采取的行动提供四个状态切片：

1. **全部**：需要处理、正在进行与最近历史的统一 Feed；
2. **需处理**：失败、阻塞、任务缺失和可立即换种等需要用户判断的事项；
3. **进行中**：下载器实时任务与排队、执行、等待中的后台作业；
4. **历史**：最近成功、取消，以及被用户忽略的后台作业。


### 「需要处理」必须有出口：忽略

失败（`failed`）是终态，取消对它无效，因此在补上忽略之前，一条失败任务
**没有任何办法**从「需要处理」里下架——只有重试、看日志、交给 Agent 三条
"接着处理"的路。用户决定不处理时，任务就永远挂着，侧栏红角标永不熄灭
（issue #221）。一个数不下去的角标很快会被整体无视，连带真正紧急的事一起被忽略。

忽略因此是**计数口径的一部分**，不是一个隐藏按钮：

- **不做成新的 JobStatus**。状态是执行语义（终态集合、重试链、日志溯源都建立
  在它上面），忽略是用户态度，两者正交；多一个终态会让每一处状态判定跟着改。
  忽略记在 `job.dismissed_at` 上，任务仍然是 `failed`。
- **只对失败任务开放**。活跃任务（含 `blocked`）仍占着去重键与资源锁，要真正
  终结得走取消——光藏掉提醒会留下一个谁也看不见、却挡着同名任务再次创建的幽灵。
- **必须可逆**。忽略是用户在信息不全时按下的，「已结束」里给「撤销忽略」。
- **必须能批量**。一次扫描收尾可能建出几十个字幕任务，配置错了就几十条一起失败；
  「需要处理」分区头部给「全部忽略」，服务端一次事务收口，不在前端循环发请求。

判定写在 `lib/job-attention.ts` 一处（`jobNeedsAttention` / `jobIsHistorical`），
侧栏角标与页面分区共用，避免侧栏 3、进行中 2 的自相矛盾。

#### 第二层：静音自动来源

只把卡片藏起来还不够。入库后自动生成字幕的"同一文件本进程只自动尝试一次"是
**内存**集合，容器一重启就清零——用户忽略掉的失败任务会在下次扫描时原地复活，
忽略于是成了西西弗斯。所以忽略对话框对有自动来源的任务类型（当前是
`subtitle.generate`）默认勾上「不再自动为这个文件生成字幕」，写进
`subtitle_auto_mute` 台账，扫描前置查表短路；撤销忽略时连带解除。

手动触发始终不受静音限制——静音防的是系统自动反复重试烧钱，不是禁止用户
自己再试一次。这与「监听导入清单」的人工忽略同构：用户拍板的忽略是持久的，
恢复走显式动作，不靠系统自愈。

任务来源不再作为同级导航，下载任务、Web / CLI / Agent / Scheduler 后台作业都沿同一
阅读路径展示。需要处理的任务脱离普通时间顺序置顶；其余进行中任务进入“现在”时间线，
历史按本地日期分组，最近一组默认展开、较早日期折叠。下载器的历史做种仍不展示，避免一次
读取上千条与 MovieClaw 无关的存量种子。

历史是页面唯一内容时直接承接选项卡，不额外绘制分区顶线；只有前面确实出现“需要处理”或
“现在”时才用顶线分隔。文件明细折叠后必须从时间线网格中完全移除高度，不能留下空白轨道。

标题下方只保留一条轻量状态栏：进行中、需要处理和下载器可用性。数字使用正文尺寸，
仅异常或阻塞采用强调色；需处理、进行中与历史数量作为选项卡的弱提示，首屏空间优先交给
任务列表。底部来源区继续展示每台下载器是否可用以及本次快照里的任务数。

后台作业按行动级别使用两种密度：失败与阻塞保留带边界的操作卡，容纳错误说明与处理动作；
正常运行和历史则使用无外框 Feed 行。运行行的主标题只回答“处理谁”，正文回答“正在做什么、
做到哪里”，并展示进度条、处理数量、来源和取消动作。历史行固定为“时间 + 完成/取消图标 +
业务标题 + 一行结果”，不再复用完整 Job 卡片；长 release 名优先由已确认的作品名替代。
颜色只表达运行状态和异常，不按任务类型着色。

入库成功历史必须回答“本次处理了什么”，不能用“内容已全部在库”暗示整部剧已经更新完成。
当 Job 保存了 `imported_files` 时，主摘要展示本次新增的季集范围与文件数，并可展开核对完整
文件名；无需搬运时用 `ready_files` 展示本次检查的季集范围并明确“均已在库，未复制”。旧任务
若只保存了候选文件和复制数量，界面必须标注未保存具体复制文件，不得从候选列表反推结果。

下载任务按稳定媒体条目合并；当 `download:<infohash>` 关联到 `library.ingest` Job 时，进行中
Feed 行把“已投递 → 下载 → 入库”投影为一条纵向业务过程，并从普通 Job Feed 隐去重复的入库
记录。只有异常下载保留操作卡片。这只是展示层串联，不新增统一状态表，也不改变下载器与 Job
的事实源。

状态与审计信息不混成同一个控件：状态独立固定在右上角，移动端压缩为单个彩色圆点；触发
来源与发起时间固定在卡片底部，作为低对比度审计签名。时间使用 `created_at` 表达实际发起
时刻，不使用会随进度更新的 `updated_at`；悬停可查看完整来源与本地绝对时间。

字幕生成成功后的主摘要展示目标语言（双语任务同时展示两种语言），不重复长输出文件名。
存在模型调用记录时提供按需展开的消耗区，展示请求数、输入/输出/缓存 Token、供应商模型
以及累计/最慢响应耗时；旧任务没有保存用量时不伪造数据。

侧栏入口直接进入 `/activity`（带上角标对应的视角），减少一次无意义的中转操作。侧栏计数
与页面计数同出一源（`useTaskActivity`），只读全站共享的 Job / 下载快照 Provider，
不额外请求下载器。

## 下载聚合契约

`GET /downloaders/tasks` 并行读取所有下载器的一次列表快照，并批量建立两类关系：

- `wanted_item.in_scope=true + info_hash` → 订阅、媒体条目、季集单元；
- `manual_download_intent.info_hash` → 手动下载确认的媒体条目。

接口只返回：

- 下载器中的未完成任务；
- 虽已下载完成、但订阅工单或手动意图仍在等待入库收尾的任务；
- 本地仍有业务工单/意图、但可用下载器中已经找不到的缺失任务。

无业务关联的完成/做种历史被过滤。单台下载器读取失败只将该来源标为 `error`，其余
下载器继续返回；前端展示修复入口，不因局部故障让整个任务中心白屏。

任务级 `state=error` 与来源级故障是两回事：前者是下载器里**这一条任务**出了问题
（qBittorrent 的 `missingFiles` / `error`、Transmission 的 `error≠0`），下载器本身
连接正常。适配器把下载器给出的原因透出为 `error_message`（文件缺失、errorString），
卡片据此告诉用户该去下载器重新校验还是删掉任务，不再把人引去"检查下载器"。
外部任务（无订阅/手动身份）出错只观察不报警：它们没有工单可救援，也没有入库可
推进，若全部计入「需要处理」会把真正要处理的订阅任务淹没（见
`lib/download-attention.ts`）。

「待处理事项」（system_notice）与任务视角「需要处理」的分工：前者是**全局红灯**，
只放"不修就永远卡着、且在任何页面都该被感受到"的运行时故障（路径映射、下载器/
站点失效、落点核验失败）；后者按任务组织，回答"这条任务现在要我做什么"。两者
不能各说各话：落点核验失败的红灯会以 `landing_error` 挂回对应的下载任务，卡片
据此计入「需要处理」、把入库一步标成"无法入库"并给出删除重下的出口；用户删掉
该任务时工单当场退回、红灯随之熄灭。

### 红灯的粒度等于修复动作的粒度

上面这套"症状可见、有出口"仍然不够：一次挂载故障（容器的 `/download` 绑定
静默失效成空目录，配置看着完全正常）影响 3 部剧、16 个种子，用户看到的是 16 条
「《某剧》下载完成但无法入库」，没有任何一条说"你的下载目录整个不可见"。从
症状归纳到根因是专家才做得到的事，系统必须替用户做。四条规则（`services/
download_health.py`、`services/downloader_paths.py`）：

1. **能自动判定的，不做成给用户的选择题。** 落点核验失败时先做路径体检，
   把「映射缺失 / 目录不存在 / 目录为空（挂载失效，重启容器即可）/ 文件被
   移动」判成互斥的一种，文案直接说结论和该做什么；不再写"可能是 A 或 B 或 C"。
2. **按根因分组，而不是按症状实例。** 体检结论是目录级的（空/不存在/未覆盖），
   一个种子就足以确认是目录的问题：升格为一条目录级红灯
   （`downloader.landing:{下载器}:{目录}`），把同目录的单种子红灯收编——子告警
   **保持活跃**（任务卡片靠它们挂"无法入库"红标），只在 payload 打
   `grouped_under`，告警中心据此折叠。目录可见但该种子内容不在，是种子级问题，
   不分组。下载器「测试连接」也顺带体检每条映射的本地侧
   （`downloader.paths:{下载器}`），发现同一故障时目录级红灯再往它下面收编，
   两个入口谁先撞上都只亮一张卡。
3. **红灯是控制信号，不只是状态展示。** 目录级红灯活跃期间，落在该目录的
   订阅**自动**换源刹车（一小时后再看）——目录都看不见，换再多源也只是往同一个
   黑洞里倒，真实事故里 45 小时白烧了 90GB。用户手动「立即换种」不受限；用户
   忽略红灯即"我知道，别管"，刹车随之松开。红灯正文累计代价（卡住的任务数与
   体积），把"某部剧没更新"变成"正在持续烧盘"。
4. **高频例行事件不能盖住低频真信号。** 每换一次源就新建一个 attempt、各记一条
   "停滞 15 分钟"，一晚上几十条会把两条真正的 `import_failed` 淹没。同订阅、
   同单元、同原因的停滞在 24 小时内折叠为一条并计数（时间线活动"只增不改"的
   唯一例外，理由写在 `record_stalled`）。

### 每条待办的第二出口：交给 AI 分析

告警卡、需要处理的下载卡、失败/阻塞的 Job 卡都带「交给 AI 分析」
（`components/handoff-button.tsx`）。它永远是**第二个**按钮：第一个按钮是那条
事项确定性的出口（去处理 / 删除 / 认领），AI 负责"我不知道该选哪个"。

工单由后端按事项类型组装（`services/diagnosis_handoff.py`，
`POST /agent-handoff`），前端拿到文本后照常走 `session.start`——不复制会话
所有权与递归防护。组装那一刻**把自检跑掉**：路径现场 stat、下载器里的实时
状态、落点是否可见。理由：Agent 的诊断上限取决于它能感知什么，真实事故里决定性
的证据（容器内目录是空的）不在任何接口里，Agent 看到的和用户一样少，只会得出
同样错误的结论。工单固定六段：发生了什么 / 系统已判定的事实（现场）/ 系统已经
自动做过的事 / 相关时间线 / 你可以执行的动作 / 请你做什么。动作清单与界面按钮
**同一份**，标出破坏性动作——Agent 能做的等于界面能做的，多了失控，少了只能
"建议"；解决不了就要求它直说，不用一段听起来合理的步骤掩盖产品缺口。

取消季订阅后，该季的工单仅保留历史身份，不再构成业务关联；仍留在下载器里的种子
按外部任务展示。用户删除该下载器任务后，`cancelled` 尝试不得单独合成缺失任务，
因此记录会立即从任务中心消失。

已识别的订阅和手动下载同时返回 `media_item_id`、标题、类型与海报地址。前端只按稳定的
`media_item_id` 把同一电影或剧集的多个资源合成作品卡片，作品层展示海报，资源层继续
保留每个种子的下载状态、进度、季集范围和入库状态。未识别资源没有可靠身份锚，必须
保持独立卡片，不能仅凭相似标题猜测合并。

前端页面可见时每 10 秒读取一次下载快照，窗口恢复可见时立即校准。后台 Job 仍走
SSE + 15 秒低频轮询，两者分别遵守自己的更新节奏。页面不提供重复的手动刷新按钮，
最近更新时间作为自动更新是否正常的轻量反馈；瞬时断线保留最近快照并由下一轮自动恢复。

监听规则确认下载完成后创建 `library.ingest` Job，并以 `download:<infohash>` 来源资源
关联原下载。下载卡片据此继续投影“正在入库 / 入库待处理”和 Job 的真实阶段、进度或
错误；关联 Job 合入下载卡的业务过程，不在同一 Feed 重复展示。没有 infohash 的浏览器、
网盘等来源仍作为独立后台作业观察，不伪造下载器关系。

## 观看视角

### 观看视角的三个切片

观看视角内部再按**时间语义**分三片，形态与任务视角的状态切片相同（一行胶囊
切片，共用同一个 `view` 查询参数，值 `playing` / `plays` / `stats`，与任务切片
不撞名；默认落点「正在播放」不带参数）：

- **正在播放**（`playing`）：此刻的实时卡片与整文件下载，8 秒轮询；切片上带在播数，
  切到别的片也看得见「家里有人在播」；
- **最近播放**（`plays`，切片文案；内容仍是播放记录）：每场一行、按天分组（复用任务时间线的「今天 / 昨天 /
  9 月 4 日」分组），每行带成员、设备、看到百分比、观看时长、是否看完；滚动到底
  自动续载（哨兵提前半屏触发，「加载更多」按钮兜底），翻页用服务端游标
  （`before` = 上一页最后一行 id，按 (started_at, id) 往前走）而不是 offset——记录
  一直往前追加，续载期间新开的一场会把 offset 整体后推，同一行就会重复出现；
  不轮询；
- **观看统计**（`stats`）：一段时间的汇总，周期由工具栏选。

此前三段东西按顺序摞在一页里：实时段几秒一刷，历史段按场按人翻看，统计段按周期
切，阅读方式与刷新节奏都不同，用户进来既要扫实时又要看报表，没有一个明确的任务。
「最近观看」（按成员×作品保留进度的状态视图）与「播放记录」还互相重叠，本次从活动页
撤掉，成员自己的「继续观看」首页本来就有，管理员想看「某成员看到哪了」在播放记录
那一行的百分比里看。

切片下面一行**工具栏**：左边是三个切片，右边是作用于整个切片的筛选下拉（`FilterMenu`，
「标签 · 当前值 ▾」，与卡片菜单同一套 Radix 菜单皮肤）：范围口径三片都有，播放记录
多一个「成员」，观看统计多一个「周期」。筛选站在整个视角的入口处，作用域才一目了然；
挂在某个分区标题上会让人以为只管那一段。窄屏切片独占一行，筛选换到下一行。

观看视角两段数据、两个事实源，全部只读投影，不新增状态表、不做迁移：

- **正在播放 / 正在下载**：`movieclaw_playback.activity` 的进程内实时注册表。
  播放器上报提供"谁在看什么、看到哪、是否暂停"，取流响应
  （DisconnectAwareFileResponse 的 byte_sink）提供"传了多少字节、多快"，两条通路
  以设备 device_id 关联。会话超过 5 分钟无上报且无活跃流即过期；进程重启清空，
  与下载器"实时快照不落库"同哲学。
- **最近观看**：`playback_state` 领域表的全成员视角（每个成员×作品只保留最后
  活动的一集），与首页按成员隔离的 `/playback/recent` 是同一事实源的不同口径。

### 两条播放入口、一份上报逻辑

网页播放器（`POST /playback/progress`）与 Jellyfin 协议（`/Sessions/Playing*`、
legacy `PlayingItems`）都汇到 `movieclaw_api/services/playback/watch.py`：落
`playback_state`、发 webhook、刷新实时注册表三件事只在这一处做。协议路由只负责
把自己的形态翻译成 `ClientInfo` 与播放单元（解 GUID、换算轨序号、读 PositionTicks）。
曾经只有 Jellyfin 路由接了实时注册表，网页端播放在活动页上完全不可见（2026-09
的用户反馈：成员用网页看片，「正在播放」里没有）；收口之后两条入口不可能再分叉。

网页端没有设备凭据，设备标识由前端生成一个稳定的浏览器 id 存在 localStorage
（`lib/player/device.ts`，语义对齐 Jellyfin 客户端的 DeviceId），随进度上报与开会话
请求一起带上，服务端加 `web-` 前缀与 Jellyfin 设备 id 隔开。客户端名固定
`MovieClaw Web`，设备名从 User-Agent 推浏览器与平台（「Safari · iPhone」）。取流
token 也带这个标识：档 0 直出按 Range 连接登记字节流（与 Jellyfin 取流同一套，
停止上报能主动停止读盘），HLS 会话整场共用一条计量器（分片是几秒一个的小请求，
逐请求登记会让连接数与速率在分片间隙反复归零），会话停止时回收。网页会话不在
`jellyfin_device` 表里，接口用 `revocable=false` 标出，卡片不渲染「注销此设备」。

### 结束播放

卡片菜单对两类会话都提供「结束播放」：只掐断**本次**播放，凭据与观看进度都不动，
设备重新点播放即可继续；「注销此设备」只对持 Jellyfin 凭据的会话提供。接口是
`POST /playback/activity/sessions/{device_id}/end`，做三件事：实时会话立即消失并让
该设备进入 60 秒的**拒绝窗口**（`activity.end_device`）、停掉仍在读盘的直出取流、
停掉这台浏览器的转码会话（`TranscodeSession.device_id`）。

拒绝窗口是「结束」成立的前提：直出播放器每次缓冲续拉都是新的 Range 连接，网页
播放器会把会话 404 当成超时回收去原地重开——只掐当前连接等于没结束。窗口内该设备
的取流、分片、开会话一律拒绝（Jellyfin 取流回 400「播放已被管理员结束」，网页开会话
回 409）；进度心跳照常落库（位置不能丢），但响应带 `ended_by_admin=true`，网页播放器
据此退出并说明原因，不再走重开。设备重新上报「开始播放」（用户亲手再点了播放）
即解除窗口，不必等满 60 秒。Jellyfin 客户端没有会话控制通道，看到的是一次播放
中断，重新点播放即可。

### 播放日志与统计

`playback_state` 是状态不是日志（同一集重看会覆盖），标不出哪台设备、什么时候、
看了多久。新增 `playback_log` 表：**每场播放一行**，由两条入口共用的上报服务写入
（`watch.py`），字段有成员、单元、设备与客户端、起止时间、起止位置、实际观看时长、
是否看完。条目与成员都只存数字锚不做外键，并快照片名与形态——统计要在条目删除、
刮削改名之后仍然成立。

写入规则：
- 开始上报开一行；同一设备同一单元在保鲜期（5 分钟）内重复开始视为同一场（seek、
  暂停后恢复、换源重协商都会再发 Playing）；同一设备换片时把此前没收口的行按最后
  一次心跳收口；
- 进度上报按位置增量累加 `watched_ms`：暂停不计、单次增量超过两分钟的视为 seek
  跳过不计，与「播到哪」是两个读数；丢了开始包（Jellyfin 只发 Progress、服务刚重启）
  就地开行；
- 停止上报写 `ended_at`。播放器异常退出不会发停止，读侧按「最后心跳超过保鲜期」视为
  已结束、结束时间取最后心跳，仍在保鲜期内的算进行中。

读侧两个接口（管理员，口径跟随范围切换）：`GET /playback/history` 是播放记录列表，
`GET /playback/stats/watch?days=&tz_offset=&member_id=` 是一段时间内的播放场次、
观看时长、看完场次、活跃成员，及按成员 / 客户端 / 天 / 星期×小时 / 作品 / 播放方式
的分解。按天分组用浏览器时区，否则晚上的观看会被算到第二天。作品榜与记录列表走
可见范围折叠，其余是不出片名的聚合数。聚合在 Python 里做：家庭服务器几十天的日志
也就几千行，比跨方言的 SQL 分组省心。

统计接口同时返回**上一周期**（紧挨着的前 `days` 天）的汇总与逐日序列：一个数字
没有参照物读不出好坏，「45 小时」要和「上期 29 小时」放在一起才是信息。日志不足
两个周期时 `previous_available=false`，前端显示「暂无上一周期数据」而不是「+100%」。

活动页的「观看统计」切片按 BI 仪表盘的读法组织，从上到下是「结论 → 走势 → 构成 →
习惯」：

- **指标卡**：观看时长、播放场次、看完率、活跃成员，各只有本期大数字（单位排小字）、
  一枚涨跌标签（看完率用百分点，没有上期就不出）与「上期 x」参照。不放迷你走势：
  走势主图已经画了，卡片里再画一遍是没有标注的重复信息，看完率那种空位多的序列
  还容易被读成数据缺失。卡片可点，选中哪张主图就画哪个指标；
- **主图**：所选指标的逐日**柱图**，上期是同坐标系里的虚线。按天合计是离散量，柱子
  比折线诚实：零值日就是空位，有观看的日子一眼可数，折线会把相邻两天连起来暗示
  中间有过渡值。带 y 轴整齐刻度、x 轴日期、悬停高亮与本期 / 上期数值提示。刻度
  个数按图宽定；一根柱子摆不下 6px 时按周折桶（最新一桶一定是完整的一周，活跃
  成员没法从日数据里去重、折桶后取日均并在提示里注明）；
- **最受欢迎**：紧跟指标卡的 **TOP 3**（结论先于走势），借 Netflix「TOP 10」的语法：巨大的
  描边数字压在海报左后方、海报盖住数字右侧一角，数字本身就是装饰，不需要徽标；
  第一名的数字与海报都更大；整块的背景是第一名海报放大模糊后的环境光，随作品换色。
  这是整页唯一的图像锚点，也是这一页里唯一允许「隆重」的地方。口径是**看过的成员
  最多**，并列取时长长的、再取场次多的
  ——与「看得最多」（按时长）是两个问题：一个人刷完一整季会稳居时长榜首，三个成员
  各看一遍的电影才是「家里谁都在看的」。成员就三五个，并列常见，第二排序键不能省。
  每张卡片对照上一周期的前三：同名次「蝉联」、换了名次「上期第 n」、上期不在前三
  「新上榜」；钻取到单个成员时人数没有意义，退成「本期看得最多」。同一部片同时占
  两头是允许的，也是信息：既有人看又看得久。范围外的作品跳过，由后面可见的顶上；
- **分解面板**：按成员、按客户端、看得最多、按播放方式四块同构（名称 · 值 · 占比条）。
  四块的行数天然不同（成员三五个、客户端两三个、作品榜十个、播放方式最多五档），
  不管就是高矮参差：每块**封顶五行**，多出来的按成员 / 客户端合成一行「其他 N 个」
  （占比仍合计 100%），作品榜留「展开全部」；按行数相近配对摆放（成员与客户端一行，
  作品榜与播放方式一行）；同一行两块等高、内容顶对齐，留白在卡片里而不是卡片外。
  不做面板内滚动，也不画空行占位——空行看起来像数据缺失。
  前三块的值都是观看时长，避免同一页里时长条与场次条混排。「按播放方式」来自网页端
  转码会话的档位记录（直连 / 重封装 / 硬件 / 软件转码），只有场次没有时长，Jellyfin
  客户端恒为直连，面板上写明只统计网页播放；
- **钻取**：点成员名把整个切片收到该成员（`member_id`），指标卡、主图、其余面板一起
  变，与「播放记录」的成员筛选共用工具栏里的同一个下拉；
- **时段热力图**：星期 × 小时的观看时长（`by_hour`，浏览器时区），回答「家里什么
  时候在看」。

图全部是内联 SVG，不引图表库：折线、面积、迷你走势加起来百来行，引一个库的体积与
样式接管都不划算。「播放记录」切片（按天分组、加载更多）也从这两个接口出。这两片不
轮询：日志按场记，几秒一刷没有意义，切周期、成员或口径时重拉。

### 空状态与读取中

三个切片、统计里的每一块，没有数据时都不留空白，也不用警告色——空不是故障。
统一一个 `EmptyState`（图标、标题、一句说明、可选动作）承接，说清三件事：这里
本来会有什么、为什么现在没有、接下来能做什么。动作只给「换个口径再看」这一类：
清掉成员筛选、把周期拉到 90 天、把范围切到「全部」；不给无关的跳转。

- **正在播放**没人在看：说明设备开始播放后几秒会出现、两条入口都算，动作是
  「查看播放记录」——实时为空时，用户多半想看的是刚才谁看了什么；
- **播放记录**为空分三种：还没有任何记录（说明会记什么）；筛选了某个成员而 TA
  没有记录（点名，动作「查看全部成员」）；有记录但全在浏览范围外（说明来自哪、
  动作「显示全部」）；
- **观看统计**分层：两个周期都没有日志，整块只出一个空状态，不摆一排 0；本期
  没有、上期有，指标卡与主图仍有对照价值（主图里标「本周期没有播放，虚线是上一
  周期」），其余分解用一个空状态代替五块各写「没有数据」；有播放但 TOP 3 为空
  （作品全在范围外或条目已删），一行 compact 空状态说明去向；「按播放方式」为空要
  说清是「没有网页播放」而不是没有数据——Jellyfin 客户端不经转码，本来就不在这里；
  热力图没数据也把 7×24 的空格子画出来，空格子本身就在说明这里会是什么；
- 两期都为 0 的指标不出涨跌标签；
- **读取中**用与最终布局同形的骨架（指标卡、主图、TOP 3、四块分解；记录列表是
  一个日期组头加四行），内容到达时整页不跳动，不用一行「正在读取…」占位。

### 范围切换

`admin_visible` 是超管给自己设的浏览过滤，不是安全边界（超管随时能把库翻回
可见）；典型场景是把不刮削的内容放进「其他」库并对自己隐藏，开活动页时旁边有人
也不该看到那些片名。但活动页又是管控视角，管理员有权看到所有人的全部播放活动。
两个诉求都成立，所以是一个显式的口径开关（`GET /playback/activity?scope=`），
以「范围」下拉的形态放在观看视角的工具栏里，三个切片共用：

- **我的浏览范围**（`visible`，默认）：正在播放、正在下载、最近观看三个区块统一
  按超管的可浏览库集合折叠，范围外记录只报个数（`hidden_session_count` /
  `hidden_download_count` / `hidden_recent_count`），不出片名与海报。此前只有
  最近观看折叠、实时区块照出片名，是一处自相矛盾，本次一并修掉。
- **全部**（`all`）：跨成员、跨库全量。范围外记录带 `browsable=false`，前端不渲染
  详情链接（条目详情接口对范围外超管是 404）并标「仅管理」——与库首页对超管不可
  浏览库的标签同一措辞。

折叠提示行可操作（「另有 N 条不在你的浏览范围内 · 显示全部」），既有持久的筛选，
也有就地的入口。选过的档记在本浏览器（`lib/activity-scope.ts`），默认口径不落存储；
超管的设备由超管自己负责。按成员筛选与范围切换正交，播放记录切片提供。

### 设备的处置而非罗列

页面不单列设备清单。一个只读的设备列表比没有更糟——它把"这台设备我不认识"
这种安全信号摆出来，却不给任何处置手段。设备身份已经写在每张播放/下载卡的
元信息行里（成员 · 客户端 · 设备名 · 版本），处置能力挂在卡片右上角的菜单上
（形态复用任务中心的 `TaskActionsMenu`，不新造交互）。

菜单提供「结束播放」与「注销此设备」两个动作（前者见下文「结束播放」）。注销
要同时做三件事，缺一不可：删 `jellyfin_device` 行（设备级长期 AccessToken 即刻
失效）、`activity.report_stop`（否则实时视图还会按保鲜期显示一台已不存在的设备
在播放）、`stop_device_streams`（播放器不会因 token 失效就主动断开已建立的 Range
连接，不停就会继续为已注销的设备转磁盘）。观看进度按成员保存，不受注销影响。

已知缺口：这条路径只能处置**当前正在播放或下载**的设备。真正需要注销的往往是
卖掉的旧设备、长期未用却仍持有有效凭据的设备——它们不在活动页出现。补齐要靠
独立的设备管理入口（设置分区），本期不做。

`playback_state` 没有设备维度（键是 成员×条目×季×集，且是"状态"不是"日志"，
同一集重看会覆盖），因此"最近观看"无法标注是哪台设备播的。按设备、按时间的播放
历史由后来新增的 `playback_log` 承担，见「播放日志与统计」。

速率语义如实呈现：本地文件直连展示滑动窗口平均速率、累计字节与连接数；strm
网盘条目播放走 302 直链、流量不经过服务器，标注"网盘直链"而不是伪造 0 速率。
播放方式认台账里的文件形态（是否 strm），不靠"是否已经看到字节"倒推——上报先于
取流到达是常态，用字节证据会把刚开播的本地文件误标成网盘直链；只有条目没有在位
台账行时才退回字节证据。速率在还没有字节流时输出 null（展示为"本地直连"），
与真实的 0 速率区分。同一设备同一文件的多条 Range 连接（断点续传、并发分段）
在展示层聚合为一条，字节与速率求和。

整文件下载的进度按「Range 起点 + 本次已传」还原真实下载位置——断点续传从文件
中段开始，只看本次已传字节会把进度算回 0。多连接取推进得最远的那条：顺序下载
（播放器离线缓存的常态）下即真实位置，并发分段下载会偏乐观，不为该类客户端把
读数复杂化。文件大小未知时不画进度条，而不是画一条假的。

进度条贴卡片底边、横跨全宽、3px 细条（Jellyfin 控制台、Plex 活动、Netflix 缩略图
的通行形态）：多张卡片的进度共享同一基线可以互相比较，进度条只当视觉指示器，
具体时刻与百分比留在文字区，不被拉到卡片另一端。状态徽标在窄屏收敛为单个彩色
圆点（与本页既有约定一致），文字降为 sr-only 而非从 DOM 摘除，读屏仍可听到状态。
整文件下载（/Items/{id}/Download 的离线缓存）**独立成「正在下载」分区**——它不是
播放，把它塞进「正在播放」会让标题名不副实、计数也把非播放算进去。下载相对少见，
因此该分区只在真有下载时渲染，常态下页面仍只有一个实时分区；分区标题已表明性质，
卡片不再重复一个同义徽标。它不参与会话判定，但同样计量速率。

聚合接口是 `GET /playback/activity`（管理员专属，跨成员可见，沿用本页的
`require_admin` 边界；`scope` 参数见「范围切换」）；前端按 8 秒节奏轮询，页面隐藏
时暂停。

轮询按**权限**门控，不按视角——「观看」旁的实时圆点（有播放或下载在进行时亮起）
要在任务视角也能亮，那正是它存在的意义：处理任务时一眼看到家里有人在播。只在
观看视角轮询的话，圆点只有在你已经盯着播放卡片时才亮，等于没用。门控口径与
download-tasks / jobs 两个 Provider 一致，成员直接访问本页不会拉出 403 报错。

同理，页面组件不能按视角加 `key`：切视角要经 `router.replace` 改写查询串，带 key
会让整个视图重新挂载、把已拉到的活动快照连同轮询状态一起丢掉（表现就是切到
任务后圆点熄灭）。视角状态由页面组件自己持有，浏览器前进/后退经一个同步 effect
回灌。播放失败上报（Failed=true）目前仍静默丢弃，未来若进"需要处理"区需要
单独设计事件留存。

## 权限与动作

任务中心属于管理员运维视角：Job 可能暴露执行输入、错误与模型使用信息，下载器视图
涉及全局下载资源，均沿用管理区的 `require_admin`。成员的“我的订阅”继续使用已有的
订阅详情页，不获得全局下载器可见性。

任务中心只提供其能安全表达的动作：

- Job：取消、重试、打开设置/日志、交给 Agent；
- 下载任务：回到订阅详情或下载器设置排障。

暂停、删除种子等破坏性下载器操作不在这一期增加；若未来引入，必须先扩展下载器抽象
的跨客户端控制契约，并对删除数据提供单独确认。
