# 追新资源发布时间预测

## 1. 目标与边界

站点索引的正常轮询频率会随发布活跃度动态变化。对已经订阅、尚未播出的剧集，
系统从 E2 开始利用同季前序单集的真实发布时间预测下一集资源窗口，并在窗口内
临时提前既有站点同步。它不替代以下两条原有通道：

- 站点正常自适应同步仍持续运行；
- `air_date + 48h` 的主动搜索仍是漏抓兜底。

首版只做可解释的统计预测，不引入机器学习，也不猜官方播出时区。

## 2. 为什么只增加一个 JSON 列

不新增 `release_observation`：`site_torrent` 已保存 `site_id`、`torrent_id`、
`publish_time`、`created_at`（首次发现）、标题、外部 ID 和季集解析，足以重建原始
观测。复制到新表会产生双写、去重与历史修复问题。

不新增 `site_sync_hint`：临时探测点可由当前未满足工单的预测快照直接合并；
`SiteSyncCursor.last_sync_at` 可以判断探测是否已被消费，而且普通同步同样算消费。

唯一新增字段是 `wanted_item.release_forecast`（可空 JSON）。它是“本集当前预测”
的派生快照，便于接口展示、调度读取与冻结首次预测；删除它不会损失任何事实数据，
可随时从 `site_torrent` 重算。

## 3. 观测口径与预测算法

只接受满足以下条件的种子作为样本：

1. 能通过现有身份匹配内核确认属于本剧；
2. 明确落到同季单个 `(season, episode)`；
3. 有真实 `publish_time`；
4. 发布时间位于播出日前 2 天至播出日后 7 天，排除很久以后出现的重发/洗版；
5. 排除整季包、全集包与多集包，因为其发布时间不能代表某一集。

同站同集存在多个质量版本时取最早发布时间；跨站以最早发布时间作为该集的全网
发布时刻。预测目标集时，只取同季最多四个较早单集，把每个历史发布时间按两集
`air_date` 的天数差平移到目标日期，再对近期样本赋更高权重取中位数。因此日播和
周播使用同一套算法，无需预设剧种。

置信度与窗口：

| 样本 | 等级 | 窗口 |
|---|---|---|
| 1 | `bootstrap` | 预测前 2 小时至后 8 小时 |
| 2 | `growing` | 预测前 1.5 小时至后 6 小时 |
| ≥3 | `stable` | 按滚动回测误差确定，至少覆盖前后各 1 小时 |
| ≥3 且误差窗口 >12h | `volatile` | 仅保留观察结果，不触发额外同步 |

快照同时保存样本集、种子行 ID、重点站点、站点历史延迟与探测点。`first` 子对象
冻结该集第一次预测，后续滚动修正不覆盖它，便于以后计算窗口命中率。

## 4. 站点探测与停止条件

快照按“最近一集有发布、历史覆盖多、相对全网发布延迟小”保存站点排名；执行时
只从当前启用站点中取前两个，因此停用站点后可自动回落。第一站在窗口
20%/50%/80% 处探测，第二站在 50%/80% 处探测。

全局 120 秒同步 tick 读取这些时间并与 `SiteSyncCursor.next_sync_at` 取较早者；
同一站的所有订阅自动合并，且预测探测之间至少间隔 15 分钟。现有认证、限流、
失败退避与熔断逻辑保持不变。

以下任一条件成立时，预测不再产生额外站点访问：订阅暂停或完成、工单已投递、
预测窗口过期、档期与快照不一致、置信度为 `volatile`。元数据改档、新种子入库、
主动搜索回填、订阅创建/调整/恢复都会触发重算。

## 5. 实际拉取耗时

预测回答“什么时候可能出现”，投递后的时间链回答“实际上隔了多久才拉到”。成功
投递时复用既有 `subscription_activity(type=grabbed)`，在 payload 中冻结：

- `resource_publish_time`：站点标注的资源发布时间；
- `resource_first_seen_at`：`site_torrent.created_at`，即 MovieClaw 首次索引时间；
- `submitted_at`：成功提交下载器的时间；
- `units`：本资源覆盖的季集号，一个整季包据此映射到每一集。

详情接口据此返回“发布→索引、索引→提交、发布→提交”三段秒数。使用活动 payload
而非给 `wanted_item` 增列，是因为它本来就是不可变的投递历史，而且能够表达同一集
重新下载多次；详情默认展示最近一次。上线前的老活动若没有冻结字段，则凭活动里的
站点/种子 ID 从仍存在的 `site_torrent` 回补；索引已删除时安全降级，不伪造时间。

## 6. 订阅首页的预计入库摘要

`GET /subscriptions/today-arrivals` 聚合当前账号可见的待播集，以及仍处于下载、
整理阶段的内容。接口不复制海报和下载百分比，只返回剧名、季集号、工单阶段、预测
快照与下载任务关联所需的 infohash。

**今天优先，一周内回退。** 这块首屏区域回答的问题是“我下一次能看到新东西是
什么时候”，因此候选先按 `today .. today + 7` 收集，再收敛到单个焦点日：今天有
安排就只回今天，否则只回窗口内最近一个有安排的日子。订阅少的用户因此不会天天
面对一个空栏目（空着不说话会让人以为追踪停了），首页也不会退化成一张七天流水账。
每行带 `expected_day`（站点日历日）与 `days_ahead`（0=今天）——站点日历是
Asia/Shanghai，与浏览器时区可能不同，“是不是今天”由服务端一次算好，前端不复制
这套时区规则。

`?window=week` 跳过焦点日收敛、整周按日期原样返回，给 iOS App 订阅首页的「日程」
日期条用：那里本身就是一周的日历，用户点哪天看哪天，不存在流水账的问题。候选口径
（哪些工单算、预计日怎么定）两种模式完全一致，默认值仍是 `focus`。

同一页的「刚刚入库」由 `GET /subscriptions/recent-arrivals` 提供：最近 7 天整理入库、
当前账号还没看完的内容，一部作品一张卡，入口指向这一批里第一个没看完且文件在位的
单元，整批看完即消失（规则见 `services/subscription/recent_arrivals.py`，“看完”与
“在位”的口径同媒体库首页的「接下来继续」）。

**电影只在管道内纳入。** 电影没有播出日，还在找资源时给不出可信的预告时间，
常年挂着的电影会天天占据首页；已投递/已下载的电影则和剧集一样，“下载中 /
整理中”对用户完全成立。`media_kind` 让前端把 `(0,0)` 哨兵季集号显示成“电影”。

首页展示的“预计入库”不是把出种预测直接改名，而是在 `predicted_at` 上叠加本订阅
历史 `grabbed_at → imported_at` 的中位耗时。没有历史样本时冷启动按 60 分钟估算；
下载器已经提供实时 ETA 后，前端改用 `ETA + downloaded_at → imported_at` 的历史
中位耗时（冷启动 10 分钟）。预测窗口失效或置信度为 `volatile` 时不继续展示过时
时间，按信息量依次降级为“下次探测时刻 → 播出日期 → 时间待更新”。

首页的“下载中”不展示速度与百分比；管理员点击后深链到任务中心的“下载任务”Tab，
完整进度、换种和删除等操作仍由任务中心承载。
