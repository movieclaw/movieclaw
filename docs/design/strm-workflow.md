# 网盘 strm 工作流：整理输出与媒体库解耦——设计

> 状态：v2（2026-08-02）已实施。v1（库级换根）同日被推翻，见第 7 节决策记录。
> **v3「回流入口」（2026-08-06，issue #94）：设计定稿待实施，见第 8 节起**——
> v2 只解决了链路前半段（整理落点可自定义），二级分类在后半段丢失。
> 源起：issue #44（二级分类跟目录问题）、issue #39（strm 识别，已验证可用）、
> issue #94（二级分类在硬链接阶段丢失）。
> 关联文档：[library.md](library.md)（媒体库架构）、
> [library-routing.md](library-routing.md)（路由与"订阅止于投递"语境）。

## 0. 问题定位

### 0.1 网盘 strm 玩法的目录三角

PT + 网盘用户的典型工作流涉及**三个**目录，而 movieclaw 现有模型假设
后两者是同一个：

```
下载目录（保种，PT 原名，不可动）
   │  硬链 + 识别 + 重命名（movieclaw 的核心价值）
   ▼
中转目录（规范命名的真实文件 —— 上传网盘后即可删除）
   │  上传网盘 + 生成 strm（外部工具，movieclaw 不参与）
   ▼
媒体库根（只放 strm 占位文件 —— Emby/Jellyfin 扫这里）
```

现状的绑定点：监听导入的整理落点恒为某个库的主根（`derive_save_path`）。
于是真实大文件被硬链进本该只放 strm 的库目录（issue #44 的核心抱怨
"硬链接文件夹无法自定义，媒体库文件夹又是 strm 文件夹"）。

### 0.2 issue #44 的两条诉求拆解

| 诉求 | 结论 |
|---|---|
| "没有二级分类" | 区域/类型粒度已由**多库 + 收藏范围**覆盖（library-routing.md），回复引导即可；单库内分目录形态是既有 v2 开口（库内二级目录），本设计不涉及 |
| "硬链接目录无法自定义" | **真实缺口**，本设计解决 |

## 1. 方案：监听导入目标支持「自定义目录」

### 1.1 分层定位（用户决策 2026-08-02，本方案的第一性）

- **监听导入 = 转移编排层**：源在哪、怎么搬（硬链/复制）、搬到哪。
  复杂转移与将来的自定义操作（后处理、模板等）都归这一层演进；
- **媒体库 = 内容层**：只有三件不可约的职责——根目录、台账、扫描
  入账。库根里有什么，库就是什么。**本设计对库模型零改动**。

整理动作本来就发生在监听导入（`_ingest_entry`），落点选项属于转移
配置，自然长在监听导入规则上，而不是把转移关注点塞进库模型。

### 1.2 方案概述

监听导入规则的目标从二态扩展为三态：

| 目标 | 存储 | 语义 |
|---|---|---|
| 指定库 | `library_id` | 现状：整理进该库主根 |
| 自动路由 | `library_id` NULL + `kind` | 现状：识别后按收藏范围路由选库 |
| **自定义目录** | `target_path` + `kind` | **新增**：识别改名后落该目录，不涉及任何库 |

自定义目录规则**完整复用识别链**：识别 → 按库同款规范命名
（`{title} ({year})/…`）→ 硬链/复制 → 落 `target_path`。kind 必填
（识别链按 movie/tv 分叉的先验，与 auto 模式同理）。

完整链路（仅第一段是新行为，其余全是现状）：

```
下载目录 ──[监听导入：识别+重命名 → 自定义目录]──▶ 中转目录   ← 本设计唯一改动
中转目录 ──[外部：上传网盘 + 生成 strm]──▶ 库根              ← movieclaw 不参与
库根 ──[现有：扫描/实时监控收 strm → 识别入账]──▶ 台账       ← 零改动（#39 已验证）
台账 ──[现有：库存对账]──▶ 工单关闭、订阅进度、时间线         ← 零改动
```

**命名规范同源是两段之间唯一的衔接机制**：中转文件名在整理时已规范，
strm 生成工具照网盘结构镜像，回流文件名天然规范 → 扫描识别精准命中。
不发明任何显式的关联协议。

### 1.3 产品面约束：能力中性，玩法进文档（用户定位决策 2026-08-02）

movieclaw 的产品定义是**媒体库**，网盘只是一种资源组织方式——产品
只提供解决需求的能力，不把"网盘支持"做成功能点：

1. **配置项中性**：界面不出现"网盘 / strm 模式 / 中转"这类玩法词汇。
   新目标就叫「自定义目录」，对任何"整理结果需经外部流转（上传、
   转存、人工确认）再进入媒体库"的场景都成立，网盘 strm 只是其一。
   且它长在监听导入表单——用户本来就在这里思考"从哪搬到哪"，
   理解成本趋近于零；
2. **运行时文案陈述事实，不陈述模式**："文件放到了哪、接下来等
   什么"；strm 一词只在对象确实是 strm 文件时自然出现；
3. **玩法配方放用户手册**："常见玩法"页收录三目录结构怎么配、配合
   哪些网盘工具——产品暴露正交能力，文档负责把能力组合成玩法。

## 2. 行为定义

### 2.1 整理落点与"过客"语义

自定义目录规则整理出的文件是**过客**——上传后会被删除，因此：

- **不写 `library_file` 台账、不生成海报/nfo 资产**（入账只会制造
  缺失告警）；识别产生的 `media_item` 身份档案照常建立（回流入账
  与订阅对账都依赖它）；**v3 修订**：条目级身份 NFO 改为照写（几 KB
  文本、不产生缺失告警，且是回流侧零歧义识别的关键），图片资产维持
  不写——见 9.5；
- ffprobe 完整性门禁保留（挡残缺文件的价值与落点无关）；
- `ingest_entry` 源侧台账照记（幂等与退避不变），其 `library_id`
  对路径规则恒空；
- 入库结论文案陈述事实：
  "已识别为《风筝》，硬链接到 /staging/剧集；文件进入媒体库根目录后
  将自动入账"。

### 2.2 回流侧：零改动

库根扫描/实时监控本就接纳 `.strm`（layout.py 的 `SCAN_VIDEO_EXTS`），
识别按文件名走，规格列留空（strm 无媒体流，ffprobe 无意义）。
strm 入账后 `close_fulfilled_wanted` 照常关闭工单。#39 已确认此路可用。

### 2.3 订阅兼容性（本设计的验收重点）

前提事实：**订阅止于投递**（download_progress.py）——订阅不亲自搬运，
完成搬运由监听导入认领或库扫描完成，工单由库存对账关闭。兼容性由
三个小扩展 + 两个不变达成：

| 环节 | 行为 | 改动 |
|---|---|---|
| 路由与定格 | 收藏范围选库、创建时定格 `library_id`；对走路径规则的下载，定格库不再决定落点，仅用于弹窗预选与时间线展示 | 无（语义澄清） |
| 投递 | `resolve_dispatch_dir` 查找链延一格：目标库专属规则 → 同 kind auto 规则 → **同 kind 路径规则** → None | 一处扩展 |
| 完成搬运 | 沿用"规则声明压倒路由"：落点由规则定（= `target_path`）。info_hash 认领**保留但只取身份**（免重新识别、命名更准），不决定落点 | 身份与落点分离 |
| 工单关闭 | 库存对账按条目身份（media_item + 季集）核销，**不筛库**（wanted_fulfillment 已如此）——strm 回流进任何库根都能关单 | 无 |
| 救援巡检 | 卡死/删种判定基于下载器状态，与回流无关，不会误退回重下 | 无 |

在途语义：种子下载完成、已整理到自定义目录、strm 未回流期间，工单
停在 GRABBED——这是**正确的**："库里有"才是订阅的完成定义。
"上传中"这个状态被现有机制天然表达，不需要新状态机。

手动下载的 save_path 预选沿用同一查找链：命中路径规则时预选其
**源目录**（下载完成后由监听导入接力识别整理），无命中回落现状。

### 2.4 校验（保存时前置报错，中文文案）

- `target_path` 与 `library_id` 互斥；`target_path` 时 `kind` 必填；
- `target_path` 不得与任何库根、任何监听源目录重叠；
- 硬链接同盘检测：源目录 vs `target_path`——
  "监听目录与整理目标目录不在同一文件系统，硬链接会失败；请改用
  「复制」策略，或调整存储布局"；
- 每 kind 路径规则至多一条（与 auto 规则同理：`resolve_dispatch_dir`
  的投递落点不能歧义）。

## 4. 交互设计

### 4.1 配置入口：监听导入表单的目标下拉加一项

```
目标： [电影库] [动漫库] … [自动路由（电影）] [自动路由（剧集）] [自定义目录…]
```

> 适合整理结果还需外部流转（如上传、转存、人工确认）再进入媒体库
> 的场景：文件后续出现在某个库的根目录时，将被自动扫描入账。

库表单**零新增配置**。校验错误在表单内联报出，文案给修法（见 2.4）。

### 4.2 引导与自检：展示真实链路，不解释模式

- **用户手册「常见玩法」**：网盘 strm 工作流作为配方收录（库根放

  词汇只出现在这里；
- **模拟一单**（订阅设定页，已有）：投递命中路径规则时，预演展示
  完整事实链："路由选库 → 投递到 /downloads → 整理输出到 /staging →
  等待文件进入库根后入账"；
- **链路体检**（已有）：路径规则的转移段步骤条为"投递 → 整理输出 →
  外部流转 → 入账"，外部流转节点固定为说明性状态（movieclaw 不判
  外部环节死活），同盘检测按 2.4 锚点。

## 6. 边界与风险

1. **按库分中转不支持**：路径规则按 kind 收口（电影一条、剧集一条），
   区域级分流（华语库/动漫库各自的中转）在整理阶段做不了，由用户在
   网盘/strm 生成侧自己组织。接受：玩法纵深里靠后的需求，不值得为它
   污染库模型；真有强需求，将来在监听导入层加落点模板，顺着分层走。
   **v3 已解决（issue #94），但走的不是这里预留的"落点模板"**：中转
   仍然不分库，二级分类改在 strm 回流那一跳由既有路由引擎完成——
   见 8.2 与决策 14.2；
2. **回流断链无原生提醒**：上传工具挂掉时工单长期在途，movieclaw
   不误退回（救援只看下载器状态），但也不知道链路断了。v1 接受
   （体检的外部流转节点已提示外部依赖）；若反馈强烈，v1.1 加"整理
   后超 N 天未见回流"的时间线提醒，判定素材（`ingest_entry` 的整理
   时间与条目身份）都已在账；
3. **strm 条目的规格与洗版降级**：strm 无媒体流，规格列为空（既有
   的文件事实，与任何配置无关），按规格洗版对这类条目天然不可用，
   实体替换也发生在库外。降级挂在文件事实上，不发明"网盘库"分类；
4. **strm 生成端的目录约定**：strm 须镜像进对应库的根目录，属外部
   工具配置，写进配方页；
5. **内置上传 + strm 生成**：明确不做，留作独立开口——那是把外部
   环节纳入管线的产品级决策（网盘认证、限速、失败重传……），与本
   设计正交，届时整理段与回流侧无需变更。

## 7. 决策记录（2026-08-02）

1. **分层定位**：监听导入 = 转移编排层，媒体库 = 内容层（根 + 台账 +
   扫描）。落点选项属于转移配置，长在监听导入规则上；
2. **推翻同日 v1（库级 `staging_root` 换根）**：转移关注点入侵内容
   模型；与监听导入未来的自定义转移能力形成两处落点决策；订阅兼容
   扩展经核实很小（`resolve_dispatch_dir` 延一格 + 认领身份/落点
   分离），不构成库级方案的理由。代价 = 放弃按库分中转，接受（6.1）；
3. **认领身份与落点分离**：info_hash 认领只取身份，落点由规则声明
   决定（"规则声明压倒路由"语义的自然延伸）；
4. **两段衔接 = 命名规范同源**，不发明显式关联协议；
5. **在途语义复用"库存对账关闭工单"**（对账按条目身份、不筛库），
   不加新状态机；
6. **否决的其他备选**：中转目录建成库（台账语义与过客文件冲突）、
   中转当监听源（重命名发生在入库环节，顺序不对）、"原样转移不刮削"
   模式（与需求矛盾、无增量价值）；
7. **产品面中性**（1.3）：配置项叫「自定义目录」，事实文案，玩法
   配方进用户手册，不设玩法开关/模式；
8. issue #44 的二级分类半边：引导多库 + 收藏范围，单库分目录维持
   既有 v2 开口不变。

# v3：回流入口——二级分类放到回流那一跳

> 状态：设计定稿（2026-08-06），待实施。源起 issue #94。

## 8. 问题与第一性

### 8.1 issue #94 的诉求

客户原话：「下载文件夹—硬链接文件夹（处理好二级分类）—上传网盘—网盘
生成 strm 文件（到主根目录）」，卡点是"缺少了在生成硬链接的同时处理
二级分类，所以导致上传网盘时，不能严格按照媒体库的主根路径进行操作"。

v2 已经解决了他抱怨的前半段（整理落点 = `target_path`，不再被迫硬链进
strm 库根）。**后半段是真缺口**：中转目录是扁平的
`{target_path}/{标题 (年份)}`（`ingest.py:707-710`），而本项目的"二级
分类"是靠**多库 + 收藏范围**实现的（每个库一个根）。中转结构 ≠ 库根
结构 → 外部 strm 生成工具面对一个混着动画与国产剧的目录，无从判断谁该
去 `/media/anime`、谁该去 `/media/tv`。

这正是 6.1 自己写下的边界"按库分中转不支持"。#94 就是那个强需求。

### 8.2 第一性：二级分类不必在整理时做

推翻 6.1 那句"将来在监听导入层加落点模板"的隐含前提——它假设中转目录
必须镜像库根结构。**不必**：中转目录只是上传缓冲区，没人从那里播放。

**把选库推迟到 strm 回流那一跳**，让 movieclaw 自己把 strm 收进对应库根，
二级分类就由既有的 `route()` 引擎解决，与订阅/下载选库同一套收藏范围、
同一套中文理由。链路变成三段两规则：

```
/downloads    ──[规则1 自定义目录 kind=tv]──▶ /staging/tv    硬链+改名，不进库
/staging/tv   ──[外部：上传网盘 + 生成 strm]──▶ /reflow/tv    movieclaw 不参与
/reflow/tv    ──[规则2 自动路由 kind=tv]────▶ /media/anime 或 /media/tv
                                                    ▲
                                         二级分类在这里发生，用既有路由引擎
```

对比被否决的备选（均在 #94 讨论中逐一评估）：

| 备选 | 否决理由 |
|---|---|
| 中转按"库主根末级目录名"开二级目录 | 改库根会让中转落点**静默漂移**（`library-routing.md:63-68` 明令堵死的"配置还在、悄悄不工作"类坑）；且只在"所有库根同父目录"的布局下成立，而布局是用户的事 |
| 库级「整理中转目录」（v1 `staging_root` 的变体） | 需推翻决策 2；且落点决策落到库与规则两处 |
| 监听导入落点模板（6.1 原开口） | 用户要学模板语法，是三者中唯一引入新语法的 |
| 回流规则按 kind 拆多条绑库 | **结构上不成立**：`import_watch.source_path` 有唯一索引（`models/import_watch.py:46`），一个源目录只能有一条规则，而回流目录只有一个 |

v3 相对它们的要点：**不动 `library` 模型、不推翻决策 2、复用两个既有目标
形态**（自定义目录 + 自动路由），用户不需要理解任何新的路径推导规则。

## 9. 五个必须补的缺口

全部已在现有代码中定位。**9.1 是致命的**——不补则链路根本跑不起来。

### 9.1 投递会命中回流规则，种子被投进 strm 目录（致命）

`resolve_dispatch_rule`（`import_watch_config.py:350-397`）的查找链是
**目标库专属规则 → 同 kind auto 规则 → 同 kind 自定义目录规则 → None**。

规则2 是 auto 规则，命中在**第 2 级**，早于规则1（第 3 级）。于是订阅
投递算出的 `save_path` 是 `/reflow/tv`——**种子被下载到 strm 输出目录**，
规则1 永远收不到东西，规则2 反而把 PT 原始文件当内容收进库根。链路彻底断。

这不是配置能绕开的：只要 auto 规则存在，它就在查找链上。

**解法：监听导入规则新增「接受下载投递」开关**（`accepts_dispatch`，
默认 `True`）。查找链只在 `accepts_dispatch=True` 的规则里找；回流规则
关掉它，声明"本目录的内容来自外部流转，不是下载落点"。

这个开关**不是为 strm 特设的**（符合 1.3 能力中性）：任何"源目录内容不
来自下载器"的场景都需要它——用户手工往某目录丢文件让 movieclaw 整理
入库时，同样不希望种子被投进去。

### 9.2 ingest 刻意不接纳 strm

`ingest.py:201` 用的是 `VIDEO_EXTS`（不含 `.strm`），而非扫描侧的
`SCAN_VIDEO_EXTS`。规则2 扫 `/reflow` 会一个视频都收不到，直接
`SKIPPED`："条目中没有视频文件，已跳过"。

`layout.py:52-54` 写明这是刻意的：

> **下载入库链（监听导入 ingest）刻意不收 strm**：那里的 ffprobe 完整性
> 门禁（挡残缺文件）对 strm 必然失败，会陷入"探测失败自动重试"的死循环。

**该理由只成立于"收了 strm 却不豁免门禁"**。库扫描侧对 strm 早已豁免
（`scan.py:852-856`，规格列留空）。把同一套豁免搬到 ingest，死循环不存在。

**解法**：ingest 的接纳集合改用 `SCAN_VIDEO_EXTS`，并同步 9.3。
`layout.py` 那段注释一并改写为豁免口径，避免留下自相矛盾的注释。

### 9.3 ffprobe 门禁对 strm 必然失败

两处：主文件门禁 `ingest.py:638-644`、逐文件门禁 `ingest.py:766-770`。
strm 探不出流 → `spec is None` → `FAILED` 退避重试。

**解法**：`.strm` 跳过门禁（口径与 `scan.py` 同源，规格列留空）。门禁的
价值是挡"下载了一半的残缺文件"，strm 天然没有这个状态。

改为**内容合法性轻校验**替代：文件非空、首个非空行能被
`movieclaw_playback.streaming` 的 `_ALLOWED_STRM_SCHEMES`（http/https/
rtsp/rtp，`streaming.py:22`）接受。挡住空文件与写了一半的 strm——这才
是 strm 真正的"残缺"形态。不合法按 `FAILED` 退避重试（外部工具写完会
改变 mtime，指纹变化自然触发重试）。

### 9.4 strm 链接更新会在库根堆重复版本

`_same_payload`（`ingest.py:971-978`）按 **inode 相同或尺寸相同**判定同
内容。strm 是纯文本 URL：

- 网盘换直链、URL 长度恰好不变 → 误判为同内容，**更新丢失**；
- URL 长度变了 → 判为不同内容 → 退让到多版本命名
  `标题 (年份) - S01E01 - 1080p.strm`，**库里堆出重复条目**。

多版本语义对 strm 同名冲突是错的：同一集的 strm 换了 URL 是**更新**，
不是新版本（真的多版本会因分辨率不同而文件名不同，走不到同名冲突）。

**解法**：`.strm` 走内容比对（几百字节，读全文无压力）——

- 内容相同 → 静默幂等（现状语义不变）；
- 内容不同 → **原地更新**（写 `.part` 后 `os.replace` 原子替换），台账
  `file_mtime_ns`/`size_bytes` 随迁，结论文案记"已更新 N 个播放链接"。

`os.replace` 只对 strm 开放；普通视频的 `os.link` 原子防覆盖语义不变。

### 9.5 回流侧识别只能靠文件名

`_ingest_entry` 的 `if imported and staging is None`（`ingest.py:812`）——
中转目录不写 NFO。上传网盘后 strm 树里也就没有身份声明，规则2 只能走
`guess_evidence` + `verify_resolve` 的文件名识别链。

文件名是规范的（v2 的命名同源保证），识别命中率高，但不如 NFO 确定。

**解法**：中转目录写**条目级身份 NFO**（`write_entry_nfo`，内含 tmdbid），
随 strm 树回流后被 `_identify` 的 NFO 优先分支零歧义命中
（`ingest.py:919-932`）。

注意**只写身份 NFO，不调 `ensure_assets`**——2.1"过客不生成资产"的理由
是"入账只会制造缺失告警"，那指的是海报/thumb 图片资产；身份 NFO 是几 KB
的文本，不产生告警，且是回流识别的关键。二者本就是两个函数，分开即可。

**这是优化不是依赖**：strm 生成工具若不镜像 `.nfo`，回落文件名识别，
链路仍然可用。配方页会说明"建议开启 nfo 同步"。

## 11. 行为定义

### 11.1 投递查找链

`resolve_dispatch_rule` 的三级查找**全部加上 `accepts_dispatch == True`
过滤**，级次与顺序不变（目标库专属 → 同 kind auto → 同 kind 自定义目录）。

三级都无命中时返回 None（现状：回落下载器默认目录）。这意味着用户如果
**只**配了回流规则、没配投递入口，订阅会退回下载器默认目录而非报错——
符合"路由永不失败、绝不阻断投递"的铁律（`library-routing.md` 铁律 2），
链路体检负责把这个降级说清楚（11.5）。

### 11.2 每 kind 一条的限制随之放宽

现有校验"每 kind 至多一条 auto 规则 / 至多一条自定义目录规则"
（`import_watch_config.py:198-217`、`:242`）的**唯一理由**是查找链取一条、
落点不能歧义。`accepts_dispatch=False` 的规则不参与查找链，该理由不成立。

**改为只统计 `accepts_dispatch=True` 的规则。** 这条放宽是必需的而非顺手：
客户若已有一条直接入库的 auto 规则（老配置），不放宽就**建不出回流规则**。

不接受投递的规则可以同 kind 多条（多个网盘各自一个回流目录是合理布局）。

### 11.3 strm 接纳、门禁与更新

见 9.2 / 9.3 / 9.4。补充两条边界：

- `_IGNORE_MARKERS`（sample 过滤）与 `IN_PROGRESS_MARKERS`（`.part` 等）
  对 strm 同样生效，不特例；
- strm 条目的 `LibraryFile` 规格列（resolution/codec/duration…）全部留空，
  与库扫描收 strm 的既有事实一致，不新增字段、不发明"网盘条目"分类。

### 11.4 幂等、时序与工单闭环（均已验证，无需改动）

| 环节 | 结论 |
|---|---|
| strm 工具**全量重建** | 重建改 mtime → 指纹变（`_snapshot` 的"总大小:文件数:最大mtime"）→ 重新处理 → 9.4 的内容比对判定为同内容、静默幂等；URL 真变了则原地更新。不堆垃圾 |
| 稳定窗口 | 回流条目匹配不到下载器种子（目录名是规范名，种子名是 PT 原名）→ 无 `verdict` → 走启发式：同指纹静默 `QUIET_SECONDS`（300s）才处理。**回流有约 5 分钟延迟，这是正确行为**（strm 工具批量写入期间不该抢跑） |
| 订阅工单关闭 | 规则2 目标是库 → 走 `ingest.py:812-822` 的 `close_fulfilled_wanted`。**工单在 strm 入库时关闭**，与 2.3"库里有才算完成"的在途语义一致，无需改动 |
| info_hash 认领 | 回流条目无 info_hash 匹配（种子 save_path 是 `/downloads`），自然走识别链。9.5 的 NFO 让它精确 |
| 库根 watchdog | 规则2 把 strm 搬进库根会触发 watchdog 去抖扫描；ingest 已在搬运时写 `library_file` 台账，扫描幂等空跑 |

### 11.5 校验与链路体检

**校验**（`import_watch_config`，保存时前置中文报错）：

- 源目录唯一、不与任何库根重叠、不与任何 `target_path` 重叠：**全部不变**。
  这套既有校验恰好保护了本链路——用户若把 strm 生成到 `/staging` 下会被
  拦下（防成环），提示改到独立目录；
- 同盘检测：回流规则若选硬链接，仍按 auto 规则的现有口径对该 kind 全部
  路由可达的库根逐一检测。**配方推荐「复制」**——strm 是几百字节文本，
  复制成本可忽略，且行为可预测（硬链共享 inode，外部工具删除重建时 inode
  会断，反而不可预期）。

**链路体检**（`subscription/health.py`）：`_transfer_checks` 的同盘锚点
逻辑（`:174-175`）不变。步骤条在"外部流转"节点后增加一个**回流节点**：

- 存在同 kind、`accepts_dispatch=False` 且目标为库/auto 的规则 → 绿：
  "外部工具生成的 strm 放入 `/reflow/tv` 后，将自动路由入库"；
- 不存在 → 黄（降级而非错误）："未配置回流入口，strm 需自行放入库根，
  由库扫描入账"——这是 v2 的现状路径，仍然可用，只是没有二级分类；
- 投递查找链因 `accepts_dispatch` 全为 False 而落空 → 红："没有接受下载
  投递的监听目录，种子会落到下载器默认目录且不会自动整理"。

## 12. 交互设计

- **监听导入表单**：目标选择下方增加开关「接受下载投递」（默认开），
  说明文案按场景而非玩法（1.3）：

  > 关闭后，订阅与手动下载不会把种子投递到这个目录。适合目录内容来自
  > 外部流转（如其他工具生成、人工放入）而非下载器的场景。

- **监听导入清单**：关掉该开关的规则在卡片上标注"仅接收外部内容"，
  避免用户困惑"为什么种子没下到这里"；
- **用户手册「常见玩法」**：网盘 strm 配方页从"一条规则"升级为完整三段
  链路（两条规则的完整字段值 + 外部工具需开启 nfo 同步 + 推荐复制策略 +
  12.1 的已知边界），这是本设计唯一出现"网盘/strm"词汇的地方；
- **库表单 / 库卡片**：**无变化**。

### 12.1 必须写进配方页的两条已知边界

1. **库根 strm 是副本，删除不同步**：网盘删文件后，外部工具会删掉
   `/reflow` 里的 strm，但库根那份是 movieclaw 复制过去的独立文件，不会
   跟着消失——Emby 里会留下一个点开即失效的条目。v2 的现状路径（strm
   直接生成到库根）没有这个问题，这是换取二级分类付出的代价。
   `auto_clear_missing` 救不了（文件在，只是 URL 失效）。
   处理姿态同 6.2"回流断链无原生提醒"：v3 接受并写进文档；反馈强烈再考虑
   给规则加"源删则目标删"的镜像语义（那是新概念，不为假想需求先付）。
2. **回流有约 5 分钟延迟**（11.4 的静默窗口），不是故障。

## 14. 决策记录（2026-08-06）

1. **二级分类放到回流那一跳做**，不强求中转目录镜像库根结构——中转只是
   上传缓冲区，没人从那里播放；
2. **推翻 6.1 的"落点模板"开口**：模板是三个备选里唯一引入新语法的；
   `source_path` 唯一索引让"回流规则按库拆多条"结构上不成立（8.2 表）；
3. **维持决策 2**（库模型不承载转移关注点）：v3 全部改动落在监听导入层与
   ingest 引擎，`library` 表零改动；
4. **`accepts_dispatch` 是能力中性的开关**，不是 strm 专用旗标——语义是
   "本目录内容是否来自下载器"，任何外部投放场景通用；
5. **strm 同名冲突 = 更新而非新版本**，原地 `os.replace`；多版本语义只对
   真实媒体文件保留；
6. **中转写身份 NFO 但不写图片资产**："过客不生成资产"的理由是缺失告警，
   身份 NFO 不产生告警且是回流识别的关键；
7. **删除不同步接受并文档化**（12.1），不发明镜像语义。

## 15. 风险与开口

1. **外部工具不镜像 `.nfo`**：回落文件名识别，链路仍通（9.5 是优化不是
   依赖）；表现为个别条目识别不准，走既有的人工认领；
2. **用户关错开关**：把唯一的投递入口关掉 → 种子落下载器默认目录。体检
   红项直指此项（11.5），且不阻断投递（铁律 2）；
3. **strm 内容比对的成本**：每次重处理读全文。strm 数百字节、且只在指纹
   变化后触发，可忽略；真出现超大 strm（非法内容）由 scheme 校验先挡下；
4. **v4 开口**：若"删除不同步"反馈强烈，在监听导入层加"镜像模式"（源删
   则目标删）——顺着分层走，不碰库模型。
