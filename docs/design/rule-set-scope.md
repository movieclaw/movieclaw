# 规则组适用范围：订阅时按作品自动选规则组——设计

> 状态：v1 已实施（2026-09-24）。
> 关联文档：[library-routing.md](library-routing.md)（媒体库收藏范围，本文复用其
> 条件结构与求值器）、[quality-upgrade.md](quality-upgrade.md)（规则组与洗版）、
> [member-management.md](member-management.md)（成员订阅用自动结论）。

## 0. 问题与方案

**问题**：规则组不分电影和剧集，全站只有一个默认组。电影和剧集要的品质往往
不一样（电影追 4K，剧集 1080p 控体积；日韩动画要指定压制组……），用户每次订阅
都得在弹窗里手选一遍。

**方案**：**规则组自述适用范围**。规则组新增 `match_rules`，声明"本组适用于
什么作品"；新订阅未显式指定规则组时，在全部规则组里找适用范围命中的那个，都不
命中落默认组。这与媒体库「库自述收藏范围」是同一个心智模型——用户学过"库收
什么"，"规则组管什么"就是同一套界面、同一套文案、同一种兜底逻辑。

**"按类型分默认"是它的特例**：只写「剧集」一个条件的组，就是剧集的默认组。
所以不另设 `is_default_movie/is_default_tv` 两列——两套默认机制并存会出现
"徽标说是默认、实际用的是另一个"的歧义。`is_default` 保留原义：兜底组。

否决的方向：

- **规则组加 kind 字段做成电影专用/剧集专用**：会逼用户把通用规则复制两份，
  还要处理"订阅类型与组类型不符"的边界；
- **AppSetting 里存 `{movie: id, tv: id}`**：不用迁移，但与 `is_default` 形成
  两套默认机制（quality-upgrade.md §3.2 当初正是为避免双机制才定了"改默认组
  即改全局"）；
- **规则组跟着媒体库走（库绑组）**：存储位置与画质要求是两个正交的问题，
  绑在一起会逼没分库的用户为了画质去建库。

## 1. 模型

`rule_set.match_rules`：JSON 条件列表，默认 `[]`。

```json
// 日韩动画：剧集 + 日韩 + 动画
[
  {"field": "kind",             "op": "any_of", "values": ["tv"]},
  {"field": "origin_countries", "op": "any_of", "values": ["JP", "KR"]},
  {"field": "genres",           "op": "any_of", "values": [16]}
]
```

| 约定 | 内容 |
|---|---|
| 字段 | `kind`（movie/tv）+ 媒体库收藏范围的全部字段（v1：`genres` TMDB 类型 ID、`origin_countries` 国家码） |
| 条件间 / 条件内 | AND / any_of（同库路由） |
| 特异性 | 条件条数；多组命中时多者赢，打平取 `id` 小者（创建早优先） |
| kind 双选 | 电影+剧集 = 不限，写入时丢弃这条条件（否则白白抬高特异性） |
| 空列表 | 未声明——只能手选，或作为默认组兜底 |
| 元数据缺失 | `kind` 永远已知，只写类型的组照样命中；其余条件保守不命中 |

校验复用 `validate_match_rules`（报错名词换成「适用范围」），求值复用
`evaluate`、命中理由复用 `hit_parts`——库路由与选组的口径同源。

## 2. 选组：`RuleSetService.pick(kind, facts)`

三条铁律照搬库路由：

1. **只决定默认值**：订阅弹窗预选、用户可改；已有订阅的挂靠永远不动（改适用
   范围不追溯，与"改默认组不改既有订阅"同理）；
2. **永不失败**：未命中、元数据拿不到都落默认组；
3. **全程可解释**：`reason` 是整句中文——"按适用范围选用「日韩动画」：剧集、
   区域=日本、类型=动画"。

消费点：

- **订阅创建**（`SubscriptionService.create`）：`rule_set_id` 缺省时选组，
  与选库共用同一份作品事实（`RouteDecision.facts`，不重复装配）；命中时理由
  写进"已创建"活动。成员订阅、API/CLI/Agent 直接创建、媒体库"补下缺失"都走
  这条路径；
- **投递预检**（`/subscriptions/download-routing-preview`）：与库路由同条件
  （未指定库且带 tmdb_id）返回 `rule_set_id/name/matched/reason`。订阅弹窗据此
  预选并显示「自动选组：…」徽标，用户改组即消失；设置页「模拟一单」多一步
  展示选中的规则组。弹窗提交时带的是显式 `rule_set_id`，所以经弹窗创建的订阅
  活动里不重复写选组理由（与库路由一致）；
- **洗版变体弹窗**：只在带洗版目标的组里选，适用范围结论组不带目标时退回默认
  组/第一个候选。

## 3. 交互

- **规则组编辑器**：名称下方新增折叠段「适用范围」（折叠头显示当前范围摘要）：
  作品类型三选一（不限/电影/剧集）+ 复用媒体库表单的区域/类型 chips
  （`ScopeEditor`，kind 为不限时类型取电影与剧集两表并集）；
- **规则组列表**：有适用范围的组显示「适用：剧集 · 日韩 · 动画」徽标；
  「设为默认」的含义改为"都不匹配时用它"；
- **复制**不带适用范围：两个范围一模一样的组只有更早的那个会被选中。

## 4. 兼容

- 迁移 `b6e2d8f4a193`：纯新增带默认值的列。回退旧版本后新订阅退回"一律默认
  组"，适用范围配置原样保留，再升级即恢复；
- API：`RuleSetPayload.match_rules` 创建缺省=不声明，**更新缺省=不改**
  （老客户端/CLI 只改 spec 时不会清空范围），传 `[]` 才清空。

## 5. 开口

- 维度扩展随库路由：年代（老片没有 4K，追 2160p 只会一直等）需要区间算子，
  是 v2 最值得加的；导演/公司/系列同库路由 v2；
- 范围重叠提示：库路由有"同特异性重叠"只读警示，规则组 v1 未做，靠「模拟一单」
  验证；真实使用里出现困惑再补。
