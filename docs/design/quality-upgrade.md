# 洗版功能设计方案

> 状态：**已实现**（P6，§10 七个 Phase 全部落地）。前置调研见
> `quality-upgrade-research.md`（Sonarr/Radarr/MoviePilot/nas-tools 的机制拆解
> 与真实用户反馈），本文不重复论据，只引用结论。行文沿用 `subscription.md`
> 的惯例：每节先给结论（决策），再给理由与被否掉的备选。
> 实现与设计的两处已确认落差记录在 §12。

## 0. 目标与反目标

**产品目标**（按优先级）：

1. **零新概念**：不给用户引入"打分 / Custom Format / cutoff 分数"等任何新词。
   用户已经认识的概念只有：订阅、规则组、分辨率、片源（WEB-DL/蓝光/Remux）。
   洗版设定必须完全落在这些既有概念里。
2. **三层用户，渐进披露**：
   - 默认层：什么都不配，行为正确（默认不洗版，收齐即止）；
   - 简单层：想洗版的用户做**一次选择**（"洗到哪一档"），之后无人值守；
   - 高级层：深度用户用规则组既有的全部维度（制作组白名单、HDR、体积……）
     组合出精细玩法，不需要任何洗版专属的高级机制。
3. **全程可解释**：当前版本是什么档、目标是什么档、差几档、为什么某个候选
   没有被拿来洗，用户在详情页一眼看懂。

**架构目标**（吸取调研教训，编号对应 research §5.1）：

| # | 教训 | 本设计的对策 |
|---|---|---|
| 1 | arr 双轨 cutoff 语义分裂是最大共性痛点 | 洗版只有**一条档位阶梯、一条停止线**（§2） |
| 2 | 微小分差触发重下（arr 补 Increment 才治好） | 用**离散档位**代替连续分数，档位不升不洗，天然免疫抖动（§2.3） |
| 3 | 抓取与导入两次判定不一致 → 无限循环 | 基线快照单调递增、只在确认升级时刷新 + 证伪候选进排除清单（§4.3、§6.3） |
| 4 | "为什么抓/不抓/又抓"是两边社区高频求助 | 复用活动时间线 + 单元级"当前档→目标档"派生展示（§8.4） |
| 5 | 策略外包给 TRaSH 生态的代价 | 洗版目标就是 3 个内置档位选项，**没有需要抄的配置**（§8.2） |
| 6 | 洗版烧 ratio / 断种被封号 | 旧任务清理**复用换源的所有权/H&R 保护状态机**（§7.2） |

**反目标（第一版明确不做）**：

- 不做同档位内的"更好版本"替换（同为 1080p Remux 换官组）——这是 arr
  Custom Format 的深水区，需要组偏好序与组内打分，复杂度与收益不成比例。
  制作组白名单作为硬过滤依然生效（想只要官组：白名单 + 洗版目标即可组合出
  "洗到官组 Remux 为止"）；
- 不做 Proper/Repack 追新；
- 不做 HDR/DV/编码维度的档位升级（作为硬过滤继续生效：`hdr=require` 的规则组
  从第一次下载起就只接受 HDR，不存在"先 SDR 后洗 HDR"的路径，见 §11 开放问题）；
  **§14 起改为可选参与**——缺省仍不参与，用户显式把维度加进 `upgrade_ladder`
  才生效，简单层体验不变；
- 不做 per-订阅的洗版参数覆盖（理由见 §3.1）；
- 不做电影多版本长期共存的收藏家模式（`library_file` 天然支持多行，留给未来）。

## 1. 一句话设计

**洗版 = 规则组里的一个字段（"洗到哪一档为止"）。** 订阅收齐后，若规则组配了
洗版目标且某单元的当前版本档位低于目标，被动匹配和低频主动搜索会继续为它找
**严格更高档位**的候选；新版本走既有投递→下载→入库管线，入库成功后旧版本进
回收站、旧下载任务按换源同款规则安全清理；单元到达目标档位后自然安静。
订阅的"已收齐"语义不变。

数据流总览（只标注新增/改造点，其余全部复用现状）：

```
规则组 spec ──── upgrade_source / cutoff_resolution（新字段，§3.2）
                     │
被动匹配（主通道）    │         主动搜索 worker（低频兜底）
evaluate_and_dispatch ┴─ 缺口单元：现有逻辑不变
                      └─ 洗版单元（新）：imported ∧ in_scope ∧ 快照档位 < 目标档位
                              │
                    规则组硬过滤（复用 evaluate_rules）
                              │
                    排除清单（新，§4.3：该单元既往证伪的候选不再抓）
                              │
                    档位比较 compare_upgrade（新纯函数，§5）
                       candidate.rank > snapshot.rank ？
                              │ 是
                    dispatch 投递（复用，attempt 标记洗版语义，§6.2）
                              │
                    下载完成 → 监听导入 → ffprobe 实测 → 洗版验证（§6.3）
                       实测档位 > 当前快照 → 确认升级：替换旧版本、
                         刷新 wanted.quality 快照、写 UPGRADED、旧版清理（§7）
                       实测档位 ≤ 当前快照 → 证伪：不替换，该候选进排除
                         清单，写验证失败活动，连续证伪触发熔断（§6.3）
```

## 2. 核心概念：档位阶梯（唯一的序，唯一的停止线）

### 2.1 结论

> §14 起，本节的二元组是 N 维阶梯在 `upgrade_ladder=["resolution","source"]`
> 时的特例（也是缺省值）。下面的全部性质——离散、字典序、单一停止线——
> 在推广后原样成立。

洗版比较使用一条**二元组字典序**的档位阶梯：

```
rank = (分辨率位次, 片源档)          # 字典序比较，分辨率严格优先

分辨率位次：规则组 resolutions 列表的偏好顺序（第一位最高）；
           未配置时用内置默认序 2160p > 1080p > 720p
           （与 rules._DEFAULT_RESOLUTION_SCORE 同源）

片源档（source tier，内置固定，不暴露配置）：
  T5  Remux            （attrs.remux=True）
  T4  Blu-ray 重编码    （Blu-ray / UHD Blu-ray，remux=False）
  T3  WEB-DL
  T2  Rip 类           （WEBRip / BDRip / HDRip / DVDRip）
  T1  TV 录制类        （HDTV / TVRip / DVD）
  ——  未知             （不可比，见 2.4）
```

**升级判定**：`rank(候选) > rank(当前快照)` 严格成立才算升级。
**停止判定**：`rank(当前快照) ≥ rank(洗版目标)` 即到顶，不再调度。
洗版目标 = `(cutoff_resolution 或 resolutions 首选, upgrade_source)`，见 §3.2。

### 2.2 为什么是"分辨率 × 片源"二元组，而不是别的

- 这两个维度是**用户讨论"版本好坏"时实际使用的语言**（"1080p WEB-DL"、
  "4K 原盘"），也是种子侧（enrich）与文件侧（probe/enrich）都能可靠拿到的字段
  （两侧字段对齐度分析见 §4.2）；
- 分辨率位次取自规则组已有的 `resolutions` 偏好序，**复用了用户已经表达过的
  偏好**——想"1080p 优先于 2160p"的用户（省空间党）调整既有列表顺序即可，
  洗版自动跟随，不需要 arr 那种 merge-quality hack；片源位次同理，实现期补齐的
  `media_sources`（§3.3）让"优先 WEB-DL 而不是蓝光"也走同一条路；
- 字典序 = 单一全序 = 每次比较可以用一句中文解释（"候选是 1080p WEB-DL（T3），
  当前已是 1080p 蓝光（T4），不构成升级"）。

**被否备选：连续打分 + 分数 cutoff（arr 式）。** 打分的表达力上限更高，但调研
显示它是复杂度和不可解释性的主要来源（用户看不懂 1001 分为什么洗 1000 分），
还需要 Increment 字段打补丁。movieclaw 的评分公式（free/做种/分辨率）继续只做
**候选间选优**，不参与"是否构成升级"的判定——促销和做种数是"现在下谁划算"，
不是"这个版本更好"，两件事分开。

**被否备选：把 HDR/编码纳入阶梯（三元组、四元组）。** 每加一维，"为什么不
洗"的解释难度翻倍，且文件侧与种子侧的 HDR/编码字段命名空间不一致（§4.2），
第一版先不背。HDR 用户用 `hdr=require` 硬过滤从源头保证。

### 2.3 离散档位天然免疫抖动

arr 的 "+1 分洗整部" 问题根源是连续分数上任何正差值都算升级。档位阶梯下，
同档位内的任何差异（不同制作组、不同体积、免费与否）都**不触发**洗版，
不需要"最小提升步长"这类补丁概念。

### 2.4 未知不可比——但只在未知的维度上（三态铁律 + 部分可比）

沿用 `matcher/rules.py` 的三态原则与换源 `quality_not_lower` 的既有立场
（"未知不是最低品质"），并加一条部分可比规则：**字典序逐位比较，首个双方
都已知且不同的维度即可定序；只在能证明的维度上行动。**

> §14.4 对本节有一处修订：**双方都未知的维度视为该位平局、继续比较下一位**
> （现实现会直接判不可比）。单侧未知仍然一律判否，三态铁律不变。

- **候选**分辨率未知 → 不参与洗版（拒绝码 `upgrade_not_comparable`）；
  分辨率已知但片源未知 → 只能构成分辨率维度的升级（片源位按未知处理，
  无法证明"更好"的比较一律判否）；
- **当前快照**整体缺失 → 该单元不参与洗版，详情页如实标注
  "无法识别当前版本，洗版未启动"（而不是把未知当最低档乱洗）；
- 快照分辨率已知、片源未知（常见于手工入库文件，§4.4）→ 仍参与**分辨率
  维度**的洗版：候选分辨率位次严格更高即构成升级；同分辨率的片源升级
  因无法证明而不发生；
- 调度口径同理：只有**可证明低于洗版目标**的单元才参与排期——快照已到
  目标分辨率但片源未知的单元不再调度（证明不了"还差着"，就不打扰站点）。

## 3. 配置模型：洗版设定住在规则组里

### 3.1 结论：规则组是洗版策略的唯一家，订阅不加开关

- 规则组 spec 新增洗版目标字段（§3.2）；**目标为空 = 不洗版**，即默认行为；
- 订阅通过 `rule_set_id` 继承洗版设定，**不新增任何订阅级字段**；
- 想给某部剧单独的洗法 → 换/复制规则组（既有哲学："想微调就复制一个规则组"，
  `rule-sets-panel.tsx` 文件头注释明示；换组弹窗 `RuleSetSwitchDialog` 已存在）。

理由：

1. 规则组的职责边界（`rule_set.py` docstring）本来就是"什么可接受 + 谁更好，
   预留洗版 cutoff"——"好到什么程度为止"是同一职责域的自然延伸；
2. 全局默认 + 订阅覆盖的诉求（MoviePilot 的批量配置痛点）被规则组机制**原地
   解决**：改默认规则组 = 改全局默认，换组 = 单订阅覆盖，零新机制；
3. 避免"策略有两个家"（arr 的 Upgrades Allowed 开关在 profile、Propers 开关在
   Media Management、体积上限在 Quality Definitions，用户找不到北）。

**被否备选：订阅详情页"更多"菜单加洗版开关（与"自动续订"并列）。** 语义上
诱人（都是订阅的可选延长阶段），但它会制造第二个策略家：开关在订阅、目标在
规则组，用户要在两处拼出完整心智。且 MoviePilot 的教训恰恰是逐订阅开关带来
批量操作冗余。订阅详情页只做**展示与解释**，不做配置（§8.3）。

### 3.2 `RuleSetSpec` 字段（`src/movieclaw_matcher/models.py`）

```python
# 洗版（P6 启用；两个字段都缺省 = 不洗版）
upgrade_source: str | None = None
    # 洗版目标片源档："web-dl" / "blu-ray" / "remux"
    # None = 不洗版。这是用户在 UI 上做的那"一次选择"。
cutoff_resolution: str | None = None
    # 洗版目标分辨率（已预留字段，正式启用）。
    # None = 取 resolutions 列表首选；resolutions 也为空时取 "1080p"
    # （保守缺省：不因洗版把用户从 1080p 意外带进 4K 的磁盘占用，
    #   对应调研里 44GB Forrest Gump 的教训）。
sites: list[str]        # 维持预留，本期不动
```

校验：`upgrade_source` 只接受三个枚举值；`cutoff_resolution` 必须出现在
`resolutions`（若后者非空）——洗版目标不能是规则组自己都不接受的分辨率；
同理 `upgrade_source` 必须出现在 `media_sources`（若后者非空，见 §3.3）。

### 3.3 `media_sources`：片源不再只是洗版的附属（实现期补齐）

**缺口**：片源原本只以"洗版终点档"（`upgrade_source`）和阶梯上的一位存在，
于是**不洗版就表达不出片源偏好**——"只要蓝光/WEB-DL""优先蓝光"都写不出来。
分辨率、编码、平台、HDR 全都有"白名单 + 偏好序"，唯独片源没有，这是实现期
才暴露的不对称。

```python
media_sources: list[str] = []
    # 允许的片源档，值域 MediaSourceTier：
    #   remux(T5) / blu-ray(T4) / web-dl(T3) / rip(T2) / tv(T1)
    # 顺序即偏好；空 = 不限片源（存量规则组零变化）
```

四个决定：

1. **单位是"档"不是词表原值**。用户谈论版本时说的就是"蓝光""WEB-DL"，
   档内写法差异（Blu-ray / UHD Blu-ray）实际由分辨率那一维表达；按档还天然
   免疫词表演进——新增写法自动落进已有档。前三档与 `UpgradeSource` **刻意
   同值**，两个字段说同一种语言才能互相校验；
2. **过滤口径与分辨率一字不差**：配了就只接受这些档，且**识别不出片源的
   资源被排除**（`media_source_unknown`），保守方向 + 如实说明原因，UI 提示
   与分辨率同款（"可用「手动选种」兜底"）；
3. **偏好序参与候选选优**（`rules._score`，片源 20 分/档 < 分辨率 30 分/档）。
   这是它与编码/平台/HDR 的区别：那三维的顺序只在洗版阶梯上有意义（§14.11
   步骤 1 的既定决策，避免改变存量缺口选优），而分辨率与片源是 §2.2 认定的
   两个主轴，值得进选优。**只在显式配置时生效**——没配就是"不限片源"，任何
   内置片源序都是替用户做主张；
4. **配了之后，洗版阶梯的片源位次改由用户序决定**（`media_source_rank`）。
   省流党把 WEB-DL 排在蓝光前面，洗版与选优就都按他说的算，与 §14.3
   "偏好即优先级"对编码/平台/HDR 的处理一致。**白名单外的档位次未知
   （不可比），不当最低档**——与 `_resolution_ladder` 同一取向：把"白名单外"
   一律当最低，会让 `[web-dl, blu-ray]` 这种倒序偏好把已入库的 Remux 判成
   最低档而白洗一次，那是删掉更好的文件。唯一例外是 T0 哨兵（人工标注
   "按最低档"），它的语义就是"低于一切"，保留可比。

UI：`RuleSetEditorDialog` 里「片源」与「分辨率」并排放在最外层（两个主轴，
且片源必须排在洗版之前——终点档只能从这个白名单里挑）；收窄白名单把终点档
排除在外时，直接清掉终点而不是留到保存时报错。

**修改不追溯已 grabbed** 的既有约定继续适用；修改规则组的洗版目标对"洗版中"
单元的影响是幂等重算：目标降低/清空 → 已达标单元自然停止调度；目标升高 →
下个调度周期继续洗。无需任何迁移动作。

## 4. 质量快照：实测优先，一次固化

### 4.1 结论：抓前相信种子命名，入库后实测覆盖一切可测维度

原则一句话：**抓取决策只有种子名可用（没下载之前无法 ffprobe），如实采信；
文件一旦落地，能实测的维度一切以 ffprobe 为准，实测不出的出处维度采信
名称解析。** 没有任何阈值启发式。

```python
# wanted_item 新增列
quality: dict | None    # 满足该单元的当前版本质量快照（QualitySnapshot）
                        # NULL = 未满足或无法识别；洗版比较的唯一基线
```

`QualitySnapshot` 各字段的取值来源（值域统一归一到 enrich 词表）：

| 字段 | 来源 | 理由 |
|---|---|---|
| `resolution` | **ffprobe 实测**（宽度判据，`media_probe` 现成能力） | 物理真相；升频/标称虚高一测便知，这是档位阶梯的第一比较位，必须是真的 |
| `hdr` | **ffprobe 实测**（`Dolby Vision`→`DV` 等归一映射） | 物理真相；仅展示用，但展示也不该撒谎 |
| `media_source` / `remux` | 名称解析（`attempt.quality` 或文件名 enrich），如实采信 | 出处不是物理属性，测不出来，名称是唯一来源；残余风险见 §4.2 |
| `release_group` | 名称解析 | 仅展示 |
| `bit_rate` | ffprobe 实测 | 留证据：随快照留存并在详情页展示，片源标称的真伪最终留给人眼判断 |

### 4.2 为什么不能只信种子名，以及接受哪些残余风险（设计修正记录）

早先方案曾考虑"快照直接取投递时的 `attempt.quality`（种子名解析）、比较
永不二次解析"来防循环。这个方案有一个不可接受的暴露面：**种子名会撒谎**——
标称 2160p 实为 1080p 升频时，名称基线把单元记到高档，洗版从此永久停止，
用户以为库里是真 4K。谎言骗到的不是一次下载，是永久的台账。因此可实测
维度必须以实测为锚，防循环改由 §4.3 的机制承担。

**明确接受的残余风险：片源维度的标称造假机器无法证伪。** 标称 Remux 实为
二压时，probe 测不出出处，快照会如实记为 Remux 并让该单元提前"到顶"。
接受它的理由：① 分辨率/HDR 这两类最常见、最伤的虚标已被实测全覆盖；
② 有审核的 PT 站片源标称造假罕见（命名规范是站规）；③ 被骗的代价有限且
可恢复——一次多余下载 + 该单元停洗，详情页展示实测码率（"Remux · 9 Mbps"
一眼即知有诈），删除该版本文件即可恢复洗版；④ 机器证伪片源只能靠码率阈值
启发式，动画/纪录片等低码率内容天然不稳，错杀比放过更伤信任。若真实运行
数据显示此类造假成规模，再评估引入（§11）。

（摸底确认的两侧字段差异——`hdr` 命名（`DV` vs `Dolby Vision`）、
`video_codec` 命名空间（enrich 词表 vs ffprobe `codec_name`）——由快照写入
时的归一映射层消化，映射表进 matcher 并单测锁死。）

### 4.3 防循环的真正机制：基线单调 + 证伪排除

实测基线意味着"抓取按名、导入按实测"两次判定天然可能不一致——这正是 arr
至今未根治的死循环场景（Radarr #11422：抓了 → 导入判定不是升级 → 拒收 →
下次搜索又抓同一个）。防循环不靠回避实测，靠三件事：

1. **基线单调递增**：快照只在"确认升级"时刷新（§6.3），其余任何事件都不动
   它——同一候选第二次出现时，比较结果与上次必然相同；
2. **证伪排除**：实测验证失败的候选记入该单元的排除清单（复用换源"已试过
   候选排除"的 attempt 历史模式，零新表），同一个撒谎 release 不会被抓第二次
   ——arr 缺的正是这一层。每个假资源最多付一次下载代价，判定收敛。

### 4.4 手工入库与存量回填

- 手工入库/扫描收编的文件：`resolution`/`hdr`/`bit_rate` 走 probe（`library_file`
  已存，零额外成本），出处维度对文件名跑 enrich 解析；文件名信息尽失时
  出处记未知，单元仍可参与分辨率维度洗版（§2.4）；
- 存量回填：规则组首次配置洗版目标时，引用它的订阅存在 `quality IS NULL` 的
  imported 单元 → 排入一次性回填任务。所需数据（probe 各列 + `media_source`/
  `release_group`）`library_file` 里都有，**回填是纯 DB 变换，不重新探测文件**；
  后台 tick 逐批做，不阻塞规则组保存。

## 5. 决策引擎：`decision.py` 终于有了正文

新增纯函数（延续 matcher 无 IO、表驱动单测的约定）：

```python
# movieclaw_matcher/decision.py

def upgrade_rank(snapshot_or_attrs, spec) -> tuple[int, int] | None:
    """算档位 rank=(分辨率位次, 片源档)；关键维度未知返回 None（不可比）。"""

def compare_upgrade(candidate, snapshot, spec) -> UpgradeVerdict:
    """洗版判定。三个否定出口 + 一个肯定出口，reason_text 为完整中文句：
       - upgrade_not_comparable   候选/快照关键维度无法识别
       - upgrade_at_cutoff        当前版本已达洗版目标
       - upgrade_not_better       候选档位不高于当前版本
       - accepted                 构成升级（附 from/to 档位中文标签）
    """
```

片源档映射表放在 matcher 内（值域对齐 `movieclaw_enrich/vocab.py` 的
`MEDIA_SOURCE`），**补全换源 `_SOURCE_RANK` 缺失的 BDRip/HDRip/DVD 档**；换源的
`quality_not_lower` 后续可迁移到这张表上（见 §10 Phase 5），消除两套片源序。

接线（`services/subscription/matching.py`）：

- `load_match_context` 除缺口外，加载"洗版单元"：
  `status=imported ∧ in_scope ∧ quality 非空 ∧ rank(quality) < rank(目标)`
  ∧ 该单元当前没有在途的洗版 attempt（§6.2 去重）
  ∧ 未触发证伪熔断（§6.3）；
- `evaluate_and_dispatch` 第一遍对洗版单元的判定链：
  身份匹配 → `evaluate_rules`（硬过滤照旧，免费/做种/体积/黑白名单全部生效）
  → **排除清单**（该单元既往证伪的候选直接跳过，§4.3）
  → `compare_upgrade`；
- 第二遍选优不变：同一单元多个合格升级候选，按既有 `(is_pack, score, seeders)`
  排序——评分公式在这里发挥作用（同为升级候选时优先免费、做种多的），
  与"是否构成升级"的判定完全解耦；
- **整季包对洗版单元沿用 Sonarr 的铁律**：包覆盖的每个单元都必须"缺失 或
  构成合法升级"，任何一个单元判否即拒绝整包（`covered_units` 后逐单元判定），
  杜绝"为洗 3 集重下整季"。

**拒绝记录的噪音控制**（沿用"身份不匹配不记录"的既有粒度决策）：
`upgrade_not_better` / `upgrade_at_cutoff` 是常态而非异常——热门剧每个新种子
都会对洗版单元比较一遍——**不写活动**。可解释性由详情页的派生展示承担
（"当前 1080p WEB-DL → 目标 1080p Remux，已搜 3 次"，§8.4）；`upgrade_not_comparable`
按 MATCH_REJECTED 既有去重规则记录（这是用户需要知道的数据质量问题）。

## 6. 管线：状态机不动，洗版活在 attempt 层

### 6.1 结论：不重开工单，`wanted_item.status` 保持单调

`wanted_item` 的四个状态"每一步对应不可逆的现实事件"，且 imported 由库存对账
推导。若洗版把 imported 退回 wanted，对账会立刻看见旧文件在位又把它关回
imported——**状态机与真相源直接打架**。因此：

- 洗版单元的 `status` 始终是 `imported`；
- 洗版在途状态完全由 `subscription_download_attempt` 表达（该表按
  `(subscription_id, info_hash)` 建模，天然支持一个单元同时存在旧主源与洗版
  新源两条 attempt——换源已经验证过这个形态）；
- `in_scope` 语义不变，出范围的单元同时退出洗版。

**被否备选：新建 `upgrade_item` 表。** 与 wanted 单元 1:1 冗余，两张表同步
in_scope/调度字段，纯增熵。

### 6.2 投递与在途去重

- dispatch 复用现状；attempt 新增一列 `purpose: str`（`"download"` 缺省 /
  `"upgrade"`），用于：① 洗版在途去重（同单元至多一个洗版 attempt）；
  ② 活动与通知文案分流（写 `UPGRADE_GRABBED` 而非 `GRABBED`）；
  ③ 旧版本清理时定位被替换的旧 attempt；
- 洗版 attempt 的下载观察（心跳/死种/换源救援）**零修改复用**——洗版源死了
  同样走 replacement 救援，救援比较基线 `quality_not_lower` 用的正是 attempt
  自己的 quality 快照，语义自洽。

### 6.3 入库验证：实测说了算

监听导入发现洗版 attempt 的新文件 → **先 ffprobe 实测、按 §4.1 计算新快照**，
再决定去留（"trust by name, verify by probe"）：

```
新文件来自洗版 attempt（purpose="upgrade"）：
  rank(实测新快照) > rank(现有快照)
    → 确认升级：替换旧版本、刷新 wanted.quality、
      写 UPGRADED 活动（"S01E03 已洗版：1080p WEB-DL → 1080p Remux"）、
      触发旧版本清理（§7）、IM 推送复用 imported 通道（event="upgraded"）
  否则 → 证伪：
    - 新文件不入库、不替换旧版本，旧文件与快照原样不动
    - attempt 置 FAILED（记证伪原因），从此进入该单元排除清单（§4.3）
    - 写 UPGRADE_VERIFY_FAILED 活动
      （"S01E03 洗版候选证伪：标称 2160p，实测为 1080p，已排除该资源"）
    - 已下载数据与种子不立即删除，按 §7.2 同款保种规则处置（证伪≠可以 H&R）
    - 单元证伪计数 +1；连续 3 次证伪 → 该单元洗版转入 30 天长冷却，
      并出 system_notice 提示人工介入——防连环造假资源烧流量烧 ratio

新文件不来自洗版 attempt（手工入库/扫描收编）：
  实测更优 → 同样刷新快照并写 UPGRADED（手工升级是合法路径，实测为证）
  实测不优 → 仅收编为多版本文件，不动快照
```

证伪只会由**实测可抓的谎言**（分辨率/HDR 虚标）触发；片源标称造假按 §4.2
作为残余风险如实入账。排除清单保证"抓取判定与导入判定不一致"在结构上
**收敛**（同一候选最多付一次代价），而不是像 arr 一样循环。

**订阅 `completed` 语义不变**（收齐即"已收齐"）——洗版不计入
`recompute_subscription_status` 的开放条件。理由：目标版本（如 Remux）可能
永远不发布，若"到顶才算完成"（nas-tools 模式），订阅会无限期停在未完成态，
违背"内容收齐了"的用户心智。前端在 completed 且存在洗版单元时显示
"已收齐 · 洗版中"的复合态（§8.3），洗版全部到顶后自然回到纯净的"已收齐"。

### 6.4 调度：被动为主，主动极低频

- **被动匹配是洗版主通道**（对应 arr 的 RSS 比对模式）：新种子入库即评估，
  零额外站点成本——这决定了洗版的时效性天然够用，主动搜索只是兜底；
- 主动搜索复用 wanted worker 与 `next_search_at` 调度字段（imported 态下这组
  字段已闲置，语义文档化为"洗版搜索调度"）：
  - `priority = -10`（低于补旧 0 与追新 10，永远排在缺口后面）；
  - 专属退避曲线：`7d → 14d → 30d 封顶`（洗版不急，对 PT 站克制是铁律）；
  - 触发排期的时机：规则组配置/修改洗版目标（回填任务顺带排期，首搜分散在
    24h 内错峰）、订阅换到带洗版目标的组、单元完成首次入库且未达目标；
  - "立即搜索"按钮的语义扩展为同时覆盖缺口与洗版单元（不新增端点）。

## 7. 文件替换与做种保护

### 7.1 旧库文件：回收站兜底

> 演进：回收机制已升格为媒体库层的公共设施——`library_file`「待回收」
> 第三态 + 公共延迟删除，与订阅解耦、洗版只是触发方，含文件区可视化
> 与恢复/立即清理操作。完整方案见 `docs/design/library-file-recycle.md`，
> 本节保留首版实现的决策记录。

新版本确认入库（§6.3）后，旧版本的 `library_file` 行与物理文件处理：

- 物理文件移入 `data/trash/`（遵循"运行期数据全部落 `data/`"约定），
  保留 7 天后由既有清理 tick 删除；`library_file` 行标记删除原因后移除
  （不复用 `missing_since`——那是"意外消失"，这是"主动替换"）；
- 第一版**不暴露**"永久删除/保留并存"配置项，回收站是无条件的安全网
  （对应调研教训：误洗回退是刚需，arr 的 Recycling Bin 是唯一保险）；
- 库详情页多版本视图（`library_file` 多行天然支持）保留手动删除入口。

### 7.2 旧下载任务：复用换源清理状态机

洗版成功后，被替换的旧 attempt 进入换源既有的清理通道
（`cleanup_pending → superseded / retained`）：

- `owned_by_movieclaw ∧ 无 H&R 风险 ∧ 做种达标` → 删除下载任务；
- 否则 `retained` 保留做种（**洗版绝不制造 H&R**——这是对 PT 场景最重要的
  承诺，也是 arr 至今没有原生方案的缺口）；
- ~~下载目录与库文件是同一物理文件的部署（inplace 模式）：旧库文件不进
  回收站（`st_nlink == 1` 判据）~~——**2026-08-17 收敛为一律进回收站 +
  保留期倒计时**：复制入库部署下库文件 nlink 恒为 1，该判据必然全命中，
  回收站承诺形同虚设（NAS 实测 53GB 永久滞留）。回收站即安全网，想保留
  由用户「恢复」；inplace 部署的断种取舍由洗版 opt-in 副文案讲明，机制
  不再猜测。见 library-file-recycle.md §3 决策记录。

## 8. UX 设计

### 8.1 概念账本

用户视角新增的概念**只有一个**："洗版目标"（规则组里的一行 chips）。
新增术语对齐既有术语表：UI 用「洗版」（该词在 UI 中尚未被占用；
内部命名用 `upgrade`，**避开 `replacement`**——已被死种换源占用）。

### 8.2 规则组编辑器（唯一配置点）

`RuleSetEditorDialog` 新增一个 Field（复用既有 `Field`/`ToggleChip` 积木）：

```
洗版
  [ 不洗版 ] [ 洗到 WEB-DL ] [ 洗到蓝光 ] [ 洗到 Remux ]
  副文案：收齐后继续追更高版本，直到达到目标档位。新版本入库后
         旧版本进回收站保留 7 天，做种中的任务不受影响。
  （选中非"不洗版"时追加一行小字：目标分辨率 2160p——取上方
    分辨率偏好的第一位，可在高级里单独调整）
```

- 三个档位选项**就是内置预设**——不存在需要照抄的社区配置（教训 #5）；
- 副文案把后果讲在操作之前（回收站、做种安全），沿用既有文案风格；
- 高级层：`cutoff_resolution` 作为洗版 Field 展开后的次级选择（默认跟随
  分辨率偏好首选，绝大多数用户不需要碰）；
- `specSummary()` 新增芯片：`洗到 2160p Remux`——订阅创建弹层、换组弹窗、
  规则组清单**自动**获得洗版可见性，这是"让用户自然学会"的主路径：
  用户在任何看到规则组摘要的地方都会遇到这枚芯片。

**表单顺序：洗版排在最后一段**（实现期修正，原稿把它紧跟分辨率）。三个理由，
按分量排：

1. **依赖方向**——洗版的每一项都引用前面的维度：目标分辨率跟随分辨率偏好首项，
   洗版优先级里的 HDR/编码/平台三维只有在「画质与来源」配了偏好才生效（否则标
   「未配置」并被跳过）。排在前面等于让用户先配一个引用了下文的东西，那个
   「未配置」角标在用户还没走到那一段时就亮起来，读起来像 bug；
2. **与底部回执同向**——回执是"先这样筛掉不要的 → 再一级级往上洗"，表单顺序
   照此排列，配置动作与回执叙述才是同一条线；
3. **洗版是高级功能**（默认不开，§8.5），不该是新建规则组时第一眼撞上的东西。

代价接近于零：中间两段是折叠的（收起态各占一行），洗版仍在首屏。

**订阅创建弹层零改动**（维持"一次点击完成订阅，复杂度沉到默认值"的戒律，
弹层已有 5 个概念，不再+1）。

### 8.3 订阅详情页（只展示，不配置）

- Hero 摘要卡：规则组 fact 带出洗版目标（"规则组：4K 精选 · 洗到 Remux"）；
  状态文案在 completed ∧ 存在洗版单元时显示**"已收齐 · 洗版中"**；
- 追踪明细 `WantedRow`：imported 且洗版中的单元，徽标从「已入库」变为
  「洗版中」（青色系），说明行显示
  `当前 1080p WEB-DL → 目标 1080p Remux · 已搜 3 次`；到顶后回到「已入库」；
- 「更多」菜单不加洗版项；想改洗法走既有「更换规则组…」。

### 8.4 可解释性通道

- 新增 `ActivityType`：`upgrade_grabbed`（"S01E03 发现更高版本，已提交下载：
  1080p Remux-FLUX，来自 xx 站"，绿系）、`upgraded`（"S01E03 已洗版：
  1080p WEB-DL → 1080p Remux，旧版本已移入回收站"，绿系）、
  `upgrade_verify_failed`（证伪，含标称与实测证据的中文句，琥珀系）——
  message 照旧由后端写完整中文句，前端 `activityColor()` 各加一个 case；
- 常态否定（`upgrade_not_better`/`upgrade_at_cutoff`）不进活动流（§5），
  解释责任由单元行的派生展示承担；
- 库详情页：多版本文件各自显示档位徽标（`1080p WEB-DL` / `1080p Remux`），
  回收站内旧版本可见可恢复（7 天内）。

### 8.5 自然学习路径（对照产品目标 2）

1. 新用户：默认规则组不洗版，全程零感知；
2. 用户在规则组摘要芯片/编辑器里**看见**"洗版"字段与一句人话副文案——
   认识这个功能只需要读一行字；
3. 已收齐的订阅详情显示每个单元的当前版本档位——用户对"我库里是什么档"
   建立感知，产生"想要更好"的动机时，答案（规则组里那行 chips）已经见过；
4. 深度用户：分辨率偏好序 + 制作组黑白名单 + `cutoff_resolution` + 免费/体积
   约束的组合已经覆盖"官组洗版""省流洗版""只在 free 时洗"等高级玩法——
   **高级能力来自既有维度的组合，而非洗版专属配置**。

沿用统一信封与 snake_case，不新增端点：

| 面 | 变更 |
|---|---|

## 12. 实现落差记录（实现期确认的两处细化）

1. **证伪文件"不入库"的实际形态**（§6.3）：入库引擎（监听导入/扫描）不感知
   洗版，验证在库存对账钩子运行——洗版投递的文件会先正常入库成多版本行，
   验证证伪后**移入回收站并删除台账行**。可观测结果与设计一致（旧版本不动、
   证伪文件不留在库、候选进排除清单），且入库引擎保持零改动。
2. **回收站位置**（§7.1）：从 `data/trash/` 改为**各媒体库根目录内的
   `.movieclaw-trash/`**——与媒体文件同一文件系统，重命名瞬时完成，避免把
   40GB 旧版本跨盘搬进 `data/`；保留期仍为 7 天，由洗版基线回填 tick 顺带
   清理。
3. **attempt→工单的关联对洗版是另一套语义**（状态机审查的最大教训）：缺口
   语义的关联是 `wanted.info_hash == attempt.info_hash ∧ status 在途`，对洗版
   attempt **恒为空**（工单不重开、info_hash 直到确认前指向旧版本）。死种
   巡检、试用目标判定、换源候选评估凡是要回答"这个 attempt 还在为谁工作"，
   洗版必须走按 `attempt.units` 定位 imported 行的专属解析
   （`upgrade_attempt_wanted_rows`），试用源继承 `purpose`——否则洗版
   attempt 会在投递后首个巡检 tick 被当成"工单已闭合"错误完结、死掉的
   洗版源永远换不了源。
4. **"被抢先"不是"证伪"**（§6.3 的细化）：洗版下载期间基线可能被更优版本
   （如手工入库）刷高。投递文件实测**达到其声称档位**只是不再需要 →
   attempt 收口为 CANCELLED，不计熔断、不进排除清单；只有实测**低于声称**
   才是证伪。错误的惩罚会把诚实资源永久拉黑。

## 13. 手动洗版：单条目一键触发（设计稿）

> 状态：已实施（按 13.7 的四步落地）。覆盖两个场景：A）已有订阅的存量内容（如已收齐的完结剧）
> 换上带洗版目标的规则组后，逐集体检并立即触发一轮洗版；B）媒体库已有
> 但**没有订阅**的条目，一键洗版。本期只做单条目，不做整库扫描。

### 13.1 先说结构性缺口：已拥有单元没有工单行

订阅创建会**跳过库里已有的单元**（`core.py` 的 owned 过滤——"库里已有
N 个单元，无需重复下载"）。而洗版的全部状态（基线快照、证伪计数、搜索
排期）都住在 `wanted_item` 行上——**恰恰是用户最想洗的存量内容，没有
承载洗版状态的工单行**。自动洗版没暴露这个问题只是因为它洗的都是
"经订阅下载入库"的单元（天然有工单）。

**结论：新增"工单物化"（materialize）原语**——为期望集合 E 中库里已有
但无工单的单元，幂等补建 `status=imported` 的工单行（`imported_at` 取
文件入库时间、`air_date` 从 media_episode 回填；唯一约束天然防重）。
物化是手动洗版的第一步，也顺手治好了自动洗版的同一盲区（换组开洗版时
存量单元同样无行可挂）。

**被否备选：改订阅创建逻辑总是为 owned 单元建 imported 行。** 语义上更
统一（工单=单元物化，本来就"不只是缺口"），但改的是主创建链路、影响所有
既有订阅的行为预期（activity 文案、进度统计口径），收益只在洗版场景。
物化按需做，主链路不动；若未来验证顺畅，可再收编进创建流程。

### 13.2 核心原语：「一轮洗版」（upgrade run）

一个订阅级的同步动作，场景 A/B 共用（B 先建订阅再跑它）：

```
POST /subscriptions/{id}/upgrade-runs        body: { rule_set_id?: number }
```

执行五步，全部复用既有机制：

1. **（可选）换组**：body 带 `rule_set_id` 时先换组——"选一个带洗版设定
   的规则"与"触发一轮"合成一次调用；目标组必须配置洗版目标，否则 400
   给可读中文错误；
2. **物化**：materialize 已拥有单元的 imported 工单行（§13.1）；
3. **补快照**：对 `quality IS NULL` 的 imported 单元当场跑 `fill_snapshots`
   （不等 15 分钟回填 tick——这是"仔细检查每一集"的数据基础）；
4. **逐集体检**：对每个 in_scope 单元派生状态（纯读，见 13.3），其中
   `upgradable` 的单元：`next_search_at=now`、**priority=0**（用户显式触发
   =补旧级别，不排在自动洗版的 -10 队尾）、熔断中的视为人工介入解除
   （与「立即搜索」同语义）；
5. **踢一脚**：`kick_search_soon()` 立即开搜；被动匹配上下文本就实时读
   spec，无需额外动作。

返回体检报告（`UpgradeRunView`），前端直接渲染：

| 单元状态 | 语义 | 动作 |
|---|---|---|
| `upgradable` | 可证明低于洗版目标 | 已排期立即搜索 |
| `at_cutoff` | 已达目标档位 | 无 |
| `in_flight` | 已有在途洗版投递 | 无（等验证） |
| `not_comparable` | 无法识别当前版本（快照 `{}`） | 无；报告中如实展示，提示可手动选种 |
| `missing` | 该单元库里没有文件（工单开放中） | 走缺口逻辑（照常搜索下载） |

每行附 `current_label` / `target_label`（后端生成，前端零拼接）。
报告是**同步返回的一次性快照**，不落库——后续进展看既有的追踪明细
（「洗版中」徽标）与活动流水，不造第二套状态展示。

### 13.3 场景 B：无订阅条目 = 订阅弹层 + 自动接一轮洗版

**结论：不发明"无订阅洗版任务"，一键洗版就是建订阅。** 洗版需要长期
追踪载体（被动匹配、退避、验证、换源救援全都挂在订阅上）；给库条目
另造一个"洗版任务"实体等于第二个状态机，前三轮审查证明一个状态机的
交叉已经够多了。

动线：库详情页「洗版」按钮 →
- 条目已有订阅 → 跳订阅详情并打开「洗一轮版」弹层（处理机制见 13.4）；
- 无订阅 → 打开**既有订阅弹层**，三点预设差异：
  - **季勾选按媒体库库存预填**：默认勾选"库里已有文件的季"（洗版场景的
    用户意图是洗手里有的，而非订阅弹层默认的"全部已播季"）；库里没有的
    季不勾，用户可自行加。勾选的季若缺集，弹层如实提示"该季缺 N 集，
    将一并补齐"——这是订阅语义的自然结果，不做"只洗不补"的特例开关
    （被否：E 的定义是季的全部集，把"洗"与"补"拆开需要给 wanted 增加
    第三种范围语义，复杂度远超收益；不想补缺的用户可以不勾那个季）；
  - 规则组选择器只列**带洗版目标的组**（一个都没有时内联「+ 新建规则组」，
    编辑器里洗版字段就在眼前）；
  - `follow_future` 默认关（洗版场景不追新，用户可自行打开）。
- 创建成功 → 前端自动接 `POST /upgrade-runs` → 展示体检报告。

### 13.4 已有订阅时的处理机制（订阅唯一约束下的并轨）

一个条目至多一个订阅（`uq_subscription_media_item`），库详情的「洗版」
按钮在条目已有订阅时**并入既有订阅**，绝不建第二个。「洗一轮版」弹层
统一处理三种既有状态，全部复用现有接口：

| 既有订阅状态 | 弹层行为 | 复用机制 |
|---|---|---|
| 规则组未配洗版目标 | 先选一个带洗版目标的组（含新建入口），确认即"换组+触发"一次调用 | `upgrade-runs` 的 `rule_set_id` 参数 |
| 库里有文件但**不在订阅范围**的季（如只订了 S2、库里还有 S1） | 列出这些季供勾选并入范围，随后物化并纳入本轮体检 | 既有 `PATCH /subscriptions/{id}`（调整 selected_seasons）→ 再 `upgrade-runs` |
| 订阅已暂停 | 提示"订阅已暂停"，提供「恢复并触发」 | 既有 tracking-state 接口 → 再 `upgrade-runs` |

范围外的季不静默纳入——扩大订阅范围是用户决策（会连带补缺下载），
弹层如实展示后由用户勾选确认。

### 13.5 操作入口（明确只有两处）

两处入口，语义收敛到同一个「洗一轮版」弹层：

- **订阅详情「更多」菜单**：新增「洗一轮版…」——存量订阅（如已收齐的
  完结剧）的主入口。规则组已带洗版目标 → 直接跑并弹报告；未带 → 按
  13.4 先选组；
- **库详情页**：条目级「洗版」按钮（电影/剧集通用）——从"我库里有这个"
  出发的入口，按 13.3/13.4 分流（无订阅建订阅、有订阅并入）。
- 不加第三入口（海报卡/列表页）：洗版是需要看清当前状态再决策的操作，
  两个详情页有足够上下文，列表页一键触发容易误触且无处展示报告。
- **报告弹层**：按季分组的单元列表（复用 WantedRow 的徽标语言），顶部
  一句中文摘要（"12 集可洗版已排期，3 集已达目标，1 集无法识别"）。

### 13.6 边界与预留

- **整库扫描本期不做**：「一轮洗版」是干净的单条目原语，整库=对符合
  条件的订阅枚举调用 + 节流排队，属于独立的批量编排问题（届时还要面对
  站点压力与用户确认界面），预留即可；
- 物化出的工单与自动洗版共用全部后续机制（验证/证伪/熔断/换源/清理），
  零新状态；
- `upgrade-runs` 幂等：重复触发对已排期/在途单元无副作用（体检重算、
  排期覆盖为 now）。

### 13.7 落地顺序

| 步骤 | 内容 | 验证 |
|---|---|---|
| 1 | materialize 原语 + 单测（幂等、air_date 回填、in_scope 约束） | 存量完结剧换组后物化出 imported 行并可洗 |
| 2 | upgrade-run 服务 + API（换组/物化/补快照/体检/排期/解熔断/踢搜索） | 端到端：完结剧一键触发 → 报告正确、搜索立即执行 |
| 3 | 前端：订阅详情「洗一轮版」+ 报告弹层（含 13.4 三种既有状态处理） | 交互走查场景 A 与并轨场景 |
| 4 | 前端：库详情「洗版」入口 + 订阅弹层预设变体（库存季预填） | 交互走查场景 B（无订阅剧集/电影一键洗版） |

### 13.8 「无法确认」单元的闭环：常驻感知 + 手动选种承接（已实施）

体检报告是一次性快照，「无法确认」（快照 `{}` 或部分快照证明不了高低）
单元需要常驻感知与真实的人工出路，否则报告里"可手动选种替换"的提示是
空头支票（此前无缺口时手动选种入口隐藏、后端也拒绝）：

- **常驻感知**：`WantedUpgradeView` 增加 `indeterminate` 派生字段（证明不了
  低于目标也证明不了达标）；`{}` 哨兵单元不再隐形（此前被跳过、渲染成普通
  「已入库」行），标签「版本未识别」。追踪明细对这类单元如实说明
  "不参与自动洗版，可手动选种替换"。
- **手动选种承接洗版**：`grab_manual` 在规则组配置了洗版目标时，把已入库
  in_scope 单元也纳入可投递目标（无缺口不再直接拒绝），以
  `purpose="upgrade"` + **`manual=True`**（attempt 新列）投递。
- **手选的验证裁决与自动投递不同**：实测证明更优 → 照常替换（旧版进回收
  站）；**证明不了更优 → 新旧版本共存保留**（attempt 置 RETAINED），用户
  显式挑的文件绝不被系统丢弃，也不计熔断、不进排除清单——自动管线的证伪
  惩罚针对的是"资源命名造假"，不能落在用户的选择上。共存后基线刷新为实测
  最优：手选版本命名可信时，「无法确认」的基线随之修复，单元回到可判定
  状态。不需要的版本走库详情既有的单文件删除。
- 订阅详情「手动选种」入口条件放宽：有缺口，或配了洗版目标且有已入库单元。

## 14. 多维洗版阶梯：偏好即优先级（设计稿）

> 状态：**设计稿**，未实现。本节把 §2 的二元组阶梯推广为 N 维，并连带统一
> 规则组多选维度的语义。**缺省配置下行为与 §2 完全一致**——存量规则组零改动、
> 零迁移，本节全部是可选的高级层能力（对应 §0 目标 2 的第三层）。
> 本节推翻 §0 反目标第三条（"不做 HDR/DV/编码维度的档位升级"）与 §11 的
> HDR 开放问题，理由见 14.2。

### 14.1 结论

三句话：

1. **规则组的所有多选维度统一为「列表即白名单 + 顺序即偏好」**——`resolutions`
   本来就是这个语义，`video_codecs`、新增的 `platforms`、以及 HDR 跟进；
2. **洗版阶梯从写死的二元组推广为 `upgrade_ladder` 指定的 N 维向量**，
   仍然是字典序逐位比较、仍然是离散档位、仍然只有一条停止线；
3. **`upgrade_ladder` 缺省 `["resolution", "source"]`** —— 即 §2 的原样行为。
   往列表里加一位，就是用户显式接受"更精细的洗版 = 更多次重复下载"。

一句话：**用户排好的偏好顺序，就是洗版的优先级顺序。没有第二套配置。**

### 14.2 为什么是"维度列表"，以及否掉的三个备选

- **零新概念（目标 1）**：用户在 `resolutions` 上已经学过"列表顺序即偏好"，
  这里是同一套心智的第三次复用（第一次是分辨率评分，第二次是平台/编码白名单）。
  没有引入"权重""半档""Custom Format"任何新词；
- **一个字段同时表达"哪些维度参与"和"谁优先"**，不产生第二个策略家（§3.1）——
  不需要"启用开关 + 排序"两套东西，也不需要每个维度各配一个 cutoff；
- **表达力覆盖真实分歧**："1080p DV 优于 2160p SDR"这一派把 `hdr` 拖到
  `resolution` 前面即可；省空间派把 `1080p` 排在 `resolutions` 首位即可。
  两种人用同一个机制，谁也不需要 hack。

**被否备选一：连续加权打分。** 回到 arr 老路，§2.2 已经论证过——不可解释、
需要 Increment 打补丁。本节的向量比较仍然是离散字典序，§2.3 的抗抖动性质
原样保留（同一位内的任何差异都不构成升级）。

**被否备选二：每维一个 `upgrade_xxx` 开关 + 内置固定的维度顺序。** 配置面
更小，但表达不了维度间的优先级分歧（上面 DV 那一派无解），且开关数量随维度
线性增长，正是 arr "策略散落在四个页面"的复现。

**被否备选三：§11 记的"HDR 视为高半档"。** "半档"是一个纯粹为 HDR 发明的
新概念，只解决一个维度——编码和平台还得各自再发明一次。而一旦承认"维度可以
排序"，半档就不需要存在了。§11 的这条开放问题由本节关闭。

### 14.3 字段定义

```python
# RuleSetSpec（movieclaw_matcher/models.py）

upgrade_ladder: list[str] = ["resolution", "source"]
    # 参与洗版比较的维度及其优先级——列表顺序即位次，字典序逐位比较。
    # 值域：resolution / source / hdr / video_codec / platform
    # 缺省 = §2 的二元组，存量规则组行为不变。
```

每一位的位次来源是异构的，这没问题——每位只需要一个 `rank() -> int | None`：

| 位 | 位次来源 | 目标（停止线）取值 | 数据来源 | 典型识别率 |
|---|---|---|---|---|
| `resolution` | 规则组 `resolutions` 列表序 | `cutoff_resolution`，缺省取列表首项 | **ffprobe 实测** | 高 |
| `source` | **内置片源档 T1–T5**，不暴露配置（§2.1） | `upgrade_source` | 名称解析 | 中 |
| `hdr` | 规则组 HDR 偏好列表序（14.8） | 列表首项 | **ffprobe 实测** | 高（缺席即 SDR） |
| `video_codec` | 规则组 `video_codecs` 列表序 | 列表首项 | **ffprobe 实测** | 高 |
| `platform` | 规则组 `platforms` 列表序 | 列表首项 | 名称解析 | 低 |

**为什么只有 `resolution`/`source` 有独立的 cutoff 字段，其余直接取列表首项？**
因为只有这两个维度会成数量级地改变磁盘占用，才需要"我接受但不主动洗"的区分
（§3.2 里 44GB Forrest Gump 的教训）；同一个 `(分辨率, 片源)` 格子内换
HDR/编码/平台，体积几乎不变，洗到首选没有代价，多一个 cutoff 字段是纯负担。
这条不对称也正是这两位默认排在最高位的理由。

**洗版总开关仍然是 `upgrade_source`**（`None` = 不洗版，§3.2 原样）——它就是
简单层用户做的那"一次选择"。想表达"只洗 HDR、片源不动"的用户，把
`upgrade_source` 设成当前已有的档（如 `web-dl`）即可：`source` 位立刻恒达标，
比较自然落到后续位。不需要为此新增任何字段。

**校验**（`RuleSetSpec` 的 model_validator）：

- `upgrade_ladder` 的值必须在枚举内且不重复；
- **某一位对应的偏好列表为空 → 该位自动跳过**，不参与比较、不产生截断
  （见 14.4；空列表当"未知"会让整条阶梯哑火，必须显式跳过）；
- 名称维度（`platform`）排在实测维度之前时**不报错，但编辑器必须告警**——
  理由见 14.4 的截断规则。

### 14.4 比较算法：部分可比的 N 维推广

`decision.py` 现在有三个函数（`provably_below_cutoff` / `provably_at_cutoff` /
`compare_upgrade`）各自展开了一遍逐位逻辑。加维度后这必须先收敛成**一个**
比较函数，三个谓词由它导出——否则三处逐位逻辑会各自腐化：

```python
def compare_ladder(a, b, spec) -> int | None:
    """a 与 b 的档位向量比较：>0 = a 更优，0 = 等价，None = 不可比。"""
    for dim in spec.upgrade_ladder:
        if dimension_unconfigured(dim, spec):
            continue                      # 偏好列表为空的位直接跳过
        ra, rb = rank(a, dim, spec), rank(b, dim, spec)
        if ra is None and rb is None:
            continue                      # 双方都未知 = 该位平局，继续比下一位
        if ra is None or rb is None:
            return None                   # 单侧未知 = 不可比，且后续位不再比较
        if ra != rb:
            return 1 if ra > rb else -1   # 首个定序位，结束
    return 0

provably_below_cutoff(snap, spec)  →  compare_ladder(snap, target(spec), spec) == -1
provably_at_cutoff(snap, spec)     →  compare_ladder(snap, target(spec), spec) in (0, 1)
洗版成立(cand, snap, spec)          →  not provably_at_cutoff(snap) and
                                       compare_ladder(cand, snap, spec) == 1
```

三条规则里有一条是**对 §2.4 的修订**：

> **双方都未知 = 该位平局，继续比较下一位。**
> 现状（`compare_upgrade`）在 `cand_tier is None` 就直接 reject，两边都测不出
> 片源时本该是平局却被判成不可比。这是个独立于本节就该修的收敛性 bug，
> 在 N 维下影响会被放大（低位维度的双侧缺失会挡住整条比较）。
> 三态铁律不受影响——**单侧**未知仍然一律判否，绝不把未知当已知用。

**由截断规则推出的硬约束**：单侧未知会让**它后面的所有位都够不着**。平台标记
在种子标题里的识别率远低于分辨率（PR #120 的实测样本里，平台识别还要求同段
文本带 WEB 来源上下文才成立），若把 `platform` 排在高位，绝大多数候选会直接
落进 `upgrade_not_comparable`，洗版整体哑火。因此：

> **实测维度必须排在名称维度之前。** 这不是默认值的品味问题，是机制的要求。
> 编辑器允许拖拽，但名称维度上浮时明确告警"会让大量候选无法比较"。

推荐默认顺序（也是编辑器的初始态）：
`resolution > source > hdr > video_codec > platform`。

### 14.5 快照与回填

`QualitySnapshot`（`wanted_item.quality`）新增两个字段：

```python
video_codec: str | None = None   # ffprobe 实测，值域归一到 enrich 词表
platforms: list[str] = []        # 名称解析；空列表 = 未识别（三态：未知）
```

- **编码的两侧命名空间由编码族消化，不需要额外的映射层**：`vocab.codec_family()`
  同时接受 ffprobe 的 `codec_name`（`hevc`/`h264`/`av1`）与标题解析的归一值
  （`x265`/`HEVC`/…），两边查同一张表得到同一个族（§16.1 已实现）。§4.2 点名的
  这个问题在编码维度上就此消解，HDR 侧仍走 `_PROBE_HDR_TO_VOCAB`；
- **存量回填仍是纯 DB 变换**：`library_file.video_codec` 是现成的 probe 列，
  平台对文件名跑一遍 enrich，**不重新探测文件**——§4.4 的结论原样成立；
- **老快照这两位为空 = 未知**，因为它们在推荐顺序的低位，只损失自己那一位、
  不截断前面的比较。这正是 14.4 那条硬约束的兑现价值。

### 14.6 重复下载的收敛性

维度多了，"严格更优"的状态就多了——一个单元理论上可能被逐档洗 4–5 次。三条
约束足够，且都不是新机制：

1. **`upgrade_ladder` 的长度本身就是闸门**。缺省 2 位；加一位是用户在配置面上
   可见的显式取舍，不是隐藏行为；
2. **一轮最多投一次，且投的是本轮最优候选**。`pick_best` 已经在选优，只需明确
   写死"洗版单元一轮只投一次" ⇒ 实际收敛是 1–2 跳直达目标，而不是逐档爬 5 次；
3. **单调基线 + 证伪排除清单（§4.3）原样成立**，N 维下不会退化成死循环；
   整季包的"每个单元都必须缺失或构成合法升级"铁律（§5）也不变。

**必须正视的副作用**：加维度后"已到顶"的单元显著变少，`provably_below_cutoff`
为真的面变大 ⇒ **洗版排期规模与站点压力上升**。缓解手段是季级两阶段洗版
（一季只放一个锚点单元先洗，确认后整季按已验证档案跟进）——那是独立的一节，
**本节的落地必须与它同批**，否则一季 24 集 × 5 维会把搜索排期撑爆。

### 14.7 拒绝码与文案

拒绝码**不新增**，仍是 §5 的三个；变的是 `reason_text` 收敛成"首个定序位"的
固定句式，每次比较永远只解释一个维度：

| 码 | 触发 | 文案模板 |
|---|---|---|
| `upgrade_not_better` | 首个定序位上候选更低或等价 | 候选 `{cand}` 与当前版本在{前序维度}上相同，**{定序维度}位次更低**（{候选值} 排在 {当前值} 之后），不构成升级 |
| `upgrade_at_cutoff` | 当前版本已达目标向量 | 当前版本 `{cur}` 已达到洗版目标（`{target}`），不再洗版 |
| `upgrade_not_comparable` | 某位单侧未知，比较被截断 | 无法识别{维度}（候选：{值或"未标注"}），洗版比较在该维度中断 |

档位标签渲染为点分串：`2160p · Remux · DV · x265 · NF`（`quality_label` /
`upgrade_target_label` 按 ladder 逐位拼接，未配置的位不出现）。§5 的噪音控制
不变：`upgrade_not_better` / `upgrade_at_cutoff` 是常态，不写活动。

### 14.8 HDR 字段合并（已决策：方案 A，落地形式为"新键 + 双写"）

**结论**：HDR 的硬过滤与偏好合并成**一条有序列表**，语义上取代 `hdr`/`dv`
两个三态策略字段；但**不原地改 `hdr` 键的类型**，改用新键并对旧键双写，
理由见下方"回退兼容"。

```python
hdr_levels: list[str] = []
    # 值域（内置序仅作编辑器初始顺序，实际序以用户列表为准）：
    #   ["DV", "HDR10+", "HDR10", "HLG", "SDR"]
    # 列表即白名单（空 = 不限），顺序即偏好，首项即洗版终点（14.3）。
    # "SDR" 是哨兵值，对应 attrs.hdr 为空（命名惯例：缺席即否定）。

hdr: HdrPolicy = HdrPolicy.ANY   # 旧键，deprecated：仅在 hdr_levels 为空时消费
dv:  DvPolicy  = DvPolicy.ANY    # 旧键，同上
```

旧语义全部可表达，`_reject_hdr_dv_conflict` 互斥校验器随之删除——矛盾组合
在列表语义下根本写不出来：

| 旧配置 | 新配置 |
|---|---|
| `hdr=any, dv=any` | `[]` |
| `hdr=require` | `["DV","HDR10+","HDR10","HLG"]` |
| `hdr=forbid`（含 dv=forbid） | `["SDR"]` |
| `hdr=require, dv=forbid` | `["HDR10+","HDR10","HLG"]` |
| `hdr=any, dv=require` | `["DV"]` |
| `hdr=any, dv=forbid` | `["HDR10+","HDR10","HLG","SDR"]` |

#### 过滤与排序是两个问题，用两条规则

落地时浮现的一处关键区分（设计稿原文没写清）：

- **要不要（过滤）**：白名单"任一命中即过" + 黑名单"命中即拒"，**不做蕴含展开**。
  多值属性上"只要 A"表达不了"排除 B"，所以必须两份；
- **谁更好（排序）**：按资源"能播的最高格式"取位次，**做蕴含展开**，且展开
  只对用户本来就接受的格式生效——蕴含是"这个文件也能当 HDR10 用"的补充说明，
  不能变成绕过排除项的后门。

#### 位次规则：取最高位次标记，且高格式蕴含低格式

资源带多个 HDR 标记（`DV.HDR10` 双标很常见）时，**位次取命中集合中最高的
那个**。并且蕴含关系要显式建模：

```
DV     ⇒ {DV, HDR10}       # DV Profile 8 自带 HDR10 基础层
HDR10+ ⇒ {HDR10+, HDR10}   # HDR10+ 是 HDR10 的动态元数据扩展
```

**为什么必须建模蕴含**：`library_file.hdr` 是**单值列**，ffprobe 对双标文件
只会给一个 `Dolby Vision` 标签。若不建模，一个"偏好 HDR10 胜过 DV"的用户
（播放设备对 DV 支持差）会把一个**已经含 HDR10 基础层**的文件判成低位次，
触发一次纯粹无谓的洗版下载。DV Profile 5 确实不含 HDR10 基础层，但标题与
probe 都无法区分 profile——按"能播 HDR10"这一侧保守建模，错的方向是**少洗
一次**而不是多下一次，这与 §4.2 接受残余风险的取向一致。

#### 连带修正：`build_snapshot` 的 probe 覆盖策略

现实现在 `probed=True` 时用单个 probe 标签**整体替换**名称解析的 HDR 集合，
双标信息被丢弃。今天 `hdr` 只用于展示，无害；§14 后它是定序位，丢弃会造成
基线位次虚低。改为三分支：

| probe 判定 | 名称集合 | 快照取值 |
|---|---|---|
| HDR 家族 | 包含该标签 | **保留名称集合**（更完整且与实测不矛盾） |
| HDR 家族 | 不含该标签或为空 | 取 probe 单值（实测推翻名称） |
| SDR（`library_file.hdr` 为 NULL） | 任意 | **清空**（实测推翻虚标，§4.1 的核心价值，不可动） |

#### 回退兼容：为什么不能原地改 `hdr` 的类型

`CLAUDE.md` 硬约束三与 `in-app-update.md` 的一键回退机制要求**向前兼容**：
用户可以从新版本回退到旧版本，数据不能变成旧代码读不懂的形态。
`hdr` 从 `str` 枚举原地改成 `list[str]` 是**同名不同型**——回退后旧代码执行
`RuleSetSpec.model_validate({"hdr": ["DV"]})` 会直接 ValidationError，
规则组全线解析失败，匹配管线整体崩溃。这是不可接受的。

因此落地形式是**新键 + 双写**：

- **读取**：`hdr_levels` 非空 → 用它；为空 → 由 `(hdr, dv)` 按上表推导。
  归一在 `RuleSetSpec` 的 model_validator 里做一次，下游只见到 `hdr_levels`；
- **保存**：写 `hdr_levels`，**同时 best-effort 回写等价的 `hdr`/`dv`**——
  能精确表达就精确写（`["SDR"]` → `hdr=forbid`），表达不了顺序或混合集合时
  写最宽松的等价值（`["HDR10","DV"]` → `hdr=require`；`["SDR","HDR10"]` →
  `hdr=any`）。回退后行为退化为"必须 HDR / 不限"这类粗粒度，**不精确但不崩、
  不危险**；
- 旧键在下一个大版本移除，届时回退窗口已过。

#### 兼容层落点清单

| 落点 | 动作 |
|---|---|
| `movieclaw_matcher/models.py` | 加 `hdr_levels`，旧两键标注 deprecated；归一 validator；删互斥校验器 |
| `movieclaw_matcher/rules.py` | HDR 硬过滤改读归一后的列表（`[]` = 不限） |
| `apps/web/components/rule-sets-panel.tsx` | chips 文案与编辑器从三态按钮改为可拖拽有序列表（14.9） |
| `src/movieclaw_api/data/spec.json` | 契约基线重生成（`tests/api/test_spec_baseline.py` 守护） |
| OpenAPI / `schemas` | 规则组读写契约加字段，旧字段保留 |
| alembic | **不需要数据迁移**——双写让新旧形态在同一行共存，读取端归一 |

### 14.9 UX（规则组编辑器是唯一配置点，§3.1 不变）

- **渐进披露**：洗版区默认仍然只是那一个"洗到哪一档"下拉（简单层用户的体验
  零变化）；下方折叠一个「洗版优先级」高级区，展开后是可拖拽的维度条，
  初始只有「分辨率」「片源」两块，从候选区拖入 HDR/编码/平台即加位；
- 每个多选维度的编辑器统一为**可拖拽的有序列表**（分辨率已是此形态），
  首项旁标注「洗版终点」角标——让"顺序即优先级、首项即目标"一眼可见；
- 名称维度被拖到实测维度之前时，条目下方出现橙色告警条（14.4）；
- **底部回执从"一句话"升级为"一条看得见的路"**（已落地，`lib/upgrade-ladder.ts`
  + `RuleSetEditorDialog`）：开了洗版之后规则组不再是一个筛子而是一条有序阶梯，
  一行"洗到 1080p 蓝光 · DV"读不出它真正的两个后果——**终点之下还有多少档**
  （每上一档就是一次重复下载，§14.6 的代价在这里才具体）与**哪些档已经算达标**
  （分辨率排在首位时任意 2160p 都优于 1080p 蓝光，洗版直接停在那儿）。于是回执
  分两段渲染：先是硬性筛选的摘要芯片，再是阶梯——终点卡在最上方（含"更高档同样
  算达标，最高 X"与旧版本去留一句），下方按档位降序列出至多 5 档过渡版本，余下
  的折成"更低的 N 档同理"。阶梯**默认折叠**（完整形态十来行，常驻会把配置本身
  挤出视野）：收起态只留一行"再一级级洗到 X"+「看会经过哪些档 ›」，点开才铺陈。
  用点击而非 hover——弹窗在手机上同样要用，触屏没有 hover，且这是要读几行的
  解释而非一句提示；折叠形态与同弹窗里的「洗版优先级」「画质与来源」一致；实现把生效维度的偏好序当成一个**混合进制数**（每维
  一位，位值 0 = 该维最优），"终点的下一档"就是"终点序号 + 1"，与后端字典序比较
  天然同构，不重复实现比较逻辑；口径（跳过未配偏好的维度、终点取
  cutoff/首项、片源档序）与 `decision.py` 一一对齐，纯展示、不参与任何决策；
- 订阅详情页仍然**只展示不配置**（§8.3）：目标标签渲染为
  `2160p · Remux · DV`，追踪明细复用 §8.4 的"当前档 → 目标档"句式。

## 15. 季内版本一致性与锚点洗版（设计稿）

> 状态：**设计稿**，未实现。与 §14 是同一批工作的两半：§14 解决"洗到什么版本"，
> 本节解决"一季 24 集会不会洗成 24 个不同版本"，以及"洗版排期会不会撑爆站点"。
> §14.6 已经写明：§14 的第 3–4 步**必须与本节同批发布**。

### 15.1 结论

1. **版本一致性默认是"偏好"，不是硬过滤**——它只影响同样合格的候选谁先被抓，
   不影响一个候选要不要；
2. 想要强一致的用户在规则组显式开 `season_lock`，此时才升级为硬过滤，
   且带**自动降级出口**（找不够久就放宽，绝不饿死缺集）；
3. **洗版按季两阶段**：一季先只放一个锚点单元去洗，锚点实测确认后，
   该季其余单元才一次性入列。

### 15.2 为什么一致性不能默认硬过滤

PR #120 的 `lock_first` 把首集入库版本的平台/组/分辨率/HDR 固化成后续集的
硬过滤条件，**没有任何降级出口**——锁定的组不再发某一集，那集就永远补不上。

- **收齐 > 一致**：用户订阅一部剧的第一诉求是把集数收齐，版本齐整是第二位的。
  一个把第二位需求实现成"可以牺牲第一位"的机制是错的；
- 硬过滤还会与规则组既有的过滤维度叠加，用户面对"为什么这集一直没下"时，
  归因路径从"看规则组"变成"看规则组 + 猜锁定档案"；
- 偏好形态天然不需要出口：找不到同版本的就抓个合格的，下次洗版再收敛——
  这恰好是洗版机制本来就在做的事。

**被否备选：把一致性档案存成 `subscription.quality_policy` JSON（PR #120 的形态）。**
制造了策略的第二个家（§3.1 反对的形态），且运行态与配置混在一个 JSON blob 里，
并发投递、进程重启、多单元对账都要靠它，脆且难测。本节的档案是**实时导出的
派生值，零新状态**（15.3）。

### 15.3 季版本档案：从快照实时导出，不落任何新列

```
season_profile(季) = 该季全部 imported 单元的 quality 快照，
                     逐维度各取众数（并列时取最近入库单元的值）
```

- **零新状态**：`wanted_item.quality` 已经是每个单元的版本事实，档案只是它的
  聚合视图。规则组改了、文件换了，档案下一轮自然跟随，没有需要维护的缓存；
- **逐维度取众数**而不是"取某一集的完整档案"：不同集可能各缺不同维度
  （这集识别不出平台、那集识别不出组），逐维度投票比整体取样稳；
- 参与维度：`platform` / `release_group` / `resolution` / `hdr_levels` / `video_codec`
  ——即 §14 的阶梯维度加上制作组（组不参与洗版定序，但它是"看起来是同一版本"
  最强的信号）；
- 空季（该季一个 imported 单元都没有）→ 无档案 → 一致性不参与本季任何判定；
- 计算落点：`load_match_context` 构造 `MediaContext` 时一次算好
  （与 `upgrade_snapshots` 同一趟），逐种子比对时零额外查询。

### 15.4 一致性如何参与选优：洗版与缺口的不对称

| 场景 | 排序键 | 理由 |
|---|---|---|
| **洗版候选** | `(is_pack, 档位向量, 一致性命中数, score, seeders)` | 洗版**不急**——单元已经有可用版本。一致性优先于成本，宁可等一个同组的 |
| **缺口候选** | `(is_pack, score + 一致性加分, seeders)`，加分 = 命中维度数 × 30 | 缺口是**现在就要**。免费与做种数（成本与可得性）仍是第一位，一致性只作为与"一档分辨率"同权的加分项参与既有评分，不喧宾夺主 |

这里同时修掉了一个现存问题：**洗版候选的选优今天用的是评分而非档位**
（`entries.sort(key=(is_pack, score, seeders))`）。`_FREE_SCORE = 100` 会压过
"一档分辨率 = 30"，于是系统可能先抓一个"免费但只高半档"的版本、下一轮再洗一次
——同一个单元付两次下载。洗版排序键改成档位优先后，每轮直接跳向可得的最高档，
§14.6 承诺的"1–2 跳直达"才真正成立。缺口侧不动（免费优先是 PT 场景的既有决策）。

### 15.5 `season_lock`：可选的硬过滤 + 自动降级出口

```python
# RuleSetSpec
season_lock: bool = False   # 锁定季内版本：同季后续单元必须匹配季版本档案
```

- 开启后，季档案里**已识别的维度**成为该季候选的附加硬过滤（档案里未识别的
  维度不产生约束——不能拿未知当已知，三态铁律）；
- **降级出口（单元级）**：某单元连续搜索达到内置阈值（`search_attempts >= 5`，
  复用既有列，零新字段）仍无同版本候选 → **该单元自动降级为偏好模式**，
  并记一条活动：「S01E05 找不到与本季一致的版本（{档案摘要}），已放宽为任意
  合格版本」。降级只影响这一个单元，同季其他单元继续锁定；
- 降级后若该单元最终抓到了不同版本，它会作为一票参与下一轮众数计算——
  档案自然演化，不需要人工重置。

### 15.6 锚点洗版：一季一次只洗一个单元

**阶段一**：某季进入洗版时，只有**一个锚点单元**入列。锚点 = 该季可洗单元中
`(季号, 集号)` 最小者（稳定、可预测、用户一眼能理解"从第一集开始试"）。

**阶段二**：锚点**实测验证通过**（`verify_upgrades` 确认升级、快照刷新）后，
该季其余可洗单元一次性入列，并把锚点确认后的版本作为一致性档案的强信号
（它已经是该季最新的一票）。

- **锚点失败**（证伪 / 熔断）→ 顺位换下一个单元当锚点，避免某一集的资源缺失
  永久卡住整季；
- **电影不适用**（只有一个单元），逻辑短路；
- 收益：同一个撒谎 release 只被证伪一次而不是 24 次（排除清单是按单元存的）；
  搜索排期规模从"季集数 × 维度数"降到"1 × 维度数"；混版窗口从整季收敛到一集。

**闸门必须落在 `load_match_context` 的洗版单元筛选上，不能只落在 `arm_upgrade_wanted`。**
现实现里 `upgrade_ready` 只看"快照可证明低于目标 + 未熔断"，**不看排期**——
主动搜索的排期由 `arm` 控制，但**被动匹配（种子同步）会对全部可洗单元生效**。
只在 arm 侧限流的话，被动匹配会整季绕过锚点，等于没做。

### 15.7 与整季包铁律的冲突及解法（必须处理）

§5 的铁律：整季包覆盖的每个单元都必须"缺失或构成合法升级"，任一判否即拒整包；
实现上，不可洗的已入库单元进 `ctx.upgrade_blocked`，包碰到它就整体放弃。

**锚点直接与这条铁律相撞**：阶段一里非锚点单元不入列 → 落进 `upgrade_blocked`
→ 任何整季包都会碰到它们 → **整季包洗版永远不成立**。而整季包恰恰是洗版最高效、
也最能一次性达成全季一致的形态，丢掉它是功能性倒退。

解法：把"不可洗"二分——

| 集合 | 含义 | 对整季包 |
|---|---|---|
| `upgrade_blocked` | **真的不可洗**：已到顶 / 不可比 / 在途 / 熔断中 | 阻挡整包（现状正确，不变） |
| `upgrade_deferred` | **本身可洗，仅因锚点阶段暂缓** | **不阻挡**，且整季包命中时连它们一起洗 |

于是锚点与整季包变成协同关系而非冲突：单集候选走锚点节流，整季包一次性把全季
洗成同一个版本——一致性天然满足，也正好是用户最想要的结果。

### 15.8 UX

- 规则组编辑器：`season_lock` 是洗版高级区里的一个开关，文案「锁定季内版本
  （找不到同版本时自动放宽）」——**把降级出口写进标签本身**，避免用户以为
  会卡死；
- 订阅详情页（只展示不配置，§8.3）：季分组标题旁展示档案摘要
  `本季版本：2160p · DV · NF · CtrlHD`；洗版中的锚点单元标注「正在试洗（本季
  先洗这一集）」——让"为什么只有一集在动"自解释；
- 降级发生时记活动（15.5），用户在时间线上能看到放宽的事实与原因。

### 15.9 落地顺序

| 步骤 | 内容 | 验证 |
|---|---|---|
| 1 | `season_profile` 导出 + `MediaContext` 装载 | 表驱动单测：逐维度众数、并列取最近、空季无档案 |

### 16.1 第 3 条：编码族（已修复）

`vocab.VIDEO_CODEC` 把同一编码的不同写法归一成**三个不同的规范值**：
`x265` / `H.265` / `HEVC`（AVC 侧同理 `x264` / `H.264` / `AVC`）。而
`rules.evaluate_rules` 的白名单是精确匹配 ⇒ 规则组写 `x265` 时，标 `HEVC`
的资源被 `codec_not_allowed` 拒。

**这不是一个待决的产品问题——项目早就决策过了，只是决策只落在了前端。**
`apps/web/components/rule-sets-panel.tsx` 的 `CODEC_FAMILIES` 按族提供选项，
注释写得很清楚："用户想表达的是「要 H.265 这一族」，UI 选一族即把全部等价
写法写进白名单，避免因发布组写法不同而漏掉资源"。后端从来不知道族的存在，
于是漏掉了三种情况：

1. **绕过 UI 写入的规则组**——API / CLI 直接写 spec，或早于 `CODEC_FAMILIES`
   引入之前建立的存量规则组，`video_codecs` 里可能只有单个写法；
2. **洗版的编码位次根本无法成立**（§14 的硬阻塞）：`library_file.video_codec`
   是 ffprobe 的 `codec_name`（`hevc`/`h264`/`av1`），标题解析给的是
   `x265`/`HEVC`，后端不认族则基线与候选永远不同位次；
3. 同一个领域概念的两个家的雏形——今天只有一个家，而且在错误的那一层。

**处置**：族下沉到后端，前端一行不动。

```python
# movieclaw_enrich/vocab.py
VIDEO_CODEC_FAMILY = {"x265": "h265", "h.265": "h265", "hevc": "h265", ...}
def codec_family(value: str | None) -> str | None: ...   # 表外编码各自成族
```

- `rules.evaluate_rules` 的编码白名单按族比较；跨族仍然拒绝，族外编码
  （VC-1/VP9/…）各自成族，既不误伤也不互通；
- §14 的编码位次同样按族——这是它能落地的前提；
- 前端保持现状继续写三个值：族匹配下与写族标签完全等价，因此这次改动
  **零迁移、不动 DB、不动 API 契约、不动前端**，可独立发版。把前端简化成
  只写族标签是后续可选清理，且涉及回退兼容（旧后端不认族标签，得双写），
  不必现在做。

**关于"想精确区分二压与原封"的诉求**：诉求是真的，但用编码写法表达它本来
就不可靠——大量原封 WEB-DL 也标 `x265`，写法是发布组的命名习惯而非事实。
可靠的维度是 `media_source` + `remux`（片源档 T3/T4/T5），洗版阶梯的第二位
用的正是它。所以族归一没有牺牲任何**可靠**的表达力，它去掉的是一个假的
表达力——这也是前端当初直接按族做、没留"精确写法"开关的原因。

### 16.2 第 4 条：`{}` 哨兵与 `exclude_defaults=True`

`fill_snapshots` 用 `snapshot.model_dump(exclude_defaults=True)` 写快照，
并把 `{}` 当作"已尝试构建但关键维度全部无法识别"的**已处理哨兵**
（`upgrade_ready` 与回填任务都据此跳过该单元）。

今天成立：全部字段取默认值确实意味着什么都没识别出来。**§14 后不再成立**——
`hdr_levels` 语义下"SDR"对应 `hdr` 空列表，而空列表正是默认值。一个
"实测确认是 SDR、其余维度未识别"的快照会被 dump 成 `{}`，于是被当成
"无法识别"永久排除出洗版，而它本该是一个**可定序的合法低位次基线**。

处置：哨兵不再用"空对象"表达，改为显式键（如 `{"unidentified": true}`），
或改用 `exclude_none=True` 保留空列表。同时给 `{}` 存量行写一次性升级。
**这条必须先于 §14 落地**，否则会静默漏洗。

### 16.3 第 5 条：快照版本与回填

回填 tick 的查询条件是 `WantedItem.quality IS NULL`，只覆盖"从未回填"的单元。
§14 给快照新增 `video_codec` / `platforms` 两个维度后，**存量非空快照永远补不上
这两位**——高位维度全部打平时，比较会在这两位上遇到单侧未知而截断，
结果是这些单元**大面积变成不可比、洗版停摆**（在 §13.8 的口径里显示为
「版本未识别」）。

处置：快照结构加版本键 `v`，回填条件改为 `quality IS NULL OR v < 当前版本`。
重算仍是**纯 DB 变换**（probe 各列与 `library_file` 都在，不重新探测文件），
成本与 §4.4 的既有回填一致。这是 §14 落地的**前置迁移动作**，不是可选项。

### 16.4 前车之鉴：平台值域的向前兼容

PR #120 的平台校验对不在词表里的值直接抛 `ValueError`。我们自己实现时
**不要重蹈**：`RuleSetSpec` 的立身之本是"加维度不需要迁移"，一旦词表调整
（合并平台、改规范值），存量规则组会在读取时整体解析失败，波及的是匹配管线
而不只是那一个维度。平台白名单里的未知值应当**忽略并告警**，或只在写入路径
校验、读取路径宽容。
