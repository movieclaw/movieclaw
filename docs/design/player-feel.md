## 0. 验收标准（先定标准再动手）

「丝滑」必须能被观察，否则改完只能靠感觉吵架。六条：

1. **进度条匀速**：播放中圆点每帧走一次，不是每 250ms 跳一格。录屏 60fps
   逐帧看，圆点位移应连续；React DevTools 里播放中的 re-render 次数**不因此
   项增加**（仍是 `timeupdate` 的 4Hz）。
2. **一个位置只有一个读数**：落点胶囊、进度条、时间文字三者同源
   （2026-09-08 已修，见 §2.A0）。
3. **点一下必有反应**：单击 → 控制层开关；双击 → 明确的第二种动作；长按 →
   倍速。三者互不误触发，且单击的反馈不被双击判定拖延 300ms。
4. **连按不打架**：连按三次快进，只发生**一次**跳转，画面走 30 秒，
   不是三次「黑一下再走 10 秒」。
5. **拖动跟手**：直通/VOD 模式下拖动进度条时画面跟随；转码会话下松手才跳，
   但拖动全程有缩略图 + 时间 + 章节名。
6. **卡住能自愈**：解码类错误先就地恢复，能救回来的不许降档——降档意味着
   画质掉一级 + 几秒黑屏，是最后手段而不是第一反应。

## 2. 分项方案

### A0（已完成，2026-09-08）拖动读数同源

横滑落点驱动进度条；胶囊在手势被第二根手指/换元素打断时收走；片长转未知时
清掉进度条的 `dragging`。提交 `1597cb4`。

### A1 进度条 60fps 重绘（P0，感知最大） ✅

**问题**：`video-player.tsx` 的 `timeupdate` 是唯一位置来源，浏览器只给约
4Hz 且间隔不均；`player-controls.tsx` 的已播段与圆点又没有任何过渡，于是圆点
每 250ms 跳一格。

**方案**：位置的**绘制**与位置的**状态**分家。

- 绘制：`player-controls.tsx` 里一个 rAF 循环直接写 DOM —— 已播段
  `style.width`、圆点 `style.left`。读数按优先级取：`dragging`（进度条拖动）
  → `overrideMs`（横滑落点/连按累积落点，父组件传）→ `video.currentTime`
  （配 `startMs` 换算成文件时间）。
- 写 DOM 必须**合帧**：照 emby-slider 的写法，排新帧前先
  `cancelAnimationFrame` 掉上一帧，保证一帧最多写一次。
- 状态：`positionMs` 这个 React state 保持 `timeupdate` 4Hz 不变，继续供
  时间文字、片尾卡片、上报、诊断面板用。**绝不在 rAF 里 setState**。
- 生命周期：`playing && !document.hidden` 才跑循环；暂停、seek、换会话各补画
  一次；`override` 存在时停循环、由 React 直接写一次。
- 缓冲段维持事件驱动（`progress`/`timeupdate`）：变化慢，60fps 是浪费。

**新增 prop**：`PlayerControls` 需要 `video`、`startMs`、`overrideMs`；
`positionMs` 语义收窄为「文字用的秒级位置」，注释写明。

**纯函数**：`lib/player/timeline.ts` 加 `progressRatio(positionMs, durationMs)`。

**验收**：§0 第 1 条。**风险**：iOS 低电量模式 rAF 降到 30fps（可接受）。

### A2 桌面微交互对齐（P2，顺手） ✅

圆点 `hover: scale(1.2)`、`active: scale(1)`（ArtPlayer 同款，按下有回弹）。
纯 CSS，跟 A1 一起做。

### B1 触屏双击左右 ±10 秒（P1） ✅

**要推翻一条旧决策**：`video-player.tsx:1691` 现在写着「触屏的双击就是两次
控制层开关，净效果回到原状」。双击左右快退快进已经是肌肉记忆，值得改，改完
在 `web-player.md §6.5` 记一笔。

**判定**：不用 `dblclick`（触屏上不稳），照 ArtPlayer 的做法自己数 tap，
300ms 窗口。画面横向三等分：左 1/3 双击 → `seekBy(-10)`；右 1/3 双击 →
`seekBy(+10)`；中 1/3 维持控制层开关（整块画面当暂停键的误触代价我们吃过）。

**单击不能被拖延**：第一次 tap 照旧立刻切控制层；第二次 tap 命中左右区时
触发 seek，并把控制层恢复到第一次点之前的状态，净效果就是只 seek。

**纯函数**：`lib/player/tap.ts` 的 `resolveTap({ nowMs, lastTapMs, xRatio })`。

### B2 长按倍速（P1） ✅

**触发**：按住画面 500ms（ArtPlayer 用 1000ms，偏迟钝）→ 倍速；松手/取消/
手指移动过门槛（说明是横滑）立即还原。

**倍数**：统一 **2×**，不做 3×。转码会话是边转边给的单向流，3× 必然追上
编码器，用户得到「快进两秒然后转圈」，比没有更糟。2× 也要带护栏：
`stall.ts` 判到 starve（缓冲耗尽）时自动退出倍速并提示一次。

**细节**：`preservesPitch = true`（Safari 还要 `webkitPreservesPitch`）；
长按结束要**吞掉那一次 click**；HUD 复用现有胶囊。

**纯函数**：`lib/player/hold-speed.ts` 状态机。

### B3 横屏锁屏（P1） ✅

横屏时控制层加一颗锁。`isLock` 为真时所有触摸手势（横滑、竖滑、tap、长按）
一律 return，控制层不再被唤出，只留解锁键悬浮 3 秒后淡出。锁屏优先级高于
`chromeMustStayVisible`。

### B4 连按快进合并成一次 seek（P0，新增） ✅

**问题**：`seekBy` 每次调用都立刻 `seekToFileMs`。转码会话下一次 seek 可能
就是一次「杀 ffmpeg → 换会话/重启直奔目标」，连按三次 ⟳10 就是三次重启，
画面黑三次才走到 +30 秒——这是「不丝滑」里最难受的一种。

**方案**（照 Jellyfin emby-slider 的 keyboardDragging）：`seekBy` 只累积
落点并立刻更新 UI，防抖窗口内没有新按键才真正提交一次 seek。

- 窗口取 **400ms**（Jellyfin 用 1000ms，单次快进要等 1 秒才动，太钝）。
- **判据是「这一跳贵不贵」**：有转码会话 **且** 落点不在已缓冲区间内才合并。
  实施时纠正过一次——最初按 `seekBeyondBufferedRestarts` 判，而 VOD 预生成
  列表下它恒为 false，可那条路上服务端**照样**会按分片请求把 ffmpeg 杀掉
  重启（只是不换会话而已），最常见的转码路径反而不会合并。同一条判据
  （`isCheapSeek`）也给 C2 的拖动跟随用：便宜就跟，贵就等松手。
- UI 侧现成：`flashSeek` 已经在累加显示（连按三下显示 ±30 秒），累积落点
  正好喂给 A1 的 `overrideMs`，进度条同步跟着走。
- 键盘 J/L/←/→ 与中央 ⟲10/⟳10 走同一条路。

**纯函数**：`lib/player/seek-batch.ts` —— 累积器 + 该不该防抖的判定。

**验收**：§0 第 4 条；转码会话下连按三次，服务端日志只出现一次重启。

### C1 进度条章节标记 + 气泡三合一（P1，数据现成） ✅

后端 `services/library/chapters.py` 已经算好有效章节，详情页与 Jellyfin 协议
都在用，播放器没画。

- **后端**：会话/决策响应加 `chapters: [{start_ms, title}] | null`，复用
  `_chapter_views` 的 `effective_chapters`。只带时间和标题，**不带图**
  （预览图由 trickplay 负责）；**合成章节（`synthetic`）不下发**——等距分段
  没有信息量，画出来就是一排毫无意义的竖条。
- **前端**：轨道上按 `start_ms/durationMs` 画竖条；把**章节名并进现有的
  trickplay 气泡**（Jellyfin 的气泡是「缩略图 + 章节名 + 时间」三合一，
  拖动时知道自己拖到了哪一段，比只有时间有用得多）。
- 不做「点竖条跳章节」：小目标在手机上点不中。

### C2 拖动实时跟随（P2，谨慎）✅

松手才提交是转码会话逼出来的规矩（拖动中每次 move 都跳会让服务端一路杀
ffmpeg 重启）。但跳转不要钱时没有理由不跟随：**档 0 直出**（整个文件随便跳）
或**落点已在缓冲里**（数据就在手上）就跟着手指走，其余情况维持松手提交。
节流 100ms：hls.js 在列表内跳转会取消在途分片请求，一秒跳六十次反而让缓冲
永远建立不起来。判据与 B4 共用 `isCheapSeek`。

### C3 回拖不再必然重取分片（P1，新增） ✅

`engine.ts` 的 `BACK_BUFFER_S = 30`：回拖超过 30 秒就要重新请求分片，转码
会话下还可能触发服务端重启——而回拖恰恰是最常见的操作（没听清、走神）。
Jellyfin 反着来：客户端 `backBufferLength: Infinity` + 服务端默认**不删分片**
（`EnableSegmentDeletion = false`），所以回拖零成本。

我们不必上 Infinity（长片内存确实会炸，那条注释是对的），但 30 秒太紧。
提到 **180 秒**（约 4Mbps × 180s ≈ 90MB，可接受），并在 QoE 里盯一段时间的
内存与卡顿指标；同时确认服务端会话目录内已产出的分片在会话存活期间不被清理
（`_enforce_disk_watermark` 的水位是否会误伤当前会话的历史分片）。

### D1 hls.js 解码错误就地恢复阶梯（P0，新增） ✅

**问题**：`engine.ts` 现在遇到 fatal `MEDIA_ERROR` 直接 `onFailed` → 降档。
用户看到的是画质掉一级 + 几秒黑屏，而这类错误（buffer append error、
bufferStalledError 后的解码器抽风）hls.js 自己往往就能救回来。

**方案**（照 jellyfin-web `handleHlsJsMediaError`）：

1. 第一次 → `hls.recoverMediaError()`（重建 SourceBuffer，不重新拉流，
   通常 1 秒内恢复）；
2. 3 秒内又来 → `hls.swapAudioCodec()` + `recoverMediaError()`（音频编解码
   选错是这类错误的常见成因）；
3. 再来 → 才 `onFailed` 走降档。

与 `stall.ts` 的关系要理清：`decode-stalled` 判定（8 秒没进展且缓冲充足）
仍然走降档，但它的**前面**多了这两级便宜的自救；两条路都要记 QoE 事件，
否则「恢复了几次」这件事在遥测里彻底看不见。

### D2 direct 档的错误重挂（待评估，先不做）

### G 外网播放：拖进度不顺 + 换流闪黑屏（P0，新增，2026-09-08 第七轮）

真机反馈：**局域网里挑不出毛病的三件事，在外网上全线暴露**——拖进度反应慢、
切进度会闪一下黑屏、而且完全不知道该怪谁（网慢？服务端转得慢？）。
根因是三件互相独立的事，分开修。

#### G1 落在缓冲里的跳转不该掐掉取流管线 ✅

`engine.ts` 的 `HlsEngine.seek()` **对每一次跳转**都
`stopLoad()` + `startLoad(target, true)`。这套是给「跳到没缓冲的地方」准备的
重手段：它把在途的分片请求整个取消。局域网上重下一遍只是几十毫秒，外网上
是把已经下了大半的几百 KB 白扔，而且重新装载会先清缓冲——**这本身就是一次
黑屏**。

而走到这条路的跳转里，有一大半落点其实已经在缓冲里：进度条松手提交、回拖
（C3 之后有最多 180 秒的已播缓冲）、连按 ±10 秒没跳出去。这些数据就在手上，
hls.js 自己的 `seeking` 处理器接着往下续就行，什么都不用我们插手。

**方案**：落点在 `video.buffered` 之内就只写 `currentTime`，直接返回。
判据复用 `timeline.ts` 的 `isWithinRanges`，与 B4/C2 的 `isCheapSeek` 同源。

#### G2 冻结帧：换流与远跳不再黑屏 ✅

**黑屏不是错觉，是 MSE 的必然**：hls.js 处理越出缓冲的跳转时会清掉当前那段
SourceBuffer 从新落点重新装载；换会话更彻底——引擎销毁把 `src` 摘干净。
这两种情况下 `<video>` 手里一帧都没有，浏览器只能画黑（挂了 poster 就闪一下
海报，同样是「画面没了」）。局域网上这段空窗一两百毫秒看不太出来，外网上是
实打实的两三秒。

注意这**不是**已经修过的那两条：暂停压暗层的反复淡入淡出（2026-08-26）和
起播转圈的 450ms 延迟都还在，它们盖的是别的洞。

**方案**（`lib/player/freeze-frame.ts`）：跳转/换流**之前**把当前帧
`drawImage` 进一张常驻 canvas，盖在 `<video>` 上（同样的 `object-contain`，
盖上去画面纹丝不动），等新位置真的出画了再撤。用户看到的是「画面停住 →
转圈 → 新画面」，而不是「黑屏 → 转圈 → 新画面」。

- **哪些时刻冻**：凡是会让 `<video>` 一帧不剩的动作——seek 换会话、seek 出
  缓冲、换画质、换音轨、换烧录字幕、取流断了原地重开。落在缓冲里的跳转
  **不冻**：本来就不会黑，多盖一层反而让本该瞬时的跳转看着像卡了一下。
- **撤的判据必须宽**：`seeked` / `playing` / `canplay` / `timeupdate` 四个
  事件轮流问同一个纯函数 `canReleaseFreeze`（不在 seeking 中且
  `readyState >= HAVE_CURRENT_DATA`），外加 15 秒硬时限与「进报错/同意态、
  切集立刻撤」。**撤不掉的代价是画面永远冻着而声音在走，比黑屏糟得多**，
  所以宁可早撤一帧也绝不能漏。
- 抓不到帧（还没出过画、跨源没带 CORS 头）就什么都不做，黑屏照旧——盖一张
  空白 canvas 比黑屏更糟。
- 4K 源缩到 960 宽再画：这张图的全部意义只是骗过那两三秒，原样画进 canvas
  是 8MB 的一次分配，手机上光这下就够卡一下。

#### G3 取流速度读数 ✅

外网上最难回答的问题是「现在到底卡在谁身上」。没有读数时用户只能看着转圈
猜，我们看日志也只能猜。**一行实测速度就把这件事一刀切开**：速度贴着码率跑
= 线路吃得下、卡的是服务端转码；速度远低于码率 = 带宽不够，该降一档画质。

口径是本条唯一的设计点（`lib/player/bandwidth.ts`）：

- **传输期速率**（字节 ÷ 真正花在传输上的时间），不是墙钟平均。墙钟口径在
  缓冲喂饱之后会掉到接近 0——线路明明很好，读数却在报警。
- **服务端等待不算进分母**。转码会话是边转边给的，一个分片请求可能先在服务端
  挂几秒等 ffmpeg 追上来（`ensure_segment` 最长挂 30 秒）。那几秒一个字节都
  没在传，算进去速度被压到十分之一，然后用户以为自己宽带坏了。所以取
  hls.js `stats.loading.first`（首字节到达）而不是 `start` 作为传输起点。
- **直出档没有字节计数可数**（`<video src>` 什么都不给），只能用「两次
  `progress` 之间缓冲涨了几秒 × 台账码率」反推，且只在
  `networkState === NETWORK_LOADING`、间隔不超过 2 秒时采样。误差来自码率是
  全片均值，对「够不够」这个量级的判断够用。
- 样本不够（<64KB 或 <120ms）**不给读数**，界面上那一格直接不出现。宁可不
  显示也不显示错的。

**界面位置**：控制条时间药丸旁边一颗同款药丸（「↓ 3.2 MB/s」）——「现在下得
动吗」和「放到哪了」是同一类持续关注的读数，凑一起扫一眼就够；右上角那排是
按钮区，塞读数进去会让人想去点它。另外**起播/缓冲转圈下方补同一行**：那正是
用户最想知道「到底是谁慢」的时刻。诊断面板里与「实时码率」并排（单看任一个
都会误诊）。

单位用 MB/s 而不是 Mbps：用户对下载速度的全部直觉来自下载器和浏览器下载条，
换成 Mbps 会让人以为快了八倍。

#### G4 远跳盖「落点的缩略图」，不是上一帧 ✅

G2 落地后又有一条反馈：**拖远和拖近的感受还是不一样**。把远跳这条路逐段量
过之后，结论是它已经贴着物理下限了，剩下的差距要用感知手段去填。

**远跳的耗时构成**（VOD 按需供片，`session.py` 的 `_maybe_restart_for`）：

| 段 | 时间 | 还能压吗 |
|---|---|---|
| 客户端请求分片 → 服务端判定要重启 | 1 个 RTT | 不能，外网就是这么远 |
| 杀掉 ffmpeg，`-ss` 从目标关键帧重启 | 0.3~1 秒 | 已经是 input seek（`-ss` 在 `-i` 之前） |
| 编出**一整个** 4 秒分片 | 1~3 秒 | 见下面「没采纳」的第一条 |
| 分片下行 | 码率 ÷ 带宽 | 不能，这就是 G3 那行读数量的东西 |

`-readrate_initial_burst 60` 已经让每次重启后的头 60 秒全速转（不受 1.5 倍
限速拖累），`_RESTART_AHEAD_SEGMENTS = 1` 已经把「干等转码追上来」换成「超前
一段就杀掉直奔」。也就是说**服务端这条路已经调到头了**，2~6 秒是结构性的。

那就换个方向：远跳与近跳的体感差别，有一大半根本不是「等得久」，而是
**等的时候屏幕还停在原地**——用户已经把进度条拖到 1:20:00，画面却还是
0:40:00 那一帧，这一拖看着像没生效，直到几秒后画面才忽然换过去。

**方案**：G2 的冻结帧在远跳时盖的不再是上一帧，而是**落点的 trickplay
缩略图**（图源就是进度条气泡在用的那张雪碧图，多半已在浏览器缓存里）。
视觉上这一跳当场就落地，之后等的只是「动起来」。YouTube 的 storyboard、
Netflix 的远跳都是这么处理的。

两步走，保证任何时候都不黑：先同步抓当前帧盖上（雪碧图要现加载），缩略图
到手再原地换成落点那一格；没有 trickplay 索引（还没生成）就停在第一步。
在途的缩略图用一个自增 token 作废——晚到的那张绝不能把已经出画的画面重新
盖回去，而远跳时缩略图与首帧常常是前后脚到。

雪碧图缓存留最近四张：一张解码后就是几 MB，连着远跳十几次能攒出几十 MB；
连按快进反复要的是同一张，四张够接住。

#### G5 想过但没采纳

- **分片时长 4 秒 → 2 秒**：直接把「编出一整个分片」的时间对半砍，是唯一
  真能压缩远跳等待的服务端手段。**但这是在翻 `ffmpeg_args.SEGMENT_SECONDS`
  已经权衡过的账**：2 秒列表对两小时的片是三千多行、请求数翻倍（外网上每
  个请求都是一个 RTT，前向缓冲反而更容易断），而它换来的是远跳快 1~1.5 秒。
  这笔账要不要翻，得先有真机数据，不能凭感觉改。
- **拖动停顿时预热落点**（手指停住 500ms 就先去请求那一片，让 ffmpeg 提前
  动身）：看着诱人，实际是负收益。预热就是一次真实的分片请求，会触发
  `_maybe_restart_for` 杀掉当前 ffmpeg 直奔预热点；用户接着又拖到别处，
  真正的落点还得再重启一次——**猜错一次就是把等待翻倍**。拖动路径上不该
  有会杀进程的动作。
- **进度条画出「服务端已转出区间」**（让快慢可见）：信息是对的，但它不让
  任何事情变快，而且要给心跳响应加字段、给进度条加第三层底色。等真有人
  问「为什么这里快那里慢」再说。
- **回拖为什么反而快**：值得记一笔——服务端在会话存续期间不删已产出的分片，
  所以往回跳到已转出的区间时 `ensure_segment` 直接命中文件，**不重启
  ffmpeg**，只剩 1 个 RTT + 下行。前端这侧再配上 C3 的 180 秒已播缓冲，
  回拖基本是即时的。慢的只有「往前跳进还没转过的地方」这一种。

### F 小项集合（P2，攒一批一起做）

- ✅ **起播 seek 收紧**：目标与当前差 <1 秒就不 seek。VOD 列表里流本来就从
  目标分片起，再赋一次 `currentTime` 会打断刚建立的缓冲，首帧要多等一拍。
- ✅ **暂停时逐帧步进**：`.` / `,` 各走一帧，帧率取台账 `source.frame_rate`、
  未知按 24 兜底（宁可一次走得偏少——多按一下总比跳过想看的那一帧强）。
- ⏸ **快退/快进步长可配置**（Jellyfin 默认后退 10 / 前进 30 且可改）：**暂缓**。
  它的血脉比看上去长——中央簇那两颗按钮的图标把「10」直接画进了 SVG，还牵动
  aria-label、键盘映射、双击跳转四处取值。为一个 P2 便利项改图标与四处调用，
  不如等倍速菜单一起做（那时设置面板本来就要动）。
- ⏸ **高码率下调小前向缓冲**（jellyfin-web 在 ≥25Mbps 时把 `maxBufferLength`
  从 30 压到 6，规避 hls.js#876）：**按本条原定的条件暂缓**——先在 QoE 里看
  有没有对应现象，有再加这个分支。凭别人的阈值给自己的播放路径加条件分支，
  等于把一个没验证过的假设写进代码。

### E 明确不做

- **迷你进度条**：`web-player.md` 已拍板全出全收，不因为别人有就翻案。
- **3× 倍速**：见 B2。
- **服务端 ffmpeg 节流**（Jellyfin `TranscodingThrottler`：客户端领先 60 秒
  就给 ffmpeg 发暂停键）：Jellyfin 自己在 10.11 的迁移里把它**默认关掉**了
  （`DisableTranscodingThrottling`，理由是「对某些格式是坏的」）。我们用
  `-readrate 1.5` 达到同样目的且没有暂停/恢复的状态机，不引入。
- 截图 / 弹幕 / 画面翻转 / 长宽比：与本项目定位无关。

## 6. 参考源码结论

### 6.1 ArtPlayer（2026-09-08）

四条并入 §2：rAF 重绘（A1）、长按倍速（B2）、自己数 tap 的单/双击判定（B1）、
锁屏（B3）。小的三条：`preload` 在 Safari 用 `auto` 其余 `metadata`；所有跳转
走单一入口（我们的 `seekToFileMs` 已经是）；notice 统一 2 秒节流（我们的
两段式退场更细）。

不学的：它的 seek 就是 `currentTime = clamp(...)` 一行，没有会话/降档概念。

### 6.2 Jellyfin + jellyfin-web（2026-09-08）

**客户端（jellyfin-web）**，四条新条目：

- `handleHlsJsMediaError` 的三级恢复阶梯 → **D1**（我们缺得最明显的一条）。
- emby-slider 的 `KeyboardDraggingTimeout = 1000`：键盘调整只改本地值，
  静默 1 秒后才发一次 `change` → **B4**。
- `backBufferLength: Infinity` → **C3**（我们 30 秒太紧）。
- 气泡「缩略图 + 章节名 + 时间」三合一 → 并入 **C1**。

佐证既有决策的两条：`setBufferedRanges` 只画包含播放头的那一段（与我们
「只认播放头所在那段连续缓冲」的注释同一个理由）；进度条的 DOM 写入全部
放进 rAF 并 `cancelAnimationFrame` 合帧（A1 的实施细节照抄）。

注意**它并不是 60fps**：`updateValues` 由 `timeupdate` 事件和一个 100ms
`setInterval` 驱动，rAF 只是合帧不是驱动源。所以进度条平滑这件事，
ArtPlayer 的 `USE_RAF` 才是范本，Jellyfin 不是。

**服务端（jellyfin）**，`DynamicHlsController.GetDynamicSegment` 是核心：

| 请求的分片 | Jellyfin 的处置 | 我们的处置 |
|-----------|----------------|-----------|
| 已在磁盘上 | 直接给（回拖不重启） | 同（`completed_segments` 台账） |
| 早于当前转码头 | 杀掉重启直奔该段 | 同（带 `_PROBE_GRACE_S` 宽限，防 iOS 的 seg0 连发） |
| 超前转码头 ≤ 24 秒 | **等它转过来** | 超前 >1 段就重启 |
| 超前 > 24 秒 | 杀掉重启直奔该段 | 同 |

差异只在「超前多少才值得重启」：Jellyfin 24 秒，我们 1 段（约 4 秒）。
我们的注释里有实测理由——`-readrate 1.5` 限速下等转码追 n 段要 n×4/1.5 秒
（最长 16 秒），而重启直奔实测 1~3 秒。**这是被 readrate 逼出来的取舍**，
留一个待验证的实验：seek 之后短暂解除 readrate 让 ffmpeg 冲刺，追上再回到
1.5——那样短距离前跳就可以「等」而不必重启，省掉一次前向缓冲的丢弃。
不排期，等 A1/B4 落地后看 QoE 里前跳的实际分布再说。

分片就绪判据上我们更准：Jellyfin 用「本片存在**且**下一片也存在」来绕开
「ffmpeg 正在写这一片」，我们直接读 `live.m3u8` 台账（远端走原子替换），
不靠下一片的存在来推断。

另外两条只作记录、不改：Jellyfin 默认**不删分片**（`EnableSegmentDeletion
= false`，开了也保 720 秒），配合客户端 Infinity 回退缓冲，是他们回拖顺滑的
根本原因（对应我们的 C3）；`TranscodingThrottler` 已被他们自己默认关掉，
见 §2.E。

## 7. 端到端验收（2026-09-08）

真浏览器 + 真视频 + 真后端跑通，脚本落在 `scripts/perf/e2e_player_feel.py`
（Playwright + 本机 Chromium，用法见文件头）。

**样片**：ffmpeg 合成 120 秒 480×270、VP9 + Opus、每 2 秒一个关键帧、内嵌三个
章节（0 / 40 / 80 秒）。**为什么不用 H.264**：Playwright 的 Chromium 不含专有
解码器（`canPlayType('video/mp4; codecs="avc1…"')` 返回空串），VP9 + Opus 封进
mp4 才能在这台浏览器里真的出画面，同时仍然走档 0 直出这条路。

一次实跑：

```
首帧 1032 ms（rVFC）
✓ 进度条匀速：1.2 秒内 73/73 帧取值不同
✓ 双击前进十秒：+11.28 秒
✓ 长按倍速：按住 2× → 松手 1×，保音高 True
✓ 拖动跟手：拖动中画面走到 [36.0, 42.1, 48.1]
✓ 章节刻度：['33.3333%', '66.6667%']，气泡 ['中段', '1:00']
✓ 逐帧步进：暂停后走了 0.042 秒
```

第一条是本次改动的直接度量：跟着 `timeupdate` 走时 1.2 秒内只有个位数个不同
取值，每帧自绘则等于采样数本身。章节刻度只有两条——0 秒那条按 C1 的规则不画。

**D1 的自救阶梯已在真会话上验过（2026-09-08 第四轮补）**：让 Chromium 去播一路
真的档 1 HLS 会话，它解不了 H.264，服务端日志按顺序收到
`hls-media-recover{step:recover}` → `{step:swap}` → `hls-media-recover-failed`，
之后才落到降档与错误页——正是设计的三级。`backBufferSeconds` 的接线
（FRAG_LOADED 实测码率 → 收紧保留时长）在这台浏览器上够不着：编解码错误发生
在初始化段解析时，媒体分片根本没机会加载完，那条只有纯函数单测。

**转码 / HLS 的正常播放不在浏览器里验**（同一个原因：Chromium 解不了 H.264），
改走真 HTTP + 真 ffmpeg：起一路档 1 remux 会话 → 拉 VOD 列表（30 个分片、
覆盖全片 120 秒）→ **直接请求最后一个分片**（模拟拖到片尾，走服务端「按分片
请求杀掉 ffmpeg 重启直奔目标」那条路），188 毫秒返回 200 → 把 init + 30 个
分片顺序拼起来，`ffprobe` 解出 120.05 秒的 h264 + aac，`ffmpeg -f null` 全片
解码零报错。

两条如实记录：`tests/api/test_playback_e2e.py` 的四个用例在本容器里等分片
超时，**同样的失败在改动前的基线上复现**，是环境问题不是回归（上面那条真
HTTP 路径覆盖了它们要验的东西）；D1 的自救阶梯要构造坏流才能触发
`MEDIA_ERROR`，本轮只有纯函数单测覆盖，标为真机待验。

## 8. 复查订正（2026-09-08 第二轮）

对着 jellyfin-web 把上一轮的实现逐处再看一遍，改掉八处：

**自己的疏漏（五处）**

| 处 | 症状 |
|----|------|
| 片长转未知时 `paint` 直接返回 | 上一路会话画的宽度留在条上，成了与新内容无关的进度 |
| 合帧没算上 rAF 循环 | 循环在跑时 `timeupdate`/`seeked` 还会再排一帧，同一帧写两次 |
| 双击链断在跳转那一下 | 连点第三下退回「开关控制层」，而胶囊上的累加读数还在往上走 |
| 合并计时器扣着旧闭包 | 那 400 毫秒里会话可能已换过一轮（降档/换轨/自愈），旧闭包拿过期的 session 去跳 |
| 章节数组每次渲染换身份 | 下游 `useMemo` 白算一遍 |

**对照 jellyfin-web 补上的（三处）**

- **气泡贴边要夹回轨道内**：气泡按触点居中，拖到两端时有一半探出播放器
  （加了章节名之后更宽更明显）。ArtPlayer 的 `showTime` 与 jellyfin-web 的
  `updateBubble` 都在这里夹一次，我们此前漏了。
- **媒体会话只做了一半**（§6.5 把它列为 P0）：补 `seekto`——锁屏/通知栏那条
  进度条能拖靠的就是它，`seekbackward/forward` 是「±10 秒」按钮顶不了位；
  补 `previoustrack`（上一集的回调本来就有）；补 `setPositionState` 喂位置与
  时长，否则注册了 `seekto` 却没有位置可拖，比不注册更奇怪。
- **`maxMaxBufferLength` 跟着钉死**：只设 `maxBufferLength` 的话 hls.js 仍会
  在码率低时把目标一路涨到默认的 600 秒，而 C3 刚把回退缓冲放宽到 180 秒，
  前后加起来十几分钟的解码数据挂在 SourceBuffer 上——正好撞回那条「长片放到
  一半标签页没了」。jellyfin-web 两个都设。

复查中确认**不必改**的几处（记下来免得下次重复查）：`-force_key_frames` 强插
关键帧对齐分片栅格、进度上报 10 秒一次 + 暂停/恢复即时补报、缓冲段只画播放头
所在那一段、分片请求挂起等待而不是 404——这几条与 Jellyfin 同构或更细。
`playbackState` 两边都没显式设（浏览器按页面里的 video 自己推），不跟。

## 9. 再复查（2026-09-08 第三轮）

又找出五处，前两处是真会伤到手感的：

- **拖动跟随走了重手段**：`scrubTo` 调的是 `engine.seek()`，而它内部是
  `stopLoad()` + `startLoad(target)`——那是给「跳到没缓冲的地方」准备的：
  把在途的分片请求全掐掉重来。拖动跟随一秒十次地掐断加载管线，恰恰把这条
  路本来想改善的手感反过来毁掉（拖完缓冲是空的）。跟随只在数据已经在手上
  时才发生，直接改 `currentTime` 就够。实测拖完前向缓冲仍有 7.5 秒。
- **绝对跳转没撤在途的连按累积**：数字键跳百分比、逐帧步进都直接改位置，
  没经过 `commitSeek`——用户连按两下快进又改主意按「5」，那个 400 毫秒的
  计时器会在之后把画面拽回连按的落点。两条都改走撤销路径。
- **锁屏按钮只认自己的横屏键**：多数人是直接把手机转过来（系统自动旋转），
  根本不会去按播放器的横屏按钮——最需要防误触的那批人反而看不到这颗按钮。
  加 `(orientation: landscape)` 媒体查询一起判。
- 端到端脚本按「轨道里的第二个子元素」找已播段，轨道里多加一层就会悄悄量
  错东西。改成 `data-player-played` 锚点。
- （复核确认无误）连点第三下现在确实继续累加：真机脚本实测三下 = +20 秒
  （第一下是唤出控制层，之后每下 10 秒，与 YouTube 一致）；片头连点两下
  夹在 0 而不是负数；气泡拖到最右端 overflow 为 0。

## 10. 第四轮：伪横屏下整套坐标换算是错的（2026-09-08）

**这一轮找到的是本系列里最严重的一个，而且它比这次的改动早得多。**

iOS Safari 没有元素级全屏，所以横屏走的是 CSS 伪横屏——整个 `.player-root`
`rotate(90deg)`。转过来之后，元素的**布局 x 轴沿物理 y 轴**，而
`getBoundingClientRect()` 给的是旋转后的外接矩形。真机尺寸视口（390×844）
实测：进度条的外接矩形是 **44 × 788**，`rect.width` 是它的**厚度**。

于是 `(e.clientX - rect.left) / rect.width` 这个写法（进度条的按下、拖动、
悬停预览三处都是它）在 iPhone 横屏下等于**把整部片映射到 44 个物理像素上**：
手指沿用户眼里的横向拖，clientX 几乎不变、进度条不动；而横跨条厚度的一点点
抖动却是几分钟的跳变。同一个坑也套住了本轮新加的双击分区（它按物理 clientX
三等分，转过来之后分区跑到竖直方向上去了）。

`touch-adjust.ts` 里本来就有 `toLayoutPoint` 处理这件事——**滑动手势做了换算，
进度条与轻点没有**。补一个同源的 `pointerOffsetX(point, rect, fakeLandscape)`，
三处进度条换算与双击分区一起改走它。

验证（Chromium 按掉元素级全屏 → 走的正是 iPhone 那条伪横屏）：拖到七成落在
84 秒（= 0.7 × 120，此前恒定落在 60 秒），双击右/左 = +10 / −10 秒。这一条已
并入 `scripts/perf/e2e_player_feel.py`，作为第 6 条验收长期盯着。

同轮另外三处：

- **C3 自己埋了一颗内存雷**：`backBufferLength` 的单位是**秒**，而 180 秒在
  4Mbps 的片子上是 90MB、在档 1 原样封装的 4K 蓝光原盘（80Mbps）上是 **1.8GB**
  ——标签页必崩，正是 C3 那条注释想避开的事故，被我自己用一个常数请了回来。
  改成按**字节预算**（96MB）反推秒数，上限 180 下限 30，码率由 `LEVEL_LOADED`
  带回来后立刻收紧（那时连 30 秒都没播到，收得及）。
- **长按松手要吞的那次 click 会泄漏**：浏览器不一定补 click（Android 长按弹
  菜单就没有），标记留着会把**下一次正经轻点**吞掉。新一次触摸开始就清掉。
- **缓冲告急掐得太宽**：`waiting` 在正常播放里也会发（seek 之后、转码会话追
  编码器时），而它当时会把**刚按下去还没生效**的长按一并否掉，表现是「按住
  了却没反应」——那 500 毫秒里根本没有倍速在吃缓冲。改成只掐已经生效的。

## 11. 第五轮：对着「顶级播放器的常识」再筛一遍（2026-09-08）

四处，前两处是**我上一轮引入的回归**：

- **拖动跟随把 QoE 指标搅了**：跟随每 100 毫秒写一次 `currentTime`，每次都发
  `seeking`。QoE 的 `seek_count` 于是从「用户跳了几次」变成「写了几次
  currentTime」，一次拖动记十几次，指标废掉。改成：一次拖动只记第一次
  （他确实跳了），之后的写入按同一个动作算。
- **状态机每次 seeking 都造新对象**：`{...state, phase: "seeking"}` 在相位
  已经是 seeking 时照造不误——配上跟随的每秒十次，就是每秒把整个播放器重
  渲染十遍。相位没变就返回同一个对象。
- **防息屏只申请了一次**：规范规定文档转入后台系统就把锁收走，且此时
  `request()` 直接拒绝。用户切出去回个消息再回来，锁就永远没有了，电影放到
  一半屏幕自己暗下去——而这正是这段代码要防的事。**那条注释一直写着「回来
  时重新申请」，但没人真的写。** 补 `visibilitychange` 重新申请，并监听
  `release` 把手上的引用丢掉（否则回到前台会以为还锁着）。
- **拖动跟随改用 `fastSeek`**：浏览器专门为「拖动预览」准备的接口——就近落
  在关键帧上，省掉从关键帧解到精确帧的那段解码。Safari / Firefox 有，Chrome
  至今没有，所以要探测。松手那一次仍走精确 seek（落点差半秒用户看得出来）。

**考虑过但明确不做的**（记下来免得下次又想一遍）：

- **`startFragPrefetch`（hls.js 的起播预取）**：看着是白捡的首帧优化，对我们
  却是**有害的**——它会在 attachMedia 之前就把「第 0 段」的请求发出去，而
  `EngineOptions.startPositionS` 的注释里写得很清楚：服务端的按需供片会把这个
  杂散请求当成「seek 回开头」，杀掉刚在续播点起好的转码从头重启。续播直接
  变成从零转。
- **下一集预取**（Netflix 派：片尾提前拉下一集的头几段）：真正的优化，但它要
  和「会话并发额度、转码配额、自动连播是否开启」一起设计，不是播放器单方面
  能定的事，留给后续。
- **片尾兜底**：最后一个分片取不到时，播放器会停在 99.9% 直到停顿看门狗按
  「供流中断」判死（45 秒）再降档，而正确的处置是当成播完。hls.js 的
  `endOfStream` 覆盖了正常情况（我们的列表带 `#EXT-X-ENDLIST`），只有「末段
  一直取不到」才会踩到，本轮不动它，记在这里。

## 12. 第六轮：生命周期与「拖动中控制条自己没了」（2026-09-08）

- **在途的连按合并会活过切集**：播放器在切集时**不重挂**（player-page 没给它
  key，只换 unit），那个 400 毫秒的计时器于是活了下来——用户在片尾按一下快进、
  随手点「下一集」，400 毫秒后它把**新一集**跳到上一集的落点上。换集时撤掉。
- **触屏拖动进度条时控制条会自己淡出**：拖动不算「活动」，四秒倒计时照走。
  指针捕获让拖动照旧生效，于是手指底下的进度条消失了、人还在拖，松手才知道
  跳到哪儿。CDP 派真触摸事件复现：修复前第 3.5 秒起 `data-chrome` 变
  `hidden`，修复后全程 `visible`。
  **桌面遮住了这个 bug**：鼠标的 pointermove 会顺带重排倒计时，只有触屏踩得到
  ——这也是为什么排查时必须用真触摸事件，`page.mouse` 验不出来。

## 13. 为什么每轮都还有新 bug，以及怎么系统性地收口

前后六轮复查，每轮都还能找出新的。**这说明「再仔细看一遍」不是方法**——它
只是把同一双眼睛再用一次。把这一路的 20 多个 bug 按根因归类之后，它们其实
只有七类，每类都有一个「让这类不可能再发生」的做法：

| 类别 | 这一路踩到的 | 为什么「再看一遍」抓不到 | 结构性对策 |
|------|-------------|------------------------|-----------|
| **同一个量有两份真相** | 落点胶囊 9:58 vs 进度条 19:00；文字读数与自绘各算一遍 | 两处各自都读得通，只有并排看才看得出不一致 | 收敛成**一个纯函数**：`shownPositionMs`（§13.1） |
| **判据用了近似量** | 连按合并按「会不会换会话」判，而真实成本是「落点在不在缓冲里」 | 近似在大多数路径上恰好成立，测不出来 | 判据也做成纯函数、名字直接写成本：`isCheapSeek` / `seekBatchWindowMs` |
| **坐标系与单位** | 伪横屏下的 `clientX`；`backBufferLength` 的「秒」× 码率 = GB | 类型系统看不出 px 与 px、秒与秒的区别 | 换算收进一个模块（`toLayoutPoint` / `pointerOffsetX`）；**带单位的量不许写字面量常数**，必须由函数算（`backBufferSeconds`） |
| **在途状态的生命周期** | 合并计时器活过切集；长按吞 click 的标记泄漏；落点胶囊被第二根手指遗弃 | 只有「中途发生了别的事」才暴露，正常路径永远正常 | 每个在途状态回答三问（§13.2） |
| **形态分叉** | 触屏拖动时控制条淡出；伪横屏坐标串轴 | **桌面路径恰好把它遮住**（鼠标 move 顺带重排了倒计时） | 端到端脚本改成形态矩阵，触屏那两档用 CDP 真触摸事件 |
| **注释承诺 ≠ 实现** | 防息屏「回来时重新申请」——注释写了十个月，代码从来没写 | 注释读起来完全合理，且没人会去验证注释 | 承诺必须落成断言：要么单测，要么端到端的一条 |
| **新行为污染既有读数** | 拖动跟随把 QoE 的 `seek_count` 灌成十几倍 | 指标在另一个文件里，改交互时根本看不见 | 改交互时必答：这条路上原来有谁在计数/上报 |

### 13.1 已经落地的收口

- **位置读数只有一份**：`shownPositionMs`（timeline.ts）定义四个来源的优先级，
  时间文字与进度条自绘都只能调它，带单测。「两个读数各说各话」这一类从此
  在结构上不可能。
- **形态矩阵**：`scripts/perf/e2e_player_feel.py` 现在跑三种形态——桌面鼠标、
  触屏竖屏（CDP 真触摸）、触屏伪横屏，八条断言。这两轮里**只在触屏出现**的
  两个 bug，都会被它挡住。
- **判定全在纯函数里**：tap / hold-speed / seek-batch / media-recover /
  buffer-budget / progressRatio / pointerOffsetX，都是「输入→输出」的表，
  单测覆盖。组件里只剩接线。

### 13.2 每次动播放器之前的必答题

不是流程仪式，是上面七类的直接翻译。**动了哪一类就答哪几条**：

1. 这个改动新增了「在途状态」吗（计时器 / 标记 / 累积值）？**谁清它？切集
   清不清？组件不重挂时清不清？被别的入口接管时清不清？**
2. 它引入了新的「当前位置 / 当前状态」的读法吗？能不能改成调已有的那个函数？
3. 它碰了坐标或带单位的量吗？伪横屏下还成立吗？换一个码率/分辨率还成立吗？
4. 它在鼠标与手指上行为一样吗？**只在桌面验过的，等于没验。**
5. 它经过的路径上原来有谁在计数、上报、判定卡顿？会不会被灌脏？
6. 注释里写下的承诺，有没有一条测试盯着它？

### 13.3 剩下的做不到的部分

**「修完所有 bug」做不到**，把它当目标只会自欺。能做到的是三件事：

- 把**整类**封死（§13.1），而不是逐个修；
- 把**发现成本**降到自动化：形态矩阵每次改动跑一遍，几分钟；
- 把**用户遇到 → 我们知道**的链路缩短：客户端事件（`hls-media-recover`、
  `hls-back-buffer`、nudge、降档）已经在往服务端日志里写，QoE 指标进
  `playback_metric`。**这一轮就是靠日志确认 D1 阶梯真的按三级跑的**——
  遥测不是锦上添花，它是唯一能看见真机上发生了什么的东西。

真正该盯的不是「还有没有 bug」，而是**这三条防线有没有在退化**：纯函数覆盖率
掉了、矩阵少跑一档、遥测事件没人看——那才是下一批 bug 的温床。
