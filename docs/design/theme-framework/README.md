# 主题框架插件化改造（theme-framework）

> 2026-09-21 立项。目标：把现在的 Netflix 主题从"散落在 30 个文件里的主题分支"收编为
> **一个可整体搬运的主题包**，并让"基于通用主题框架开发新主题"成为字面成立的开发方式。

## 1. 目标

1. **主题 = 插件**：一个主题的全部资产（设计变量覆盖、结构组件、专属页面）聚合在一个
   约定目录里，与业务代码只有一个交点（注册表）。预留后期"下载主题"能力（本期不实现）。
2. **布局进变量层**：页面级左右留白从 18 个文件 44 处 `isNf ? … : …` 三元表达式，收敛为
   全站 4 个语义工具类消费的 CSS 变量。新主题适配布局 = 设几个变量。
3. **结构层完整坑位注册表**：顶栏 / 底栏 / 返回键 / Hero / 专属页等组件替换点全部走
   注册表解析（含运行时回落与校验），外壳与页面不再硬编码 `components/netflix/*` import。
4. **边界纠偏**：vendor/liquid-glass 不再认识具体主题名；防闪烁脚本白名单不再硬编码。

## 2. 现状与痛点（勘察结论，2026-09-21）

主题框架已有底子：`lib/themes.ts` 注册表（纯数据 + `structural` 标记）、`html[data-theme]`
三层覆盖机制（§3.3）、防闪烁内联脚本、设置卡自动遍历渲染。痛点在四个"没长完"：

| # | 现状事实 | 位置 | 后果 |
| --- | --- | --- | --- |
| 1 | 布局留白主题判断散落：`? "px-[4vw]"` 三元重复于 **18 个文件**，全站 80 处 4vw 字面量 | media-detail / library-* / search-results 等 | 每个新页面都要手写双主题留白；第三个主题 = 主题数 × 页面数的爆炸（4vw 提交一次改 26 文件即证据） |
| 2 | 结构组件硬编码 import：外壳与 13 处页面直接 `from "@/components/netflix/*"` | app-shell / library-page / subscriptions-page / app/(app)/my 等 | 主题资产混在业务组件树里，无法整体搬运 |
| 3 | vendor 反转：`LiquidGlassButton/IconButton` 内部 `if (theme.id === "netflix") return` | vendor/liquid-glass 两个文件 | 第三方代码认识具体主题名，边界倒置 |
| 4 | 防闪烁脚本白名单硬编码 `"netflix"` + `#000000` | app/layout.tsx:108 | 新增主题必须记得改内联脚本，漏改即首帧闪烁 |

另有一处"资产放错家"：`components/netflix/brand.tsx` 的 `MovieclawMark` 被银玻璃的
brand-loader 消费（公共品牌资产，不是 Netflix 专属）。

## 3. 方案结论

维持 **单应用 + 注册表** 的既有框架，不动路由结构、不拆应用，做四件事：

1. **主题目录化**：`apps/web/themes/<id>/` 一目录一主题（`theme.ts` 定义 + `tokens.css`
   变量覆盖 + `chrome/` 结构组件 + `pages/` 专属页）。银玻璃 = 基础实现本身，不设目录
   （"无插件即默认"）。
2. **完整坑位注册表**：`themes/registry.ts` 把 `id → 坑位 → 组件` 全表化，解析时归并
   基础缺省实现，缺坑位回落、未知坑位 dev 断言、缺主题回落默认主题。
3. **布局变量层**：`--page-inset` / `--content-inset` 两组变量（按"主题 × 断点"赋值）+
   `page-inset` 系语义工具类，页面代码不再出现主题判断。
4. **边界泛化**：防闪烁脚本由注册表序列化生成；vendor 以 `glassEnabled` prop 接收能力，
   主题以 `capabilities.glass` 声明能力。

## 4. 已确认决策（用户拍板，2026-09-21）

| # | 决策 | 选择 |
| --- | --- | --- |
| 1 | 主题物理形态 | 约定目录 `apps/web/themes/<id>/`（不做 workspace 包，monorepo 不动） |
| 2 | 布局变量形态 | 纯 CSS 变量 + 语义工具类（零 JS，响应式由 CSS 管） |
| 3 | 结构层程度 | **完整坑位注册表**（id→坑位→组件全表 + 运行时回落校验） |
| 4 | 主题组件数据边界 | 允许直接调用 `@/lib/api/*`（主题是 UI 资产插件，不是安全沙箱） |

## 5. ⚑ 已拍板决定（替用户决定，附理由）

| # | 决定 | 理由 |
| --- | --- | --- |
| ⚑1 | 银玻璃不目录化：基础 token 留 `globals.css :root`，基础组件留 `components/` | 默认主题 = 无插件；少一层间接，与"纯换肤主题只需变量覆盖组"的既有文档口径一致 |
| ⚑2 | `ThemeMeta` 新增 `themeColor` 字段；防闪烁脚本由服务端从注册表序列化生成 | 消灭 layout.tsx:108 的硬编码白名单；新增主题零改动不闪烁 |
| ⚑3 | `tokens.css` 由 `globals.css` 顶部 `@import` 静态引入 | 构建期打包无运行时开销；Tailwind v4 普通 CSS import 即可，不引入动态样式加载 |
| ⚑4 | vendor 反转用 prop：`LiquidGlass*` 增 `glassEnabled`（默认 true），调用方从主题 `capabilities.glass` 取值 | vendor 回归"机制不做决策"；能力声明放主题定义处，主题知识不进 vendor |
| ⚑5 | 主题专属整页（/my、设置索引、订阅页）的路由壳留在 `app/(app)/`，内容组件从主题目录取 | Next.js App Router 路由是构建期静态的，无法由插件动态注册；这是硬约束不是设计取舍 |
| ⚑6 | `MovieclawMark`/`MovieclawWordmark` 移到 `components/brand.tsx` | 公共品牌资产被银玻璃消费，放 `components/netflix/` 属于放错家 |
| ⚑7 | 实施 = 4 个独立可回滚的提交（框架/布局/坑位/边界），银玻璃逐像素零变化为硬验收门 | 仓库既有"主题提交 + 银玻璃零变化"纪律（design-consistency 记忆） |
| ⚑8 | "下载主题"预留缝 = 目录产物 + 注册表动态 import 分支；本次不实现 | 明示：JS 主题是同源可信代码，不是安全沙箱；市场/签名/沙箱属未来独立立项 |

## 7. 范围外（本期不做）

- 主题下载 / 主题市场的分发、签名、版本管理机制（只留目录产物 + 动态 import 的缝）。
- 主题沙箱化（iframe / Web Assets 隔离）、第三方不可信主题的安全模型。
- 运行时热换 CSS（现在就是构建期打包，换主题走 `data-theme` 属性，已经够用）。
- 后端主题资产（主题 = 纯前端资产；后端只存偏好里的主题 id 字符串，现状不变）。
