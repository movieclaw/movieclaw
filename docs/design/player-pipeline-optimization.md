> **D 实测不可行**，理由与数据见 §7.4，本轮不实施。

> [player-feel.md](player-feel.md)（手感、seek 判据、节流）。本文不重复那两份

## 0. 评判口径

播放器只有两个用户可感知的数：**首帧多久出画**、**跳转多久落地**。
消耗的成本有四种：**CPU/GPU**（转码）、**盘**（IO 与空间）、**带宽**、
**复杂度**（在途状态的数量，直接决定 bug 数）。

对现有设计的评估结论（本文的出发点）：

- 前端这一半贴着原理走：直通优先、seek 便宜/贵判据统一（`isCheapSeek`）、
  连按合并、缓冲内跳转不掐管线、降档排在最后。剩下的差距是结构性的。
- 后端有三处偏离，同一个根因（NAS 盘小、CPU 弱、要防播放拖垮整个应用）：
  1. **供片速度是开环常数**（`-readrate 1.5`），把缓冲攒满的速度与 seek
     策略（`_RESTART_AHEAD_SEGMENTS = 1`）绑死；
  2. **转码产物不跨会话复用**（会话结束 `rmtree`），续播、重看、多人看同一
     片都整部重转；
  3. **单变体无 ABR**，外网弱网只能等 45 秒判「供流中断」，而那条路降的是
     编码档不是码率档。

三处都不是原理性错误，是取舍。本文给出的是「在同一前提下更贴近原理」的
改法，不是推翻前提。

## 2. 分项方案

### A. 闭环供片节流（P1）

**现状**（`ffmpeg_args.py:92` 起的常量注释，`session.py:791`）：

- 转码档 `-readrate 1.5`、直通档 `-readrate 4`，`-readrate_initial_burst 60`。
  目的是控盘：不限速时 remux 档以磁盘 IO 速度把 30 GB 的片几分钟写完。
- 副作用注释里自己写了：「1.5 倍配合前端 60 秒的缓冲目标，起播后要播满两
  分钟缓冲才攒得够，这期间任何抖动都直接 stall，实测每次会话卡 2~3 次」。
  直通档因此提到 4 倍，转码档没动。
- 更深的后果是它把 seek 策略绑死了：readrate 限速下「等转码追 n 片」要
  n × 4 / 1.5 秒，于是 `_RESTART_AHEAD_SEGMENTS` 只能设成 1，前跳 10 秒也
  要杀进程重启（1~3 秒黑屏）。两个参数互相拉扯，`session.py:791` 的注释也
  承认这一点。

**为什么开环是错的口径**：控盘要控的是**绝对量**（转码头领先播放头多少
秒 × 码率 = 盘上多少字节），readrate 控的是**速率**。速率限住了，领先量
仍然随时间无界增长（用户暂停一小时，转码头照样往前走一小时）；速率不限，
领先量又可以很小。用速率去近似绝对量，两头都不准。

**改法**：去掉 `-readrate`（或放到很高只作兜底，如 8 倍），改由服务端按
「转码头领先播放头的秒数」暂停/恢复 ffmpeg。

- **领先量**：`lead = boundaries[produced + 1] - boundaries[last_served]`。
  两个量都是现成的：`_highest_produced` 与 `ensure_segment` 里的
  `last_served_segment`。不需要给心跳加字段。
- **迟滞两档**：`lead > LEAD_HIGH_S`（建议 120 秒）→ `SIGSTOP` 整组；
  `lead < LEAD_LOW_S`（建议 60 秒，与 hls.js `maxBufferLength` 同值）→
  `SIGCONT`。机制完全复用 `_enforce_disk_watermark` 已有的
  `_signal_group` / `disk_paused` 与远程的 `registry.pause/resume`。
- **检查时机**：每次 `ensure_segment` 进入时判一次（播放头动了）；外加
  一个 1 秒的轻量循环只在有活跃本地会话时跑（播放头不动但转码头在动）。
  `REAP_INTERVAL_S = 15` 太粗，不能挂在 reaper 上。
- **两个暂停来源合并**：`disk_paused` 改成 `pause_reasons: set[str]`
  （`disk` / `lead`），任一非空即暂停，全空才恢复。`stop()` 与 seek 重启前
  先 `SIGCONT` 的逻辑保持不变（SIGSTOP 状态下 SIGTERM 会排队不生效，现有
  代码已处理）。
- **连带调参**：转码全速后，「等它转过来」变便宜（n 片 × 4 秒 / 实际倍速，
  硬件档通常 4~10 倍速），`_RESTART_AHEAD_SEGMENTS` 可以从 1 放回 3~6
  （Jellyfin 是 24 秒）。这是次级收益，**必须实测后再动**，不随本项一起改。

**利**：

- 起播与 seek 后前向缓冲以硬件速度攒满，60 秒缓冲从「两分钟才攒够」变成
  硬件档十几秒、直通档几秒。弱网抖动的容忍度直接对应缓冲深度。
- 盘占用峰值有硬上限：`LEAD_HIGH_S × 码率`。120 秒 × 80 Mbps 原盘 = 1.2 GB，
  比现在「速率限住但总量无界」更可控。用户暂停一小时，转码头停在领先 120 秒
  处，不再空烧一小时 GPU 与盘。
- 前跳 10~30 秒可以「等」而不必「杀」，少一次黑屏。

**弊**：

- 暂停中的 ffmpeg 仍占着编码器会话（NVENC 消费级有 3~5 路上限）、内存与
  一个并发槽。现在也占，只是现在它在慢慢转而不是停着；实质变化是**并发
  上限的语义不变、但每路的 CPU 占用从「持续 1.5 倍」变成「脉冲式全速 + 停」**。
  软件转码档全速时会把 NAS CPU 打满一段时间，比现在的持续 1.5 倍更「尖」。
  这是软转档用户会感知的变化：搜索、扫描在起播后十几秒内明显变慢，之后
  恢复。文档 §3.6 的同意弹窗文案要改一句。
- 多一个状态机（暂停/恢复 × 本地/远程 × 与磁盘暂停叠加）。Jellyfin 的
  `TranscodingThrottler` 就是同一机制，他们在 10.11 默认关掉，理由是「对
  某些格式是坏的」。本项目在磁盘低水位上已经真机跑过 SIGSTOP/SIGCONT，
  且只服务已完成分片（半片被暂停不影响服务），格式问题的暴露面比 Jellyfin
  小，但不能说没有。
- `-readrate_initial_burst` 一并失效，起播首片的行为不变（全速本来就是
  burst 的目标）。

**风险**：中。主要在「暂停来源叠加」与「远程 Worker 暂停恢复的往返延迟」
（远程暂停走 WebSocket，恢复要一个 RTT，`LEAD_LOW_S` 对远程要加余量）。

**验证**：

- QoE `rebuffer_ms` / 会话（现有指标）：目标从「每会话卡 2~3 次」降到接近 0。
- 服务端「分片就绪：等待 X 秒（顺序追赶）」日志分布：追赶路径的等待应缩短。
- 盘占用峰值：`du` 会话目录 ≤ `LEAD_HIGH_S × 码率 + 一片`。
- `tests/playback/test_session_manager.py` 加：领先超阈值暂停、回落恢复、
  暂停期间 stop 先 SIGCONT、磁盘暂停与领先暂停叠加时的恢复条件。

**工作量**：`session.py` 约 150 行，`ffmpeg_args.py` 删常量，测试若干。
不动运行时依赖，不 bump `runtime-version`。

### B. 转码产物延迟回收 + 按指纹复用（P2）

**现状**（`session.py:1351` `stop`、`:344` `cleanup_orphans`）：

- `stop()` 立即 `rmtree` 会话目录；180 秒无心跳即 stop；启动时目录下的
  一切都当垃圾删掉。
- 转码结果其实是（文件、档位、参数）的**确定性函数**，但每次开会话都从零
  转。续播（看到一半退出，第二天接着看）、重看、家里两个人先后看同一部片，
  都整部重转。

**改法**：

- **目录按指纹命名**，不按会话 id。指纹 = 稳定哈希（`file_id`、文件
  mtime/size、tier、`VideoPlan`、`AudioPlan` 含选中音轨、烧录字幕轨、
  `max_height`、`hw_backend`、ffmpeg 参数版本号 `FFMPEG_ARGS_VERSION`）。
  任何影响输出字节的输入都必须进指纹；漏一项就是播错流。参数版本号让
  改 ffmpeg 参数时旧缓存整体失效。
- **目录里落一份 `manifest.json`**：指纹明文、`segment_plan`、
  `completed_segments`、最后使用时间。它是跨进程的台账，替代现在只在内存
  里的 `completed_segments`。
- **stop 不删目录**，改标记为冷却（`cooling`），记最后使用时间。
- **开会话时先找缓存**：指纹命中且 manifest 可读 → 认领目录，
  `completed_segments` 从 manifest 导入，ffmpeg **不起**；第一次请求到未
  完成分片时，`ensure_segment` 现有的「进程不在且分片未就绪 → 重启直奔」
  分支自然把它拉起来。已看过的部分首帧就是读文件。
- **同指纹同时只允许一个写者**：两个会话可以同时读同一目录，但只能有一
  个 ffmpeg 在写。第二个会话要写时走现有的 `_restart_lock`，锁挂在目录上
  而不是会话上。`stop_for_file` 的语义从「杀同文件同成员的会话」改为
  「杀同目录的写者」。
- **回收策略**：LRU 按现有 `auto_quota_bytes`（剩余空间的四分之一，钳在
  2~100 GB），外加固定保留期（建议 24 小时）。启动清理改为「删无 manifest
  的目录 + 超期目录」，不再全删。`_check_disk` 的写前查盘与低水位急停
  **原样保留**：注释里那句「不要指望 LRU 跑得比写入快」在这里更成立。
- **取流 token 绑定 session_id 不变**：新会话新 id，URL 变，浏览器缓存
  自然不命中，由服务端文件缓存接住。

**利**：

- 续播首帧：从「起 ffmpeg + 转首片」（硬件档 1~3 秒、软转 5~10 秒）变成
  读文件，与档 0 同量级（< 300 ms）。这是用户最常做的动作之一。
- GPU/CPU 不重复：一部片只转一次。远程 Worker 场景收益更大，Worker 离线时
  已转部分照样能播（`_segment_ready` 已经先查文件再查 Worker 在线）。
- 多人共享：两个成员先后看同一片同一档，第二个人零转码。

**弊**：

- **盘占用从「活跃会话之和」变成「配额上限常驻」**。用户会看到 `data/`
  下多出几十 GB 并且不自己消失。`storage/registry.py` 里 `transcodes` 这
  条的「用途 / 能否清理 / 后果」文案要改成「可清理，清理后续播要重转」，
  存储管理页要能一键清。
- **指纹漏项 = 播错流**，而且是静默的（换了音轨仍命中旧缓存，用户听到的是
  上一次选的那条）。对策是指纹字段有单测逐项覆盖、加参数版本号、诊断面板
  显示「命中缓存」。
- **两个会话共读一个目录时的 seek 语义变复杂**：A 在看 20 分钟处，B 拖到
  80 分钟，B 要写时会按现有逻辑杀掉 A 正在用的写者直奔 80 分钟，A 的前向
  供片断掉。要么禁止第二个写者（B 等或被拒），要么允许第二个 ffmpeg 写
  不同区段（需要 `-start_number` 不冲突且台账合并，复杂度高）。**建议第一
  版禁止**：同目录只有一个写者，第二个会话的越界 seek 返回「稍候」，并发
  看同一片本来就少。
- manifest 与内存台账双写，多一个一致性来源。写 manifest 用临时文件 +
  rename，损坏即视为无缓存。

**风险**：中。主要在指纹完备性与共读目录的写者仲裁。

**验证**：

- 续播首帧时间（`首片供给` 日志的「距会话创建」）：命中缓存时应 < 300 ms。
- 缓存命中率日志（命中 / 未命中 / 指纹不匹配原因）。
- 盘占用曲线：稳定在配额之下；LRU 触发时不影响活跃会话。
- `tests/api/test_storage.py` 的登记守卫要过；`test_session_manager` 加
  指纹命中、manifest 损坏降级、写者互斥。

**工作量**：`session.py` 约 300 行，`limits.py` / `registry.py` 文案，
`plan.py` 指纹函数，测试。不动运行时依赖；不新增 `data/` 目录（仍在
`transcode_dir` 下）；无数据库迁移（manifest 是文件）。

### C. 实测带宽 → 转码目标码率（P0，最小）

**现状**：

- `maxrate_for_height` 只按目标高度查表（`BITRATE_LADDER`），与线路无关。
- 前端已经有可靠的取流速度读数（`bandwidth.ts`，Resource Timing 口径，
  player-feel.md §2.G3 / §15），但只用来**显示**。
- master 列表单变体，`BANDWIDTH=80000000` 是假值，没有 ABR。外网带宽不够时
  播放器只会 stall，45 秒后判「供流中断」走降档，而降档降的是编码档，
  解决不了带宽问题。

**改法**：

- 开会话与重开会话（seek 换会话、降档、心跳自愈）的请求体加可选字段
  `downlink_bps`：客户端窗口中位数，样本不足不带。
- 服务端**只对转码档（3/4）生效**：`maxrate = min(阶梯值, 0.8 × downlink)`；
  若 0.8 × downlink 低于当前高度阶梯的下一档，则高度也降一档。用户手动选
  的画质（`quality.ts` 的 `max_height`）优先级高于自动，自动只在「自动」
  档生效。
- 直通档（0/1/2）码率改不了。补一条**提示**而不是自动切：`downlink <
  源码率 × 1.2` 持续 10 秒 → 顶栏读数旁出一句「线路不够，可切到 1080p」，
  点了走现有的手动画质切换。
- `stall.ts` 的 `starved` 判定与带宽读数结合：starve 且 `downlink <
  bitrate` → 触发的是「按带宽重开」（同档、更低 maxrate），不是降编码档。
  这条要动 `machine.ts` 的 failed 分支，新增一个事件类型。

**利**：

- 外网弱网从「等 45 秒然后降档」变成开会话时就选对码率。
- 零新依赖、零多变体，复用现有读数与现有的会话重开路径。
- 直通档给用户一个明确的动作，而不是让他看着转圈猜。

**弊**：

- **只在开/重开会话时生效**，播放中带宽变化不会自适应。真正的 ABR 是逐片
  切变体，这里做不到（多变体 = 多路转码）。带宽掉了要靠 starve 判定触发
  一次重开，那是几秒黑屏，比 ABR 的无缝切换差一个量级。
- 带宽测量在起播初期样本少、burst 期间偏高。首次开会话大多没有读数，
  只有重开时才有，所以第一次播放仍按阶梯值。
- 下调容易上调难：会话中途不能升码率，带宽恢复后要等下一次重开。
- 多一个「自动选的码率 vs 用户选的画质」的优先级规则，诊断面板要显示
  「按带宽下调至 X」，否则用户会以为画质设置坏了。

**风险**：低。最坏情况是估错一次码率，下一次重开纠正。

**验证**：

- 离线：`test_ffmpeg_args` 加 `downlink_bps` 参数的 maxrate 断言。
- 真机：外网限速到 5 Mbps 播 1080p 转码档，QoE `rebuffer_ms` 与现状对比。

**工作量**：小。`routes/playback.py` 请求模型、`ffmpeg_args.py`、
`video-player.tsx` 重开路径带参数、`machine.ts` 一个事件。

### D. seek 后分片边写边发（P3，实验）

**现状**（player-feel.md §2.G4 的耗时表）：远跳 = 1 RTT + 杀进程重启
0.3~1 秒 + **编出一整个 4 秒分片 1~3 秒** + 下行。分片必须完整落盘、进
`live.m3u8` 台账后才可服务（`_segment_ready`）。

**方案 1（本项）：目标分片边写边发。** `ensure_segment` 对「本轮重启直奔的
目标分片」在文件**出现**时（不等完成）就开始 chunked 响应，跟随文件增长
发送，直到台账记完成为止。

- 客户端默认要整个响应收完才 `appendBuffer`，所以收益只是**下行与服务端
  编码重叠**：局域网上几乎没差，外网上省掉「等编完再传」的串行，约 1~2 秒。
- 再进一步是开 hls.js `progressive: true`（fetch loader，CMAF chunk 逐块
  append），可以在分片编完之前就出画。该选项在 hls.js 里标 experimental，
  且要求分片内部按 moof/mdat 分片（`-frag_duration` 之类），与现有
  `-hls_segment_type fmp4` 的默认切法是否吻合**未验证**。

**方案 2（否掉）：重启后第一片切短。** `hls_init_time` 可以让第一片短，
但与预生成 VOD 列表冲突：列表边界是全片固定的，重启点不可预知，切短就会
多出一段，hls.js 按列表请求不到它。除非放弃预生成列表回到 EVENT 列表，
那是 §12 之前的旧方案，已经因 iOS 闪黑屏与进度漂移被换掉。**不做。**

**利**：外网远跳减 1~2 秒（方案 1），progressive 模式下可能更多。

**弊**：

- 半片被 SIGKILL 重启（用户连续远跳）时，在途的 chunked 响应必须**断连**
  而不是发出一个截断的分片：Content-Length 未知走 chunked，直接断即可，
  hls.js 走 `errorRetry` 重拉；但断连在 hls.js 侧是一次网络错误，计入
  `MAX_NETWORK_RECOVERIES = 4`，连续远跳可能触发「取流持续失败」。计数
  规则要改。
- 边写边读同一个文件的 tail-follow 逻辑，与「文件出现 ≠ 写完」的现有注释
  （`_segment_ready` 的本地分支）是同一个坑，要小心。
- progressive 模式的稳定性未知，iOS ManagedMediaSource 下更未知。

**风险**：中高。收益只对外网，局域网用户零收益。

**建议**：先不排期。等 A 落地后用 `scripts/perf/` 的真 HTTP 路径重量远跳
耗时，转码全速后「编一整片」这段可能已经从 1~3 秒缩到 0.5~1 秒，那时
D 的收益要重新算。

---

### E. 直通档落盘放大（不做，记录理由）

档 1/2 `-c:v copy` 把整个文件重写到盘上只为换容器，写入放大 = 一个文件
体量。替代是流式 remux 直出（`-f mp4 -movflags frag_keyframe+empty_moov`
chunked 到 `<video>`，不落盘）。

不做的理由：

- fMP4 流不能 Range，seek 只能重启进程 + 前端时间轴偏移，退回「会话相对
  制」，那套逻辑正是 VOD 列表方案替换掉的东西。
- iOS 原生 HLS 与 ManagedMediaSource 对非 HLS 的 fMP4 流兼容差，实测路径
  没有。
- B 落地后写入放大被「写一次多次用」部分抵消，A 落地后写入总量被领先量
  上限约束。两者之后再看数据。

### 7.4 D 为什么没做：分片是原子落盘的

提案 D 的前提是「分片在写的过程中可以边写边发」。实测（ffmpeg 6.1，`-f hls
-hls_segment_type fmp4`，直通与 libx264 转码各测一次，每 100 ms 采一次文件
大小）：**分片文件在完成的那一刻才出现、且一出现就是完整大小**，中间没有任何
可读的部分：

```
直通 remux（readrate 1）:  4.0s: seg00000=405015   7.5s: seg00001=421886
libx264 转码（全速）:     0.3s: seg00000=257076   0.4s: seg00001=271555 ...
```

原因在 movenc：hls muxer 用 `frag_custom` 让 mov muxer 把整个分片的 moof+mdat
攒在内存里，到分片边界一次性写出。加 `frag_duration=1000000` 试图让它每秒
flush 一次，结果是 hlsenc 的切分被搅乱（seg00000 只剩 24 字节的 styp 头，
内容跑到下一片）。要拿到部分分片只有两条路：改用 dash/ldash 的 chunked 写法
（整套 VOD 列表与台账要重做），或者放弃预生成列表让重启后的首片切短（回到
EVENT 列表——正是 §12 之前因 iPhone 闪黑屏被换掉的方案）。两条都超出「小改
动」的范围，本轮不做；远跳的结构性 2~6 秒仍靠冻结帧 + 落点缩略图填感知差距
（player-feel.md §2.G2/G4）。
