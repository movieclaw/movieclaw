## 0. 核心裁决：ASR 是第三个 SubtitleSource，产物独立落盘

三条一次定死：

1. **ASR = `SubtitleSource` 抽象的第三个实现**（现存外挂/内封抽取之外），
   产出"原语言 srt 事件序列"。翻译管线的输入接口本就是"任意 srt 事件
   序列"（subtitle-ai-translate.md §8 预留），ASR 与翻译**解耦**：识别
   完成即形成独立价值，翻译只是可选的下一段。
2. **原语言识别产物先落盘再谈翻译**：`<stem>.asr.<语言>.srt` sidecar，
   与 PGS OCR 留存同款逻辑——耗时数小时得到的识别成果是资产，即使
   后续翻译失败或用户根本不需要翻译（英语片要英文字幕、听障/外语学习
   场景），它都可复用、可预览、可校准；台账由 watchdog 自动入账。
3. **本地识别是默认，云端转写是显式选择**。产品的立身之本是"数据全在
   你自己的机器上"——把整部影片的音轨上传第三方绝不能是静默默认。
   本地 faster-whisper 慢（NAS CPU 小时级）但自治；云端快但必须用户
   在确认框里明确选择供应商并知情"音频将被上传"。

## 1. 引擎选型：三条路线的对比与裁决

| 维度 | A. faster-whisper（进程内） | B. whisper.cpp（外部二进制） | C. OpenAI 兼容云转写 |
|---|---|---|---|
| 语言覆盖 | Whisper 全系 ~100 语言 | 同左 | 取决于供应商（多为 Whisper 系） |
| 词级时间戳 | 原生支持（L3 精修依赖它） | 弱（实验性，断句质量差） | 多数不提供 |
| 断句/参数控制 | 完整（Python API，逐段回调） | 只能吃 CLI 输出 | 无（产物即终态） |
| 取消/断点/进度 | 进程内协作式，逐块断点自然 | 杀进程重跑整块 | 按分块请求粒度 |
| 部署 | pip wheel（amd64/arm64 均有） | 第二套跨架构二进制矩阵（seconv 已付过一次维护成本） | 零部署 |
| NAS CPU 速度 | small/int8 约 0.5-1.5× 实时 | 相当 | 分钟级 |
| 隐私 | 全本地 | 全本地 | 音频上传第三方 |

**裁决：A1 期做 faster-whisper 作为唯一本地引擎，A2 期加云转写作为
显式可选加速；不做 whisper.cpp。** 理由：词级时间戳是断句重排和 L3
时间轴精修的硬前提（B/C 都给不出）；逐段回调让进度、取消、断点续跑
直接复用既有 Job 惯例；B 相对 A 的唯一优势是"不进 Python 依赖"，但
代价是再养一套 per-arch 二进制下载/校验/探针矩阵——工程成本论据不敌
能力论据（与选源反转的判断框架同款）。

**SenseVoice/FunASR 不做**（进不做清单）：中文识别确实显著强于
Whisper，但 ASR 兜底的典型场景恰恰是"无任何中文字幕的**外语**片"——
中文片在 PT 生态几乎必有中文字幕流，轮不到 ASR。语言覆盖
（zh/yue/en/ja/ko 五种 vs 约 100 种）在这个场景是硬需求，不做双引擎。

新依赖 `faster-whisper` + `ctranslate2` + `av`（其硬依赖）进 pyproject
dependencies → **bump `docker/runtime-version`**，两个架构的 wheel
可导入性进镜像冒烟测试（CT2 后端可用即可，不在构建期跑真模型）。
`tokenizers`/`onnxruntime`/`numpy` 已在依赖，零新增。

## 2. 模型分发：沿用 Release 惯例，默认 small/int8

- 模型是 CT2 格式目录，落 `data/models/whisper/<model_name>/`；
  **不进镜像、不进包**（NER 模型同款铁律）。
- 分发走 GitHub Release 转存 + `build-model-manifest.sh` + sha256 校验 +
  原子落位（tag 形如 `whisper-small-ct2-v1`）——不直连 HuggingFace：
  国内 NAS 直连 HF 不可达是常态，Release 链路是项目已验证的解法。
  用户自带模型目录同样认（放对路径即启用，silero-vad 同款语义）。
- **默认推荐 `small` int8（~250MB）**：NAS 无 GPU 的现实下，它是
  "质量可用 × 耗时可忍"的平衡点（2 小时影片约 1.5-4 小时，见 §5 的
  耗时预估）。`base` int8（~80MB，更快更差）与 `medium`/`large-v3`
  （有 GPU 或强 CPU 的用户）作为可选项发布，确认框里按已安装模型选择；
  质量与耗时的取舍交给用户，不替用户猜。
- 预检发现模型缺失 → 确认框给"下载模型（约 xxx MB）"一键入口，下载
  本身是一个 Job（进度/取消/sha256 校验/原子切换），完成后回到预检。
  silero-vad 未安装时同框提示一并下载（VAD 在本管线从"可选增强"升级
  为"强烈建议"，见 §4.1；仍允许降级能量法跑）。

## 3. 音轨选择与音频抽取

### 3.1 选轨：规则打分，预检可改

候选 = ffprobe 音频流列表（库存台账现成）。打分维度从高到低：

1. **排除项**：title 命中评论轨特征（`commentary`/`评论`/`导评`）——
   导演评论轨识别出来的"字幕"是灾难性错配；
2. **语言匹配**：轨道语言标记 = 影片原语言（`media_metadata.original_language`）
   最优；其次 default 旗标轨；再次第一条轨；
3. **形态平分决胜**：声道多者优先（≥6 声道可提取中置声道，见 §3.2）。

选轨结果与理由在确认框展示且**可改**（与参考字幕可选同款交互）——
多音轨国配/原声并存时，用户比规则更清楚自己要识别哪条。轨道语言标记
缺失且原语言未知时，走 §4.2 的语言自动检测，不阻塞发起。

### 3.2 抽取：分块 PCM，中置声道优先

- ffmpeg subprocess 直抽（沿用 extract.py 风格：线程池、超时保护、
  失败中文日志，不引 ffmpeg-python）：16kHz 单声道 s16le PCM；
- **≥6 声道时用 `pan=mono|c0=FC` 只取中置声道**：影院混音里对白集中
  在 C 声道，配乐音效在环绕声道——这一步等于免费的人声增强，对识别
  质量的提升比换大一号模型更实惠；立体声普通 downmix；
- **按块抽取，不落全片 WAV**：2 小时 16k/16bit 单声道 ≈ 440MB，全片
  落盘没必要。按 §4.1 的 VAD 分块结果用 `-ss/-t` 逐块抽，块文件用完
  即删，`data/cache/subtitle_gen/` 峰值占用控制在百 MB 级；
- strm 条目无本地音轨：预检结构化原因如实提示"云端文件不支持音轨
  识别"（subtitle-ai-translate.md §5.3 的 Range 抽段是远期，本期不做）。

## 4. 识别管线

### 4.1 VAD 前置分块：省时 + 从源头消灭幻觉

复用 `subtitle_gen/sync.py` 的两级 VAD 基建（silero 优先、能量法兜底），
先对全片音轨过一遍轻量 VAD（能量法扫全片 + silero 精判语音段边界）：

- 语音区间聚合成 **5-15 分钟的处理块**，切点永远落在静音区间——
  不切断句子；块级时间偏移在汇总时加回；
- **纯音乐/静音区间不送模型**：Whisper 对无语音输入会产生整段幻觉
  （凭空的"谢谢观看"类文本），VAD 门控是最有效的一级防线，同时省下
  这些区间的推理时间（片头片尾曲、纯配乐场景占比可观）；
- VAD 结果同时给出全片"总语音时长"——它是进度分母和耗时预估的基数。

### 4.2 faster-whisper 参数（防幻觉的第二级）

- `word_timestamps=True`：断句重排（§4.4）与 L3 时间轴精修的原料；
- `condition_on_previous_text=False`：不让上一段文本作为下一段的
  prompt——代价是跨段上下文丢失，换来的是幻觉不滚雪球（一段错、
  段段错的模式在长片上是常见事故）；
- 语言：original_language 已知则显式指定；未知时取语音密度最高的
  一块采样检测，检测结果与置信度入任务日志并回填确认框；
- `initial_prompt` 注入片名与主要人名（媒体元数据现成）——专有名词
  拼写正确率的廉价提升；
- `no_speech_threshold` / `avg_logprob` 双阈值丢弃低置信 segment。

### 4.3 幻觉清洗（确定性代码，第三级）

- 重复 n-gram 压缩：同一短语连续重复 ≥3 次折叠为一次（Whisper 经典
  失败模式）；
- 已知幻觉句词表：多语言的"感谢观看/请点赞订阅/字幕由 XX 提供"类
  训练数据污染句，整句丢弃并计数入任务报告；
- 时间越界裁剪：落在 VAD 语音区间之外的事件直接丢弃。

### 4.4 断句重排：模型 segment ≠ 合格字幕条

Whisper 的 segment 常见 10 秒+ 长句，直接当字幕条违反全部可读性标准。
用词级时间戳重新分条（纯规则，`asr/segment.py`）：

- 切分优先级：句末标点 > 逗号/连接词 > 词间停顿（≥0.3s）；
- 硬约束对齐 subtitle-ai-translate.md §3.3 的 R 维度：单条 1-7 秒、
  ≤2 行、行长按书写体系阈值（西文 42 字符/行，CJK 16 字/行）、CPS
  超标时在停顿处再切；
- 条边界用词时间戳 + VAD 边界收紧（起点不早于首词、终点不晚于
  VAD 语音段尾）——这就是 §5.2 预留的"L3 ASR 精修"，在生成时一次
  做对，不留给事后校准；
- 复检走既有 `validate.py` 机检，指标（CPS 超标率、清洗计数）入
  任务报告。

### 4.5 汇入翻译（可选串联）

- 确认框提供两种目标："仅识别（原语言字幕）"与"识别并翻译成 X"。
  原语言 = 目标语言时自动收敛为仅识别；
- 串联时是**一个 Job 两阶段**（阶段进度沿用 Job 的 mode/阶段机制）：
  识别产物先按 §0 落盘成 `.asr.` sidecar，再作为参考源进既有翻译管线
  产出 `.ai-chs.` 等译文 sidecar——翻译阶段失败不吞掉识别成果；
- 翻译阶段的选源、分块、术语表、机检、断点、成本护栏**零新增设计**，
  全部是 subtitle-ai-translate.md §3 的既有实现；token 预估沿用现有
  系数，在确认框与识别耗时预估并列展示；
- ASR 产物进选源候选池的来源世代排序：原文/普通外挂 → PGS OCR →
  **ASR** → AI 单语 → AI 双语（provenance 增加 `asr`）——它比 OCR
  多一层"听写"误差，默认不优先，但作为"唯一可用源"时正是本设计的
  存在意义。

## 5. 任务形态：Job 复用 + 块级断点 + 耗时诚实

- 持久化 Job 承载（dedupe_key = 文件 + `asr` + 语言组合；同文件资源锁
  单飞），预检→原子创建→`202 + JobView`，查询/取消/重试统一走 `/jobs`；
- **块级断点**：每个音频块的识别结果（events JSON）落
  `data/cache/subtitle_gen/<file_id>.asr.checkpoint.json`，原子写盘
  （临时文件 + replace，同 `write_srt`）；重启/崩溃后从未完成块继续，
  已烧掉的 CPU 小时不重花——与翻译断点完全同款的惯例；
- **CPU 并发护栏**：ASR 是纯 CPU 密集型，与转码/刮削抢核。单实例
  同时只执行 1 个 ASR Job（Job 调度器的资源键扩一个全局 `asr` 槽），
  推理线程数默认 `min(4, cpu_count)`；转码属于用户正在看片的即时
  需求，优先级天然高于后台识别——线程上限就是让路机制，不做动态
  暂停（复杂度不配收益）；
- **耗时预估要诚实**：发起前展示"总语音时长 × RTF 系数"的预估区间。
  RTF 系数首次任务用保守默认值（small/int8 按 1.5× 实时），每次任务
  完成后把实测 RTF 写入设置域自校准——第二次预估就是这台机器的真实
  数字。进度 = 已完成块语音时长 / 总语音时长，块内按 segment 回调
  推进，心跳 10 秒（沿用翻译管线惯例），不伪造百分比；
- 云转写（A2）：走既有 openai SDK（自定义 base_url 的 audio API），
  供应商/密钥复用 LLM 设置域的形态；分块上传粒度即断点粒度；确认框
  明示"音频将上传至 X"，无静默回退——本地失败不自动切云端，云端
  限流退避沿用接入层语义。

## 6. 触发与 UI

- 入口就是现有"AI 字幕"预检弹窗的**第三种可用路径**：无任何文本源时，
  结构化原因从"没有可用的参考字幕"升级为提供"从音轨识别"选项（与
  PGS OCR 路径并列；两者同时可用时 OCR 排前——读比听准）；
- 确认框展示：选中音轨（可改）、识别模型（可选已安装模型/下载入口）、
  仅识别或串联翻译、语言、预计耗时（§5）、串联时的 token 预估；
  模型/VAD 缺失在框内给下载入口，不允许静默降级；
- 管理员专属沿用（消费的是小时级 CPU 与可选的 LLM 配额）；
- **不进自动生成开关**：现有 G2 自动开关的额度模型按"LLM token"设计，
  ASR 的成本单位是 CPU 小时，批量入库自动识别等于让 NAS 连轴转数天
  ——有真实诉求再单独设计额度模型，本期 ASR 永远手动发起。

## 8. 不做清单

| 不做项 | 理由 |
|---|---|
| whisper.cpp 二进制引擎 | 无词级时间戳与逐段控制；第二套跨架构二进制矩阵不配"省一个 pip 依赖"的收益（§1） |
| SenseVoice/FunASR 双引擎 | 语言覆盖窄；ASR 兜底场景以外语片为主，中文片几乎必有现成字幕（§1） |
| 说话人分离（diarization） | 字幕产物不标说话人；pyannote 栈重且慢，无消费端 |
| 本地失败自动回退云端 | 音频上传必须显式知情选择，成本与隐私都不能静默发生 |
| 批量/入库自动识别 | CPU 小时级成本无额度模型兜底，本期永远手动（§6） |
| strm 云端文件 Range 抽音 | 前置设计已列远期（subtitle-ai-translate.md §5.3），不在本期 |
| 实时/流式识别 | 无场景：产物是文件字幕，不是直播 |

## 10. 开放问题
