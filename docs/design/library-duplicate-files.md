## 0. 问题与摸底

### 0.1 现象

同一**单元**（电影 = 条目本身，剧集 = 某一季某一集）下有两个以上在位文件。
用户面对它们只能看到文件名，答不出三个问题：**它从哪来、它和另一个有什么区别、
留哪个删哪个**。

### 0.2 重复从哪来（代码摸底）

| # | 来源 | 证据 | 本方案的处置 |
|---|---|---|---|
| 1 | **监听目录导入的非订阅内容**：换个发布组 / 换个扩展名的包，以版本退让名 `… - 1080p.mkv` 落库 | 入库的「同档预检」只对 `identity_source == "subscription"` 生效（`ingest.py` 2244 行附近，注释明确写着"订阅之外的路径不受影响"）；同名幂等只挡得住同扩展名（`_resolve_transfer_target`） | 检测清理；是否堵源头见 §7 决策 A |
| 2 | **存量扫描发现**：外部工具（其他下载器 / 整理器）或人工放进库根的文件 | 扫描的定位是盘点不是守门，"绝不移动 / 重命名 / 删除任何存量文件"（`scan.py` 模块头） | 检测清理（源头无法堵，也不该堵） |
| 3 | **同一 inode 的多个名字**：外部工具改名后又硬链、或整理器落位后原名残留 | 扫描按路径入账，同尺寸在位行**不参与**改名归并（`_try_relink`："路径仍在磁盘的同尺寸行是复制/硬链，不是改名"），于是两行并存 | 检测为「同一文件」类；清理不省空间但消歧 |
| 4 | **洗版在途**：新版本已入库成多版本行、验证尚未裁决 | `quality-upgrade.md` §12.1：入库引擎不感知洗版，证伪 / 替换发生在验证钩子 | **放行**——不能与验证打架 |
| 5 | **洗版「保留共存」规则**（`upgrade_keep_old`） | `upgrade.py` 900 行附近 | **放行**——用户明确要的多版本 |

结论：1、2、3 是真正的冗余，4、5 是有意的多版本。检测必须能把两类分开。

### 0.3 台账里已经有、但没给人看的来源信息

`library_file` 已有 `source`（imported / scanned）、`site_id` / `torrent_id`（投递来源戳）、
`added_batch_id`、`identity_source`。但：

- 文件区只把 `source` 传给了前端，**没有任何展示**（`LibraryItemFile.source` 无消费方）；
- 手动下载的身份锚 `ManualDownloadIntent` **入库成功即删除**（`ingest.py`："和台账一起提交删除"），
  之后只剩 (site, torrent) 两个 id；
- 哪条监听规则、硬链还是复制、哪个下载器、是首次投递还是洗版投递、是自动还是人工选种——
  这些当时都知道，**都没落**。

## 1. 一句话设计

给每个文件行落一份**来源快照**（`origin`），文件区直接展示「它从哪来」；重复文件页只把
多文件单元分成**两堆**——「一模一样」一键清、「不同版本」每个单元回答一次「留哪个 /
都留着」——清掉的走 `recycle_file` 进回收站，7 天可恢复。没有策略、没有类别筛选、没有
守卫：机器只负责把"确定没区别"的和"有区别"的分开，"有区别的要不要留"永远由人一眼看
着规格与来源决定。

> 设计取舍记录（2026-09-13 第二稿）：第一稿把冗余分成五类、配两档策略、再加 HDR /
> 音轨守卫与逐文件「刻意保留」标记，是把判定精度堆到了用户面前。收藏家的问题
> （"不同品质的版本被扫出来怎么办"）在第一稿里要靠三层机制兜，在第二稿里只是
> 「都留着」一个按钮——因为"有区别的文件要不要留"本来就不该由机器分档回答。

## 2. 来源附注（目标 1）

### 2.1 数据：`library_file.origin` JSON 快照

沿用 `trash_context` 的范式：**存展示用快照、不外键**——订阅可以取消、监听规则可以删、
种子表会滚动，快照文案永远能读。只存三个键，就是展示要用的三样：

```json
{ "kind": "subscription",                       // subscription / manual_download / watch_import / scan
  "label": "订阅《九门》自动投递",                 // 第一行
  "detail": "HDSky · Nine.Gates.2025.S01.1080p.WEB-DL.H264.AAC-CHDWEB · qBittorrent · 硬链接入库" }  // 第二行
```

| kind | label 示例 | detail 从哪来（入库现场都有） |
|---|---|---|
| `subscription` | 订阅《九门》自动投递 / 订阅《九门》洗版投递（人工选种） | `_DeliveryProvenance.attempt_for()` 返回的投递记录：站点、`torrent_title`、下载器、搬运策略 |
| `manual_download` | 手动下载 | `ManualDownloadIntent`（删除前取值）+ `SiteTorrent.title` + 下载器 + 策略 |
| `watch_import` | 监听目录自动识别入库（未匹配到任何下载任务） | `ImportWatch.source_path` + 策略 |
| `scan` | 存量扫描发现（非本系统入库） | 「发现于 2026-06-03（手动扫描）」 |

写入点四处：`ingest.py` 三个 `LibraryFile(...)` 构造（原盘、普通文件、「其他」形态）与
`scan.py` 的新行落账。条目转移 / 根路径归并只改路径，`origin` 原样随行。

### 2.2 历史行：读时推导，不做回填

`origin IS NULL` 的旧行在文件视图装配时推导（`derive_origin(row)`）：`source=imported`
且带 (site, torrent) 戳 → 查投递记录拼订阅名，查不到 → 查 `SiteTorrent.title` 记「手动或
监听导入」；无戳 → 「监听目录导入（来源种子未记录）」；`source=scanned` → 「存量扫描
发现于 {created_at}」。不写回。

### 2.3 展示

条目详情页文件区展开面板加一行「来源」：第一行 `label`，第二行 `detail`。收起态不加徽标。
`LibraryFileView` 新增 `origin: {kind, label, detail}`。重复文件页的每个文件行也显示
`label`——**知道它从哪来，才敢决定留哪个**。

## 3. 重复文件：两堆，两种决定

### 3.1 单元与候选

单元 = `(media_item_id, season_number, episode_number)`；候选 = 该单元 `in_place` 的行 ≥ 2。
`missing`（可能是拔掉的盘）、`trashed`、未识别行都不参与。一条按单元分组
`HAVING COUNT(*) >= 2` 的聚合圈出全部多文件单元；不 ffprobe、不算哈希，唯一的磁盘访问是
对这些文件各 `stat` 一次取 inode。

### 3.2 两堆

| 堆 | 判据 | 用户要做的事 |
|---|---|---|
| **一模一样** | 单元内所有文件两两满足：同一 inode，或 尺寸相等且实测时长相等（±2 秒） | 什么都不用想。一键「全部清理」，每个单元留一个 |
| **不同版本** | 其余全部——同档不同组、1080p 与 2160p、HDR 与 SDR、国配与原声、片源未知比不了…… | 每个单元看一眼规格与来源，回答一次：**留哪个 / 都留着** |

只有这一条分界线，它的两侧对用户的意义截然不同：左边是"多出来却没多任何东西"，
右边是"有区别，区别值不值得留只有你知道"。第一稿里同档 / 低档 / 无法判定三类的区分，
在这里退化为**展示差异**（两行规格并排，不同的维度加粗），不再是三种处理路径。

### 3.3 「建议保留」只是一个标签

每个单元系统给一个文件贴「建议保留」，用于「一模一样」的一键清理和「不同版本」的
「全部按建议清理」（§3.6）。规则复用洗版的 `_file_sort_key`，按序：

1. 档位阶梯（该条目订阅的规则组，无订阅用中性阶梯）——比不出来（单侧未知）时跳过这一位；
2. 实测码率 `bit_rate`；
3. 来源可追溯：订阅 / 手动 > 监听 > 扫描；
4. 命名规范：不带 ` - 版本标签` 退让后缀者优先；
5. `id` 大者。

阶梯比不出来时标签旁写一句「档位无法比较，按实测码率建议」。它只是建议：用户点哪个
「留这个」就留哪个。三态铁律在这里的体现是**建议要说明依据**，而不是不给建议——
面对的是看得见文件的人，不是自动流程。

### 3.4 每个单元的两个动作

```
九门 2025 · 电影
  [建议保留] Nine.Gates.2025.2160p.WEB-DL.H265-CHDWEB.mkv   2160p WEB-DL · 8.1 GB   订阅《九门》自动投递      [留这个]
             Nine.Gates.2025.1080p.WEB-DL.H264-CHDWEB.mkv   1080p WEB-DL · 4.2 GB   订阅《九门》自动投递      [留这个]
             九门 (2025) - 1080p.mkv                         1080p WEB-DL · 4.0 GB   存量扫描发现            [留这个]
                                                                                                    [都留着]
```

- **留这个**：留下这一个，单元里其余文件移入回收站。确认一句：「留下 A，把 B、C 移入
  回收站（7 天内可恢复）」；
- **都留着**：这些文件都是我要的。单元从列表消失，直到单元里**出现新文件**才回来
  （届时只需对新文件做决定）。

存储：`library_file.kept_at`（datetime NULL）——「都留着」给单元内当前每个文件盖上时间戳。
判定时**全部文件都带标记**的单元不列出；有任何一个未标记文件（新来的）就列出，已标记的
文件行灰显「你留下的」。撤销：文件区展开面板的「取消『都留着』」。沿用待识别清单
`ignored_at` 的范式，不加新表。

洗版规则组开了「保留共存」的条目，其单元视同「都留着」（不列出）——用户已经在规则组里
回答过这个问题。洗版验证在途的单元也不列出（页脚一句「N 个单元正在洗版验证中」），
避免与验证打架。

### 3.5 剧集：按季折叠，同构的版本整季一次决定

剧集的重复几乎总是**整季成批**来的：另一个组的季包、复制过一遍的季目录、换源后两个包
先后投递。一集一块地列，一部剧就是 24 块、两部剧就占满一页，而用户要做的决定其实只有
一个："这一季留 CHDWEB 的还是留扫描进来的"。

**判定仍按集**（单元不变，§3.1），**展示与决定按季**：

- 同一条目同一季的多文件集聚成一块；块标题「权力的游戏 · S01 · 24 集有重复」，只有一份的集
  不参与（全季集数与重复集数不同时补一句「全季 30 集」）；
- 对每集的文件按**版本签名**分组：签名 = (质量标签, 来源 label)，如
  `("1080p WEB-DL", "订阅《繁花》自动投递")`。若这一季所有集的签名集合一致（允许某个版本
  缺几集），这一季就是**同构**的：块内不列 24 集，只列**版本行**——一个版本一行，写这版本
  覆盖几集、合计多大、来源；「建议保留」按 §3.3 逐集算、取多数；
- 版本行的动作是 **「整季留这个」**：每集留该版本的文件、其余进回收站；某些重复集没有
  这个版本时（三个版本以上才会出现）自动留下那集的建议保留者，确认弹窗写明「E05、E07
  没有这个版本，保留原有文件」；块右下 **「整季都留着」**；
- 「展开各集」可以看逐集明细，每集仍有自己的「留这个」（只动那一集）；
- **不同构**的季（各集的版本组合不一样，少见）不做版本行，直接列各集，每集就是 §3.4 的
  一个小单元；
- 季的归堆按集：一季所有集都「一模一样」→ 整季在「一模一样」堆；否则在「不同版本」堆。
  若一季里两种都有（罕见），两堆各出现一次，各带自己的集数。

电影没有季，条目块就是单元块，§3.4 不变。

```
权力的游戏 2011 · 剧集 · S01 · 24 集有重复                                          一模一样
  [建议保留]  1080p Blu-ray · DEMAND        24 集 · 69.6 GB   监听目录自动识别入库      [整季留这个]
              1080p Blu-ray · DEMAND (1)    24 集 · 69.6 GB   存量扫描发现              [整季留这个]
                                                                        [展开各集]    [整季都留着]

繁花 2023 · 剧集 · S01 · 28 集有重复 · 全季 30 集                                   不同版本
  [建议保留]  2160p WEB-DL · 28 集 · 174 GB     订阅《繁花》自动投递                    [整季留这个]
              1080p WEB-DL · 28 集 · 62 GB      存量扫描发现                            [整季留这个]
                                                                        [展开各集]    [整季都留着]
```

### 3.6 批量

- **「一模一样 · 全部清理 · N」**：整堆一键，每个单元留建议保留的那个。确认弹窗只写
  文件数、总大小、7 天可恢复；
- **「不同版本 · 全部按建议清理 · N」**：整堆按建议保留清理。确认弹窗**逐条列出将被清理
  的文件**（片名 + 规格），滚动可看，这是唯一一处需要用户认真看的确认——它把"不同版本"
  一次性按机器建议处理，收藏家不该按它，按之前想留的先点「都留着」。

不做逐文件勾选与底部批量条：决定的粒度是单元，单元内的选择就是「留这个」。

### 3.7 清理通道

只调 `recycle_file(reason="duplicate_cleanup", trigger={"kind": "member", ...},
note="重复清理：与「A」一模一样，已保留 A" / "重复清理：留下 A（2160p WEB-DL），移除本版本
（1080p WEB-DL）")`。回收站「原因」胶囊加「重复清理」。执行前逐文件重验：仍在位、单元
现状仍与决定时一致（文件集合没变），否则跳过并返回 `error`。清理后刷库统计、通知媒体
服务器。

**管理页第三个标签「重复文件 N」**（`?tab=duplicates`，与回收站标签同构）。页面从上到下：


## 6. 决策点（需要拍板）

**A. 要不要堵第一个源头**——监听导入的非订阅路径也做同档预检？

- 赞成：它是重复的最大来源；预检逻辑现成（`_covered_by_library`），改一个条件；被跳过的
  文件仍留在监听目录（硬链保种不受影响），`ingest_entry.message` 写明跳过原因；
- 反对：现状是有意留白——人工放进监听目录的内容是显式意图，可能就是想要多版本；
- **建议**：堵。想要多版本的人有洗版规则组的「保留共存」和「都留着」两个出口。

**B. 「不同版本 · 全部按建议清理」要不要做**

- 它是唯一可能一次清掉用户想留的版本的按钮；但没有它，几百个单元只能逐个点；
- **建议**：做，确认弹窗逐条列出将清理的文件；页面上放在堆标题右侧、样式弱于「一模一样」
  的批量按钮。

## 7. 边界与不做

- 不做内容哈希；不做自动清理（清理动作永远经人，定时检测 + 通知「发现 N 个重复」可作后续）；
- 不做跨库重复；不改播放侧多版本选择；不动 `_same_payload` 的尺寸判等；
- 不做策略档、类别筛选、逐文件勾选、HDR / 音轨守卫：这些在两堆模型里都不需要——差异只
  展示，不分类；
- 回退兼容：`origin`、`kept_at` 均为可空列默认 NULL；`duplicate_cleanup` 只是 `trash_context`
  的新词。无运行时依赖变更，**不 bump runtime-version**；
- 原盘目录只按整体参与（inode 判等不适用，落「不同版本」堆）。

## 9. 第二版：扫描一次、结论落库、按"要花多少心思"分档

> 2026-09-14。起因是真实反馈的两句话：**「每次打开都特别慢」** 与
> **「打开之后整屏都是文件，不知道从哪下手」**。

### 9.1 慢在哪：检测跑在打开页面的请求线上

第一版 `GET /libraries/duplicate-files` 每次都现算全库重复关系。一次调用里：

1. 一条聚合圈出全部多文件单元；
2. 取回这些单元的全部在位行；
3. **给每个候选文件各 `stat` 一次**——这是唯一的磁盘 IO，网络盘（NAS / SMB / NFS）
   上就是几千次往返；
4. **给每个候选文件各跑一遍 `enrich` 发布名解析**，才排得出「建议保留」
   （`_suggest` → `snapshot_from_file`，对**全部**列出单元做，不只本页——第一版
   开头那句"只对列出的页做"与代码不符，是这次一并修掉的落差）；
5. 分堆、按季折叠，最后才把 20 个条目切出来返回。

也就是说**翻到第几页都要把全库算一遍**。更糟的是两处轮询：重复文件标签
`useVisiblePolling(reload, 30_000)` 每 30 秒重算一次；管理页哪怕停在「媒体库」
标签，也每 120 秒为了标签上那个数字算一遍全库。一万多个文件、几千条重复的库，
每一下都是几十秒。

### 9.2 改法：和「扫描媒体库」同一种东西

检测本身没问题，问题是**什么时候算**。现在它是一个可恢复的后台作业：

| | 第一版 | 第二版 |
|---|---|---|
| 什么时候算 | 每次 GET、每 30 秒、每 120 秒 | 用户按「开始扫描」；媒体库扫描 / 整理作业结束后自动排一轮 |
| 算在哪 | 请求线上 | `library.duplicate-scan` 作业（低优先级、不占库租约、同时最多一份） |
| 页面读什么 | 现算的结果 | `library_duplicate_unit` 里上一轮的结论 |
| 轮询 | 一直轮 | 只有扫描在跑时轮（看进度），跑完即停 |

- **结论表**：一个单元一行，存"当时那一轮算出来的事实"——哪一堆、哪一档、
  哪些文件、建议留哪个、依据、清掉能腾多少。**不存展示文案**（规格标签、来源
  label 都从台账现拼），那些只在翻到的那一页才需要，存下来反而会在改名、重新
  探测之后变成过时的假话；
- **整表重建**，不做增量维护：重复关系会因为入库、洗版、扫描、手工删文件而变，
  维护一份随时可能失真的增量索引比重算一遍更容易出错；
- **结论会过期**：读的时候按 `file_ids` 与台账现状逐单元比对，**集合不等**（少了
  文件、或多了文件）就既不显示也不清理，等下一轮扫描修正。绝不按过期结论删文件；
- **做完决定就地销账**：处理掉一个单元就删掉它那一行，摘要数字立刻变小，不必为
  一个决定重扫整库。

代价说清楚：**结果会过时**。「都留着」之后新进来的文件、恢复出回收站的文件，
都要等下一轮扫描才重新列出。这是这个取舍的正面——用户不希望自己刚做完的决定
在下次打开时又被问一遍；页头永远写着「上次扫描：X 分钟前」，要新的自己按一下。

### 9.3 分档：机器有没有把握

两堆（一模一样 / 不同版本）是**按判定**分的，没解决"几千条从哪下手"。第二版在
它之上加一层**分诊**，按"要用户花多少心思"分三档，判据只有一条——机器有没有把握：

| 档 | 判据 | 用户要做的事 |
|---|---|---|
| **可以放心清理** `safe` | 一模一样堆（同 inode，或尺寸与时长都相等） | 一个按钮。清掉不丢任何东西 |
| **建议清理** `suggested` | 不同版本，且档位阶梯**真的分出了高下**（`suggest_basis == "ladder"`） | 逐条看一眼清单，然后一个按钮 |
| **需要你决定** `review` | 其余全部——同档里按码率 / 来源 / 命名挑出来的，以及阶梯比不出来的 | 一个个看，或按取舍类型成组回答 |

分界线落在 `suggest_basis` 而不是建议文案上：「档位最高」意味着机器真的比出了
高下，「同档，实测码率更高」只是同档里按次级信号挑了一个——**那种"建议"不足以
支撑批量清理**，必须由人看一眼。这是三态铁律在分诊上的落点。

`review` 档再按**取舍类型**分组，同一种取舍聚成一组：

| `review_kind` | 什么情况 | 为什么值得单独成组 |
|---|---|---|
| `unknown` 规格不全 | 任一文件的分辨率或片源没探到 | 机器没有比较的依据，和"两个分辨率之间选一个"完全不是一回事 |
| `resolution` 分辨率不同 | 分辨率不同但阶梯分不出（如 2160p WEB-DL vs 1080p Remux） | 要画质还是要体积，用户对此**只有一个答案** |
| `hdr` HDR 与 SDR | 同分辨率同片源，HDR 值不同 | 很多人两个都留着（不支持的设备上发灰） |
| `same_tier` 同档不同版本 | 规格完全同档，差的是发布组 / 码率 | 挑一个熟悉的组，或者都留着 |

`unknown` 判在最前：分辨率是 `None` 时说"分辨率不同"是句假话。

**成组动作**是分组存在的全部理由：`POST /resolve-all` 的作用域从"一堆"收窄成
"一档 / 一组"，并多一个 `keep_all`——用户对"HDR 和 SDR 我两个都要"只需回答一次，
而不是在几百个单元上各点一次「都留着」。逐单元的两个动作一个没少。

### 9.6 窄屏：把"重复的信息"折掉，只留差异

> 2026-09-14 第二次走查。真实反馈：「一行堆叠的信息太多了，信息密度有点大，
> 而且看不过来。」

宽屏的文件行是四列一张表（名字 / 规格 / 来源 / 动作），重复的规格上下对齐反而
好扫。窄屏叠成一列就成了灾难——**最常见的那种重复恰恰是"规格与来源完全相同、
只有文件名不同"**（同一个包被扫进来两次、外部工具改过名），于是同样的两行文字
各印一遍：

```text
三体 S01E16 - 2160p H.265 AAC ADWeb.mp4      ← 尾部截断后两行看起来一模一样
2160p · AAC 2.0 · 1.01 GB · 3.1 Mbps
存量扫描发现（非本系统入库）
[留这个]
三体 S01E16 - 2160p H.265 AAC.mp4
2160p · AAC 2.0 · 1.01 GB · 3.1 Mbps         ← 逐字相同
存量扫描发现（非本系统入库）                    ← 逐字相同
建议保留 · 同档，最近入库
[建议保留] [留这个]
```

十二行文字，没有一行告诉用户该留哪个——真正的差异只有文件名尾部那个 `ADWeb`，
而窄屏恰恰是从尾部截断的。三条针对性的减法（都只在 `max-md` 生效，宽屏一格不动）：

1. **共有信息上提**（`sharedFacts` / `sharedLine`）：单元内所有文件都一样的规格
   与来源，提到单元头上说一次，文件行里整格隐藏。同构季的版本行同理
   （`sharedVersionOrigin` 提到块头）；
2. **文件名折公共前缀**（`commonNamePrefix`）：公共前缀淡显并允许截断，**差异的
   尾巴永远完整显示**，窄到一半宽度也看得出差在哪。两个门槛——前缀短于 8 个字符
   不值得折，尾巴长于 28 个字符不折（尾巴不截断，太长会把行撑破）；
3. **名字与动作并排**：窄屏的行栅格从一列改成「名字 + 动作」两列（`order` 把动作
   提到第二格），规格与来源整行排在下面。

同一个单元因此从十二行压到四行：

```text
E16 · 2160p · AAC 2.0 · 1.01 GB · 3.1 Mbps · 存量扫描发现（非本系统入库）
三体 S01E16 - 2160p H.2…ADWeb.mp4                            [留这个]
三体 S01E16 - 2160p…  .mp4                        [建议保留] [留这个]
建议保留 · 同档，最近入库
```

块头同样收了：档名不再被截断（窄屏允许计数换行而不是挤掉标题），批量按钮整行
铺开，而档的一句话说明在窄屏隐藏——明细层只能从摘要卡进来，那句话刚刚才读过。

**第二次走查又改了三处**（同一天的第二轮反馈：「返回摘要那个按钮位置是不是也不
太好？文件名和留这个在一行，长期看是不是也不好？」）：

- **「‹ 返回摘要」换成分档胶囊行**。原来它和标题抢同一行，更要紧的是它只是个
  **单向出口**：在这一档做完想去下一档，得先回摘要再点一次——而"做完一档接着做
  下一档"恰恰是这里最常见的下一步。现在一行胶囊 `[‹ 摘要] [可以放心清理 2]
  [建议清理 4] [需要你决定]`，换档一次点击，**选中的那枚同时就是标题**，标题行
  连同它省下的空间一起没了。选了取舍分组时，那一组作为可关掉的胶囊接在后面
  （与「只看《某片》」同款）；
- **文件名独占整行**。动作区的宽度是**变的**（带不带「建议保留」胶囊差一截），
  和名字挤在同一行会让同一个单元里两行文件名截断在不同位置——而这一页的全部意义
  就是横向比对两个名字，对不齐直接把这件事毁掉。整行给名字之后它多数时候根本不用
  截断；说明与动作合占第二行，两个「留这个」右对齐成一列。窄屏因此不再显示
  「建议保留」胶囊（说明行里写着同一句话），改用一道内嵌色条标出建议保留的那行——
  不占宽度，对齐才保得住；
- **宽屏最后一列写死 11rem**（原来是 `auto`）。同一个病根：带胶囊的那一行会把前
  三列挤窄，于是两行的规格截断在不同位置。写死之后四列上下对齐成真正的一张表。

还修了一个真 bug：差异的尾巴常常以空格开头（`…AAC` + ` ADWeb.mp4`），HTML 默认
把它折掉，两段拼起来成了 `AACADWeb.mp4`——一个磁盘上并不存在的名字。两段都要
`whitespace-pre-wrap`（既保空白又允许长名换行）。

**第三次走查：「需要你决定」的取舍分组行。** 它不是密度大，是布局塌了——三个
按钮 `shrink-0`、文字 `flex-1`，窄屏上按钮吃掉大半宽度，名字、计数、说明全被挤
成一根一百来像素宽的文字柱，右边一大片空白（`同档不同版本（不同发布组 / 不同
码率）` 竖着排了三行，说明排了五行）。三处：

- **一组两行**：名字与分量一行、三个按钮一行。名字只留主干，解释一律交给
  `REVIEW_KIND_HINTS`（`同档不同版本（不同发布组 / 不同码率）` → `同档不同版本`，
  括号里那句本来就和说明重复）；分量用 `compactSummary`（`562 个单元 · 933 GB`），
  少一段文件数——文件数在「按建议清 · N」上原样写着；
- **说明挪到明细层**：这张卡上三档各有一句，再叠四段取舍说明就是一面墙。取舍说明
  改成点进那一组之后显示在明细层顶上——你正要动手的时候才需要读它。三档那句仍在
  摘要卡上，明细层窄屏不再重复；
- **分档胶囊行自动把选中项滚进视野**：窄屏胶囊要横滚，选中的那枚常落在屏外，
  进来第一眼看不到自己在哪一档，胶囊行就白做了。

### 9.7 「规格不全」不给成批清理

真实数据里这一组是 562 个单元 / 2974 个文件 / 933 GB，而按钮写着「按建议清 ·
2974」——紧挨着的一句说明却是"机器没有比较的依据"。按下去就是拿一个机器自己
声明做不出的判断，去删掉近三千个文件。

这一组的定义就是**规格没探到、无从比较**（`_review_kind` 的第一条：分辨率或片源
为空）。它当然还有一个「建议保留」（阶梯比不出来时退回实测码率），但那个建议只够
支撑"逐个看的时候给你一个起点"，不够支撑一次点击清掉一整组——三态铁律在这里的
落点就是**无从判定就交给人**。所以摘要卡与明细层都不给它「按建议清」，只留
「逐个看」与「都留着」。

接口不变：`resolve-all` 仍然接受 `review_kind=unknown`（CLI 上想那么做的人知道
自己在做什么），拿掉的是 UI 上那个一步之遥的入口。


### 9.8 按钮分三档，一眼看得出哪个会动文件

反馈原话：「『逐个看』『都留着』『建议清』这几个其实不太像按钮，有点像过滤标签。
而且这三个是不是样式和颜色不一样会比较好？因为重要程度不一样。」

确实：第一版这一页所有动作都是「细描边药丸 + 小字」，和它正上方那排分档胶囊
几乎同一套样式，于是整页读起来像一片过滤标签，没人看得出哪个会动文件。

全站的按钮体系里本来就有答案（`globals.css` 的 `.btn-accent` / `.btn-glass` 与
`--danger-solid` 的注释就是这套语言的出处），这一页此前一个都没用上。现在按
**动作的轻重**分四档：

| 档 | 样式 | 用在哪 |
|---|---|---|
| `primary` | 亮银实心 `.btn-accent` | 这张卡请你做、而且做了不丢东西的那件事：只有「可以放心清理 · 全部清理」 |
| `default` | 玻璃药丸 `.btn-glass` | 正经动作：「逐个看」「留这个」「整季留这个」 |
| `ghost` | 淡描边、无底、灰字 | 关掉 / 跳过，不动文件：「都留着」「整季都留着」「展开各集」 |
| `danger` | 实心红 + 白字 | **会把文件移进回收站、而依据只是"建议"** 的那些：「全部按建议清理」「按建议清 · N」 |

两条刻意的：

- **`primary` 一张卡至多一个**——「满屏都是重点就等于没有重点」（这句是 `globals.css`
  里状态色注释自己写的）。所以取舍分组行里的「逐个看」是玻璃档而不是亮银档；
- **`ghost` 也留一圈淡描边**。它要比玻璃档弱，但不能弱到又变回一段纯文字——
  「不太像按钮」正是这一版要修的毛病，轮廓人人有，轻重靠底色与字亮度分。

按钮高度 `h-8` 也是刻意的：分档胶囊是 `h-7`，按钮比它高一档，隔着一行也分得清
哪些是筛选、哪些是动作。

顺带修了一个错位：文件行的动作格原来靠 grid 自动流定位，而来源格在"共有"时会被
整格隐藏——一旦隐藏，动作格就掉进第一列，同一个单元里两行的「留这个」于是差了
一截。两格都钉死列号（`col-start-1` / `col-start-2`）之后才真正对齐。

### 9.9 「建议保留」的一个老 bug：未知被当成了"最差"

真实反馈：一集有两个文件，建议保留给了小的那个——

| | 分辨率 | 片源 | 码率 | 体积 |
|---|---|---|---|---|
| `交锋（2026）- S01E01.mkv`（HDR10） | 2160p | **没探到** | 14.8 Mbps | 4.83 GB |
| `交锋（2026）- S01E01.mp4`（Dolby Vision） | 2160p | WEB-DL | ~3.7 Mbps | 1.22 GB |

标签还写着「档位无法比较，**按实测码率建议**」——而码率根本没轮到：排序把未知
折成 `-1`，比任何已知片源档都低，mkv 在片源那一位就判负了。

**§3.3 第一条本来就写着「比不出来（单侧未知）时跳过这一位」，是代码没照做。**
`compare_ladder` 那边一直是对的（"未知永远不当已知用"，所以这个单元正确地落进了
「需要你决定」），错的只有排序这一段——它把"不当已知用"实现成了"当最差用"。

修法就是把代码改回规范：**单元里只要有一位一边探到、一边没探到，这一位对整个单元
失效**，直接落到下一个信号（实测码率）。三处配套：

- **全都没探到不算"没探全"**。`compare_ladder` 把双方都未知判成平局并继续比下一位，
  理由是"两边都没标片源是命名习惯的常态，不是数据质量问题"——这里同一口径：那种位
  一样不参与排序，但不因此把单元打成"规格没探全"；
- **理由文案必须是真话**。原来不论谁定的序都写「按实测码率建议」。现在前半句由
  "档位比全了没有"决定：`档位最高` / `同档，…` / `规格没探全，…`，后半句是真正
  定序的那个信号；
- **「规格没探全」进不了「建议清理」**。哪怕在剩下的位上胜出也不行——没探到的那一位
  随时可能把结论翻过来。`classify` 因此同时看 `suggest_basis` 与 `suggest_partial`。

顺带补了命名规范那一位（§3.3 第 4 条）：它原先只认整理器的 ` - 1080p` 退让名，
不认系统留下的 `副本 / 拷贝 / copy / (1)`。两个硬链接指向同一份字节时，一个名字里
写了片源、另一个没写，说明的只是命名习惯不是谁更好——这时该由"谁占着标准名"定序，
而不是让它一路平到 `id`、选中后扫到的那个。

### 9.10 边界与不做

- 分档**不改变任何判定**：`bucket`、建议保留、放行规则（保留共存 / 洗版在途 /
  「都留着」）全部照旧，分档只决定先给你看什么；
- 不做自动清理：三档的批量按钮全部由人按，清掉的文件一律进回收站、7 天可恢复；
- 不做定时扫描：入口是手动按钮 + 媒体库扫描 / 整理结束后自动排一轮。想要"每天
  凌晨扫一次"可以后续接 `scheduled_task`，但那要先有"扫完通知我"，否则只是让
  数字自己变；
- 回退兼容：`library_duplicate_unit` 是纯新增表，回退后旧代码不认识它、照旧在
  请求线上现算（功能不丢只是慢），升级回来重新扫一次即可。无运行时依赖变更，
  **不 bump runtime-version**。
