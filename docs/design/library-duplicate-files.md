> 状态：**已实施第一版**（2026-09-13，落地顺序 §8 的 1–4 步；第 5 步「堵源头」等决策 A 拍板）。
> 起源于真实反馈：电影与剧集条目下都会出现同一部片 / 同一集挂着多个文件，既不是洗版
> 留下的，也说不清是谁放进来的。
>
> 实施落差记录：①「建议保留」的档位比较复用 `snapshot_from_file`（含文件名 enrich），
> 只对列出的页做，不影响摘要计数；②同构判据落成「至少两个版本、每个版本覆盖这一季

## 0. 问题与摸底

### 0.1 现象

同一**单元**（电影 = 条目本身，剧集 = 某一季某一集）下有两个以上在位文件。
用户面对它们只能看到文件名，答不出三个问题：**它从哪来、它和另一个有什么区别、
留哪个删哪个**。

### 0.2 重复从哪来（代码摸底）

| # | 来源 | 证据 | 本方案的处置 |
|---|---|---|---|
| 1 | **监听目录导入的非订阅内容**：换个发布组 / 换个扩展名的包，以版本退让名 `… - 1080p.mkv` 落库 | 入库的「同档预检」只对 `identity_source == "subscription"` 生效（`ingest.py` 2244 行附近，注释明确写着"订阅之外的路径不受影响"）；同名幂等只挡得住同扩展名（`_resolve_transfer_target`） | 检测清理；是否堵源头见 §7 决策 A |
| 2 | **存量扫描发现**：外部工具（其他下载器 / 整理器）或人工放进库根的文件 | 扫描的定位是盘点不是守门，"绝不移动 / 重命名 / 删除任何存量文件"（`scan.py` 模块头） | 检测清理（源头无法堵，也不该堵） |
| 3 | **同一 inode 的多个名字**：外部工具改名后又硬链、或整理器落位后原名残留 | 扫描按路径入账，同尺寸在位行**不参与**改名归并（`_try_relink`："路径仍在磁盘的同尺寸行是复制/硬链，不是改名"），于是两行并存 | 检测为「同一文件」类；清理不省空间但消歧 |
| 4 | **洗版在途**：新版本已入库成多版本行、验证尚未裁决 | `quality-upgrade.md` §12.1：入库引擎不感知洗版，证伪 / 替换发生在验证钩子 | **放行**——不能与验证打架 |
| 5 | **洗版「保留共存」规则**（`upgrade_keep_old`） | `upgrade.py` 900 行附近 | **放行**——用户明确要的多版本 |

结论：1、2、3 是真正的冗余，4、5 是有意的多版本。检测必须能把两类分开。

### 0.3 台账里已经有、但没给人看的来源信息

`library_file` 已有 `source`（imported / scanned）、`site_id` / `torrent_id`（投递来源戳）、
`added_batch_id`、`identity_source`。但：

- 文件区只把 `source` 传给了前端，**没有任何展示**（`LibraryItemFile.source` 无消费方）；
- 手动下载的身份锚 `ManualDownloadIntent` **入库成功即删除**（`ingest.py`："和台账一起提交删除"），
  之后只剩 (site, torrent) 两个 id；
- 哪条监听规则、硬链还是复制、哪个下载器、是首次投递还是洗版投递、是自动还是人工选种——
  这些当时都知道，**都没落**。

## 1. 一句话设计

给每个文件行落一份**来源快照**（`origin`），文件区直接展示「它从哪来」；重复文件页只把
多文件单元分成**两堆**——「一模一样」一键清、「不同版本」每个单元回答一次「留哪个 /
都留着」——清掉的走 `recycle_file` 进回收站，7 天可恢复。没有策略、没有类别筛选、没有
守卫：机器只负责把"确定没区别"的和"有区别"的分开，"有区别的要不要留"永远由人一眼看
着规格与来源决定。

> 设计取舍记录（2026-09-13 第二稿）：第一稿把冗余分成五类、配两档策略、再加 HDR /
> 音轨守卫与逐文件「刻意保留」标记，是把判定精度堆到了用户面前。收藏家的问题
> （"不同品质的版本被扫出来怎么办"）在第一稿里要靠三层机制兜，在第二稿里只是
> 「都留着」一个按钮——因为"有区别的文件要不要留"本来就不该由机器分档回答。

## 2. 来源附注（目标 1）

### 2.1 数据：`library_file.origin` JSON 快照

沿用 `trash_context` 的范式：**存展示用快照、不外键**——订阅可以取消、监听规则可以删、
种子表会滚动，快照文案永远能读。只存三个键，就是展示要用的三样：

```json
{ "kind": "subscription",                       // subscription / manual_download / watch_import / scan
  "label": "订阅《九门》自动投递",                 // 第一行
  "detail": "HDSky · Nine.Gates.2025.S01.1080p.WEB-DL.H264.AAC-CHDWEB · qBittorrent · 硬链接入库" }  // 第二行
```

| kind | label 示例 | detail 从哪来（入库现场都有） |
|---|---|---|
| `subscription` | 订阅《九门》自动投递 / 订阅《九门》洗版投递（人工选种） | `_DeliveryProvenance.attempt_for()` 返回的投递记录：站点、`torrent_title`、下载器、搬运策略 |
| `manual_download` | 手动下载 | `ManualDownloadIntent`（删除前取值）+ `SiteTorrent.title` + 下载器 + 策略 |
| `watch_import` | 监听目录自动识别入库（未匹配到任何下载任务） | `ImportWatch.source_path` + 策略 |
| `scan` | 存量扫描发现（非本系统入库） | 「发现于 2026-06-03（手动扫描）」 |

写入点四处：`ingest.py` 三个 `LibraryFile(...)` 构造（原盘、普通文件、「其他」形态）与
`scan.py` 的新行落账。条目转移 / 根路径归并只改路径，`origin` 原样随行。

### 2.2 历史行：读时推导，不做回填

`origin IS NULL` 的旧行在文件视图装配时推导（`derive_origin(row)`）：`source=imported`
且带 (site, torrent) 戳 → 查投递记录拼订阅名，查不到 → 查 `SiteTorrent.title` 记「手动或
监听导入」；无戳 → 「监听目录导入（来源种子未记录）」；`source=scanned` → 「存量扫描
发现于 {created_at}」。不写回。

### 2.3 展示

条目详情页文件区展开面板加一行「来源」：第一行 `label`，第二行 `detail`。收起态不加徽标。
`LibraryFileView` 新增 `origin: {kind, label, detail}`。重复文件页的每个文件行也显示
`label`——**知道它从哪来，才敢决定留哪个**。

## 3. 重复文件：两堆，两种决定

### 3.1 单元与候选

单元 = `(media_item_id, season_number, episode_number)`；候选 = 该单元 `in_place` 的行 ≥ 2。
`missing`（可能是拔掉的盘）、`trashed`、未识别行都不参与。一条按单元分组
`HAVING COUNT(*) >= 2` 的聚合圈出全部多文件单元；不 ffprobe、不算哈希，唯一的磁盘访问是
对这些文件各 `stat` 一次取 inode。

### 3.2 两堆

| 堆 | 判据 | 用户要做的事 |
|---|---|---|
| **一模一样** | 单元内所有文件两两满足：同一 inode，或 尺寸相等且实测时长相等（±2 秒） | 什么都不用想。一键「全部清理」，每个单元留一个 |
| **不同版本** | 其余全部——同档不同组、1080p 与 2160p、HDR 与 SDR、国配与原声、片源未知比不了…… | 每个单元看一眼规格与来源，回答一次：**留哪个 / 都留着** |

只有这一条分界线，它的两侧对用户的意义截然不同：左边是"多出来却没多任何东西"，
右边是"有区别，区别值不值得留只有你知道"。第一稿里同档 / 低档 / 无法判定三类的区分，
在这里退化为**展示差异**（两行规格并排，不同的维度加粗），不再是三种处理路径。

### 3.3 「建议保留」只是一个标签

每个单元系统给一个文件贴「建议保留」，用于「一模一样」的一键清理和「不同版本」的
「全部按建议清理」（§3.6）。规则复用洗版的 `_file_sort_key`，按序：

1. 档位阶梯（该条目订阅的规则组，无订阅用中性阶梯）——比不出来（单侧未知）时跳过这一位；
2. 实测码率 `bit_rate`；
3. 来源可追溯：订阅 / 手动 > 监听 > 扫描；
4. 命名规范：不带 ` - 版本标签` 退让后缀者优先；
5. `id` 大者。

阶梯比不出来时标签旁写一句「档位无法比较，按实测码率建议」。它只是建议：用户点哪个
「留这个」就留哪个。三态铁律在这里的体现是**建议要说明依据**，而不是不给建议——
面对的是看得见文件的人，不是自动流程。

### 3.4 每个单元的两个动作

```
九门 2025 · 电影
  [建议保留] Nine.Gates.2025.2160p.WEB-DL.H265-CHDWEB.mkv   2160p WEB-DL · 8.1 GB   订阅《九门》自动投递      [留这个]
             Nine.Gates.2025.1080p.WEB-DL.H264-CHDWEB.mkv   1080p WEB-DL · 4.2 GB   订阅《九门》自动投递      [留这个]
             九门 (2025) - 1080p.mkv                         1080p WEB-DL · 4.0 GB   存量扫描发现            [留这个]
                                                                                                    [都留着]
```

- **留这个**：留下这一个，单元里其余文件移入回收站。确认一句：「留下 A，把 B、C 移入
  回收站（7 天内可恢复）」；
- **都留着**：这些文件都是我要的。单元从列表消失，直到单元里**出现新文件**才回来
  （届时只需对新文件做决定）。

存储：`library_file.kept_at`（datetime NULL）——「都留着」给单元内当前每个文件盖上时间戳。
判定时**全部文件都带标记**的单元不列出；有任何一个未标记文件（新来的）就列出，已标记的
文件行灰显「你留下的」。撤销：文件区展开面板的「取消『都留着』」。沿用待识别清单
`ignored_at` 的范式，不加新表。

洗版规则组开了「保留共存」的条目，其单元视同「都留着」（不列出）——用户已经在规则组里
回答过这个问题。洗版验证在途的单元也不列出（页脚一句「N 个单元正在洗版验证中」），
避免与验证打架。

### 3.5 剧集：按季折叠，同构的版本整季一次决定

剧集的重复几乎总是**整季成批**来的：另一个组的季包、复制过一遍的季目录、换源后两个包
先后投递。一集一块地列，一部剧就是 24 块、两部剧就占满一页，而用户要做的决定其实只有
一个："这一季留 CHDWEB 的还是留扫描进来的"。

**判定仍按集**（单元不变，§3.1），**展示与决定按季**：

- 同一条目同一季的多文件集聚成一块；块标题「权力的游戏 · S01 · 24 集有重复」，只有一份的集
  不参与（全季集数与重复集数不同时补一句「全季 30 集」）；
- 对每集的文件按**版本签名**分组：签名 = (质量标签, 来源 label)，如
  `("1080p WEB-DL", "订阅《繁花》自动投递")`。若这一季所有集的签名集合一致（允许某个版本
  缺几集），这一季就是**同构**的：块内不列 24 集，只列**版本行**——一个版本一行，写这版本
  覆盖几集、合计多大、来源；「建议保留」按 §3.3 逐集算、取多数；
- 版本行的动作是 **「整季留这个」**：每集留该版本的文件、其余进回收站；某些重复集没有
  这个版本时（三个版本以上才会出现）自动留下那集的建议保留者，确认弹窗写明「E05、E07
  没有这个版本，保留原有文件」；块右下 **「整季都留着」**；
- 「展开各集」可以看逐集明细，每集仍有自己的「留这个」（只动那一集）；
- **不同构**的季（各集的版本组合不一样，少见）不做版本行，直接列各集，每集就是 §3.4 的
  一个小单元；
- 季的归堆按集：一季所有集都「一模一样」→ 整季在「一模一样」堆；否则在「不同版本」堆。
  若一季里两种都有（罕见），两堆各出现一次，各带自己的集数。

电影没有季，条目块就是单元块，§3.4 不变。

```
权力的游戏 2011 · 剧集 · S01 · 24 集有重复                                          一模一样
  [建议保留]  1080p Blu-ray · DEMAND        24 集 · 69.6 GB   监听目录自动识别入库      [整季留这个]
              1080p Blu-ray · DEMAND (1)    24 集 · 69.6 GB   存量扫描发现              [整季留这个]
                                                                        [展开各集]    [整季都留着]

繁花 2023 · 剧集 · S01 · 28 集有重复 · 全季 30 集                                   不同版本
  [建议保留]  2160p WEB-DL · 28 集 · 174 GB     订阅《繁花》自动投递                    [整季留这个]
              1080p WEB-DL · 28 集 · 62 GB      存量扫描发现                            [整季留这个]
                                                                        [展开各集]    [整季都留着]
```

### 3.6 批量

- **「一模一样 · 全部清理 · N」**：整堆一键，每个单元留建议保留的那个。确认弹窗只写
  文件数、总大小、7 天可恢复；
- **「不同版本 · 全部按建议清理 · N」**：整堆按建议保留清理。确认弹窗**逐条列出将被清理
  的文件**（片名 + 规格），滚动可看，这是唯一一处需要用户认真看的确认——它把"不同版本"
  一次性按机器建议处理，收藏家不该按它，按之前想留的先点「都留着」。

不做逐文件勾选与底部批量条：决定的粒度是单元，单元内的选择就是「留这个」。

### 3.7 清理通道

只调 `recycle_file(reason="duplicate_cleanup", trigger={"kind": "member", ...},
note="重复清理：与「A」一模一样，已保留 A" / "重复清理：留下 A（2160p WEB-DL），移除本版本
（1080p WEB-DL）")`。回收站「原因」胶囊加「重复清理」。执行前逐文件重验：仍在位、单元
现状仍与决定时一致（文件集合没变），否则跳过并返回 `error`。清理后刷库统计、通知媒体
服务器。

## 6. 决策点（需要拍板）

**A. 要不要堵第一个源头**——监听导入的非订阅路径也做同档预检？

- 赞成：它是重复的最大来源；预检逻辑现成（`_covered_by_library`），改一个条件；被跳过的
  文件仍留在监听目录（硬链保种不受影响），`ingest_entry.message` 写明跳过原因；
- 反对：现状是有意留白——人工放进监听目录的内容是显式意图，可能就是想要多版本；
- **建议**：堵。想要多版本的人有洗版规则组的「保留共存」和「都留着」两个出口。

**B. 「不同版本 · 全部按建议清理」要不要做**

- 它是唯一可能一次清掉用户想留的版本的按钮；但没有它，几百个单元只能逐个点；
- **建议**：做，确认弹窗逐条列出将清理的文件；页面上放在堆标题右侧、样式弱于「一模一样」
  的批量按钮。

## 7. 边界与不做

- 不做内容哈希；不做自动清理（清理动作永远经人，定时检测 + 通知「发现 N 个重复」可作后续）；
- 不做跨库重复；不改播放侧多版本选择；不动 `_same_payload` 的尺寸判等；
- 不做策略档、类别筛选、逐文件勾选、HDR / 音轨守卫：这些在两堆模型里都不需要——差异只
  展示，不分类；
- 回退兼容：`origin`、`kept_at` 均为可空列默认 NULL；`duplicate_cleanup` 只是 `trash_context`
  的新词。无运行时依赖变更，**不 bump runtime-version**；
- 原盘目录只按整体参与（inode 判等不适用，落「不同版本」堆）。
