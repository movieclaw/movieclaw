# 片源人工标注:把「无法确认」单元交还给用户判断

> 状态:已实施(2026-08,按 §7 四步落地)。背景案例:扫描入库的《十三邀》S7 全季 16 集,
> 文件名形如 `十三邀 S07E01 - 2160p H.265 AAC ADWeb.mp4`——`ADWeb` 是组名
> 不是片源词,enrich 解析不出 media_source;规则组目标 2160p WEB-DL 与
> 当前分辨率打平,胜负落在片源档上,而片源未知不可比(quality-upgrade.md
> §2.4),单元永远停在「无法确认」第三态,每次洗版都要人工介入。

## 0. 问题与目标

- **问题**:扫描/手工入库的文件普遍没有片源 token(重命名过、或组名不含
  片源词),快照 `media_source=None`;当分辨率已达洗版目标分辨率时,
  三态铁律让这类单元既不排期也不判达标,只能反复提示「可手动选种替换」。
  提示是对的,但对整季 N 集的场景,人工成本是每一季一次、每次一集集选。
- **目标**:一次人工标注(整季批量),把「系统未知」变成「已知」,之后
  现有洗版机器自动接管。人工判断只做一次,落在数据上。
- **反目标**:
  - 不做「片源未知视同最低档」的全局或规则组开关——系统擅自把未知当
    最低档会把命名干净的手工入库 Remux 洗成 WEB-DL(洗版洗出降级);
  - 不做码率阈值自动证伪片源——§4.2 已论证并否决(低码率内容天然不稳,
    错杀比放过更伤信任),本设计不重开这个口子。

## 1. 一句话设计

「无法确认」的根因是**数据缺失,不是判定逻辑缺陷**;给用户一个整季批量的
片源标注入口(挂在洗版报告与追踪明细的失败反馈原地),标注以人工出处写入
`library_file` 并同步刷新 `wanted_item.quality` 的出处维度,未知从此变已知
(包括显式的「按最低档」),三态铁律与洗版比较逻辑一字不改地继续工作。

## 2. 核心概念

### 2.1 标注是数据修复,不是策略开洞

三态铁律(§2.4)防的是**系统擅自**把未知当已知;而用户看着文件名与实测
码率做出的判断是知情决策,存为显式档位后就是普通的已知数据。两条语义
从此并存、永不混淆:

| 状态 | 存储 | 洗版行为 |
|---|---|---|
| 系统未知 | `media_source = NULL` | 不可比,安静,等标注(现状不变) |
| 人工标注为具体档位 | `media_source = "WEB-DL"` 等 + 人工出处位 | 正常参与档位比较 |
| 人工标注「不确定,按最低档」 | `media_source = "user-lowest"` + 人工出处位 | T0 档,可证明低于一切目标,进自动排期 |

### 2.2 值域:五个真实档位 + 一个显式兜底

标注选项与后果(UI 文案必须写明后果,让每个选项都是知情选择):

| 选项 | 落库值 | 档位 | 对用户的后果说明 |
|---|---|---|---|
| Remux | `"Remux"` | T5 | 可标注的最高档,达标停洗 |
| 蓝光重编码 | `"Blu-ray"` | T4 | 高于 WEB-DL 目标即达标 |
| WEB-DL | `"WEB-DL"` | T3 | 目标为 WEB-DL 时达标停洗 |
| WEBRip | `"WEBRip"` | T2 | 低于 WEB-DL 目标,自动洗 |
| TV 录制 | `"HDTV"` | T1 | 低于目标,自动洗 |
| 不确定(按最低档) | `"user-lowest"` | **T0(新增)** | 按最差处理,整季会重新下载替换 |

（表外还有一档 **T6 原盘**（`"Disc"`）:不在菜单里,由台账结构自动判定,见下方要点。）

两个实现要点:

- **`"Remux"` 作为 media_source 值新增进 `_SOURCE_TIER`(T5)**。
  `library_file` 没有 remux 布尔列,而 `snapshot_from_file` 会用非空的
  `file.media_source` 覆盖快照出处维度(upgrade.py §4.1 分层)——把
  Remux 当作一个片源**值**存,快照与 `quality_label` 全链路自然工作
  (`"2160p Remux"`),零新列。词表 `MEDIA_SOURCE` 不加 Remux 条目
  (名称解析的 remux 仍走布尔位,两条路径互不干扰)。
- **原盘不在菜单里**（issue #163）：BDMV / VIDEO_TS / ISO 的片源由扫描与
  入库按**结构**自动落成 `"Disc"`（T6，高于 Remux，见 quality-upgrade.md
  §2.1.1），落值走自动出处、不占人工保护位。这类行因此天生带着非空片源，
  进不了标注候选池（§3.2 的口径：只收未知与此前人工标注的行），用户也
  不需要为它做判断——"这是不是一张完整的盘"是事实问题，不是判断问题。
- **T0 哨兵 `"user-lowest"` 只有人工能写入**,enrich 词表永远解析不出它;
  `quality_label` 显示为「最低档(人工标注)」。T0 低于 HDTV(T1),
  可证明低于任何已配置目标 → `provably_below_cutoff` 为真 → 进排期;
  替换候选仍要过规则组硬过滤 + 严格升级判定(任何已知档 > T0),
  最坏损失 = 一次多余下载,结果不会比现状差。

### 2.3 为什么锚在「季」这个粒度

同季文件几乎总是同一来源(整季包或同组连载)。v1 整季统一标,弹窗列出
文件名供扫一眼确认;个别集来源不同的少数场景,后续再考虑逐集(不为它
先做逐集勾选 UI)。电影条目退化为「该条目全部文件」(季号哨兵 0)。

## 3. 存储:人工出处保护

### 3.1 新列 `library_file.media_source_manual`

沿用身份维度 `identity_source=manual`「人工永不被自动翻案」的既有范式
(scan.py `_review_due`),但介质维度只需要二值,不复刻完整枚举:

```python
media_source_manual: bool  # True = media_source 为人工标注,自动解析不得覆盖
```

迁移向前兼容(加列,默认 false,旧代码可继续读写同表,符合发布规范第 3 条);
无运行时依赖变化,**不 bump runtime-version**。

### 3.2 覆盖点治理(摸底结论:现状无任何保护)

`media_source` 的自动写入路径与处置:

| 路径 | 现状 | 处置 |
|---|---|---|
| `upsert_by_path` 整体覆盖(library_file_repo) | 无条件 `existing.media_source = row.media_source` | `media_source_manual` 为真时保留人工值与标记位(扫描产生的 row 永远非人工) |
| 重扫「秒过」行的增量刷新 `_refresh_known_row` | 不碰 media_source | 无需改动 |
| 重复行合并(scan.py) | survivor 为空才补 | survivor 非人工而重复行人工时,连值带标记一起继承(对齐「人工身份优先」先例) |
| `relocate` 改名归并 | 只改路径 | 无需改动 |

### 3.3 快照同步刷新(标注服务的第二半)

摸底确认:`fill_snapshots` 只在 `quality IS NULL` 时构建,事后改
`library_file.media_source` **不会自动传导**到 `wanted_item.quality`。
标注服务必须自己刷新,规则:

- 定位该 media_item(+季)下所有订阅的 `status=imported` 工单行;
- `quality` 非空且非 `{}` 哨兵 → 只改出处维度:`media_source` 置为标注值、
  `remux` 键移除(人工标注对出处是权威的);**probe 实测字段一概不碰**
  (§4.1 实测优先);
- `quality IS NULL` → 不动,既有回填 tick 会用已标注的 library_file 构建;
- `quality = {}`(当时无在位文件)→ 不动。

与 §4.3「基线单调」的关系:基线单调防的是自动比较循环(同一候选两次判定
必须一致);人工标注与 §13.8 手选后的「基线修复」同族,是显式人工事件,
刷新后比较仍幂等,不引入循环。

## 4. API 契约

```
GET  /libraries/media-source-annotations/candidates?media_item_id=&season_number=
→ ApiResponse[[{ file_id, file_name, episode_number, size_bytes,
                 media_source, media_source_manual }]]   # 弹窗预览:将被标注的文件

POST /libraries/media-source-annotations
body: { "media_item_id": 965, "season_number": 7,
        "media_source": "WEB-DL" | ... | "user-lowest" }
（电影传季号哨兵 0,与 library_file/wanted_item 的电影单元约定一致）
→ ApiResponse[{ "files": 16, "snapshots": 12 }]
   message: "已将 16 个文件的片源标注为 WEB-DL,并刷新 12 个单元的质量快照"
```

- 命名对齐既有批量动作(复数名词资源 + POST);定位走 body,与
  `missing-record-clearances` 同风格——订阅侧入口拿不到库 id,条目 id 已足够
  (路径式单段 GET 会被更早注册的 `GET /{library_id}` 先匹配,也因此回避);
- 权限对齐库写操作:`require_admin`(库数据纠错是管理动作),前端入口以
  `isAdmin` 同步收敛;
- 幂等:重复标注同值无副作用;改标(WEB-DL → WEBRip)就是再调一次
  ——人工行始终在标注范围内;
- 值域由 schema `Literal` 锁死,非法值 422。

标注不自动触发搜索——前端在标注成功后**重跑一轮 `upgrade-runs`**,由它
完成排期与踢搜索(复用 §13.2 的五步,报告当场刷新,反馈闭环)。

## 5. UX:失败反馈的原地标注

### 5.1 时机与入口(两处,不新增页面)

- **洗版报告弹层**(`upgrade-run-dialog` 报告段):某季存在 `not_comparable`
  单元时,该季标题行出现「标注片源」按钮——用户刚点了洗版、刚被告知
  「无法确认」,意图最热、上下文最全。标注成功后自动重跑一轮体检,
  单元当场从「无法确认」翻成「可洗版 / 已达目标」,闭环发生在同一弹层内;
- **订阅详情追踪明细**(`WantedBreakdown` 季块):该季存在
  `upgrade.indeterminate` 行时,季标题行同位置给「标注片源」入口,
  作为事后常驻入口。标注成功后 reload 详情。

明确**不做**的时机:扫描入库时不问(入库时无洗版意图,问了是纯打扰;
多数扫描文件永远用不上片源信息——在真正阻塞决策的那一刻再要)。

### 5.2 标注弹窗

- 复用自研 `Modal`(嵌套在报告弹层之上时传 `raised`);
- 内容三段:该季待标注文件名列表(拉库详情、过滤本季 + `media_source`
  为空的在位文件)→ 档位单选(§2.2 六项,每项一行后果说明)→ 确认;
- 已有片源值的文件不在默认标注范围(v1 只治「未知」;改判已知值属于
  纠错场景,留给后续);
- 纯逻辑(选项表、后果文案、按季聚合「可标注」判定)抽到
  `apps/web/lib/media-source-annotation.ts`,按仓库惯例配 node:test 测试。

## 6. 边界与被否备选

- **被否:规则组开关「未知视同待洗」**。开关是策略层的洞,Remux 陷阱
  对开了开关的人重新生效,且开关粒度(规则组)与问题粒度(具体某季文件)
  不匹配;标注把同一个判断落在正确的粒度上。
- **被否:标注写进 enrich 词表 / 组名推断片源**(如 ADWeb ⇒ WEB)。组名
  与片源的对应关系不稳定且需要长期维护,错误推断污染的是全库自动解析;
  人工标注只影响被标注的行。
- **移动/改名**:`relocate` 保路径不动数据,人工标注天然存活;文件被删除
  重新入库则标注随行消失,如实回到「未知」——标注锚在文件行上,不做
  跨生命周期的记忆(简洁优先,场景罕见)。
- **多版本共存单元**:快照取 `_file_sort_key` 最优文件,标注整季所有
  未知文件,刷新逻辑与 `fill_snapshots` 同源,无特殊分支。
