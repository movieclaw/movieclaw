# 媒体库文件回收机制：「待回收」第三态与公共延迟删除

> 状态:已实施(§10 步骤 1–3;步骤 4 联动删除为可选,留待旧任务清理证据链联调)。起源于洗版旧版本清理的真实反馈(回收站
> 不可见、唯一做种副本无处安放),但机制本身是**媒体库层的公共设施,与订阅
> 完全解耦**——订阅/洗版只是第一个触发方,未来的手动删除、重复版本清理、
> 整库洗版都复用同一状态、同一展示、同一删除通道。
>
> 实现落差记录:①`trash_path` 列落地为 `trash_original_path`(语义反转)——
> `file_path` 恒为**当前物理位置**是全站不变量(缺失检测、ETag、播放都
> 依赖它),移入回收站时更新 file_path、原路径存 trash_original_path 供
> 恢复;②移动失败(权限/只读挂载)降级为原地待回收、不自动删,与做种
> 保护同一形态。

## 1. 问题与定位

现状的"回收"是一个物理动作:移文件进 `<库根>/.movieclaw-trash` + 删台账
行。三个结构性缺陷:

1. **不可见**:行删了,界面上无迹可寻,用户不知道回收站存在,更谈不上恢复;
2. **唯一副本无处安放**:可能是做种原始文件的唯一硬链接不能移动(断种、
   H&R),只能原地保留,与正常版本在文件区混作一团,去留不明;
3. **不可复用**:逻辑长在洗版验证里,下一个需要"安全删文件"的功能只能
   再抄一遍。

**定位**:把"回收"从物理动作升格为 `library_file` 的**生命周期第三态**。
现有两态:在位、缺失(`missing_since`,语义"意外消失")。新增:**待回收**
(语义"主动移除")。物理上动没动文件降级为后端内部策略,界面语言与删除
通道完全统一。

## 2. 数据模型:显式生命周期状态列 + 四个状态属性列

**现状确认**:`library_file` 至今没有生命周期状态列——`source`(入库/
扫描)与 `identity_source` 都是"来源",不是"状态";"在位/缺失"靠
`missing_since IS NULL` 推导。这正是推导态的弊端:每个消费方(播放、
展示、统计、对账)都要各自手写时间戳判空,再加一个状态就要全站再加一个
条件,漏一处就口径分裂。**趁本次把状态显式化**:

| 列 | 类型 | 语义 |
|---|---|---|
| `state` | text NOT NULL, default `in_place`, 索引 | **生命周期唯一判别式**:`in_place` 在位 / `missing` 缺失 / `trashed` 待回收 |
| `trashed_at` | datetime NULL | 进入待回收的时刻(仅 `state=trashed` 时有意义) |
| `trash_path` | text NULL | 文件当前物理位置(移入回收站后的路径);NULL 且 `state=trashed`=文件仍在原位(做种保护形态,`file_path` 即当前位置) |
| `purge_after` | datetime NULL | 预计自动删除时间;NULL=不自动删(等人工或联动触发) |
| `trash_context` | JSON NULL(none_as_null) | 审计快照,见 §4 |

**状态唯一真相与写路径收口**(防止判别式与时间戳两处真相):

- `state` 是唯一判别式;`missing_since` / `trashed_at` 降级为**状态附属
  时间戳**,只在对应状态下有意义。查询一律看 `state`,不再判时间戳;
- 状态迁移只允许经三个写路径:扫描对账(`in_place ⇄ missing`,同步维护
  `missing_since`)、回收服务(`in_place → trashed`、`trashed → in_place`,
  见 §5)、清理任务(`trashed → 删行`)。业务代码不得直接改 `state`;
- 迁移脚本按 `missing_since` 回填存量行的 `state`,两列自此保持同步。

其余决策:

- 不建独立表:第三态的全部意义在于"行不删",判别式在行上,独立表反而
  制造两处真相;
- 行被真正删除(清理完成)后审计快照随行消失——**留痕靠触发方的既有
  通道**(订阅活动流水、系统日志),机制本身不做永久审计库;
- 新列均有安全缺省,符合应用内回退契约:回退后的旧代码只认
  `missing_since`,待回收行被当作在位——已移入回收站的文件随后被对账
  标缺失、原地保留的照常在位,不丢数据只丢语义;回退期间的脏写(旧代码
  改了 `missing_since` 没改 `state`)由回退契约的"更新前自动备份恢复"
  兜底(CLAUDE.md 发布规范第 3 条),不为其设计双向同步。

## 3. 状态机与物理策略

```
在位(in_place) ──recycle()──▶ 待回收(trashed) ──purge(到期/立即/联动)──▶ 删除(文件+行)
   │   ▲                          │
   │   └────────restore()─────────┘
   ▼
缺失(missing)  ←── 扫描对账维护(既有语义不变),与待回收互斥
```

`recycle()` 的物理策略(2026-08-17 收敛,取代最初的做种保护判据):

- 普通文件**一律**移入 `<库根>/.movieclaw-trash`,`trash_path` 记新位置,
  `purge_after = now + 保留期`(默认 7 天,参数可覆盖);
- 原盘目录原地待回收不改名(内部可能住着其他在案文件行,移动会让那些行
  的路径悬空),**倒计时照常**,到期清理走 purge 的爆炸半径保护;
- 移动失败(权限/只读挂载)降级为原地待回收(`trash_path = NULL`),
  **倒计时照常**,到期清理按当前路径再试删除;
- 文件已不存在:不进待回收,直接删行(现状语义不变)。

> 决策记录:首版按 `st_nlink == 1` 做"做种保护"(原地留置、永不自动删),
> 但复制入库部署下库文件 nlink 恒为 1(做种原始文件在下载目录,不受库内
> 改名影响),保护必然全命中——NAS 实测 57 个替换旧文件 53GB 永久滞留,
> "7 天自动清理"形同虚设。收敛为:回收站即安全网,想保留由用户「恢复」;
> inplace 部署的断种取舍由触发方(洗版是显式 opt-in,副文案已讲明后果)
> 与用户操作层承担,机制不再猜测。

缺失与待回收正交:待回收期间文件消失(用户在文件系统里手动删了),
清理 tick 发现后直接删行收敛,不设 `missing_since`。

## 4. 审计快照(`trash_context`)

与订阅解耦的关键:机制不外键订阅表,只存**展示用快照**——

```json
{
  "reason": "upgrade_replaced",          // 词表:upgrade_replaced / upgrade_refuted / manual / ...
  "trigger": {                            // 谁触发
    "kind": "subscription",              // subscription / member / system
    "id": 12,
    "label": "《九门》订阅洗版"           // 快照文案,免 join、免悬空引用
  },
  "note": "洗版替换:1080p WEB-DL → 1080p Remux"   // 中文整句,文件区直接展示
}
```

## 5. 公共服务(`services/library/recycle.py`)

订阅、未来任何功能都只调这四个函数,不各自摸文件系统:

- `recycle_file(session, file, *, reason, trigger, note, purge_after=DEFAULT)
  -> RecycleOutcome`:唯一入口,返回 `moved_to_trash / kept_in_place /
  already_gone`;只改行+移文件、不 commit(跟随调用方事务);
- `restore_file(session, file)`:恢复——`trash_path` 移回 `file_path`
  (同名冲突加时间戳),原地保留形态只清状态;三个状态列清零;
- `purge_file(session, file)`:立即清理——删物理文件(`trash_path` 或
  `file_path`)+ 删行;**唯一副本的断种确认由 UI 层负责**(机制不拦,
  用户显式知情后有权断);
- `purge_due_files()`:定时任务,`purge_after <= now` 的行删文件+删行;
  文件已缺失的也删行收敛。现有 `cleanup_trash_dirs`(按 mtime 扫目录)
  降级为**无主孤儿文件兜底**保留——升级瞬间回收站里已有的老文件没有
  台账行,仍靠它清。

**调度周期**(注册为媒体库域的独立定时任务,不再搭洗版回填 tick 的便车):

- `purge_due_files`:**每小时一次**。删除滞后至多 1 小时,相对 7 天保留
  期可忽略;倒计时展示直接读 `purge_after`,精度不受执行周期影响;急迫
  需求由「立即清理」按钮覆盖,不靠缩短周期解决;
- 孤儿目录兜底清扫:**每天一次**(纯目录遍历,无台账,低频足矣)。

## 6. 库存口径收口(显式状态让审计从"加条件"变成"换口径")

状态显式化后,口径不再靠各处手写时间戳判空拼条件,而是**替换为一个共享
判别**:`LibraryFile.state == "in_place"`(或仓储层的命名常量/默认过滤,
实施时收在 `library_file_repo` 单点)。审计动作 = 把现存的每一处
`missing_since IS NULL` 机械替换为共享口径——将来再加第四种状态,
所有消费方零改动。

各接口的口径归属(实施时逐项打勾):

| 口径 | 处理 |
|---|---|
| `owned_units` / `owned_units_many`(库存 H) | 仅 `in_place` |
| 库统计(media_library_stats) | 仅 `in_place` |
| 订阅对账 `close_fulfilled_wanted` / 快照 `fill_snapshots` / 验证选优 | 仅 `in_place` |
| 任务中心手动锚对账 inventory | 仅 `in_place` |
| Jellyfin 播放/展示接口(媒体服务器不该看到待回收版本) | 仅 `in_place` |
| **扫描对账的按路径匹配** | **含 `trashed`**——原地保留形态的文件还在原路径上,匹配不到行就会被当新文件重新收编(证伪残留"重生"的老风险,第三态天然根治它,前提是匹配口径包含) |
| 文件区 API(条目详情) | 含 `trashed`,带状态与倒计时字段返回 |

扫描对路径命中待回收行时**不得复活状态**(保持 `trashed`),只更新探测
属性。

## 7. UI:文件区统一呈现(条目详情 FileSection)

待回收行(电影列全部版本、剧集列当前选中集,沿用现有布局):

- 文件名**删除线** + 「待回收」徽标;
- 副文案按形态:有 `purge_after` → "预计 X 天 X 小时后自动清理";无 →
  "做种保护中,不自动清理";末尾拼 `trash_context.note`(如"由《九门》
  订阅洗版替换");
- 行操作(canManageLibraries):**恢复** / **立即清理**——唯一副本形态的
  立即清理弹确认:"该文件可能仍在做种,清理会中断做种任务";
- 不做全局回收站面板:文件区行内呈现已覆盖"感知+操作"两个需求,低频
  管理不值得一个页面;留作扩展。
  （2026-09-06 已扩展：媒体库管理页「回收站」标签,跨库按条目分组管理,见 `library-recycle-bin.md`。）

## 8. 触发方对接(本期:洗版)

- 验证确认替换旧版 → `recycle_file(reason="upgrade_replaced",
  trigger=subscription, note="洗版替换:X → Y")`;UPGRADED 活动照记,
  文案区分"已移入回收站"与"做种保护,原地待回收";
- 证伪隔离/证伪文件移除 → `recycle_file(reason="upgrade_refuted", ...)`;
  行保留在台账里,扫描重新收编的"重生"防护从"移动成功才删行"简化为
  第三态天然成立;
- **联动删除**(quality-upgrade.md §11 开放问题,本方案的可选末段):
  旧 attempt 走证据链清理到 SUPERSEDED(任务确认已不在下载器)后,把
  对应"原地保留"行的 `purge_after` 补上,进入正常倒计时——"任务没了"
  是"可以安全删文件"的充分证据。

## 9. 规则组选项:旧版本处置

`RuleSetSpec` 加 `upgrade_keep_old?: boolean`(缺省 false):

- **false(默认)**:确认升级后旧版走 `recycle_file`(现行为);
- **true(保留共存)**:旧版不进待回收,多版本共存——服务
  quality-upgrade.md §11 预留的"电影收藏家"场景;
- 编辑器位置:规则组「洗到哪一档」下方,仅选了洗版目标时显示——
  "配置洗版的那一刻"就是询问旧版去留的合适时机;
- 放规则组而非全局设置:符合"订阅只持规则组引用,想微调就复制规则组"
  的架构,收藏家可只给珍藏影片挂"保留共存"的组。

## 11. 边界与不做

- 手动删除文件入口**本期不改**(现有二次确认直删):机制已就绪,改走
  回收站属后续统一,避免一次改动过宽;
- 保留期写死 7 天不升设置项(quality-upgrade.md §11 立场不变,机制层
  已是参数,升级零成本);
- 不做永久审计日志表:留痕在触发方的活动/日志通道。
