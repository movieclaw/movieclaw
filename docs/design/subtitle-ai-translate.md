## 0. 核心裁决：产物就做成外挂字幕文件

**是。写成视频同目录的 sidecar（`<stem>.<产物标题>.<语言>.srt`）是唯一
正确形态**，四条理由：

1. **消费链路零改动全自动生效**：文件落盘 → watchdog 字幕事件 → 台账
   重发现 → PlaybackInfo 外挂流（带 DeliveryUrl）→ 播放器可选可显、
   编码归一与格式转换照走——jellyfin-subtitle.md 建成的整条链路直接
   吃到，生成机制不需要碰 B/C 层任何一行代码；
2. **文件即资产**：跟着视频走（搬库/整理同迁）、用户可用任何工具编辑
   修正、迁回真 Jellyfin/Emby 或换任何播放器都仍然可用——不锁在
   movieclaw 的数据库里；
3. **回退零成本**：不满意删文件即可，下轮扫描台账自动消失；重新生成
   就是覆盖写同名文件；
4. **与"库存事实"模型自洽**：台账（external_subtitles）的语义是"目录里
   有什么"，AI 产物落成目录里的真实文件后自然入账，不需要第二套
   "虚拟字幕"记账体系（那会让台账三态、可见性、缓存失效全部翻倍）。

命名约定把播放器识别的 ISO 639-2/B 语言码固定放在扩展名前一段，产物类型
放进 title 段：简中 `Movie.2024.ai-chs.chi.srt`、英语
`Movie.2024.ai.eng.srt`、简中+英语双语
`Movie.2024.ai-bilingual-chs-eng.chi.srt`。这既让 Jellyfin/Plex/Kodi 等按
`chi/eng` 识别主语言，也让 MovieClaw 能显示 AI 类型和双语组合；同一语言
组合重生成覆盖同名文件，不同组合则各自保留为独立外挂。

## 1. 三级来源瀑布

```
① 现存字幕翻译（本设计主体）
   台账外挂 + 内封文本轨 → 选最优参考 → LLM 分块翻译 → sidecar
② 音轨识别（远期 P3，本文只定接口位）
   无任何文本字幕源 → ASR 出原语言字幕 → 进 ① 的翻译管线
③ 在线字幕站点（不做）
   Infuse/VidHub 自带在线字幕；服务端接字幕站生态此前已裁决不做
   （jellyfin-subtitle.md §1），本设计不推翻
```

## 2. 源选择：规则打分，不用 AI

"找准确率最高的参考"不需要 LLM 参与——决定参考质量的因素全部是
结构化事实，规则打分即可（省一次调用，且可解释可测试）：

候选池 = `external_subtitles`（文本外挂）∪ `subtitle_streams` 中的
文本内封轨（`srt/ass/ssa/subrip/webvtt/mov_text` 等）以及可由当前设备
识别的 PGS 图形轨；VobSub 等未接入图形格式仍排除。打分维度按权重从高到低：

1. **排除项**：forced 旗标（外语片段部分字幕，几百条对话缺失，绝不能
   当翻译源）；目标语言自身（已有目标语言字幕时任务本就不该发起）；
2. **语言优先**：影片原语言（`media_metadata` 可得 original_language）
   最优——原语言字幕是"第一手台词"，其他语言字幕已经是一次翻译，
   二次转译误差叠加；其次英语（字幕组世界的通用中间语言）；
3. **来源世代**：同语言时按发行原文/普通外挂 → PGS OCR 文本 → AI 单语
   → AI 双语成品排序。后两者仍允许用户手动指定，但不默认拿 AI 成品再次
   翻译，避免误差和 token 重复叠加；
4. **完整度**：解析后的对话条数与覆盖时长比（首末事件跨度/影片时长）
   ——防止选中残缺轨；内封轨条数未知时先抽取再评估（§4）；
5. **形态（评审修正 2026-08-10：反转为内封优先）**：内封轨优先于
   外挂——WEB-DL/原盘的内封多为发行方官方字幕（随片投递的专业翻译，
   与片源精确对齐、质量方差小），外挂来路多样（字幕站转载/OCR 转制/
   来源不明）方差最大。v1 曾以"免抽取一步"排外挂在前，那是工程成本
   论据不是质量论据：抽取是一次秒级 ffmpeg 调用，相对 LLM 翻译成本
   可忽略，不配影响选源。形态整体只做**平分决胜**——真正的质量信号
   是前四条与同步度（§5.2 的 L1 对内封外挂一视同仁）；sdh 可用但
   翻译前清理 `[音效]`/`(拟声)` 类标记；ass 可用（只取对白文本）。

平分时取序在前者（决定性）。选源结果与打分明细落任务日志——用户要能
看懂"为什么选了这条"。

## 3. 翻译管线（LLM 核心环节）

### 3.1 分块与上下文

- pysubs2 解析参考字幕 → 对话事件序列（时间轴 + 文本）；
- **按事件数分块**（每块 ~40-60 条），块间带**滚动上下文**：上一块的
  末尾 N 条原文+译文一起入 prompt——跨块的对话连贯性靠它（角色称谓、
  上下句衔接）；
- 全片**术语表两遍法**：第一遍快速扫全文（或抽样）让模型抽取人名/
  地名/专有名词并给出统一译名，第二遍逐块翻译时把术语表钉进 system
  prompt——同一个角色名整片一致是字幕质量的硬指标；
- 影片风格素材入 system prompt：标题/年代/类型/简介（媒体库元数据
  现成）+ 明确指令"保持台词口语化、贴合角色语气、不过度书面化"。

### 3.2 结构化输出与校验（防幻觉的硬约束）

- 请求体给**带序号的原文清单**，要求返回同序号的译文 JSON 对象
  `{"items": [...]}`；支持 JSON mode 的供应商在协议层同步启用，
  **时间轴完全不经过模型**——模型只见文本，时间轴由管线原样保留，
  从机制上杜绝时间漂移；
- 逐块校验：返回条数=输入条数、序号连续；不符重试该块（至多 2 次），
  仍失败该块保留原文并记告警——**出错的块保留原文也比整任务失败强**；
- 行长后处理：中文按 16 字/行折行（Netflix 简中标准，§3.3；规则处理，不劳模型）；
- 输出恒为 **srt + UTF-8**（最大公约格式；参考是 ass 时只翻对白，
  样式不迁移——样式迁移收益低、幻觉面大，列不做）。
- 单语每条只输出目标语言；双语每条严格输出两行，第一、第二行语言由用户
  分别选择，校验器拒绝缺行、多行或两种语言相同的任务。时间轴仍只保留一份。

### 3.3 好字幕的标准（行业规范调研结论，2026-08-10）

依据 Netflix 简体中文 Timed Text Style Guide（流媒体行业事实标准）与
Pedersen 的 FAR 字幕质量评估模型（JoSTrans 2017，学术界通行框架），
"好的字幕翻译"可拆成三个维度（恰好对应 FAR 的 F/A/R）：

**R 可读性（技术呈现，全部可机检）**——Netflix 简中硬指标：

| 指标 | 标准 |
|---|---|
| 阅读速度 | 成人 ≤9 字/秒，儿童 ≤7 字/秒（不是越全越好，读不完=没翻） |
| 行长 | ≤16 字/行，≤2 行，能一行不两行 |
| 显示时长 | 5/6 秒 ~ 7 秒 |
| 标点 | **不用句号和逗号**（简中字幕惯例，停顿用空格/直接结束）；省略号表停顿与中断；问号感叹号保留但禁 !?/??/!! 组合；全角双引号""、书名号《》、外文人名全角间隔号（威廉·莎士比亚）；**禁斜体** |
| 数字 | 一到十用汉字，其余半角阿拉伯数字，禁全角数字，四位数内不加千位分隔符 |

**A 可接受性（目标语自然度）**：像"说得出口的中国话"而非书面翻译腔；
称谓与人际关系一致（你/您、哥/先生贯穿全片不漂移）。

**F 功能对等（语义与风格忠实，FAR 中权重最高）**：语气/语域/正式度/
阶层感/年代感对齐原文；**脏话保持同等强度不消毒、不审查**（Netflix
明文规则）；**浓缩优先于直译**——字幕是压缩的艺术，CPS 超标时压缩
表达保核心语义（删冗余语气词、化长句为短句），绝不截断硬塞；文化
专有项给观众可懂的对应表达，**不加译者注**；歌词仅剧情相关时翻译；
画面上已可认知的品牌英文可保留。

### 3.4 提示词要求（§3.3 的蒸馏，逐条可进 system prompt）

```
角色：资深影视字幕翻译（简体中文）
上下文：片名/年代/类型/简介 + 术语表（人名地名译名钉死）
1. 语气忠实：语域/正式度/阶层感/年代感对齐原文；粗口保持同等强度，
   不消毒不审查；角色语气差异要能听出是谁在说话
2. 口语自然：译文必须"说得出口"，禁书面翻译腔；称谓全片一致
3. 浓缩优先：每行尽量 ≤16 字、单条 ≤32 字；超长时压缩表达而非直译
   堆字——删冗余语气词、保核心语义；绝不截断
4. 标点铁律：不用句号逗号（句尾直接结束）；停顿/中断用省略号；
   问叹号保留；全角引号/书名号/人名间隔号；禁斜体标记
5. 数字：一到十汉字，其余半角阿拉伯数字，禁全角
6. 文化项：给观众可直接理解的对应说法，禁加括号注释/译者注
7. 结构铁律：逐条对应翻译，禁合并/拆分/增删条目；只输出译文不带
   原文；非对白文本（音效标记）按 [标记] 原样保留语义翻译
8. 双语任务：每条恰好两行，严格按用户选择的第一/第二语言顺序输出，
   不加语言名、序号或括号
输出：与输入同序号的 JSON 清单
```

### 3.5 校验标准（FAR 三级落地：机检 → 半自动 → 抽样）

- **机检（每块必过，§3.2 的扩展）**：条数/序号一致；时间轴未动
  （管线保证）；输出语言=目标语言（夹带成段源语言=漏翻，该块重试）；
  简中按 16 字/行与 9 字/秒处理，日韩及拉丁/西里尔等书写体系使用各自
  行长和读速阈值，非中文标点不套用简中清理规则；双语分别检查两行而不把
  两种语言字数相加。CPS 超标率落任务报告——参考字幕时长摆在那，
  翻译只能压缩表达，
  超标率是翻译"浓缩力"的直接量化）；禁用标点扫描（句号/逗号结尾、
  全角数字）自动清理；
- **半自动（任务报告呈现）**：术语表一致性扫描——glossary 里的译名
  在全文的一致率（机检可得，人名漂移是字幕质量最刺眼的伤）；
- **抽样（G2 可选）**：LLM judge 用低成本模型对随机 N 条做语义一致性
  回评（F 维度的自动近似）；G1 靠人工验收。

### 3.6 任务形态：可恢复、可取消、有成本护栏

- 长片 1500+ 条对话 ≈ 30-40 个块，任务分钟级——必须进入持久化 Job。Job
  是状态、进度、取消、重试、审计与任务意图的唯一事实源，字幕领域不再维护
  `TaskState`、进程内主管或独立的 `*.job.json`；
- HTTP 开始接口只负责预检并原子创建 Job，返回 `202 + JobView`。查询、等待、
  取消、重试统一使用 `/jobs`；前端、CLI、Agent 与自动任务不走领域兼容接口；
- 已译块暂存 `data/cache/subtitle_gen/<file_id>.<lang>.checkpoint.json`。正常停机
  把运行 Job 退回队列，崩溃由租约恢复；重新领取后从检查点继续，成功落盘才
  清理检查点。LLM 调用是真金白银，已完成块不会重复消费；
- 成本护栏：任务发起前按事件数估算 token 量并在确认框展示；Job 调度器默认
  最多并行 4 个不同资源任务，同一文件由资源锁单飞；单个字幕任务内部从 8 个
  翻译块并行起步。遇到供应商 429 时并发
  减半并按 `Retry-After`（缺失时指数退避）重试，连续稳定完成 8 块后逐级恢复。
  术语表先统一生成，并发窗口用前一块原文补充语境，断点由协调器按块单写；
  单次运行失败块超阈值（>20%）自动中止。失败块在断点里存的是保留原文的
  占位并单独记账，续传时重新翻译而不是当成已完成跳过——否则历史失败数会在
  开跑前直接顶穿熔断，任务陷入「一重试就中止」的死锁；重译成功即销账；
- **不自设 `max_tokens`**（与 agent 侧一致，交给供应商按剩余上下文兜底）。
  曾按用途和条数估算「有界输出预算」，结果是深度思考模型的思考先烧光额度、
  译文 JSON 半截被 `finish=length` 截断（issue #194）。上限并不省钱——被截断
  的响应照样全额计费却零可用产出，等于把「付一次拿到一个块」换成「付三次
  什么都没有」；且思考长度无法预估，任何静态数字都是猜。真正的成本闸门是
  块重试上限与失败率熔断，它们按「块」计价，比按 token 猜数字可靠。
  Kimi K2.5/K2.6 官方端点仍关闭深度思考并启用 JSON mode——那是省下不需要的
  推理开销，与设不设上限无关；
- 撞上供应商自身输出上限（`finish=length`）时**立刻把块对半拆开重译**，不浪费
  同尺寸重试：天花板是确定性的，同样条数重发必然再次截断。逐层再拆但深度封顶
  两层（50→25→12，调用次数 ≤1+2+4），拆到底仍写不完就保留原文交给熔断。
  这是唯一不依赖供应商能否关思考、能否调预算的兜底；
- 断点原子写盘（临时文件 + `replace`，同 `write_srt`）：就地覆盖会在崩溃窗口
  把整份已完成译文写成半截 JSON，下次加载失败即等于已付的钱全部作废；
- Job `usage` 聚合请求数、输入/输出 token、缓存命中、最长耗时、finish reason
  与分用途用量；日志携带 job、用途、块号和重试次数，Agent 日志与字幕日志可区分；
- 术语阶段和翻译首批等待期间每 10 秒发布心跳。百分比仍只按校验通过的块
  计算，不伪造进度；明细额外给出活动块、最长等待、最近完成、限流和格式重试；
- LLM 调用经 `movieclaw_llm.router`（供应商/模型由现有 LLM 设置域
  决定），限流与重试沿用接入层语义，`LlmRateLimitError` 退避续跑。

## 4. 内封轨抽取（兑现 jellyfin-subtitle.md §6.4 的预留）

选中的参考是内封轨时，先抽成临时文本文件再进管线：

- `ffmpeg -i <video> -map 0:s:<k> -c:s srt <tmp>`（文本轨转 srt）——
  沿用 media_probe 的直接 subprocess 风格，线程池执行、超时保护、
  失败中文日志；不引 ffmpeg-python；
- `0:s:<k>` 的 k 就是 `subtitle_streams` 数组下标（与中性引用
  `embedded:<k>` 同源，ffprobe 输出序即 ffmpeg 字幕流序）；
- 抽取产物进 `data/cache/subtitle_gen/`，任务结束清理——它是中间品，
  不是资产，不落库目录；
- strm 条目没有本地视频本体：内封轨不可抽取，候选池只有外挂
  （云播放场景恰好外挂就是主形态，影响有限，任务发起时如实提示）。

## 5. 时间轴校准（比翻译更早的质量门，用户提出 2026-08-10）

参考字幕若本身错位，翻译再好也是全片错位、LLM 消费全部作废——
同步性检查必须发生在翻译之前。

### 5.1 分场景定性：什么时候会错位

**主路径天然对齐**：G1 参考只取本文件内封/同目录外挂（本就是配套
字幕），且时间轴不经过模型原样透传（§3.2）——大多数任务无需校准。
会错位的三种形态与校正模型：

| 形态 | 成因 | 校正模型 |
|---|---|---|
| 恒定偏移 | 片源片头 logo/广告长度差异 | 全局平移 `t+b` |
| 线性漂移 | 帧率差异（23.976↔25 的 PAL 加速） | 线性缩放 `a·t+b` |
| 分段错位 | 剪辑版本差异（加长/删减/插播） | 分段线性 |

触发场景：用户手工放入的字幕站外挂（配另一版本片源）、跨版本复用
（开放问题 3）、ASR 产物的时间戳漂移（P3）。

### 5.2 分级方案：以音轨为真相源

- **L1 同步度检测（G1 就做）**：silero-vad（官方 ONNX 模型 ~2MB，
  走 onnxruntime + 模型 Release 分发的既有基建）从音轨抽"语音区间"
  序列，与字幕事件区间算重叠率——**抽样即可**（首/中/尾各 ~2 分钟，
  ffmpeg subprocess 抽 16k 单声道 PCM），不必全片。两个用途：选源
  打分加一维（同步度差的参考降权）；任务发起前自检，低于阈值明确
  告警"参考字幕可能与影片不同步"；
- **L2 全局自动校准（offset + 线性缩放）**：字幕事件序列与 VAD 语音
  序列各栅格化成 10ms 的 0/1 信号，**FFT 互相关**求最优偏移；帧率
  假设集 `{1, 25/23.976, 24/25, …}` 逐个尝试取相关峰最大者 →
  `(scale, offset)` 双参数校正——ffsubsync 同款原理，numpy 几十行
  自实现（numpy 已在依赖），不引 CLI 导向的 ffsubsync 包；
- **L2' 字幕对字幕**：无音频可用而本文件已有一条确认对齐的字幕时，
  两条字幕做时间结构互相关——对齐用的是事件起止序列不是文本，
  跨语言同样成立；
- **L3 分段线性 + ASR 精修（P3）**：剪辑差异需要 alass 风格分段对齐
  （Rust 二进制，无 Python 库，届时评估外部工具调用）；ASR 产物用
  faster-whisper 词级时间戳 + VAD 边界收紧。G1 选源不引入外部字幕，
  分段错位场景暂不存在，不预做。

### 5.3 strm 的特殊性与远期解法

无本地音轨 → L1/L2 不可用，优先走 L2' 字幕对字幕；远期可用 Range
请求只拉云端文件的 3×2 分钟音频片段做 VAD 抽检（几十 MB，流量可控，
不违背"零网盘流量"的浏览原则——这是用户主动发起的生成任务）。

### 5.4 顺带的独立用户价值：字幕校准工具

校准模块与翻译解耦（`subtitle_gen/sync.py`），可单独暴露"一键校准
已有外挂字幕"：用户手工下载的不同步字幕就地修正（校准后覆盖写回
或另存 `.synced.` 副本）——不只服务 AI 管线。

## 6. 触发形态

| 入口 | 期 | 说明 |
|---|---|---|
| 手动：条目/版本详情页“AI 字幕”（目标语言可选，默认简中） | P1 | 主入口。可选单语或任意两种受支持语言的双语组合，发起前展示选源结果与成本估算 |
| 手动重生成 | P1 | 覆盖写同名 sidecar；台账由 watchdog/扫描自动刷新 |
| 自动：入库后检测目标语言缺失即生成 | P2 | 库级开关**默认关**——批量入库=批量 LLM 消费，必须用户显式授权；沿用"资源管控三件套"范式做开关与额度 |
| ASR 兜底 | P3 | 见 §8 |

手动入口与已有字幕徽章排列在同一行，用独立强调色区分“可生成的字幕”与
库存字幕。点击后先同步预检并打开确认弹窗：用户可从全部可用内封/外挂字幕
中明确选择参考字幕，默认优先英语、没有英语时回退既有质量排序；PGS 也作为
可选候选，选择后进入同一套 OCR 确认。弹窗同时显示目标语言、输出位置、对白
数和预计 token；这一步不调用 LLM。用户确认后才提交后台
任务，入口原位常驻展示当前阶段或翻译百分比；桌面端悬浮/键盘聚焦的 tooltip
与点击后的状态弹窗都展示完整阶段、块数、对白条数、耗时、模型用量、并行中
的块及最长等待；术语分析不显示误导性的 `0%`。离开页面不影响任务。
预检不能生成时仍留在弹窗内，用结构化原因区分无字幕、
仅图形字幕、已有目标语言、文本字幕损坏或不完整，并给出可执行的下一步。
当唯一可用源是 PGS 时，预检先检测当前平台、架构、SeConv、OCR 引擎及对应
语言包；能力完整才展示“先转换 PGS 并生成”，且必须用户再次确认。OCR 结果
先缓存在 `data/cache/subtitle_gen/`；通过完整度检查后，另存为视频同目录的
`<stem>.pgs-ocr.<语言>.srt` 外挂，再进入同步检测和翻译。即使后续 AI 失败，
这份耗时得到的识别字幕仍可复用、预览和校准，
VobSub 等其他图形字幕仍提供明确的不兼容提示，
不再只返回“没有可用的参考字幕”。

官方 amd64/arm64 镜像内置 Tesseract 的简繁中、英、日、韩、法、德、西、意、
葡、俄语言数据；源码运行和其他语言仍由预检逐项检测，缺少对应 traineddata
时在确认框给出安装提示，不允许静默回退到错误语言。
OCR 语言表示“PGS 图片中的文字语言”，与最终翻译目标无关。系统按轨道语言
标记 → 轨道标题 → 影片原语言依次推断：结论明确时自动采用；语言缺失、简繁
不明或元数据冲突时，才在同一个确认框展示带推荐值的语言选择。启动请求同时
绑定所选参考字幕、候选轨道和用户确认的 OCR 语言；这些参数随 Job 输入持久化，
重启续传仍使用同一来源。后台复验不一致时要求重新预检，不能换轨或换语言后
继续执行旧确认。

产物落视频同目录；目录只读（只读挂载）时写失败给明确中文错误，
不做库外落位兜底（第二条路径破坏"外挂=同目录"约定，见开放问题 1）。

## 7. 分层归属（对齐既有架构）

| 能力 | 层 | 模块 |
|---|---|---|
| 选源打分、内封抽取、翻译管线、任务编排 | A 媒体库（生产端服务） | `movieclaw_api/services/subtitle_gen/` |
| LLM 调用 | LLM 接入层 | `movieclaw_llm.router`（现成） |
| 字幕解析/写出 | 复用 | pysubs2（已入依赖） |
| 发现/台账/输出/播放控制 | 已建成 | **零改动**——sidecar 落盘即被消费 |

翻译管线不 import `movieclaw_jellyfin` / `movieclaw_playback`——它是
纯生产端，与播放两层互不感知（守护测试同款断言）。

## 8. ASR 远期（P3，只定接口位）

- 形态：`SubtitleSource` 抽象的第三个实现（现存外挂/内封抽取之外），
  产出"原语言 srt"后**汇入同一个翻译管线**——ASR 与翻译解耦，英语片
  ASR 产物本身就可直接落盘；
- 技术候选：faster-whisper（CTranslate2，CPU 可跑但 2 小时片实转
  数十分钟起）或 OpenAI 兼容的转写 API（走现有 LLM 供应商体系）。
  本地模型可沿用 NER 模型的"GitHub Release 下载、不进包"分发惯例；
- 不在本期展开：CPU 推理时长、VAD 断句质量、音轨选择（多音轨选原语言）
  都需要单独调研，先把 §3 管线的输入接口留成"任意 srt 事件序列"即可。

## 9. 不做清单

| 不做项 | 理由 |
|---|---|
| VobSub 等非 PGS 图形字幕 OCR 做翻译源 | 当前转换器只覆盖 PGS；未知格式不得静默尝试 |
| 未经用户确认自动 OCR PGS | OCR 成本高且错字会被翻译放大；必须预检能力和语言包后显式确认 |
| ass 样式迁移 | 样式迁移幻觉面大；本期只产 UTF-8 SRT |
| 服务端接在线字幕站点 | 既有裁决（jellyfin-subtitle.md §1），播放器自带 |
| LLM 参与选源 | 结构化事实规则可判，省调用、可解释、可测试 |
| 翻译产物入库不落盘 | 违背"文件即资产"与台账语义，见 §0 |

## 11. 开放问题

1. 只读库目录的产物落位（库外 data/ 落位会引入"第二路径"，需要台账
   与服务层同时扩展——有真实用户诉求再议）；
2. 翻译质量评估的自动化（抽样回译比对？）——G1 先靠人工验收；
3. 多版本条目（同片多文件）是否共享翻译产物——时间轴可能因版本
   剪辑不同而错位，v1 按"每个文件各自生成"处理，不做跨版本复用。

## 12. 实施状态（2026-08-11）

**G1 + G2 已全量落地**（`src/movieclaw_api/services/subtitle_gen/` 六模块 +
管理区五接口 + 控制台详情页入口），并已加入多目标语言、双语输出、PGS OCR
外挂留存和规范化文件名；P3（ASR + L3 分段对齐）按定稿单独
设计后实施。相对设计的实施期决策：

- 接口挂管理区（G1/G2 均管理员专属）：翻译消费 LLM 配额，成员开放待
  有真实诉求时随成员额度一起评估；
- 自动生成的每日额度为进程内按天计数（自托管单机语义，重启清零可
  接受——额度是防批量失控不是硬计费），同文件本进程只自动尝试一次；
- 一键校准覆盖写回原文件（不同步的原件无保留价值），非 srt 格式原格式
  平移缩放写回（ass 样式保留）；本就同步（偏移 <200ms）不动文件。校准入口
  收进字幕预览弹窗，结果就地展示，不再制造“校准结果是另一份最终字幕”的误解；
- 编码判定实施期重构：弃 charset-normalizer 排序，改 gb18030/big5hkscs
  双解 + 高频汉字占比打分（短样本下探测器把 GBK 误判 big5 的实际缺陷，
  生产端与播放端同步修正）；
- silero-vad 为可选增强（模型入 data/models/silero-vad/ 即启用），
  缺失降级能量法 VAD——同步检测阈值按能量法的噪声水平取宽松值。
