## 0. 现状盘点

把今天的单库页拆开看，它只有**一个维度**：

| 能力 | 现状 | 代码位置 |
|---|---|---|
| 排序 | 默认（拼音序）/ 最近添加，二选一，存 localStorage | `library-detail-view.tsx:178` `WallSortPref` |
| 服务端排序 | `title` / `added_at` / `release_date` / `probing` | `services/library/items.py` `WallSort` |
| 跳转 | A-Z 首字母索引条（按标题时）、月份档（按内容时间时） | `items.py: build_library_index` |
| 收窄 | **无**。只有全局搜索按标题匹配 | — |
| 分区 | 待识别 / 忽略 / 缺失 / 复核——都是**运维**分区，不是内容分区 | `library-detail-view.tsx` |
| 聚合 | 全局收藏页（`/library/favorites`），一种排序，无筛选 | `favorites-view.tsx` |
| 合集 | **无**。TMDB 系列只在详情页「系列作品」露出；发现页的「片单」是站外发现，不是我的库 | `movieclaw_media/service.py:702` |

**问题定义**：库过千部以后，海报墙是一条**只能从头翻的走廊**。用户心里真实的问题是
"今晚有 90 分钟，想看部评分高的老港片"、"孩子能看什么"、"我那些 4K 片都在哪"，
而墙只能回答"按拼音第 300 部是哪部"。

**同时**，可筛的事实其实**早就齐了**——这是本设计成本低的根本原因：

| 事实 | 存在哪 | 是否语言无关 |
|---|---|---|
| 类型 | `media_metadata.genre_ids`（TMDB ID） | ✅ 已为路由准备好 |
| 地区 | `media_metadata.origin_countries`（ISO 码） | ✅ |
| 年代 / 上映 | `media_metadata.release_date`、`media_item.year` | ✅ |
| 评分 | `media_metadata.vote_average` / `vote_count` | ✅ |
| 片长 | `media_metadata.runtime_minutes` | ✅ |
| 分级 | `media_metadata.content_rating`（CN 优先） | ✅ |
| 语言 / 出品 | `original_language` / `studios` | 出品是本地化名，见 6.4 |
| 人物 | `person` + `media_item_person`（cast / director） | ✅ |
| 观看状态 | `playback_state.played` / `last_played_at` / `is_favorite`（**按成员**） | ✅ |
| 剧集状态 / 缺集 | `LibraryItemView.air_status` / `missing_episode_count` | ✅ 已在墙数据里 |
| 画质 | `library_file.resolution` / `hdr` / `video_codec` / `bit_depth` | ✅ |
| 体积 / 来源 | `library_file.size_bytes` / `source` / `site_id` / `release_group` | ✅ |

**没有一个筛选维度需要新刮一次数据。** 缺的只是收窄、计数、和把收窄固化下来的能力。

## 1. 五条产品铁律

1. **筛选是改货架，不是查数据库。** 低承诺、即时生效、随时可撤。永远不做
   "打开表单 → 填写 → 提交 → 看结果"，那是搜索引擎的交互，不是货架的交互。
   一切筛选控件默认展开在墙的上方，点一下就变，再点一下就回来。
2. **永不空货架。** 每个候选值都带**当前条件下的剩余数量**，为 0 的置灰不可点；
   万一还是筛空了（多选组合），不显示空墙，而是显示"放宽哪一条能救回多少部"。
   Netflix 的货架永远不空，这不是美学，是留存。
3. **一次只学一套条件语言。** 筛选（此刻的切片）、合集（固化的切片）、库收藏范围
   （入库的切片）是同一件事的三个时态，共用 `library-routing.md` 1.1 定义的
   `[{field, op, values}]` 结构。用户在筛选条里做的每一次选择，都可以原样存成合集，
   也可以原样变成一个库的收藏范围。**不新增第二套 DSL。**
4. **「找片」与「查库」分栏。** 观看意图（类型/年代/评分/分级）和管理意图
   （画质/体积/缺集/未识别）是两种人格，混在一行 chips 里会让两边都难用。
   一级筛选条只放找片维度，查库维度收进「更多筛选」的右栏。
5. **合集不另起一个库。** 作品进了合集**不从主墙消失**——这是 Emby 把 Collections
   做成独立库最大的困惑来源，`library-routing.md` 第 0 节已经就"分库让内容消失"
   做过同样的判断。合集是库内的一层视图。

## 2. 信息架构

```
/library                    首页：最近观看 · 最近添加 · 库卡片          （不变）
/library/[id]               单库页，两个视图切换（作品 / 合集）
   ├─ 作品视图
   │    ├── 合集 chip 行（一行 30px，不是横滚封面卡，见 4.3）  ← 新增
   │    ├── 筛选条 + 排序                                    ← 新增
   │    └── 海报墙（筛选结果）              （沿用，只换候选集）
   └─ 合集视图：纵向网格，封面 2:3 与作品同形                  ← 新增
/library/[id]/c/[cid]       合集详情：一面被规则/手工定义的墙          ← 新增
/library/collections        跨库合集总览（合集多了以后才露出入口）      ← 新增，F4
/library/favorites          全部收藏 = 一个内置的系统合集              （改造：接入同一套筛选）
```

**关键 IA 决策**：合集**挂在库下面**，不做侧栏一级入口。理由——用户的心智是
"我的电影库里有一批诺兰"，不是"我有一个诺兰库"。跨库合集（`library_id = NULL`）
在模型上从第一天就允许，但入口等到 F4 合集数量真正起来再开，避免一开始就多一个
要学的层级。

## 3. 筛选模型

### 3.1 维度清单

**一级（常驻 chips，找片）**——四个，不多不少。多一个用户就开始"读"而不是"扫"：

| chip | 字段 | 取值形态 |
|---|---|---|
| 类型 | `genre_ids` | 多选，OR。按库内数量倒序排，只列有内容的 |
| 年代 | `release_date` 派生 | 2020s / 2010s / 2000s / 90s / 更早，多选 |
| 地区 | `origin_countries` | 复用路由的预设组（大陆/港台/日韩/美国/欧洲/小语种）+ 展开逐国 |
| 观看 | `playback_state` | 未看 / 在看 / 已看完 / 我收藏的（单选，语义互斥） |

**二级（「更多筛选」面板·左栏，找片）**：评分档（≥9 / ≥8 / ≥7）、片长档
（≤60′ / 60–90′ / 90–120′ / >120′）、分级、原始语言、出品方、导演/演员（搜索式）、
剧集状态（在播 / 完结）。

**二级（「更多筛选」面板·右栏，查库）**：分辨率（2160p/1080p/720p/SD）、HDR
（HDR10/DV/HLG）、编码（HEVC/H264/AV1）、位深、体积档、来源（入库 / 扫描发现 /
某站点 / 某制作组）、库存状态（缺集 / 有 missing 文件 / 未刮削 / 待探测规格）、
订阅中。

**接口有、界面上刻意没有的一维：作品系列**（`series_keys`，2026-09 随系列合集
加入）。规则层与查询参数都支持"属于系列 X"，但**不给下拉**——一个库几百个
系列，下拉根本没法用；合集才是它正确的呈现形态（见
[library-series-collections.md](library-series-collections.md) 6.6.1）。
留着这个参数是因为系列合集就是一条规则驱动的合集，规则正是这一条。

**排序**（扩展 `WallSort`）：默认（拼音）· 最近添加 · 上映时间 · 评分 · 片长 ·
体积 · 最近观看。前三个已有，后四个是新增。

**方向可切换**（2026-09-11）：每档有自然方向（标题 A→Z、片长短→长，其余大的 / 新的 /
近的在前），再点一次当前档就反转，按钮上一枚箭头、菜单里用人话写方向（「短→长」）。
接口是可选的 `order=asc|desc`，不给即自然方向，老调用方与合集的 `sort` 不受影响；反向
恰好是自然序列倒过来（收尾的 id 一起反），没数据的条目两个方向都沉底。影视库补上
「按上映时间」一档。侧边索引条**只在按标题时出现**（倒序时 Z→A）：按评分、按上映时间
试过画成分档（「9+ / 8+ / 未评分」「2010s」），只有几档、档名又宽，挤掉海报列宽却只省
下几屏滚动，撤了（后端 `item-index?sort=rating` 仍在，前端不再请求）。
排序与方向都记在 localStorage（此前只认回「最近添加」一档），「回到上次位置」按档 + 方向分开记。

### 3.2 语义

维**内 OR**，维**间 AND**——电商 facet 的标准语义，也是用户不用学就懂的语义：
勾"动画"再勾"科幻"是"两者都要看到"，再勾"日本"才是收窄。

与路由 DSL 的对齐：路由的 `[{field, op:any_of, values}]` 条件间 AND、条件内 OR，
**完全同构**。所以筛选态 → 合集规则 → 库收藏范围是三处零翻译的传递。

### 3.3 计数与永不空货架（铁律 2 的实现）

每个候选值旁边的数字，是"**在其他维度已选条件下**，勾上我还剩几部"——即计算某维
的 facet 时排除该维自身的已选条件（否则勾了"动画"后其他类型全变 0，多选就废了）。

真筛空时（多维交叉），不渲染空墙，渲染**放宽建议**：

```
没有同时满足这 3 个条件的作品。
  · 去掉「评分 ≥ 9」 → 找到 12 部          [去掉]
  · 把「日本」放宽到「日韩」 → 找到 5 部    [放宽]
                                    [清空全部条件]
```

建议由"逐条剔除已选条件后重算命中数、取最大的前三条"生成，不需要任何策略配置。
**只列命中数 > 0 的条件**——多维交叉时经常出现"去掉它还是 0 部"的剔除项（样稿里
`日韩 + 纪录片 + 已看完` 就是这种），把它们摆出来是噪音不是建议；一条都救不回时
只留「清空全部条件」并说明"这几个条件两两之间就没有交集"。

### 3.4 状态承载

- **URL 是筛选态的唯一事实源**：`?g=16,878&d=2010s&c=JP&w=unwatched&sort=rating`。
  可分享、可加书签、前进后退符合直觉；服务端渲染的首屏也拿得到。
- **localStorage 只记排序偏好**（沿用 `movieclaw.library.wall-sort`），**不记筛选**——
  上次筛的条件在下次打开时还在，是本类产品最经典的困惑来源（"我的片怎么少了一半"）。
  排序是偏好，筛选是意图；偏好该记，意图不该记。
- **位置记忆按筛选态分 scope**：`wallRecallScope("library:12")` → 追加筛选指纹
  `library:12:g16_cJP`。不加指纹的话，从筛选态返回会跳到一个不存在的 offset。

### 3.5 按库 kind 的差异

| kind | 筛选条 |
|---|---|
| `movie` / `tv` | 全量（上文全部） |
| `video`（其他库） | 无 TMDB 事实，只有**查库栏**（时间/体积/画质/来源）+ 拍摄年月。一级 chips 退化为「年月 · 时长 · 画质」 |
| `photo`（图片库） | 时间线本身就是"按月筛"。只加「只看收藏」与「相机/来源」，**不加类型/评分**——图片没有这些事实，摆上去就是永远 0 的死控件 |

铁律：**没有事实就不摆控件**。一个永远返回 0 的筛选器比没有筛选器更伤。

## 4. 合集模型

### 4.1 三类合集

| 类型 | 定义方式 | 会自己生长 | 例子 |
|---|---|---|---|
| **智能合集** | 规则（同一套 DSL） | ✅ 新入库作品自动进 | 「日漫 · 8 分以上」「90 年代港片」「我的 4K 收藏」 |
| **手动合集** | 手工挑选 + 可拖排序 | ❌ | 「周末陪娃看」「年度私影单」 |
| **系统合集** | 内置来源，不可编辑规则，可隐藏 | ✅ | TMDB 系列（漫威宇宙/哈利波特）、某导演、正在追、最近添加、我的收藏 |

**优先级：智能合集先行（F3），手动合集随后（F4）。** 理由：智能合集是筛选的直接
固化，边际成本近乎零（存一份规则）；手动合集要新增关系表、拖拽排序、"加入合集"
入口散布在详情页/海报悬浮/批量选择多处，是独立一期的量。而 NAS 家庭场景里手动
合集有真实价值（"给孩子做一个可以看的"），不能砍，只能后置。

### 4.2 「筛完存为合集」——这是整个设计的枢纽

筛选条上一旦有条件生效，工具栏右侧就出现 `⊕ 存为合集`。点开预填：

```
名称：  日漫 · 8 分以上          （由条件自动拟名，可改）
规则：  类型 = 动画 · 地区 = 日本/韩国 · 评分 ≥ 8      当前命中 42 部
形态：  ⦿ 智能合集（新入库自动加入）   ○ 固定这 42 部（存成手动合集）
可见：  ⦿ 全家可见   ○ 只有我
                                            [取消]  [创建]
```

"固定这 42 部"这一项，是手动合集在 F3 就能低成本拿到的一半价值：把规则当下的
命中集快照成一份名单——不需要拖拽、不需要挑选 UI，只需要写一次 `collection_item`。

反向也成立：合集详情页的 `编辑规则` 直接把规则**倒回筛选条**，用户在墙上边看边调，
再存回去。规则编辑器不另做——**筛选条就是规则编辑器**，这是铁律 3 的兑现。

再反向一步：智能合集的溢出菜单里放 `设为某个库的收藏范围`，把规则交给
`library.match_rules`。用户不用理解"路由"这个词，就完成了分库配置。

### 4.3 露出位置（v1.1 修订：**不做横滚封面卡**）

初稿写的是"库页顶部一行横滚合集卡"。**推翻**——横滚一行封面卡两头不讨好：
占掉约 160px 高度，却只露 4–6 个，每张还只是一扇"要点开才知道里面是什么"的门。

**行业惯例是两条泾渭分明的规则**（2026-09 核实）：

| 规则 | 谁在这么做 |
|---|---|
| **横滚行装的是「内容」，不是「容器」** | Netflix 每一行就是一个分类，行里滚的是**作品**；分类清单本身是**文字菜单**（Genres 下拉 / Categories 按钮，现已并入搜索筛选），从来没有"分类封面卡横滚"。Plex 把一个合集"发布"到首页，得到的同样是**该合集内作品的一行** |
| **要浏览「全部合集」时一律用纵向网格** | Plex 的 Collections 是库内的一个视图，纵向海报网格；Emby / Jellyfin 的 BoxSet 同理 |
| 例外：容器卡横排 | 只有 Disney+ 的品牌卡（Disney / Pixar / Marvel / Star Wars / NatGeo）。成立前提是**只有 5 个、固定不变、每个都是强 IP**——用户不是在"找"，是在"认"。合集一多就不成立 |

据此，v1.1 定三个露出面：

1. **作品视图顶部一行 chip**（不是封面卡）。理由不止于省空间——**合集本来就是
   "存好的筛选"**，那它就该长得像筛选 chip、和筛选条同属一套系统；点一下不是跳页，
   是**把当前这面墙筛成它**，已选条件行随即标出 `＝ 合集「日韩动画」`。用户改动
   任意一条，标记消失——他就从"在看一个合集"变成了"在自己筛"，两种状态之间没有断层。
   一行 30px，装不下就**换行**：换行会暴露数量，横滚只会掩盖数量。再多收进「全部合集」。
2. **库内第二个视图「合集」**（作品 / 合集 切换，Plex 的 tab 模型）：纵向网格，一次看全。
   **封面用与作品相同的 2:3 竖版**——这是 Plex 值得抄的实现细节：形状一致才能直接落进
   同一套网格，不必为合集单开一种布局。"这是一叠"的信号靠卡片背后露出的两片边给，
   不靠改变宽高比。
3. **横滚行留给内容**：库首页 `/library`（不是单库页）可以有 `日漫 · 8 分以上 ›` +
   该合集前 12 部作品的横滚行。并且要**可控**——像 Plex 那样由用户选哪几个合集上首页，
   默认一个都不上，避免首页被合集淹没。

另外两处：**作品详情页**「所属合集」（形态见 4.3.1，初稿写的 chip 已推翻）；
**合集详情页**顶部一条**规则条**——
不是说明文字，而是一排长得跟筛选条一样的**可改条件 chip** + `＋ 条件`
（`自动收录：类型=动画 · 地区=日韩 · 评分≥8　42 部 · 本周新增 2 部`），
让"它为什么在这儿"永远可解释（与路由的"全程可解释"同源）。合集内的海报**悬停**
显示它命中的条件，把可解释性落到单部作品上。

**手动合集的诚实降级**：它没有规则、只有名单，所以进入手动合集时筛选条要明说
"名单固定，没有规则——筛选条对它不适用"，而不是让控件假装还能用。

### 4.3.1 作品详情页的「系列 / 合集」两行（v1.3，推翻初稿的 chip）

初稿写的是"一行 chip"。**推翻**——chip 是筛选条那套系统的词汇，它表达的是
"可勾选的条件"；详情页这两行表达的是"它属于哪儿"，不是控件。照搬 chip 会让
用户以为点了是在这一页里筛什么。

最终形态是**两行带标签的文字链接**，与紧随其后的音轨 / 字幕行同一套布局：

```text
2016 · 1 小时 46 分钟 · 4K · HDR10
系列   新海诚系列
合集   日本动画 · 周末清单
音轨   尚未探测
字幕   无内封或外挂字幕
```

**为什么不是海报卡。** 合集封面是从**成员海报**里借的（`_cover_head` 取
`cover_item_id`，没指定就取第一个成员）。在《千与千寻》的详情页上摆一张
「日本动画」的合集卡——那张卡的封面很可能就是《千与千寻》自己。你正在看一部片，
页面下方一排卡片里有一张是它自己的海报。

更根本的：**合集的身份是它的名字，不是封面**。「周末清单」四个字已经把该说的
说完了，一张借来的图什么也没加。三家的做法是同一条判断：Netflix 详情页的
「关于本片」是纯文本链接（卡片只给「更多相似影片」——那是**推荐**不是归属）；
Disney+ 的品牌归属用 **logo** 而不是海报（但那是五个固定强 IP，做得起专属资产，
用户自建的合集没有也不该有）；Plex 的元数据区就是一行 `COLLECTIONS  <名字>`。
**归属用文字，推荐用卡片。**

**为什么分两行、各带标签词。** 系列是**这部片的事实**（片方就这么拍的，你改不了），
合集是**用户自己的归类**。两者长得一模一样，不加标签读者分不清哪个是哪个——
而这个区别正是 9 节那条风险（"合集与库的关系被理解成移动"）的同源问题。
标签列宽与音轨 / 字幕行逐字同款：四行连着排，差几个像素就看得出来。

不放数量（`日本动画 · 4 部`）：这一行回答"它在哪儿"，不回答"那儿有多大"，
后者属于合集卡片。最多摆 3 个，再多收进「还有 N 个」——一部片进了八个合集
不该把这一行撑爆。**系列合集与「我的收藏」不出现在「合集」行**：前者已经单独
一行，后者那颗心就在几十像素之外，同一件事说两遍是噪音。

**反查怎么做的（这一点决定了它能不能做）。** 合集成员是算出来的，没有反查表。
所以这里逐个合集问一遍"它在不在里面"，而每一问都走
`resolve_members(only_item_id=...)`——**与列成员同一条查询**，只是候选集收窄成
一个条目（收窄点在 `_wall_scope`，全站唯一的墙口径）。刻意不另写一套 Python
规则匹配图快：详情页说它在、点进合集找不到它，是最难查的一类不一致，而"合集
没有自己的查询"是这套设计的结构性前提（library-collections.md 第 0 节）。

N 也比看上去小：**系列合集整类跳过**（自动生成的那几十个不用问，`series_key`
直接给答案），真正要逐个问的只有用户自己存的那几个，个人库里是个位数。

### 4.4 下游：Jellyfin BoxSet

`movieclaw_jellyfin` 已有 `CollectionType` 与 `CollectionFolder` 的映射
（`catalog.py`）。合集映射成 Jellyfin 的 **BoxSet**，让 Emby / Jellyfin 客户端
也能看见同一批合集——这是"movieclaw 作为上游生产者、把整理好的结构交给下游播放器"
（library.md 1.5 第 5 条）在浏览层的延续。

**协议侧的层级与产品侧不同**：网页端合集挂在库下面，协议侧走 Jellyfin 惯例的
**一个顶层「合集」视图**（`CollectionType="boxsets"`）——两个受众的正确答案不同，
理由与全部技术细节见 [library-collections.md](library-collections.md) 第 4 节。

贯穿两端的硬约束一条：**规则求值只能有一个实现**，协议层不许自己写查询，
否则同一个智能合集会在网页里 42 部、在电视上 39 部。

## 5. 交互设计

### 5.1 桌面：静止态只留信息，不留控件

**这是 v1.1 的另一处修订。** 初稿把四个维度下拉常驻在墙前面，实测下来静止态要先
经过 4 行、约 18 个可点元素、近 200px 的控件区才看得到第一张海报。问题的本质是：
**四个都写着「全部」的下拉不承载任何信息**——它们只是把"什么都没选"这件事说了四遍。

改成**同一块地方的三种状态，永远只占一行的量**：

```
静止态（默认）
┌ 电影库                        1,284 部 · 8.2 TB   [作品|合集]  ⋯ ┐
│  合集  日韩动画 7 · 90 年代港片 3 · 2020 年代新片 5 · 全部 8 个 ›   排序 默认▾  [筛选] │
├────────────────────────────────────────────────────────────────┤
│  [海报墙]                                                   A-Z │

点开「筛选」后（多出一行，用完可收回）
│  类型 ▾   年代 ▾   地区 ▾   观看 ▾   ⚙ 更多筛选                  │

条件生效后（条件顶替控件，与面板开合无关）
│  类型 动画 或 科幻 │ 且 │ 地区 日韩    清空    筛出 42 部  ⊕存为合集 │
```

三条规则：

1. **合集在静止态是安静的文字行，不是带框 chip**——它回答"有什么"（信息），
   不是"能做什么"（控件）；选中一个才变实心。与 4.3 引的 Netflix 文字菜单同源。
2. **静止态只有一个带框按钮**（筛选）。排序用无边框的文字下拉，因为它总有一个
   当前值可显示，本身就是信息。
3. **控件因意图出现，条件因生效出现**：用户没提出筛选意图前，四个下拉是纯粹的税；
   条件一旦生效，条件本身就是最该占据那一行的东西——**面板收起不影响条件可见**。

其余不变：筛选区 sticky（用户在墙的第 800 格仍能改条件）；下拉沿用
`filter-menu.tsx` 的 Radix + `menu-surface` 皮肤，改造点只有多选与计数两处；
已选条件必须**可见且单个可撤**（收进下拉是本类产品第二大困惑来源——
"我明明筛过了，怎么找不到在哪取消"）。

**卡片同理**：画质角标（4K/HDR）收到**悬停**——它是"评估这一部"时要的信息，
不是"挑哪一部"时要的；收藏心与在看进度条留在静止态，因为那是**状态**，状态不能藏。
库管理动作（扫描/管理/刮削）收进 `⋯`：管库和看片不该抢同一行。

### 5.1.1 控件分层：形态 / 排序 / 筛选各归各位

顶栏一共只有五类控件，按**影响力**（对屏幕上这批内容的改变有多大）排定视觉权重：

| 控件 | 它改变什么 | 形态 | 位置 |
|---|---|---|---|
| 作品 / 合集 | 我在看**哪一类东西** | 分段开关 | 标题行右侧 |
| **形态**（海报墙 ⇄ 瀑布流） | 同一批内容**怎么画** | **无字图标键** | 墙控件组，最左 |
| **排序** | 同一批内容**什么顺序** | **显值、无边框** | 墙控件组，居中 |
| **筛选** | 这批内容**是哪些** | **唯一带框按钮** | 墙控件组，最右 |
| 密度 / 分组、库管理 | 低频偏好、管库动作 | `⋯` 菜单 | 见下 |

分组依据是**作用对象**：标题行的控件改变"这个页面是什么"，墙控件组改变"这面墙什么样"。

**一条可推广的规则决定了要不要写字**：

> **能从内容本身看出来的状态，控件可以无字；看不出来的，控件必须把当前值显示出来。**

- 海报墙和瀑布流长得完全不同，看一眼墙就知道自己在哪个形态 → 形态键**只要图标**
  （沿用现有约定：图标画的是"点过去会变成的那面墙"，见 `icons.tsx` 里那对图标的注释）；
- 按什么排**看墙看不出来**（"按标题"和"最近添加"在一屏之内都只是"某种顺序"）
  → 排序**必须把当前值挂在外面**。

**由此推出一处要修的现状**：排序现在被埋在 `⋯` 菜单里
（`library-detail-view.tsx` 的 `LibraryActionsMenu`，`sort` / `onSortChange` / `sortDisabled`），
用户看不到自己正按什么排。应当提到墙控件组、做成显值的无边框下拉。

**标签能去掉的前提是让值自述，不是硬删**：所以默认档不再叫"默认"，而是叫
**「按标题」**（其他库与图片库的海报墙是「按时间」）——这套叫法产品里本来就有
（`defaultSortLabel`），直接沿用即可，排序前缀二字就不用写了。合集行同理，
首项做成 **「全部 1,284」**（静止态即当前项），一行文字自己就说明了这是一组可选视图，
"合集"两个字的标签也省掉。

### 5.1.2 `⋯` 菜单要拆成两个

现状：`LibraryActionsMenu` 一个菜单同时装了**浏览偏好**（排序、瀑布流密度、按作品分组）
和**库管理**（扫描、整理、刮削…）。这两类东西的作用域根本不同，混在一起的结果是
"想调个密度得在一堆管理动作里找"。

而收藏页（`favorites-view.tsx`）**已经是对的做法**：形态键旁边挂一个 `⋯`，
且只在瀑布流形态下出现——"海报墙上没有可调的，整个菜单也就不出现"（原注释）。
单库页对齐它即可：

| 菜单 | 装什么 | 何时出现 | 位置 |
|---|---|---|---|
| 墙偏好 `⋯` | 瀑布流密度、按作品分组 | **仅瀑布流形态下** | 紧挨形态键 |
| 库管理 `⋯` | 扫描、整理、刮削、回收站… | 有管理权限时常驻 | 标题行右侧 |

排序从两个菜单里都摘出来，独立成显值下拉（5.1.1）。

**形态键的可见条件不变**：`library.capabilities.playable` 决定它出不出现，
图片库走相册墙那条路径，本次不动。

**v1.2 修订：形态键本身也收进 `⋯`，不再常驻顶栏。** 上面那条"图标即可、不必写字"
仍然成立，推翻的是它**值不值得占一颗常驻键**：

- 顶栏那一行在 390px 上是**满的**。实测：搜索 + 图床 + `⋯` 三颗之下，吸顶标题
  只剩 50.5px（勉强放下「电影库」）；再加任何一个控件，标题被挤成 **0**。
- 图床浏览是"偶尔换个看法"，不是常用动作。为它常驻一颗键，代价是**每一次滚动**
  之后都不知道自己在哪个库——这笔账划不来。
- 收进菜单反而更清楚：图标键要靠"画的是点过去会变成的那面墙"这条约定才读得懂，
  菜单项直接写「图床浏览」/「回到海报墙」，不需要约定。

于是右上角只剩**搜索**与 `⋯` 两颗。5.1.2 那张表里"墙偏好紧挨形态键"随之作废——
形态键没了，浏览偏好（含图床开关、密度、分组）统一在 `⋯` 的下半段。

### 5.2 移动端

**「作品 / 合集」挂进 PageNav 顶栏、搜索键左侧**，外观照抄发现页的 TMDB / 豆瓣
切换（2026-09-11 改）。最初挂在库名那一行的右端，理由是挂进顶栏吸顶标题会从 50.5px
变成 0（见 5.1.2 末的那笔账）；实机用下来用户是往顶栏找切换的，位置不对。现在的
取舍是：有切换时吸顶标题让位（390px 放不下 ☰ + 返回 + 切换 + 搜索 + ⋯ 之外再加
一个标题，正文里本来就有同名大标题），顶栏里也不带合集数。

**点「筛选」直接拉起底部抽屉，一二级维度全部平铺成胶囊**（2026-09-11 改，参照
Airbnb / Plex 这类多维筛选 App 的移动端做法；Netflix 只有单维单选的全屏分类浮层，
不适用）。窄屏上先后试过两种"一排下拉"的摆法都别扭：横滚——想看后面的维度得先滑，
滑动中手指一停就误触弹出下拉；两列铺开——占掉半屏，还得再点一层才看得到取值。
抽屉里点一下胶囊就是一个取值，取值与计数一眼看全，没有「菜单里再弹菜单」；一级
四维在上、二级「找片 / 查库」在下，所以窄屏没有 `更多筛选` 这扇门。宽屏不变
（一排下拉 + `更多筛选` 面板）。

抽屉**非全屏**（留出上方一截墙，让用户看得见条件在实时影响什么），底部固定
`查看 42 部` 主按钮 + `清空`。**每次勾选立即生效**，主按钮上的数字实时跳——
不做"确定"式提交。已选条件行在抽屉收起后照常显示在墙顶。

### 5.3 空态与加载

- 库本身为空 → 沿用现有空态。
- 筛选空 → 3.3 的放宽建议。
- 计数未到达 → chip 上先不显示数字（不显示占位骨架，数字跳动比数字缺席更吵）。

**端到端验收时发现的一件事**：正常操作下**点不出**空墙——计数为 0 的取值在
下拉与药丸里都是禁用的（"永不空货架"的第一道闸生效了）。所以空态只会从三个
地方来：别人分享的链接、存下来的合集、以及数据变了（片被删、文件失联）。
这不改变空态的设计，但改变了它的**验收方式**：拿链接进去，不要试图点出来。

放宽建议因此必须覆盖**全部**维度，不能只看一级四维：用「4K + 评分≥8.5」这类
纯二级条件筛空时，只看一级的实现一条建议都给不出，界面却会写「去掉任意一条
也救不回来」——那是句假话，去掉评分就救回来了。

## 6. 数据与接口

### 6.1 实现要点：筛选只改"候选集"这一步

现有管线已经是理想形状——`_wall_page_ids()` 先定"这一页是哪些条目"，
`_aggregate_wall_views()` 再只聚合这几十个。筛选**只需要在 `_wall_page_ids` 里
把候选集收窄**：

```
_wall_page_ids(session, library_id, sort, limit, offset, identity, filters)
    候选 = 命中 filters 的 media_item_id 集合      ← 新增，唯一改动点
    再按 sort 排序、切片                            ← 完全不动
```

由此**免费得到**：A-Z / 月份索引条自动变成"筛选结果的索引条"（`build_library_index`
读同一份有序名单）、分页稳定性不变、`probing` 置顶逻辑不变、图廊形态同步生效。
这是不新起一条查询链路的关键理由。

### 6.2 计数怎么算，以及**先不做什么**

v1 **不建物化标签表**。理由：

- 单库真实量级是 10³~10⁴ 条目；一次 `json_each(media_metadata.genre_ids)` 的全库
  分组统计在 SQLite 上是几十毫秒级，且计数结果可按 `library.stats_refreshed_at`
  同一时机缓存在进程内（库内容不变则不重算）。
- 物化表意味着刮削、刷新、删除、重锚四个写入点都要维护同步，是典型的
  "为不确定的性能问题先付确定的复杂度"。

**量化闸门**：单库条目数 > 50,000 或 facet 接口 p95 > 300ms 时，再引入
`media_item_facet(media_item_id, dim, value)`（维度物化表，一次迁移 + 刮削收尾写入）。
写进设计里，是为了让后来者知道这不是遗漏，是有阈值的推迟。

库存维度（画质/HDR/体积/来源）不进任何缓存——它们直接查 `library_file`，
`(library_id)` 索引已在，且随扫描频繁变化。

### 6.3 接口草案

筛选参数在三个接口上**必须完全同形**（口径分叉是这类功能最常见的 bug 源）：

```
GET /libraries/{id}/items    ?g=16,878&d=2010s&c=JP,KR&w=unwatched&rating_gte=8
                              &res=2160p&hdr=1&sort=rating&limit=60&offset=0
GET /libraries/{id}/facets   ?<同一组参数>
     → {"genres":[{"value":16,"label":"动画","count":42}, ...],
        "countries":[...], "decades":[...], "resolutions":[...], "total":42}
GET /ui/libraries/{id}/index ?<同一组参数>&sort=title
```

`facets` 与 `items` 由同一个 `LibraryFilter` 值对象驱动，共用同一个 WHERE 构造函数。

合集：

```
GET    /collections?library_id=&member_scope=
POST   /collections           {name, library_id?, mode:"smart"|"manual", rules:[...], sort, visibility}
GET    /collections/{id}
PUT    /collections/{id}      {name?, rules?, sort?, visibility?}
DELETE /collections/{id}
GET    /collections/{id}/items?sort=&limit=&offset=      ← 复用 _aggregate_wall_views
POST   /collections/{id}/items    {media_item_ids}       ← manual，F4
PUT    /collections/{id}/order    {media_item_ids}       ← manual，F4
POST   /collections/{id}/apply-to-library {library_id}   ← 规则 → library.match_rules
```

### 6.4 表结构

```
collection
  id, name, library_id FK nullable(NULL=跨库), kind,
  mode: smart|manual|system,
  rules JSON              -- 与 library.match_rules 同构；manual 为 []
  sort str                -- 合集内默认排序
  visibility: household|private,  member_id FK nullable(private 时为作者)
  pinned bool, position int,      -- 货架顺序，与库排序同款
  cover_item_id FK nullable       -- 不指定则拼贴前 4 部海报
  created_at, updated_at

collection_item          -- 仅 manual/快照合集
  collection_id FK, media_item_id FK, position int
  UNIQUE(collection_id, media_item_id)
```

**`studios` 的语言问题**：`genres` 有 `genre_ids` 兜底，`studios` 没有——它存的是刮削
语言下的本地化名（"华特迪士尼影业" vs "Walt Disney Pictures"）。所以出品方筛选
v1 **只做"从本库现有取值里选"**（候选来自库内实际出现过的值），不做跨语言规范化；
一旦要把它写进合集规则，同步在 `media_metadata` 增补 `studio_ids`（与 `genre_ids`
同一次刮削零成本带回），否则用户切语言后规则会静默失效——这正是
`library-routing.md` 1.1 已经堵过一次的坑，不能在合集上重犯。

**迁移向前兼容**（CLAUDE.md 硬约束 3）：两张新表 + `media_metadata.studio_ids` 新列，
全部是新增，回退版本读不到即忽略，无破坏性变更。不落 `data/` 新目录，不触发
`storage/registry.py` 登记要求。

## 7. 实施计划

分期原则：**先还债、再加能力、最后加实体**。F0 是纯前端的顶栏归位，不依赖任何后端
改动，可以独立发版；F1 之后才动服务端。每一期都能单独上线，不留半成品。

### 7.0 改动面清单（现状 → 目标）

| 面 | 现状 | 目标 | 期 |
|---|---|---|---|

**两处实现上的取舍**：

- **合集分享的成员是每次访问重算的**，不是创建分享时固化一份名单。规则驱动的合集
  本来就会随入库变化，固化名单等于分享出去的是一张过期快照；重算的代价是每次开分享
  页多一次墙查询，与开一次库页同量级。
- **`library_id` 为空的合集不进单库页的 chip 行**，只在 `/library/collections` 露出。
  跨库合集出现在单库的筛选条上，用户点进去会看到本库没有的片，那比"找不到入口"更难解释。
- **跨库合集只能是固定名单，不能规则驱动**：`resolve_members()` 求值需要单一
  `library_id`。接口对"跨库 + 规则"直接返回 400，而不是建出一个永远解析不出成员的
  空合集——建得成、看着像回事、就是一部片都没有，那种失败最难查。
  这条约束也正是 F4.5 卡住的地方（跨库的收藏页对不上按库的收藏合集）。

**验收**：拖拽顺序在海报墙、Jellyfin 客户端、分享页三处一致 —— 三处都走
`resolve_members()`，顺序由 `collection_item.position` 唯一决定。

**F4.5「`/library/favorites` 并入合集详情页」未做**——它要求「净删代码」与
「行为零变化」同时成立，而跨库规则求值与合集画廊模式两处前置都不在 F4 范围内。
详见 [library-collections.md](library-collections.md) 8.10。

### F5 个性化与儿童档案（F5.1 已实施；F5.2 已下线）

| 子项 | 改动 |
|---|---|
| F5.1 内容分级 ✅ | **新增** `services/library/content_rating.py`（分级 → 年龄的映射，认不出的分级返回 `None` 而不是猜）；`member.max_age` / `member.allow_unrated` 两列；`access.py` 产出 `ContentLimit`，与 `visible_library_ids` 同样的方式穿到下游 |
| F5.2 推荐行 ⛔ | 做了又撤了，理由见下 |

**内容约束落在六处，不是设计初稿说的四处**：墙、搜索、合集、Jellyfin，
外加**作品详情**与**播放决策**。少了后两处，超分级作品的详情页仍可直链打开、
仍能起播——收窄只做在列表上，等于只挡住了浏览，没挡住播放。

`ContentLimit` 只在 `access.py` 一处产生。这不是风格偏好：一个"当前观看者能看什么"的
判断如果能在多处被构造，迟早会有一处漏掉 `allow_unrated`，而这类漏洞不会报错，
只会安静地放行。

**验收**：儿童成员登录后，超分级作品在六处均不可见。
验收落在接口层（`tests/api/test_member_content_limit.py` 逐面一条 +
`tests/jellyfin/test_member_multiuser.py`），**没做浏览器端到端**：现有 e2e 全部
以超管身份跑，补一套成员建号 + 切换登录只是为了把同样的六条断言再走一遍界面，
而这六条断言里没有一条是"界面对不对"。

写这一节时对着代码逐处核，发现第六处当时是漏的：`/playback/decide` 只按库范围
收窄，儿童档案直链一个 `media_item_id` 过来照样拿得到播放计划。补在 `_decide`
（decide、开会话与两处降级重试共用的唯一入口），用例先证伪后证真——
去掉那一行是 200，补上是 404。**"四处"写成"六处"不是笔误，是这次核出来的。**

#### F5.2 为什么撤了

做的是三行"说得清楚的推荐"：「接着看」「同系列里你还没看的」「你常看X」，
标题本身就是理由。上线后看下来，**能解释不等于有用**：

「你常看动画，这 12 部动画你还没看」本质上就是一个类型筛选——用户自己在筛选条上
点两下就有，把它包装成推荐行，是拿解释性掩盖了单薄。而「接着看」这一行的价值
真实存在，但它属于首页顶部那块「接下来继续」，不该在库页里再摆一遍。

所以整块撤掉（`services/library/recommend.py`、`library.recommendations` 端点、
前端渲染块一并删除），价值合并进
[library-home-up-next.md](library-home-up-next.md)：那一行从「最近观看」改成
「接下来继续」，卡片指向的永远是**还没看完的那个单元**，看完一集自动推下一集。
首页这块位置留给"点了就能接着放"的东西，比留给"可能你会喜欢"值。

## 8. 决策记录

1. **筛选不入 localStorage**，只入 URL——意图不该被记忆（3.4）。
2. **不新造条件 DSL**，复用 `library.match_rules` 结构（铁律 3）。
3. **合集挂库下，不做侧栏一级入口**；跨库合集模型上支持、入口后置（第 2 节）。
3.1 **合集不用横滚封面卡**（v1.1 推翻初稿）：作品视图用 chip 行，浏览全部用纵向
   2:3 网格，横滚行只留给内容。依据见 4.3 的行业惯例表。
4. **智能合集先于手动合集**；手动合集的一半价值用"固定当前命中"提前兑现（4.1/4.2）。
5. **v1 不建 facet 物化表**，设 50,000 条目 / p95 300ms 的量化闸门（6.2）。
6. **出品方筛选 v1 不入合集规则**，等 `studio_ids` 落地（6.4）。
7. **没有事实的 kind 不摆控件**（3.5）。
8. **内容约束落六处不是四处**：初稿写墙/搜索/合集/Jellyfin，实施时补上作品详情
   与播放决策——只收窄列表等于挡住了浏览、没挡住播放（F5.1）。
9. **`ContentLimit` 只在 `access.py` 一处产生**：能在多处构造的「当前观看者能看什么」，
   迟早有一处漏掉 `allow_unrated`，而这类漏洞不报错，只安静放行（F5.1）。
10. **推荐行整块撤掉**（F5.2）：三行"说得清楚的推荐"里，只有「接着看」是真需求，
   而它属于首页的「接下来继续」；另两行本质是筛选的包装。能解释不等于有用。

**明确不做**：全文高级搜索语法（`genre:动画 AND year:>2010`）——那是给工程师的界面，
本产品的筛选面向"周五晚上想找片看"的人；筛选结果的批量操作（批量删除/批量刮削）
不进本期——它属于管理页，混进浏览页会让误操作代价陡增。

## 9. 风险

| 风险 | 应对 |
|---|---|
| 老档案 `genre_ids` 为空（路由文档已记录），筛选会漏掉这些片 | 与路由同款自愈：元数据刷新重刮后补齐；筛选面板顶部对"尚未刮削完成"的条目数给出提示行，而不是静默漏掉 |
| 多选 + 多维交叉的空结果率 | 铁律 2 的计数与放宽建议；0 值选项置灰不可点，从源头堵住 |
| 合集与库的关系被理解成"移动" | 合集详情页固定文案"合集不改变作品的存放位置"；作品详情页「所属合集」与「所在库」分两行 |
| 智能合集规则改动导致成员看到的内容突变 | 规则变更时在合集详情页顶部提示"规则已更新，收录从 42 部变为 57 部"，可撤销 |
